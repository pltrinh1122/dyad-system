## Part 1 — Verification of the claim

### 1.1 The claim, as the repository states it today
README: **"~54% less code (up to 94%) · ~20% cheaper · ~27% faster · 100% safe"**, footnoted:
"~54% is the mean across 12 feature tasks (Haiku 4.5, n=4); it reaches 94% where an agent
over-builds (a date picker) and is near zero where the code is already minimal … The earlier
single-shot benchmark reported 80–94% as a flat figure; against a fair agentic baseline that is the
per-task ceiling, not the average." Source: `benchmarks/results/2026-06-18-agentic.md`.

Method (from that file): headless Claude Code 2.1.177 sessions, Haiku 4.5, editing
`fastapi/full-stack-fastapi-template@cd83fc1`; twelve one-line feature tickets; four arms —
no-skill baseline, ponytail (as its real plugin), *caveman* (a terse-prose skill: the control for
"is it just brevity?"), and a seven-word prompt "Follow YAGNI principles, and prefer one-liner
solutions" (the control for "is a whole skill needed?"); `n=4` per cell; LOC = `git diff` added
lines of the files the agent leaves. A separate safety tier: six "implement this function" tasks
whose output is executed against adversarial input (path traversal, SQL injection, a forged token…).

### 1.2 What the repository's own data supports
**E1 — the aggregation.** From the per-task table (12 tasks, baseline vs ponytail mean LOC):

| aggregation | ponytail | caveman | one-liner prompt |
|---|--:|--:|--:|
| ratio of summed LOC (the README's −54%) | **−54%** | −18% | −35% |
| mean of per-task ratios | **−35%** | −10% | −24% |
| median per-task ratio | **−27%** | −6% | −16% |
| frontend six (over-build room) | **−60%** | −22% | −39% |
| backend six (CRUD, little room) | **−22%** | +5% | −15% |

The headline is the ratio of sums, carried by three frontend tasks where a native `<input>`
replaces a hand-built component (404→23, 287→23, 251→95). The README's phrase "the mean across 12
feature tasks" names the aggregate; the mean task effect is −35% and the median −27%. Both are
real, and the writeup's own text is the honest one: "huge where there's bloat to cut, nothing where
there isn't." The baseline's stated mean (191 LOC) does not equal the table's (184.75); the writeup
attributes four force-killed cells — immaterial to the direction, worth noting for a re-run.

**E2 — tokens and cost: the "in spite of more tokens" case is the author's own.**
`2026-06-17-cost-verification.md`: on Claude, ponytail is 42–75% cheaper (single-shot, 30 reps);
on OpenAI reasoning models it is **more** expensive — gpt-5.4-mini +26%, gpt-5.5 +39% — "the
ruleset is re-sent as input every call and the baseline output is already terse, so the input and
reasoning-token overhead outweighs the lines saved", correctness 100% there too. The agentic run
(Haiku) shows −22% tokens / −20% cost for ponytail, and the caveman control shows the split in one
row: −18% LOC at **+7%** tokens. So: *less code is produced whether or not it costs more tokens;
whether it costs more is a property of the model, not of the skill* — the claim as the Operator
framed it holds, scoped, and the repository scopes it itself.

**E3 — safety.** 20/20 safe for baseline, caveman and ponytail; 19/20 for the one-liner prompt
(a `../../` filename escaped on `safe-path` once in four). The lines ponytail kept were the
traversal check. One slip at n=20 is a floor, as the writeup says, not a result.

**E4 — method integrity, to the repository's credit.** A superseded run (`2026-06-17-agentic-
safety.md`, kept in place and marked) found a ~4% gap, discovered that the plugin's `SessionStart`
hook fired on the baseline arm too, fixed isolation (`--setting-sources project,local`, per-arm
`--plugin-dir`) and re-ran; the single-shot 80–94% is retracted in the README as a chatty-baseline
artifact after a public critique (issue #126). The LOC scorer (`benchmarks/loc.js`) is deterministic
and committed. The raw runs are not (`runs/<stamp>/` is gitignored, "regenerable").

### 1.3 What cannot be verified from the repository, and what it would cost
The per-run data behind every table is absent from the tree; the harness (`benchmarks/agentic/
run.py`, `tasks.py`, `judge.py`) and the pinned target repo are present, so the study is
*reproducible*, not *reproduced*. A re-run at the writeup's scale — 12 tasks × 4 arms × 4 runs
plus the safety tier, ~200 headless Haiku sessions at ~$0.04–0.10 each — is roughly **$15–25 and
an API credential**: a World action this d-work does not hold (Rule-8, Rule-14). Offered in Part 3
as an optional step; the Operator disposes. Nothing here depends on it: the direction and the
scoping are established by the repository's own internal evidence.

### 1.4 Falsification of the claim as the Operator stated it
| # | Attack | Result | Survivor |
|---|--------|--------|----------|
| 1 | "Less code" is a chatty-baseline artifact. | Refuted for the agentic run, confirmed for the retracted single-shot one | The agentic baseline is the same agent without the skill; the author retracted the single-shot figure on exactly this ground. |
| 2 | −54% is cherry-picked. | Survives, scoped | It is the ratio of sums; the mean task effect is −35%, the median −27% (E1). The README's "mean" wording is imprecise; the writeup's prose is not. |
| 3 | It's just brevity (terse prose → fewer lines). | Refuted | The caveman control writes terse prose and builds normally: −18% LOC vs ponytail's −54%; the effect is the ladder, not the tone. |
| 4 | A seven-word prompt does the same job. | Refuted, scoped | The one-liner prompt reaches −35% but is erratic (above baseline on the command palette) and is the only arm that dropped a guard. |
| 5 | Less code costs more tokens, so it is not a saving. | Survives, scoped | True on reasoning models (E2), false on Claude; the repository states both. The *code* claim is independent of the *cost* claim. |
| 6 | Less code means less safe. | Refuted at floor | 100% vs 95%, n=20; the kept lines were the guard. A floor, not a proof. |
| 7 | The numbers cannot be checked. | Survives, scoped | Internal consistency checks out (E1); the raw runs are not committed; reproduction costs $15–25 (1.3). |

**Verdict on the claim:** true as scoped by the repository itself — a large cut where an
over-build trap exists, near zero where the code is already minimal, without dropping the guards
measured, and independent of whether the model spends more tokens to get there. The headline
figure is the least careful sentence in an otherwise unusually careful repository.

## Part 2 — Proposal: what to adopt into the syseng craft

The syseng craft (`crafts/syseng/rules/`: `naming`, `invariants`, `verifiable-code`, `imports`,
`determinism`, `idempotence`, `failure`, `host-facts`) holds the implementation clauses of Rules
11–14. ponytail is a discipline about *what to write*; syseng today is a discipline about *what the
written thing must carry* (its check, its invariant, its declared imports, its deterministic build).
The overlap is real and the gap is specific: syseng says nothing about choosing the smallest
implementation, and ponytail says nothing about the check a module must carry beyond one assert.
Each candidate below is an **insight** (a sentence syseng would state) or a **mechanism** (a file,
guard, marker or preference), mapped to where it lands. Nothing here is implemented; each item is
for the Operator to strike or keep.

### P1 — The ladder as syseng's path-selection step (mechanism → rule text)
`verifiable-code.md` p2 already requires that "a plan with alternatives names the chosen path and
what it yields for reuse", and Rule-13 p1 that recurrence proposes code. Neither says *how* a path
is chosen. Proposed: a property in `verifiable-code.md` — **the path is the first rung that holds**:
(1) needs to exist? (2) already in this codebase? (3) stdlib? (4) native platform? (5) an installed,
declared dependency? (6) one line? (7) the minimum that works — run *after* the plan has read the
code the change touches, never instead of it. Rung 2 is Rule-13's own trigger restated; rung 5 is
`imports.md` p1–2 restated (import over author; declared and pinned). The plan file's "chosen path"
line would name the rung. Insight kept verbatim from the skill: *"The smallest change in the wrong
place isn't lazy, it's a second bug."*

### P2 — The never-simplify floor (insight → rule text)
"Never simplify away: input validation at trust boundaries, error handling that prevents data
loss, security measures, accessibility basics, anything explicitly requested." Proposed as the
sentence that bounds P1 in the same property: the ladder shortens the solution, never the guard.
dyad's own ledger has its instance: #47 kept `plan.base->commit` *checked* for active rows and
skipped only terminal ones — the floor is what kept the check.

### P3 — Minimum check vs the test mapping: keep syseng's, adopt the floor (decision for the Operator)
ponytail: "Lazy code without its check is unfinished … ONE runnable check … no per-function
suites unless asked." syseng p4: every module has its test at the mapped path; p5: a module's
constants carry `INVARIANTS`. These conflict on the *ceiling* (one assert vs a test module) and
agree on the *floor* (no check → unfinished). **Proposal: keep syseng's mapping unchanged** — it is
the mechanism Rule-2's Binding relies on — and adopt only the sentence "code without its check is
unfinished, and the smallest check that fails when the logic breaks is enough *inside* a mapped
test". What this would change in practice: nothing mechanical; it licenses a two-line test where
today the habit is a fixture-heavy one. The Operator may instead choose to loosen p4 for scripts
(not guards); that is a Rule-12 kernel question and would need its own falsification.

### P4 — The ceiling marker (mechanism → naming rule + a store)
`# ponytail: global lock, per-account locks if throughput matters` — a comment that names a
deliberate ceiling and its upgrade path. The frame's default is no comments; this is exactly the one
it permits (a non-obvious WHY). Proposed: a `ceiling:` marker in `naming.md`'s table (form: `#
ceiling: <what is bounded>; <when to lift it>`), and — the dyad-shaped part ponytail's
`ponytail-debt` skill points at — the markers as a **store**: a guard that lists every `ceiling:` in
the tree and fails one without a "when" clause, and a projector (sysarch) that shows them. That
turns "later means never" into a row on a surface. Smallest first: the marker alone is one table
row; the guard and projector are a second step.

### P5 — Tagged one-line findings for simplification review (mechanism → template)
`ponytail-review`'s format: `<file>:L<n>: <tag> <what>. <replacement>.` with tags
`delete:|stdlib:|native:|yagni:|shrink:`, scored `net: -N lines possible`, `Lean already. Ship.`
when nothing. Proposed as a syseng template (`templates/simplify-review.md`) for the
simplification pass a completion reply may cite — a *format*, not a new event. It fits Rule-10's
"one path, one counter" better than prose review does, and the tags are the ladder's rungs.

### P6 — Intensity as a preference (mechanism → preferences-corpus)
`lite | full | ultra` is an Operator-owned knob over how hard the ladder is pushed. If P1 is
adopted, a key `implementation-minimality` (`name-the-lazier-path | ladder | ladder-and-challenge`)
in `preferences-corpus/PREFERENCES.md`, read by the syseng rule, is the honest place for it —
the Operator sets how lazy the Agent may be, per instance. Optional; `full` is the default either way.

### P7 — The benchmark method (mechanism → syseng, the most transferable item)
What ponytail does that syseng has no equivalent of: it **measures a rule's effect on the diff**
— a fixed task set, a fair baseline (the same agent without the rule), a terse-prose control, a
minimal-prompt control, a deterministic scorer on `git diff`, `n` runs per cell, a contamination
check (does the baseline arm secretly load the rule?), a safety tier scored by executing the output.
syseng's rules are falsified by argument (Rule-9) and enforced by guards; none has ever been
measured. Proposed: a `benchmarks/` directory in the syseng craft holding one harness in this
system's shape — a script under `crafts/syseng/scripts/`, no new entrypoint noun — that runs a
task set through the kernel-only path with and without a rule file loaded and scores the diff. The
first rule to measure would be P1 itself, which would also answer 1.3 without trusting anyone's
tables. Cost and credential are the Operator's; the harness is the mechanism.

### Not proposed
- The persona ("a lazy senior developer") and the persistence hook (`SessionStart` re-injection,
  statusline flag): the frame's imports already re-inject every session, and the sentinel proves
  the load; dyad's drift problem is the merge sequence (#68), not rule fade.
- Any change to Rule-12's kernel ("code entering the package carries its mechanical check").
- `ponytail-gain` (a scoreboard of someone else's medians) and `ponytail-audit` (whole-repo sweep)
  — P5's format run over a tree is the same thing; no separate mechanism.

### What the Operator is asked to dispose
Strike or keep each of P1–P7; P3 is the one that needs a *choice* (keep the mapping, or loosen p4
for scripts). The adoption row (Part 3) is planned from whatever survives.
