What to codify

3. Adjacency is one term inside this file, not a separate criterion for now. A candidate is adjacent to an anchor (a board row, or the row just delivered) if:
   * either strong signal holds on its own:
      * S1: the anchor’s plan or completion evidence deferred it, or named it as not built or a follow-up;
      * S2: it was promised (`_cos` `promised`) while working the anchor;
   * or it scores 3 or more: S3 shared files 2, S4 shared mechanism (verb, guard, store) 2, S5 refs edge 1, S6 same owning unit 1, S7 same incident mode 1.
   * A duplicate of an existing row is never adjacent; name that row instead.
   * S3 and S4 are inferred, so state the reason beside the candidate.
4. Ranks, highest first:
   * P1: a defect in a live mechanism, or a monitoring gap;
   * P2: a promise;
   * P3: a fired trigger;
   * P4: adjacent to the last delivered row;
   * P5: a hygiene finding from #565’s sweep;
   * P6: the oldest backlog row still valid.
5. Tie-breaks:
   * an idle unit before a new one ([#559](https://github.com/pltrinh1122/dyad-system/issues/559));
   * one writer per file;
   * the smaller plan first.
6. Ceiling: at most 2 candidates per proposal, or one per idle unit with different owners.
7. Guards:
   * promotion is a proposal, never automatic: one question to me naming each candidate with its class and reason, nothing opened without my answer;
