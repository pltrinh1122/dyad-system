# Provenance #100

## 1 prompt 2026-09-20
```
Four defects in bundle v0.8.0, found by installing it into a downstream system and running the
kernel-only path. Each is reproducible with only the three crafts this repo ships — none needs a
third-party craft. Root causes below, not just symptoms. Please confirm each reproduction before
fixing; I may have misread intent somewhere.

Observed: core dyad-operator 0.5.1 -> 0.7.0; sysarch 0.1.5, syseng 0.1.4, sysadmin 0.1.0; bundle v0.8.0.

---

D1. A craft's `requires:` floor is unlinked from the core symbols it asserts over.

Symptom: installing sysarch 0.1.5 onto a system running core 0.5.1 succeeds, and the craft then
fails its own invariant immediately:
    FAIL [invariant] project_kanban: columns-are-states

crafts/sysarch/projectors/project_kanban.py:
    COLUMNS = ("open", "planned", "blocked", "backlog", "done", "archived")
    INVARIANTS = [("columns-are-states", lambda: set(COLUMNS) == dyadlib.STATES and ...)]

`archived` enters dyadlib.STATES only in core 0.7.0 (d-work #37). All three crafts declare
`requires: dyad-operator>=0.2.0`.

Root cause: the floor is hand-maintained and nothing ties it to the core symbols a craft actually
reads. Rule-11 p2's unmet-requires refusal worked correctly — it was handed a true but useless
bound. The bundle pins 0.7.0 with sysarch 0.1.5, so the coupling is known at release time; it just
isn't expressed where the installer can see it.

Suggested: sysarch's floor to >=0.7.0, audit syseng and sysadmin the same way, and consider deriving
or checking the floor from the core symbols a craft imports, so a craft asserting over dyadlib.X
cannot declare a floor predating X.

---

D2. Two guards impose contradictory version grammars on an amended installed craft.

Amend any file under crafts/<installed craft>/, commit, then `dyad check --guards`:
    FAIL [guards] infra/bundle 'syseng': crafts/syseng/ differs from tag syseng-v0.1.4
        (1 file(s)) while VERSION is still 0.1.4 — bump VERSION

Do as instructed, to a version recording the derivative:
    FAIL [guards] craft/crafts crafts/syseng/VERSION: '0.1.4+asg.1' is not one MAJOR.MINOR.PATCH line

No value satisfies both. A plain bump (0.1.5) collides with whatever you later cut under that number.

Root cause: two guards own overlapping concerns with different version grammars and no shared
definition. dyad/guards/craft/crafts.py validates a Tended craft's VERSION as strict
MAJOR.MINOR.PATCH; dyad/guards/infra/bundle.py check_drift requires VERSION to change once the tree
diverges from its tag. The core craft escapes only because its VERSION is validated on a different
path that does accept semver build metadata — so the grammar is inconsistent within the system, not
merely between two guards.

Suggested: one version grammar, and let the craft guard accept build metadata as the core's path
already does. That makes `X.Y.Z+<local>` the sanctioned way to say "derived from the release", which
is what check_drift is really asking for.

---

D3. Surfaces are the only craft-owned namespace not qualified by craft, and the rule is enforced twice.

Two crafts providing the same surface name is a hard failure:
    FAIL [guards] sysarch/registry surface 'schema' provided by crafts/A and crafts/B
        (projection.md p4: one craft per surface)

Every sibling namespace is qualified, and surfaces are the exception:
    guards            keyed (corpus, entity)     agent/frame, sysadmin/events    two crafts may share
    craft vocabulary  <craft>:term                                               two crafts may share
    schema files      crafts/<craft>/schema/...                                  by path
    surfaces          the bare surface name                                      collision

dyad/scripts/package.py:
    REGISTRY_FIELDS = ("surface", "craft", "module")
    """({surface: (craft, module)}, problems): a surface two crafts provide is a failing registry"""
    surface, craft = py.stem.removeprefix("project_"), py.parents[1].name

The craft is already in the registry — it simply isn't in the key.

Root cause, and the part that matters for the fix: the constraint is implemented twice, from two
different sources. The core derives it from its own registry; crafts/sysarch/guards/registry.py
re-derives it independently by globbing the tree (line ~56). Fixing the core's keying alone does not
silence the failure — I verified this before attempting it. Any fix must change both, or collapse
them to one source.

This bites with only your own crafts: sysarch already owns five of the most natural surface names
(entities, erd, instances, kanban, schema), so the next craft to want one collides.

Suggested: key the registry (craft, surface), accept `dyad project <craft>/<surface>`, resolve a bare
surface name when exactly one craft provides it — mirroring the guard registry exactly — and have the
sysarch guard read the core registry rather than re-derive the rule.

---

D4. The naming-contribution mechanism and its checker disagree on whether the kind list is
conjunctive or disjunctive.

crafts/syseng/guards/naming.py contrib_rules() lets every installed craft ship
guards/naming_contrib.txt, whose rows merge into the naming table — documented as the way a craft
declares shapes syseng's own table does not name:

    "the craft-contributed half of the table ... a contributed pattern is documented in the
     contributing craft's own rule, not rules/naming.md"

check_package merges them into one list:
    all_kinds = r["kind"] + [k for _c, cr in contrib for k in cr["kind"]]

But check_kinds iterates that list and requires every kind whose glob selects a path to match it:

    for pattern, glob, regex in kinds:
        for p in paths:
            if not sel.match(p): continue
            if not rx.match(p):
                if p in allow: used.add(p); continue
                msgs.append(f"{p}: does not match `{pattern}`")

So a contributed `kind:` with a broader regex cannot rescue a path that a native `kind:` also selects
and rejects — the native row still fails it. Only per-path `allow:` works.

Root cause: merging native and contributed kinds into one list implies disjunctive semantics ("a path
is valid if some kind accepts it"), while the checking loop implements conjunctive semantics ("every
matching kind must accept it"). The feature and the checker disagree about the meaning of the list
they share, so `kind:` contribution is accepted, parsed, merged — and inert.

Measured cost downstream: expressing three shapes (a craft schema/ directory, multi-word surface
filenames, one env var) took 29 `allow:` lines across three crafts where 3 `kind:` rows would have
said it once.

Reproduce: add a `kind:` row to any craft's naming_contrib.txt widening a native pattern; the native
rule still fails the path.

Suggested: make a path valid when any kind matches it, or let a contributed row declare that it
supersedes a named native pattern. Either resolves the disagreement; the first is closer to how the
merge already reads.

---

Cross-cutting note: D3 and D4 are the same shape. Both are extension points — a second craft
providing a surface, a craft contributing a naming row — that the design anticipates and the
implementation does not complete. Worth checking whether other contribution or registration paths
have the same gap.
```
