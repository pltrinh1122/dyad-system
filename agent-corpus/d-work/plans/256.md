## 1 What is actually broken

`dyad/scripts/package.py:576`, the pre-push dirty check, runs

    git status --porcelain --untracked-files=normal

and refuses the push when the output is non-empty: *the working tree has changes the push does not
carry*. Untracked counts; ignored does not. The harness places a delegated fork's git worktree
**inside** the repo:

    $ git worktree list
    /mnt/shared_data/dyad/dyad-system                              7bf55b3 [main]
    /mnt/shared_data/dyad/dyad-system/.claude/worktrees/agent-…    8b79d23 [claude/dwork-254-delegated-share]

so `.claude/` is one permanent untracked path — 7.8 MB, 1126 files — and **every** push from the
main checkout fails for the lifetime of the fork. Three branches are committed and unpushable
today: `main` @ `7bf55b3`, `claude/dwork-254-delegated-share` @ `8b79d23`,
`claude/dwork-251-chain-of-authority` @ `5040bc2`.

The fix verified read-only, without mutating anything:

    $ git -c core.excludesFile=<tmp: ".claude/"> status --porcelain --untracked-files=normal
    ?? agent-corpus/d-work/provenance/255.md
    ?? agent-corpus/d-work/rows/255.md

Only this d-work's own two ledger files remain, and the ledger commit that carries this plan takes
them. After it, the tree is clean and the push gate passes.

## 2 Why the line belongs there on its own merits, worktree or no

`.claude/` is harness state, and the repo must never track it:

- Rule-7 property 2: the raw session transcript is never committed — "it carries whatever the
  session carried, credentials included; it is megabytes per session, permanent once pushed; and
  its location is a property of one kernel and one host". `.claude/` is exactly that kernel's
  directory.
- The existing fences do **not** cover it. `provenance.py`'s `tracked_jsonl` reads only
  `git ls-files -- <instance>/d-work/*.jsonl`; a transcript at `.claude/…/*.jsonl` is outside its
  scan. `containment.py` classifies `.claude/*` as **infra** — it would *permit* a commit of the
  whole worktree, not refuse it. The one partial fence is Rule-11 property 6: 89 of the 1126 files
  match a `generated:` pattern (`__pycache__/`), so `package.py check` would refuse a commit that
  tracked those. The other ~1037 would pass. `git add -A` from this checkout is one keystroke from
  a 7.8 MB commit that nothing refuses.

So the line is a fence at the one moment that matters, not a convenience. That it also unblocks the
push is the occasion, not the justification.

## 3 Why **not** `package_rules.txt` — the core craft's seed

`.gitignore` here was written once by `hostadapter.write_gitignore`, which derives its lines from
`package_rules.txt`'s `generated:` list and **never overwrites an existing file**
(`hostadapter.py:70-88`, idempotent per `crafts/syseng/rules/idempotence.md` property 1, and Rule-11
property 2's "never overwrites a host file"). So a hand-added line is permanent: no install, build or
re-seed will remove it. The instance file is the right home, and the only change needed.

Adding `.claude/` to `package_rules.txt` instead would be wrong twice over. It would ship one
kernel's filesystem layout to every installing system — the thing Rule-14 property 2 keeps out of
the kernel row and Rule-7's own Boundaries call "a property of one kernel and one host, not of the
dyad". And `.claude/` is not generated output: `generated:` is Rule-11 property 6's list of paths
`package.py check` refuses to see *tracked*, which is a different claim from "git should not show
it". Two zones would also be touched (`dyad/` agent, `.gitignore` infra), so it could not be one PR.

### 1 The push gate's suite failed 29 times and then became unreachable — an incident

Pushing `infra/256-claude-gitignore` was refused twice, identically:

    [Rule-12] dyad/tests: Ran 601 tests FAILED (errors=29, skipped=3)

The same tree then passed in full, twice, by two other roads: `dyad check --tests dyad/tests` →
`Ran 624 tests OK`, and `dyad check --evidence` → every one of the six roots OK, rc 0, zero `FAIL`
lines. It was reproduced once more on a *different* tree — `claude/dwork-251-chain-of-authority`,
same `601 … errors=29` under the hook, `624 OK` under `--evidence` — so it is not that branch's
content and not a one-off.

**Then it stopped being observable.** A full all-roots pass writes a suite memo (Rule-12
property 2), and the next push on that tree prints

    skip [guards] Rule-12 suite: tree ab4abaadd already passed on this checkout (d-work #162)

so all three branch pushes went through on a *skipped* suite. The net mechanism: **a passing
`check --evidence` run launders a failing pre-push suite on the same tree.** The memo's own
definition is "one tree passed every root … in the same environment" — these two runs are
evidently *not* in the same environment, since one fails 29 tests where the other passes, and the
memo cannot tell them apart. 23 of the 624 tests did not run at all in the failing runs, which is
the shape of a collection error, not 29 independent assertion failures.

The error text is **lost**: the first two failures were captured through a case-sensitive
`grep -E "FAIL|rejected|error"`, which matched `errors=29` and missed every `ERROR:` line, and by
the time that was noticed the memo made the failure unreachable without deleting the memo — an
unplanned host action this plan does not authorize. So the cause is **not established**, and
nothing here claims one. What is established, and re-runnable: the failing invocation, the two
passing ones, and the skip.

Candidate rows, not opened: reproduce the hook-environment suite failure with the memo removed and
`ERROR:` captured; and separately, make the memo's environment key cover whatever differs, or deny
the pre-push path the skip when the previous pass was not itself a pre-push pass.

The merge evidence is unaffected in kind: `check --evidence` never reads a memo (Rule-12 property
2), and each of the four heads was observed by its own run. What *is* affected is the gate: it
judged none of these three pushes by a suite it ran.
