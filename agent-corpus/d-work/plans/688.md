**PR-A.** The events are not events-only in Rule-3's clerical sense: that class is the events of read-only commands, and
`subscribe` and `post` are reversible, so they travel by PR with their change-log rows (Rule-8). The desk holds the file
and the event ids, so it writes the rows; the engineer writes none of PR-A. The desk's report names each event id, its
row, and the PR's evidence sha256.

**PR-B, the zone and the file.** The path lies in the agent zone, but the ignore rule belongs in the instance's
`.gitignore`, which Rule-1's table puts in the infra zone (`containment.py zones`: `infra .gitignore`). `dyad install`
seeds that file once and never overwrites it (`hostadapter.write_gitignore`), so a line added by hand stays. The other
choice, `agent-corpus/.gitignore`, would be a second ignore file in a zone that has none, so it is not taken.
No guard needs the file tracked:
- the channels guard and verbs read it from disk (`posts.local`);
- the suite memo digests the instance's `*.local.txt` files on disk, tracked or not (`package.py`, the memo key);
- the instance's other `*.local.txt` files (`private_repos`, `public_remotes`, `provenance_legacy`,
  `traces_preview_legacy`, `merges_since`) stay tracked, so the rule names this one file, never a glob.

**PR-C, the post verb.** `record()` today writes a fresh header over whatever the body file holds, so a whole approved
message comes out with two headers and a changed sha256, and P6 cannot pass the exact bytes. The fix:
- `post` reads the body file. When its first line is `format: dyad-channels/1`, the file is a whole message and is
  written byte for byte. Its `id`, `channel` and `kind` must equal the step's arguments, and its `from` system must be
  this system; otherwise it is refused before any write. The guard's checks run on it as now.
- Any other body is wrapped in the header exactly as today.
- Test: the v1.3.0 post's bytes (sha256 `cf30bcb7256e13c7f6fb15b322d179863a1e2c017717bf31b9a77b2da09d1ae6`) go through
  `post`, and the written file has the same sha256. A whole message whose `id` differs from the argument is refused, and
  a bare body is still wrapped.

**PR-C, the postconditions.** The runner runs a postcondition as a shell command (`runbook.py` `_test`), before the
step (`already satisfied`) and after it. Both of the run-book's are prose, so as commands they always fail, and
`subscribe` exits 1 on a valid clone. The same holds for `post`, whose postcondition is prose too; it is the same
defect in the next step, so this plan fixes both:
- `subscribe`: `dyad/bin/dyad-python crafts/channels/scripts/channels.py subscribed "$URL"`, exit 0 when the clone path
  is a git work tree whose `origin` is `$URL` (compared without a trailing `.git` or `/`).
- `post`: `dyad/bin/dyad-python crafts/channels/scripts/channels.py posted "$CHANNEL" "$ID"`, exit 0 when branch
  `post/$ID` of the clone holds `channels/$CHANNEL/<system>/$ID.md`.

Both are read-only subcommands of the script, not run-book steps. Tests cover each one passing and failing, and the
sysadmin run-book guard checks the run-book.

**Version.** `channels` is unreleased (no `channels-v*` tag), so the bump to 0.1.1 needs no release and no `BUNDLE.md`
row (Rule-11 property 7: an unreleased craft may be absent).

**Evidence.** Each PR is checked by `dyad check --pr origin/main HEAD` and `dyad check --evidence --brief` on its own
head. pr-up is posted for each, in the order they go up. PR-A's evidence is the desk's.
