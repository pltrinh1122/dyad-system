# Plan #143 — architecture readiness for the Operator's client offering

Base commit of `main`: a7dd213. Builds on #142 (`plans/142.md`), whose terms and component map this
report uses without restating. Compared trees: dyad-system at `a7dd213`; dsys-repo at `37fc52e`.

## Intent as read
The Operator intends to offer clients a **general solution for governing and operating the business
workflows of human organizations**. The client's top concern is keeping reliable agent execution
within an **inferencing budget**, and clients accept spending more tokens for more reliability. The
question: how ready is each architecture to implement that offer?

**Challenge to the intent, stated first.** "Clients accept more tokens for more reliability" is a
trade-off only if both sides can be measured. The offer must be able to answer: for this workflow,
at this budget, what reliability do I get? That requires a token meter and a reliability measure
bound to the same unit of work. **Neither repo has either.** dsys deferred the Budget entity
(`doc/dyad-architecture-doc.md:447-448`, "becomes a Budget entity if cost is ever modeled"), and
dyad-system's Rule-13 record concedes "Tokens are not observable in the corpus"
(`dyad/falsification/rules/rule-13-reuse-over-inference.md`, attack 2). Until one exists, any claim
made to a client about its budget cannot be tested.

## 1. What the intent requires (the yardstick)

| # | requirement | why the intent needs it |
|---|---|---|
| R1 | **Budget as a first-class object**: set per workflow or run, metered, capped, refused or escalated on exhaustion | "top concern is to manage inferencing budget" |
| R2 | **A reliability dial priced in tokens**: named mechanisms that each buy reliability for a known token cost, chosen per workflow | "trade-off of greater token cost for greater reliability" |
| R3 | **Inference minimised by construction**: judgment codified once, then run deterministically for no tokens | the cheapest reliable token is the one never spent |
| R4 | **A multi-person organization model**: many humans, roles, delegated authority, several approvers | "human organizations", not one operator |
| R5 | **Proven reliable execution**: running, not specified | "reliable agent execution" |
| R6 | **Auditable spend and decisions**: who authorized what, at what cost | governing, and justifying a budget |
| R7 | **A portable backend**: model and vendor replaceable, since price per token differs | budget management across providers |
| R8 | **Packaged for clients**: install, upgrade, customise, attest | "propose to clients a general solution" |

## 3. Reading the matrix

- **Neither repo is ready.** The requirement the intent calls *top*, R1, scores 1 and 0.
- **dsys is closer on the value proposition.** Zero-inference execution (R3) is the budget lever,
  the org model (R4) matches "human organizations", and it has an explicit, unfilled slot for a
  Budget entity. But nearly all of it is specified, not built (R5 = 1).
- **dyad-system is closer on delivery.** It works, is enforced and is reliable in practice (R5, R6),
  but it is shaped for **one** Operator. Its execution model puts an inferring agent in every step,
  which is the opposite of budget-minimal.
- **They are complementary, not competing, for this intent.** dyad-system's proven governance loop
  would decide *what* to automate; dsys's automaton would *run it without tokens*. #142 found no
  dependency either way today, so this is a composition to build, not one that exists.

## 4. Falsification of "one of these is ready to propose to clients now"

| # | attack | result |
|---|---|---|
| F1 | A budget solution without a budget meter can still be sold on "fewer tokens by design". | **Survives, scoped.** "Fewer by design" is arguable for dsys's automaton plane, but it is unmeasured. Clients who accept a cost/reliability trade-off will ask for the numbers |
| F2 | dyad-system's governance loop is itself cheap. | **Refuted.** Every d-work spends inference on plan, falsification, evidence and ceremony (#142 alone used two survey subagents and a long synthesis). That spend buys reliability but is unmetered, so the trade-off it embodies cannot be shown to a client |
| F3 | dsys's org model makes it ready for organizations. | **Refuted as "ready".** Principal, Fleet and CoS are schema and golden-run fixtures. No multi-user runtime, identity or sync exists |
| F4 | Claude Code's own usage and cost reporting closes R1 for free. | **Survives as a seam, not a solution.** Harness-level counts exist outside both corpora. dyad-system's Rule-7 forbids reading harness files for provenance, so binding cost to a d-work needs a designed, declared adapter (a Rule-14 library row), not a scrape |
| F5 | The trade-off is linear: more tokens always buy more reliability. | **Refuted.** Both repos' reliability comes mostly from *non-inferential* checks: dyad-system's guards and dsys's validators and deterministic replay. Tokens buy reliability only at judgment points (falsification, independent review). A client dial should price judgment points, not tokens in general |

**Survivor:** *Neither architecture can yet implement a budget-governed offer: no token meter, no
budget entity, no per-workflow reliability dial. dsys holds the right shape for the cheap half
(deterministic execution, an organization model, a budget slot) but unbuilt. dyad-system holds a
working, enforced governance loop for one Operator, but no cost model and an inferring executor.*

## 5. What readiness would take (observations, not a plan; each its own d-work)

1. **A meter first (R1).** A per-unit-of-work token and cost record — per d-work in dyad-system, per
   HarnessRun/DecisionRecord in dsys — fed by a declared adapter over the agent runtime's own
   usage data. Without it, nothing else in this list can be priced.
2. **A priced dial (R2).** Name the judgment points: independent falsification, a second-model
   review, re-derivation, evidence re-runs. Give each a measured token cost and a measured catch
   rate, and let a workflow declare which it buys. dsys's typed mechanisms are the natural
   catalogue; dyad-system's incident log (48 rows, 9 failure modes) is real data for catch rates.
3. **The zero-token path made real (R3).** dsys's executor with production tools, installed
   run-books and the Harness module, so that codified workflows really run without inference.
4. **An organization model (R4).** Several disposers, roles, delegation. dsys's Principal and Hat
   are the design, and dyad-system's single-disposer Rule-2 would have to be extended, not merely
   configured. That is a Rule change the Operator disposes.
5. **One pilot workflow end to end** at two budget levels, measuring cost and outcome, before any
   client proposal. That makes F1 falsifiable.

## 6. Limits
- The scores are judgments from reading code and specs (dsys executed only as in #142). No
  benchmark was run, and no token figures exist for either repo to cite.
- "Human organizations" was read as multi-person with roles. If the offer is one operator per
  client, R4 falls away and dyad-system's position improves.
