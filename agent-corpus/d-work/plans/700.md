### The aggregate desk (entries 5 and 6)

`dyad attention` is the aggregate desk. It is one read-only view that consolidates every desk the operator attends at once: the home and every paired unit, in every system, on every host and account that syncs to the central repository. It is a view and never a unit. It holds no presence file, opens no row, asks and answers nothing, and the home stays the one home. Each attended desk keeps working in its own chat and writes its own entries by `sync`, and any desk prints the aggregate, so the operator sitting at any one of them reads the same consolidated view.

### Where the central repository is named: per checkout, never tracked

`git config dyad.attention.clone <path>` gives a local clone of the central repository. `dyad.attention.system <name>` gives this system's name in it; absent, it defaults to the `owner/repo` of `origin`. A repeated `dyad.attention.checkout "<system> <path>"` names a local checkout of each other system the reader can resolve. Git config is per checkout and untracked, so the private repository's name never enters a tracked file of a public system, and no new ignored file is needed. `*.local.txt` files are tracked here, so they are not used. With no `dyad.attention.clone`, every verb prints one line, `attention: no central repository named in this checkout`, and the closing line is today's.

### The central store: references only, append-only, one file per event

`attention/<system>/<unit>/<stamp>-<n>.md`, stamp `YYYYMMDDTHHMMSSZ` (UTC), with `key: value` lines:
- `kind`: `asked`, `answered`, `in-flight` or `landed`
- `system`, `unit`, `row`: the bare id; the slug is resolved when printed, never stored, since it is the row file's own field and storing it would be a copy (the plan's ruling on entry 4's question)
- `ref`: `<path>@<commit>`, the board entry or row file at the commit of the event
- `what`: the question's kind from `dmc:disposition-request` (`intent`, `plan`, `done`, …) or `pr <n> at <head>`
- `writer`

No question text, no evidence and no disposition is written. A `Y` stays only in its own system's ledger.

The open set is every `asked` or `in-flight` entry with no later `answered` or `landed` for the same (system, row, what). As with the inbox, no two units write one file, and no entry is edited or deleted.

### Verbs (`dyadlib.CLI` rows, `dyad/scripts/attention.py`, new)

- `dyad attention [--full]`, read-only. It fetches the clone (one try, then reads what it has and prints the age of its last fetch), folds the open set to at most seven lines, and resolves each entry from the reader's checkout of its system: `git show <commit>:<path>`, giving the question verbatim from the board entry and the row slug.
  - Line 1 is the header: the fetch time and the counts by system.
  - Lines 2 to 6 are the oldest-asked items, one per line: `<system> <unit> #<id>-<slug> <what>`.
  - Line 7 is `+<n> more (dyad attention --full)`.
  - An entry the reader cannot resolve (no checkout of its system, or a commit it lacks) prints `<system> #<id> <what> (unresolved)`.
  - The text depends only on the fetched commit and the reader's checkouts, so two units at the same fetch with the same checkouts print the same lines.
- `dyad attention sync`, write-through. It derives the events from this system's board store on `main`:
  - every recorded question (a phased entry in an `*-asked` phase, or an entry's `question`) gives `asked`;
  - every `pr: <n> at <sha>` whose head is not on `main` gives `in-flight`;
  - their disappearance gives `answered` or `landed`.
  It appends what the central store lacks for this system, commits in the clone and pushes, retrying four times with doubling backoff. It is idempotent: a second run is `0 entries`. A failed push leaves the commit in the clone for the next sync, so an outage delays an entry and never loses one, because the board stays the source. `dyad board set`, `board advance` and `session touch` call it after their own land. Its failure prints one line and never fails the board write.

### The closing line

`board.awaiting_line` reads the attention open set when a clone is named. Questions recorded in other systems join `Awaiting you` under the same kinds, labelled `in <system>/<unit>` beside #670's `in <unit>`. Matters in flight elsewhere join `Coming` as `in-flight <n>`. With no clone, the line is unchanged. A dyad unit's closing line is generated by `dyad board` as today, so every dyad unit, the home and every paired unit, ends with the same line at the same fetch.

### Limitations (Guide §8, and the Rule-3 sentence)

- Freshness is the clone's last fetch, printed with its age.
- A unit needs access to the central repository: attached to a cloud session, or granted to another account by the operator.
- An outage delays a write and never loses one.
- The operator is whoever can push to the repository: declared, never proven.
- A reference into a system the reader cannot read prints unresolved.
- A question asked unrecorded on its own board is invisible here too: an incident, as today.
- Nothing from the central repository is copied into a public store. The reader prints to chat only, and the private-cite fence (#518) still refuses a quoted citation into it on a public push.
