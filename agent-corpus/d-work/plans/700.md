Proposed mechanism, for the plan: one operator-scoped rendering of the board, from `main` alone. It lists every question asked and not answered with the unit whose chat holds it, and every matter in flight and not landed (heads not landed, PRs up, owed promises). It folds to the seven-line bound. Every dyad unit's closing line is generated from it, so the operator reads the same line in every unit. Each unit records its own questions on the board write-ahead, as the home does today, so nothing exists only in a chat.

Limitations to state in the Rule/Guide text: freshness is the last pull (a unit on a host whose push failed is stale, and says so with its `since`); the operator's identity is declared, never proven; a question asked unrecorded is invisible (an incident, as today); and units in another repo are outside it until (d') is decided.

Definition of done (proposed): from the home and from every paired unit, on any host or account with a checkout of this repo, one command prints the operator's whole attention ledger: every question asked and not answered, with the unit whose chat holds it, and every in-flight matter not landed. The text is the same in every unit at the same `main`, read from `main` alone, folded to at most seven lines, with a full form on request. Every dyad unit's reply ends with its closing line. The stated limitations are written where the operator reads them (the Guide §8, and Rule-16 Presence if a Rule sentence changes).

## Intent reading (revision 2)

Prompt (entry 2): the operator named a central repository for the ledger, a private repository of the operator's own. Its name is withheld from this public store (provenance entry 2 holds a placeholder, as #498's do); each checkout names it locally, never in a tracked file. Revision 1 is kept above.

What changes from revision 1:

| portion | class (revision 2) | against |
|---|---|---|
| (d) another host or account | new carrier, limit restated | the ledger lives in the central repository, not on this repo's `main`, so a unit reads it from any host or account the operator has given access to that repository. The harness's cross-session messages are still never the carrier |
| (d') another dyad system | resolved, in scope | every dyad system the operator attends writes to and reads from the same central repository, so attention crosses repos without a federation of the systems themselves |
| (e) keyed to the physical operator | new, keyed by the repository | one operator, one central repository: the key is the repository, not a unit or a cabinet. Limit unchanged: whoever can push to it is taken as the operator, declared and never proven |

Mechanism, for the plan: each unit appends files of its own (one per question asked or answered, one per matter in flight or landed), so no two units write one file, as with the inbox. The ledger is a projection, written through and retried. Authority stays where it is: every disposition is still recorded in its own system's ledger, and the central repository holds no `Y`. The rendering folds to seven lines, and every dyad unit's closing line is generated from it.

Limitations to state: freshness is the last fetch of the central repository; a unit needs access to it (a cloud session has it attached, another account needs the operator's grant); an outage delays a write, never loses it, since the local board stays the source; its contents are private, and nothing of it is copied into a public store; units with no access see only their own system's board, and say so.

Definition of done (proposed, revision 2): from the home and from every paired unit, in any dyad system, on any host or account with access to the central repository, one command prints the operator's whole attention ledger read from that repository alone. It lists every question asked and not answered, with the system and unit whose chat holds it, and every matter in flight and not landed. It is folded to at most seven lines, with a full form on request, and is the same text in every unit at the same fetch. Every dyad unit's reply ends with its closing line. The stated limitations are written in the Guide §8.
