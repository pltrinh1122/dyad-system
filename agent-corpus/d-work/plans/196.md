## The mechanism that makes this legal rather than a bypass
Rule-3's Ledger clause distinguishes two things a commit message may do with a row id: **`d-work #N`
is a claim of work on that d-work**, which the gate resolves and requires live; a bare **`#N` is a
cross-reference**, which it does not. The two commits currently claim `d-work #185` and `d-work #186`.
Reworded to claim `d-work #196` and to mention `#185`/`#186` plainly, they say what is true — the work
being pushed is this d-work's, landing that one's output — and the gate resolves a row that is `open`.
No guard is bypassed, no hook is `--no-verify`'d, and nothing about the diff changes.

## Resolution discipline (not negotiable, from #166)
`INCIDENTS.md` is an append-only table and both sides only append. The resolution keeps **both**, and
after it the only command run on that path is `git add <path>` — never `--theirs`, `--ours`, or any
path-scoped `checkout`. Before each push the row list is compared against `origin/main`'s row by row,
and the count must be `main`'s + 1. A `git checkout --theirs .` chained after a hand resolution
silently dropped a peer's row in this repo once (#166); that is the fence this paragraph is.

## Rule-16

is the one every session appends to and the one that has already cost a lost row here (#166) — so this
plan re-reads `origin/main`'s row list immediately before each push rather than trusting a resolution

## Rule-10
- **Path:** reword each branch's commit to claim `d-work #196` and cross-reference its original row
  plainly, rebase onto current `main` keeping both sides of `INCIDENTS.md`, push with
  force-with-lease, re-run `check --evidence` on each new head, and ask this d-work's Done-`Y` to
  ratify the two merges on those heads. Not one line of either diff changes.
- **Counter:** this is three rounds of ceremony to land a merge the Operator has already ratified on
  evidence that still holds. The local `--no-ff` path executes it now, and the fence provably does not
  look at what it lands.
- **Reconciliation:** the counter is right that the content is settled and the recovery is clerical,
  and it is right that the cheap path would probably work. It is wrong that "probably works" is the
  standard: that path's licence names a condition that is false here, and the whole value of this
  practice is that a gate is not stepped around when it is inconvenient. The reword is not a
  workaround but the form Rule-3 already provides for exactly this — a transaction that is one
  d-work's work carrying another's output. It costs one `Y` and leaves a chain a later reader can
  follow without being told.

## Revision 2 — 2026-09-30: the deadlock recurred inside its own recovery, and plan #196 was impossible as written
PR #223 merged on its ratified head `097e7ac` (merge commit `94105ed`), as the Done-`Y` ratified. PR
#224 then hit **the identical block this d-work was opened to resolve**:

    FAIL [guards] agent/prs [d-work]: #196 is done, not open

**Why this is worse than the first instance.** The first was a peer's push landing between a Done-`Y`
and a merge — bad luck meeting a real gap. This one was **structural and in my own plan**. §"Mutation
proposed" item 2 and the completion reply both prescribed: *merge #223, then rebase #224 onto the new
`main`, then merge*. A rebase requires a push, and by the time #223 merges the row is already `done`,
because Rule-3 requires the ledger's record of the `Y` to precede the merge. So the plan prescribed a
sequence its own authorization could not survive. I wrote it, asked a `Y` on it, and did not see it.

**The generalization, which is the finding.** Rule-3's order — record, then merge — is sound for a
Done-`Y` naming PRs that are *each* mergeable at the moment of the `Y`. It cannot hold for a ratified
set where one member must be **pushed again** after another merges. That is not an edge case: any two
PRs of one d-work that touch a common file are in it, and opening another row only defers the break to
that row's own second merge. Infinite regress, not a fix.

**The avoidable cause, named plainly.** #223 and #224 conflicted only because each appended a row to
`agent-corpus/audits/INCIDENTS.md`. Plan #186's 2026-09-29 amendment had already established the right
shape — *the owed rows ride one PR* — and giving #224 a row of its own undid it. Had both incident rows
ridden #223, #224 would have been mergeable at the `Y` and nothing here would have happened.

**State, exactly.** #223 merged. #224's ratified head `1006d4c` is still on `origin` and **no longer
merges** (`git merge-tree` → 1 conflict against `main` at `94105ed`). Its rebased, resolved head is
local at `a92cd4b`: `INCIDENTS.md` at 83 rows, `main`'s 82 plus this PR's one, **zero** of `main`'s rows
missing, `git add` the only command after the hand resolution. Its evidence block on that head reads
`evidence-sha256=3ac9f8f18108156cc04ecc00123f67c1728c5b70d0ef8fc683b133cb291af542`, **117 `ok`, 1
`FAIL` — and that one `FAIL` is the plan gate itself**, not a test: 599 core tests and every craft root
pass, zero errors in the run. The push is refused, so `a92cd4b` exists in this checkout only.

**What is owed.** #196's row records `merges PR #223,#224` against a state where only #223 merged —
the same unrepairable append as #185's and #186's, and now visibly a pattern rather than an accident.
The way out is the Operator's to dispose, and this time the options should be judged knowing the
regress: another row repeats this at its own Done-`Y` unless it carries **only** #224 (one PR, one
merge, nothing to push after it), which is the one shape that terminates. The alternative worth
stating is a Rule change — Rule-3's completion clause gaining a clause for a ratified set whose
members must merge in sequence — which is a d-work of its own and not something to patch inside the
recovery it broke.
