Proposed `dmc:hardening-work`, which backlog row is hardening work (all must hold):
- W1 source: the row was carried by a hardening run (`Y backlog (mandate #N)` where plan N ran `dyad/playbooks/incident-hardening.md`), or filed from an audit finding the audit's route classed `incident` or `proposal` (`dmc:diag-finding-route`), or names a fence for a failure mode of the hardening index.
- W2 restore: its fix restores what a Rule, record, check or test already states (`dmc:blocker-home`'s restore test). A fix that changes what one decides is not hardening work under the mandate: it is asked.
- W3 inside the mandate: it adds no public surface (a `dyadlib.CLI` row, a `surface.md` row, a Rule or preference text) and holds no act Rule-2 never lets a `Y` carry (a destructive host action, a release, an intake, a preference value).
- A row failing any of the three is ordinary backlog, promoted and asked as today.

Proposed `dmc:hardening-due`, when hardening work is worked under the mandate (from #691 revision 2, with capacity added):
- H1 recurred: a new incident, or a refusal the sweep reports, shows the failure mode the row names, after the row was filed. Due now.
- H2 re-tested open: an audit's re-test finds the row's fence still unbuilt while its mode has incidents in the window. Due at that audit's Done.
- H3 batch: five or more hardening rows of one run are still backlog when the next audit is due. Due, the oldest first.
- Capacity, every due row: at most the preference's ceiling in flight at once (default 1), never two rows touching one file, and only while the unit that owns the row's files by charter is idle.
- not-due: none holds. A hardening row whose mode has no incident in the window waits for ordinary promotion.

What the operator sees under the mandate: one notice line per row it opens (the `Coming` part counts it as `hardening <n>`), and each row's Done, batched with others ready (Rule-3 Batch disposition), naming the incident that made it due. Two questions per row fewer; none fewer at the merge.

The preference: `hardening-mandate`, `off` (the template's value) | `on`, with `hardening-ceiling` a positive integer (default 1). Setting it `on` is a preferences-zone PR the operator disposes (Rule-2: a preference value is never carried), after the core change lands.

Definition of done (proposed): the two records; Rule-3 Ledger and Scope naming the preference as what opens a hardening row; Rule-2's mandate and Rule-7 property 4's note form; the template rows; the promotion read opening a due row under `on` and nothing under `off`; tests of each record's outcomes and of `off`; then, asked on its own, the preferences PR setting this instance's value. Built by engineer-1537d8fb (records, code, tests) and counsel-0032b4c0 (Rule text, amendments), one agent-zone PR, then the preferences PR. Applied today, H1 holds for #652 (K-21, recurred in INCIDENTS rows 317, 318) and #658 (K-35, four refused pushes on 2026-11-12).
