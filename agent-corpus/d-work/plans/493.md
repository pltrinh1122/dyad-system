# Plan #493 — release threshold criteria: when a change set warrants a release, and which number it takes

Base commit of main: b0d88d7

## Intent as read
The Operator's `N` to `Y/N: release dyad-operator-v0.12.3?`, verbatim: "N: release should have clear threshold
criteria, e.g. a critical bug fix, a significant enhancement to an existing capability, a new capability, etc."
(recorded on #489 at b0d88d7; release held). The ask: state, once, which change sets warrant a release, who
judges, on what evidence, which semver part each class moves, how core, craft and bundle tags follow, where the
criteria live, and how a release question cites the class it meets. #489's change set is the worked example.

## What the history shows (main at b0d88d7)
- Every core release since v0.12.0 has been a patch (0.12.0 → .1 → .2 → .3), though #470 shipped a new verb
  (`dyad release`) and the held 0.12.3 ships two more. The number has followed the drift guard, not the change:
  `infra/bundle check_drift` (Rule-11 property 4) forces a `VERSION` bump on the first edit under a craft's root after
  its tag, and the bump made was always the smallest. So `VERSION` today records "changed since the tag", never
  "how much".
- Nothing states when to release. Releases were asked when a d-work happened to need one (#468, #470, #489), so a
  release has also been asked for a change set with nothing in it for an installing system but Rule wording.

## The classes
| class | what counts | evidence the seat cites | number | release? |
|---|---|---|---|---|
| **critical fix** | A defect that gives an installing system a wrong result it can act on (a wrong disposition, a ratification or merge path broken, a refused install or release, a fence that passes what it must refuse), loses or leaks data, or turns its CI red. | The incident row, the red run or a reproduction, plus the fixing PR and its Done-Y. | patch | Yes, asked as soon as the fix lands. |
| **new capability** | Something an installing system can now do that it could not: a new verb or flag, a new guard or check, a new craft, a new Rule property. | The d-work and PR, plus the help text, the guard's registry line or the Rule sentence that names it. | minor | Yes, asked with the change set. |
| **significant enhancement** | An existing capability changed in what it does or decides for an installing system: a new mode of an existing verb, a check that now catches more, a materially faster or cheaper path that changes how a seat works (e.g. the parallel suite). | The d-work and PR, plus a before/after observation (a timing, a line that now appears). | minor | Yes, asked with the change set. |
| **breaking** | An installing system must change something on upgrade: a verb or file format removed or renamed, a Rule that now refuses what it allowed, an install contract changed. Combines with the classes above. | The removed or changed contract and the upgrade step (the port play-book). | major (0.x: minor, marked **breaking**) | Yes, never without the upgrade step. |
| **maintenance** | Nothing an installing system would notice: Rule wording with no behaviour change, records, docs, tests, internal refactors, ordinary fixes with no wrong result outside this repo. | None needed. | patch (working bump only) | No. It waits for the next qualifying change set. |

A change set's class is the highest of its d-works' classes. The question is asked once per tag (Rule-11; its batch form for one d-work's tags stays available), and its last line keeps Rule-11's form. The lines before it state, per tag, the class, the d-works that meet it (one line each, with the evidence) and the number that class implies, e.g.:

    dyad-operator-v0.13.0 — class: new capability (#474 dyad bootstrap; #476 check --evidence --brief/--show), significant enhancement (#475 parallel suite, failing tests named), fixes (#465, #475 CI)
    Y/N: release dyad-operator-v0.13.0?

## Worked example: the held change set (dyad-operator-v0.12.2..1bdaa51, under `dyad/`)
| d-work | change | class |
|---|---|---|
| #474 | `dyad bootstrap` verb; `check --evidence` refuses a shallow or tagless clone; pre-push names the memo miss | **new capability** |
| #476 | `check --evidence --brief` and `--show`, the evidence block stored; Rule-2/3/14 text to match | **new capability** |
| #475 | the suite's roots and classes run in parallel; a red suite names each failing test; no auto gc in fixtures | **significant enhancement** (+ fix: the fixture gc turned main's CI red) |
| #465 | the fence's trace clause; only the bundle takes Latest (`--latest=false`) | fix + enhancement (an existing fence now refuses more) |
| #477 | Rules 1, 3, 4 and 6 name the dyad-package.yml steps | maintenance |

**Class: new capability**, so a minor bump. The core is **dyad-operator-v0.13.0**, not v0.12.3, and the bundle is **v0.17.0**, not v0.16.3 (attack 6: the highest component class). The crafts have not changed since v0.16.2. No breaking change: no verb, format or Rule contract was removed. The release the Operator held was therefore also mis-numbered, and these criteria would have caught that.

## Recommendation (Rule-10)
**Path:** the five classes and their evidence in a core release play-book, with the number set by class at release time, the bundle taking the highest component class, and maintenance waiting. Then #489 re-planned as dyad-operator-v0.13.0 and v0.16.3 → **v0.17.0**.
**Counter:** make it a Rule-11 property instead. A play-book binds nobody, so a seat can ignore it, while a Rule is swept, falsified and guarded.
**Reconciliation:** the classes are inference against evidence, and a Rule can check none of it mechanically. What must bind already does: Rule-11 keeps the release the Operator's, and the Operator reads the class lines and can answer `N`, as this time. If the play-book proves too weak, it is promoted to a Rule by a counsel PR then, with this as its falsification record.
