# Plan #32 — concurrent-session races in the d-work store

Base commit of `main`: 888eb64. Refs #23, #30 (the incidents that argue it), #27 (the rule this
instantiates three times over).
Falsification: inline below (Rule-9); the record proposed as mutation item 6 carries it in full.

## Intent as read
"Resolve #32." The row names two race classes this session hit live: two sessions sharing the
presence identity `web-sysarch`, and two sessions independently allocating the same row id (#24,
then #25). Resolve means: find what is mechanically closable with the information a single session
actually has, close it, and say plainly what is not closable that way.

## Findings — all four verified by reading or running the code, not inferred

**F1 — a shared session name silently merges two sessions' presence.**
`sessions.session_id()` returns `DYAD_SESSION` verbatim when it is shaped like a path segment; the
unset case is already collision-free (`unnamed-<uuid>`). So the collision is not a naming defect —
it is two sessions *configured with the same value*, which the code honours. The consequence is
worse than an overwrite: `touch()` unions the existing file's `rows` and `files` into its own
(`row_set = prev | mine`), so each session inherits the other's claims. Live evidence on `main`
right now: `sessions/web-sysarch.md` lists row `33`, which only ever belonged to this session.
The guard's own docstring asserts "only that session ever writes it" — an assumption nothing checks.

**F2 — on the PR path, a row-id collision is caught by nothing.**
`rows.check_transaction` opens `if branch(root) != "main": return []` — the fence judges direct
commits to `main` and is silent on a branch. The only branch-side transaction guard is `prs.py`,
whose concern is the plan gate. So for a session that can only land through a reviewed PR — which
is every harness-fenced session, this one included — nothing between allocation and merge looks at
row identity at all. `crafts/sysarch/rules/stores.md` says ids collide "only on the same id, which
the push rejects": true of two direct pushes to `main`, **false on the PR path**, where the
collision surfaces as a git add/add conflict at merge, or silently as an overwrite if the branch
was reset onto `main` first. This session hit it twice and caught it both times only by hand.

**F3 — the allocator degrades silently when its fetch fails.**
`package.cmd_dwork`: `try: git fetch …; remote = {…}` / `except Exception: remote = set()`. A failed
fetch drops the remote's ids from `max(local | remote) + 1` with no output, making a collision
markedly more likely at exactly the moment the session is least able to detect one.

**F4 — `session_id()` returns a fresh id on every call, not per process — found live while writing
this plan.** The docstring says "a fresh id per process"; the code is
`return v if _SESSION_ID.match(v) else f"unnamed-{uuid.uuid4().hex[:12]}"`, unmemoized, so three
calls give three ids (verified: `unnamed-860320759a5e`, `unnamed-37d9382ce53d`,
`unnamed-82d34b3fde0c`). Three consequences, all observed rather than reasoned:
- `touch()` calls it twice — once for the path, once for the body — so the file it writes is named
  after one id and *declares* another. The file this plan's own `dyad session touch` produced was
  `unnamed-a68afa0ec45a.md` containing `session: unnamed-8eab7613c53b` (removed, untracked, mine).
- `main()` passes `exclude=session_id()` to `same_root()` — a third fresh id — so a session never
  excludes itself and **warns about its own file**. That is the warning that run printed.
- Every `touch` without `DYAD_SESSION` adds a new file, unbounded, to a store whose whole contract
  is one file per session.
This breaks a *single* session, with no concurrency at all, and it is the opposite failure to F1's:
a false alarm and a self-inconsistent record rather than a silent merge. F1 still stands on its own
— two processes both configured `DYAD_SESSION=web-sysarch` resolve to the same id however well
memoized — so the two fixes are complementary, not alternatives.

All four are the same shape, and it is the shape `#27` has just named: the fault is knowable
earlier than it is reported, and where it is reported it is not loud.

## Mutation
**PR 1 — agent zone, citing `d-work #32`:**
1. `dyad/guards/agent/sessions.py` — an optional `writer` field holding a per-process id. `touch()`
   writes it; when the file exists, its `writer` differs and its `seen` is inside `STALE_AFTER`,
   it prints a loud warning naming the other writer and writes **only this session's** rows and
   files rather than unioning the other's. `writer` stays out of `FIELDS` and is checked only when
   present, so the two presence files already on `main` — which no session but their own may
   rewrite — keep passing.
2. `dyad/guards/agent/rows.py` — a branch-side check beside the existing main-only fence: for each
   row file added or modified in `base..head` while not on `main`, if a row of that id exists at
   `base` with a *different title*, FAIL naming both titles. `main` mode is untouched.
3. `dyad/scripts/package.py` `cmd_dwork` — the swallowed fetch failure prints a warning naming it
   and that allocation is proceeding on local ids only. No check semantics move to the runner
   (Rule-11); this is the allocator reporting its own degraded input.
4. `dyad/guards/agent/sessions.py` — **corrected while implementing** (Rule-9: reading the existing
   test before writing code falsified this item as first written). The original text proposed
   memoizing `session_id()` at module scope. `dyad/tests/guards/agent/test_sessions.py` already
   on `main`, `test_unset_session_gets_a_fresh_id_each_time`, asserts that two unconfigured
   `touch()` calls in one process must get *different* ids — an intentional per-invocation
   safety design (F1's own text: "an unconfigured caller writes its own file and never
   overwrites another's"), not a bug. Module-scope memoization would have silently broken it.
   The actual fix is narrower: `touch()` resolves `session_id()` once at its own top and threads
   that one value through both the path and the written `session:` field, so the two always
   agree; `main()`'s touch handler reuses the path `touch()` actually returned (`p.stem`) as
   `same_root`'s `exclude`, instead of a fresh `session_id()` call that almost never matched.
   `session_id()` itself stays unmemoized — the fresh-id-per-call behavior the test locks in is
   untouched. This closes two of F4's three consequences (the filename/body mismatch, and the
   self-warning). The third — an unconfigured session adds a new file per invocation, unbounded —
   is not a defect this fix (or the original, module-scope one) touches: it is the accepted cost
   of the same safety design, retired only by naming `DYAD_SESSION` consistently, a discipline
   matter, not a code fix. **Also found, not fixed here:** `main()`'s `list` verb computes its own
   `same_flag` inline with the identical fresh-`session_id()`-call bug, a third call site F4 did
   not name. Left as detected-not-disposed (frame conduct): naming it here rather than folding an
   unauthorized third fix into this mutation.
5. Tests (Rule-12 mapping): `dyad/tests/guards/agent/test_sessions.py`,
   `dyad/tests/guards/agent/test_rows.py`, `dyad/tests/test_package.py`.
6. `agent-corpus/falsification/concurrent-session-races.md` — the record, attacks below.

**PR 2 — craft zone, citing `d-work #32`** (separate PR: Rule-1, one zone each; referent before
referrer, so the code lands first):
7. `crafts/sysarch/rules/stores.md` — the id-allocation bullet corrected to say what the mechanism
   does: the push rejects a same-id collision only between direct pushes to `main`; on a branch it
   is the new row check that catches it, before the push.

**Not in this d-work, stated:** none of this makes a collision *impossible*. Two sessions holding
unpushed ids cannot see each other, and no local mechanism changes that — only a shared allocator
can, which is the LAN git server (#24) and belongs to it. This plan converts silent corruption into
a loud stop at the earliest point each session can reach, and claims nothing more.

## Falsification
- **"A palliative: only a shared allocator actually fixes this, so this is code that buys nothing."**
  Survives, scoped — and it is the honest cost. It buys one thing precisely: the difference between
  a collision discovered by hand three times in one session and a collision that stops a push with
  both titles named. Rule-13's trigger is recurrence, and recurrence is established in
  `INCIDENTS.md` (two classes, three occurrences, one session). If the Operator would rather carry
  the collisions until #24's server lands, `N` is coherent and nothing else depends on this.
- **"F2's check belongs in `prs.py`, the branch's transaction guard."** Refuted: `prs.py`'s entity
  is the PR and its concern the plan gate; the row store is `rows.py`'s entity (Rule-3 content,
  Rule-16 store). Putting a row-identity check in the PR guard would give one concern two owners —
  the gap Rule-5 names. Same guard, new mode, is the orthogonal placement.
- **"Adding `writer` breaks every presence file already written."** Refuted by construction: it is
  optional, outside `FIELDS`, checked only when present — `dev-main.md` and `web-sysarch.md` stay
  green, and neither is rewritten by this session, which would itself be the defect F1 describes.
- **"F1's warning fires on a session's own second touch."** Refuted: the per-process id is stable
  within a process, so a session re-touching its own file matches its own `writer` and is silent.
- **"F4 is a one-line fix that needs no d-work."** Refuted: the one line is small, its blast radius
  is not — it is why a session warns about itself, why a written presence file disagrees with its
  own name, and why the store grows a file per invocation. Small fixes to live stores are exactly
  what the falsification record exists to hold.
- **"F3 is cosmetic — the allocation is still correct."** Refuted: it is correct only over the ids
  it can see, and the whole point of the fetch is that local ids are not enough. Degrading from
  "authoritative" to "local-only" without a word is the exact failure mode `#27` calls unnamed.
- **Overlap (Rule-16):** read before writing this plan. `web-sysarch` holds rows 22–25, 27, 33–35,
  42, 43; `dev-main` holds 2, 3, 6, 13, 17, 21, 34, 37, 42. Neither holds #32, and both `files` sets
  are empty, so the mechanism yields no candidates. Checked by hand instead: #25 touches
  `containment.py`, #43 is branch pruning, #27 is `failure.md` — none is `sessions.py`, `rows.py`
  or `stores.md`. No overlap.
- **Note, not a claim of this d-work:** #27's rule, once it lands, has three worked instances here.
  Citing it is that d-work's to do, not this one's.
