# Plan #161 — evaluate optimization opportunities based on current patterns of use

*Rule-15 phase 1. base commit: 24f860c (`main`, 2026-09-25). refs: 160 154 159.*

## Intent as read
Evaluate — not remediate — where this practice spends time *as it is actually used now*, and
surface the optimizations worth taking. "Current patterns of use" is read as measured frequency
and measured cost on the tree as it stands today, not a hypothetical workload: what Rules 2, 3
and 14 oblige the Agent to run, how often it was in fact run over the last seven days on `main`,
and what each run now costs. #160 answered one question about one command; this evaluates the
whole act set and ranks what to change.

## Why this is not #154's audit again
`agent-corpus/audits/2026-09-24-performance-bottlenecks.md` (d-work #154, tree `097b0ce`,
2026-09-24) measured `check --evidence` at **42.75 s** and `dyad/tests` at **39.13 s** with the
runner's flag set. Re-measured on `24f860c` today, the same root is **115.4 s** and the whole
suite set **125 s**, so `check --evidence` is now about **129 s** — three times #154's figure,
one day later. #154's own remedies landed in between (#155 put Rule-12's suite inside
`check --guards`; #159 made Rule-12 property 2 forbid hand-runs), which moved the cost from
the Agent's typing into the gate, where it is now paid on every non-ledger push as well as every
merge. The evaluation therefore starts by re-measuring, and its first question is whether the 3×
is the fifth test root, tests added since, or a regression.

## Mutation proposed
1. **One audit record**, `agent-corpus/audits/2026-09-25-optimization-opportunities.md`
   (agent zone), holding:
   - *cost per act*, re-measured on this tree and on this machine, stated as such (Rule-14
     property 2: versions and timings as observed), with the ratio — not the absolute second —
     as the figure that travels;
   - *frequency required*, derived from the Rules that oblige each act (Rule-2 Binding: one
     evidence run per merge, on the head being merged; Rule-14 property 3: one guard run per
     push; Rule-3: one ledger commit per disposition);
   - *frequency observed*, from `main`'s own first-parent history over seven days —
     **110 ledger-only commits, 111 merges, 0 non-ledger direct commits** (the main fence holds);
   - *the Operator's wait*, distinguished from the machine's total: the part of the cost that
     sits inside a completion reply's critical path, where the Operator is the one waiting;
   - one attack table per candidate (Rule-9), each candidate scored as required-runs × cost-per-run.
2. **One backlog row per survivor** (Rule-3 Ledger), so each optimization is its own later d-work
   with its own plan-`Y`.
3. Row #161 to `done` on the Done-`Y`. Nothing else.
