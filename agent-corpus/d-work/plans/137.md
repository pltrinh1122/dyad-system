# Plan #137 — a core play-book for the incident-to-mitigation exercise

Base commit of `main`: cd8945a. Refs #116 (the grouping this formalizes), #128 (the inventory and
falsification step), #135 (why a play-book is the right container), #165 (the one existing play-book
and its run-book, the form followed here).

## Intent as read
Turn the last three d-works into a repeatable procedure of the core craft: group the incident log
into observed failure modes, turn each mode into a mitigation plan, execute it, and verify it — run
periodically so that reliability and resilience keep up with the system's own mutation. The Operator
also asks for naming options to dispose. This plan proposes one name and states what a different
disposition changes.

## Naming options (Operator's disposition)
| option | reads as | against it |
|--------|----------|-----------|
| **`incident-mitigation`** (recommended) | the existing play-book is `craft-instantiation`: `<domain>-<action>`, naming the recurring decision. This one decides, given the log, what gets fenced next. | says nothing about the periodic intent |
| `incident-hardening` | names the Operator's stated purpose, reliability and resilience | "hardening" is a security word the corpus does not use, and Rule-6 would want it defined |
| `failure-mode-review` | names the unit the procedure actually works in — the mode, not the incident | "review" understates it: the procedure ends in shipped code, not a report |
| `resilience-refactor` | closest to the prompt's own words | names the goal, not the decision, and no other corpus artifact is named for a goal |
| ~~`incident-sweep`~~ | would match Rule-5's periodic idiom | **excluded**: the vocabulary defines `sweep` as the pairwise coherence check of the Agent Rules, owner Rule-5, and Rule-6 allows one definition per term |
A different disposition changes only the two file names and the Rule-3 sentence's citation — a
one-line amendment to this plan, not a re-plan.

## Mutation (what a plan-`Y` authorizes)
One agent-zone PR, branch `agent/137-incident-mitigation-playbook`:
1. `dyad/playbooks/incident-mitigation.md` — the play-book, in `craft-instantiation.md`'s form:
   what it is and which Rule reads it; **Trigger** (an Operator prompt asking for the exercise, or a
   d-work that finds the log has grown past the last record); **Phase 1 Group** (one *observed
   failure mode* per row — the mechanism that would have to change, never the Rule breached and
   never the harm; primary where a row carries two; an index audit plus one record per mode, each
   with its definition, its incidents by date and d-work, the pattern, and one remediation candidate
   under attack; one child d-work per mode, as the Operator's own refactor in #116 established);
   **Phase 2 Plan** (inventory every live mitigation of the mode *from the code and the Rule text,
   never from the audit's prose*: what it is, how and when it fires, which incidents it reaches,
   whether it is shipped or a candidate, and whether anything recurred after it; then falsify "this
   mode is addressed"); **Phase 3 Execute** (each survivor under its own plan-`Y`, one zone per PR);
   **Phase 4 Verify** (re-group the incidents logged since, and test each shipped mitigation against
   the incidents it claimed; a mode closes only when a fault of it would be caught at a *named
   moment*, and the three exits are: fenced, a backlog row that names the fence to build, or
   recorded unfenceable on this kernel with the Rule that makes it so).
2. `dyad/runbooks/incident-mitigation.md` — the steps as `dyad-cmd` blocks in the core run-book
   form, six sections (Survey, Group, Inventory, Plan, Execute, Verify), every command read-only
   except none, each with its postcondition, so every exercise leaves events.
3. `dyad/rules/RULE-3-d-work.md` — one sentence in **Incidents** reading the play-book (a play-book
   is read by a Rule, never a Rule — vocabulary), plus its Provenance line.
4. `dyad/vocabulary/VOCABULARY.md` — one row, `failure mode`, owner 3, used by 3, since the Rule
   sentence introduces it (Rule-6 Conditions).
5. `dyad/falsification/rules/rule-3-d-work.md` — the amendment record with the attacks below and
   the Rule-5 pairwise statement.
No `VERSION` bump: `dyad/VERSION` is 0.9.0 and no `dyad-operator-v0.9.0` tag exists, so
`bundle.check_drift` skips rather than fails; `BUNDLE.md` already reads 0.9.0, so no infra PR and
no release follows. Verified before the counter-prompt, and re-verified in the completion evidence.

## Falsification
| # | Attack | Result | Survivor |
|---|--------|--------|----------|
| 1 | A play-book is the wrong container: Rule-13 says recurrence proposes *code*, so this procedure should be a script. | **Refuted, scoped** | Rule-13 property 1 yields a code path for a recurring *task*; this is a recurring *decision* — which incident belongs to which mode, and which mitigation is worth building — and the vocabulary's play-book is exactly "an executable procedure … for a recurring decision". The steps that *are* mechanical do become commands: that is the run-book half. |
| 2 | Rule-5 already owns periodic review, so this duplicates a sweep (Rule-5 Conditions: "The operator prompts a sweep of the set"). | **Refuted** | A sweep's target is the Agent Rule set, checked pairwise for coherence and orthogonality; this one's target is the incident log, grouped by mechanism and closed by fences. Different target, different verdict, no shared ownership (Rule-5's own orthogonality test). The name `incident-sweep` is excluded for the term's sake, not the Rule's. |
| 3 | The exercise produced nine records and zero fences last time (#128): formalizing it institutionalizes an audit nobody builds. | **Confirmed — and the reason phase 4 is written as it is** | The strongest attack, and it is why a mode may close only by one of three named exits, and why phase 2's inventory must be read from code rather than prose — the failure in #116/#128 was that a surfaced candidate had no row and no moment. The play-book cannot make the Operator dispose; it can make an undisposed candidate visible as a row instead of a paragraph. |
| 4 | The run-book half is unrunnable in this instance: `runbook.py`'s `DEFAULT_RUNBOOKS` is `workstation-corpus/runbooks`, and `workstation-corpus/` does not exist here. | **Survives, scoped** | It runs: `events_path` does `mkdir(parents=True)`, so the first run creates it. The consequence is real and is stated in the play-book rather than solved here — the events file is instance state in the *workstation* zone, so it lands in its own PR (Rule-1), and this instance's want of a host is backlog #60. `DYAD_RUNBOOKS` can redirect it. |
| 5 | Phase 1's "one observed failure mode per row" was already falsified as lossy: two rows carry two mechanisms. | **Survives, scoped** | Carried over from #116 with its answer: primary is the mechanism that *started* it, the second is named secondary in that mode's record. #116's own attack, kept rather than re-litigated. |
| 6 | The taxonomy is not closed: #128 attack 7 found a tenth pattern the nine modes do not name. | **Confirmed** | Which is why phase 1 re-derives the modes from the log each exercise instead of reading the previous index's list — stated in the play-book as a step, not an assumption. |
| 7 | Rule-3 is already the longest Rule; another clause worsens it (Rule-4 shape, Rule-5 coherence). | **Survives, scoped** | One sentence, in the clause that already owns incidents, delegating the procedure to a file — which is what a play-book is for. The alternative, a new Rule, would need its own block and a coherence statement against all nineteen. |
