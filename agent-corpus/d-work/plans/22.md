## Mutation (the mechanism for (b))
1. **The tag is a bare craft-name token in `refs`.** `refs: 1 sysarch` means "work on the sysarch
   craft". No new row field: `refs` is already free-form and already carries non-row tokens
   (`Rule-12`, `workstation-184`), is already the one field the main fence lets a row change
   (with `state` and `disposed`), and already has a CLI (`dwork state -r`).
2. **The token is checked, not conventional.** A new register row in `dyad/guards/agent/references.py`
   (Rule-20 owns the register; adding a kind is its stated condition): kind `row.refs->craft`,
   source `row`, field `refs`, target `craft`, resolver = the craft exists in the tree
   (`references.installed_crafts`, already there for `crafts/<name>/` paths). Extractor: a `refs`
   token that is a bare lower-case name matching an installed craft's shape. Severity follows
   Rule-20 property 2: no craft installed → one `skip` line, never a failure; a token shaped like a
   craft name that names no craft → `warn … unknown craft`, matching how `rule.text->path` already
   treats an absent craft, so a typo is visible without a red `main` on a core-only install.
3. **Two filter surfaces, each where its Rule puts it.**
   - Text, core: `dyad dwork list [--state <s>] [--craft <c>]` in `package.py` — what this session
     uses each turn. `--craft sysarch --state backlog` prints the seven rows above.
   - Board, craft: `crafts/sysarch/projectors/project_kanban.py --craft <name>`, filtering the
     cards and writing `<instance>/projections/kanban-<craft>.html` (a separate file, so the full
     board stays byte-identical — `crafts/syseng/rules/determinism.md`). Rendering decisions live
     in the projector (`projection.md` p4), so the board's filter is craft code, not core code.
4. **One sentence in `crafts/sysarch/rules/references.md`** naming the new kind, since that rule is
   what Rule-20's kernel reads. No Agent Rule text changes, so no Rule-5 pairwise sweep.
5. **Tag the rows**: the seven above get `sysarch` appended to `refs`; #6 and #15 also `syseng`;
   #10 gets `syseng`. Clerical execution of the table this plan-Y disposes.
6. **Tests** (Rule-12): `dyad/tests/guards/agent/test_references.py` gains the new kind;
   `crafts/sysarch/tests/test_project_kanban.py` gains `--craft` cases incl. the twice-render.

## Falsification
- **"Add a `craft:` field to the row instead."** Refuted: `dyadlib.FIELDS` is the row dataclass, the
  parser, the fence's field list, the entity card and every projector's column set; a new field
  rewrites all 22 row files and the fence's immutability rules, to carry a value `refs` can already
  carry. Survivor: `refs`.
  - Counter that survives, scoped: `refs` then conflates "the row this one depends on" with "the
    craft this row is about". Conceded; the register row is what keeps them distinct mechanically,
    and a craft name can never be parsed as `#N` or `Rule-N`.
- **"Infer the craft from the title each time; no tag at all."** Refuted: two sessions classify
  differently, nothing is auditable, and the Operator cannot correct a classification once. The
  inference happens once, is disposed by this plan-Y, and is revisable (`refs` is mutable).
- **"Text-match row titles against each craft's vocabulary and rule names — fully mechanical."**
  Refuted: that is inference wearing code's clothes (`sysarch` would match #8's "guard" and miss
  #11 entirely); `projection.md` p1 wants *parsed* data, and a disposed tag is parsed data.
- **"A row can belong to two crafts."** Survives: `refs` is a space list; the filter is membership,
  and #6 and #15 carry two tags.
- **"Tagging a backlog row guesses before its plan exists."** Survives, scoped: it does. The tag is
  a routing hint, not a claim about the eventual diff; it is revisable, and the Operator disposes
  the table rather than my reading of it.
- **"A fresh install with no Tended craft turns red."** Refuted by design: Rule-20 p2's absent-store
  pattern — `skip`, printed, never a failure. Tested.
- No honest counter found to putting the board filter in the projector rather than the core runner;
  `projection.md` p4 states it.
