# Plan #66 — preference: standing disposition for the Agent to merge ledger-only PRs

Base commit of `main`: e98db6f. Refs #65 (the incident this answers), #56 and #15 (the ledger-close
PRs the standing disposition would have covered). Falsification: inline below.

## Intent as read
"Y: standing disposition for ledger-only PRs. Capture this as a preference setting." Not a bare
disposal — it names a mechanism (a preference) and a scope (ledger-only PRs), so it opens its own
d-work (Rule-3 Scope: text accompanying a disposal is a prompt). One thing to build: a new
preference key in `preferences-corpus/PREFERENCES.md` letting the Agent merge a ledger-only PR
without a per-instance counter-prompt, scoped exactly to what Rule-3 already calls ledger-only.

## Findings

**F1 — this is a narrow extension of a principle Rule-2 already states, not a new one.** Rule-2's
*Not ratification* list already covers "ledger-only commits to `main`... they record a prompt
received or a disposition already given, never a decision" when pushed directly. The only gap is
Rule-1's #23 case: a session-level branch fence forces the same content through a PR instead. The
preference makes explicit what #23 already implies — the *merge* of such a PR is the same
not-a-decision as the direct push it stands in for — rather than leaving it to fall through the
gap the way it did five times (#27, #38, #40, #41, #43) before #65 named it.

**F2 — the scope must be exactly Rule-3's own definition, not "any agent-zone PR" or "anything this
Agent opens."** Rule-3: "ledger-only commits (touching nothing outside `agent-corpus/d-work/`)."
`INCIDENTS.md` is agent zone but lives under `agent-corpus/audits/`, not `agent-corpus/d-work/` — a
PR carrying it (like #65's own pending mutation) is **not** covered, and stays on the existing
`merge-disposition: with-done` path. The preference must name the path prefix, not the zone, or it
silently widens past what Rule-2 already permits itself to exempt.

**F3 — the check must be mechanical before each use, not asserted.** Before merging under this
preference, the Agent runs `containment.py staged`-equivalent over the PR's full diff (every
changed path under `agent-corpus/d-work/` and nothing else) — the same check already run before
every commit this session, just read once more at merge time. A PR that turns out to carry one
non-ledger file does not qualify, full stop; it goes back to the existing merge-disposition path.

**F4 — provenance must survive the exemption.** A merge under this preference still needs a
record the Operator can audit afterward without having been asked: the merge commit message cites
the preference by name and the PR's ledger-only file list, so `git log` alone shows why no
counter-prompt preceded it (Rule-7's spirit, applied to a merge rather than a d-work prompt).

## Falsification
- **"This should be a Rule-2 amendment, not a preference — it changes what counts as a
  ratification event, which is Rule-2's own content, not a tunable."** Survives, scoped, and is the
  most serious counter. Reconciliation: Rule-2's *Not ratification* list is not exhaustive by
  Rule-4's own block requirements — it is illustrative prose under a Rule that already delegates
  *how* ratification is asked to preferences (`merge-disposition`, `batch-disposition-mode`) without
  itself listing every preference by name in its own text. This preference is the same kind of
  delegation, applied to a narrower question (*whether* a counter-prompt fires at all, for one
  mechanically-checked class) rather than *how* one is phrased. The distinction is real — this is
  the first preference to remove a counter-prompt entirely rather than reshape it — which is why F3
  and F4 exist: the mechanical check and the merge-commit provenance are what keep "no counter-prompt"
  from becoming "no record."
- **"Ledger-only is not as safe as it sounds — a row transition could still be wrong (a bad state
  transition, a stale disposition) even though it touches no code."** Refuted for scope: `rows.py`'s
  append-only fence and transition table already run as a transaction guard on every push
  (`agent/rows transaction`), checked before this preference would ever be invoked; a
  guard-passing ledger-only PR is exactly as trustworthy as the ledger-only *direct push* Rule-2
  already treats as not-ratification. This preference does not weaken that guard; it only changes
  who executes the merge once the guard has already passed.
- **"Scope creep: today it's ledger-only PRs, tomorrow it's every PR this Agent opens."** Refuted by
  F2's own wording — the preference's `allowed` values and its reading Rule cite the path prefix,
  not a zone or an author. Widening it later is a new preferences-zone PR of its own, falsified on
  its own terms.
- **"No attack needed — self-evidently correct."** Rejected per Rule-9's easy-agreement clause;
  the three attacks above are the ones pushed to a result before acceptance.
- **Overlap (Rule-16):** presence read before writing this plan; all three sessions' files stale,
  none declaring `preferences-corpus/PREFERENCES.md`. No overlap.
