# Plan #194 — the pre-push hook judges what is pushed; countersign's stale SINCE_ID sentence

Base commit of `main`: 807271d. Refs: #191 (attack 48 and the reported leftovers), Rule-14, Rule-1, Rule-7.

## Intent as read
Remediate the two items #191 reported and left out of scope:
- (A) The pre-push hook judges `origin/main..HEAD` and the checked-out tree, not the refs git actually pushes.
- (B) countersign's `rules/interaction.md` still reasons from `provenance.SINCE_ID` (164), which #191 removed.

## Findings (807271d)
- **The hook ignores its input.** `dyad/hooks/pre-push` is one line: `exec … package.py check --guards`. It
  ignores the `<local ref> <local sha> <remote ref> <remote sha>` lines git writes to its stdin (git 2.43 here).
  `cmd_guards` then takes `head = git rev-parse HEAD`, and every state check reads the working tree.
- **Three ways the gate judges something other than what leaves the machine:**
  1. Pushing a branch other than the checked-out one, e.g. `git push origin gap` while on `main`. Neither
     half sees the pushed commits. The reverse also happens: a clean push fails over an unrelated HEAD.
  2. A dirty working tree. The state checks judge uncommitted files, so they can pass what the commit lacks,
     or fail on what it will not carry.
  3. A tag pushed on its own. Its commit is not HEAD.
- **The transaction guards need only the head changed.** Their base stays `origin/main` by design: the plan
  gate reads every commit message the branch adds, so a later push need not re-cite its d-work. Only the head
  is wrong.
- **countersign `rules/interaction.md` line 74-77, I6's severity paragraph, gives three reasons.** Two are now
  false:
  - "`provenance.SINCE_ID` (164) lies above every row id … no id cut-off separates the legitimate gaps":
    `SINCE_ID` is gone. The instance's `provenance_legacy.local.txt` now names exactly the legitimate gaps.
  - "a concurrent session opens rows without having loaded Rule-7 (the reason Rule-7 itself only warns)": since
    #191, Rule-7 fails a missing record at the push that creates it, and at the state check outside the list.
  - The third reason (D8 is a heuristic) stands, and alone it still justifies warn-only.
- **countersign has not been released** (no `countersign-v*` tag, no `BUNDLE.md` row), so no drift guard
  (Rule-11 property 4) forces a `VERSION` bump. Its record's R8 cites the same sentence and is corrected by an
  amendment, not a rewrite.
- **Overlap (Rule-16).** Three presence files list `dyad/scripts/package.py`, because they derive their files
  from every open row and #191 was one. No live row of theirs plans the hook or `cmd_guards`. Not a conflict.

## Mutation — two PRs, one per zone (Rule-1)
**PR 1 — agent zone (A):**
1. `dyad/hooks/pre-push` passes its arguments and stdin to `package.py check --guards --pre-push`.
2. `package.py` `cmd_guards` gains `pushed_refs(stdin)`, which reads git's lines. It then:
   - skips deletions (a zero local sha);
   - allows a tag, or any ref, whose commit is already reachable from `origin/main`, since it pushes no new
     commit;
   - refuses, with the command to fix it, any other ref whose commit is not the checked-out HEAD — the state
     checks can judge only the tree on disk;
   - refuses a working tree with tracked changes or untracked files (`git status --porcelain`, ignored files
     excepted);
   - otherwise runs as today, with the transaction head set to the pushed commit.
   Without `--pre-push` — `dyad check --guards` typed by hand, the evidence path — nothing changes.
3. **Tests (`test_package.py`)**, a scratch repo with a bare remote and `core.hooksPath dyad/hooks`, pushed
   with real `git push`:
   - a clean HEAD passes;
   - another branch is refused;
   - a dirty tree is refused;
   - a deletion passes;
   - a tag on an ancestor of `origin/main` passes.
4. **Rules.** Rule-14 property 3 gains one sentence: the hook judges the commits and tree being pushed, and
   refuses a push it cannot judge. Rule-1's Conditions bullet names `--pre-push`. Both falsification records
   get amendment #194 with the pairwise statement (Rule-5). Rule-14 owns the kernel-only path, so the Rule-1
   edit is its one condition line only.

**PR 2 — craft zone (B):**
5. `crafts/countersign/rules/interaction.md`: I6's severity paragraph is rewritten to the reason that stands
   (D8 is a heuristic) and to the one #191 changed. The instance's legacy list names the gaps Rule-7 accepts,
   and Rule-7 now fails the rest itself, so I6 would only repeat it. Warn-only stays.
6. `crafts/countersign/falsification/interaction.md`: amendment #194, correcting R8's `SINCE_ID` sentence.
   No `VERSION` bump: the craft is unreleased.

## Falsification
| # | Attack | Result | Survivor |
|---|--------|--------|----------|
| 1 | Judge each pushed ref in a temporary worktree at its commit, rather than refusing. | Refuted, scoped | It would cost the full suite once per ref, and a worktree's hook environment is the #152/#169 class of bug. Refusing with the one command to run (`git switch <ref> && git push`) judges exactly what leaves, at no extra cost. |
| 2 | Use the remote sha as the transaction base, the true "new commits". | Refuted | The plan gate would then fail a follow-up push whose new commits do not re-cite the d-work, which is a behaviour change nobody asked for. The base stays `origin/main`; only the head moves. |
| 3 | Refusing a dirty tree blocks ordinary work (a stray scratch file). | Survives, scoped | Ignored files pass; scratch belongs outside the repo or in `.gitignore`. A dirty tree is exactly when the state checks judge the wrong thing. The refusal names the files. |
| 4 | Tags: a release pushes a tag from a checkout that is not the tagged commit. | Survives | A tag whose commit is already on `origin/main` adds no commit and is let through; a tag on an unpushed commit is judged like a branch. |
| 5 | Fetch `origin` in the hook to get a fresh base. | Refuted | The kernel-only path must not depend on the hosting (Rule-14 property 3). A stale `origin/main` only widens the range judged, which is conservative. |
| 6 | Is the countersign sentence only cosmetic? | Refuted | It states the reason I6 is warn-only, and two of its three reasons are now false. A reader deciding whether to promote I6 would reason from a removed constant. |
