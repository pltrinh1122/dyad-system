## Mutation
1. **The name, and the clash (point 1).** The craft is a new Tended craft, root `crafts/channels/`, `VERSION` 0.1.0,
   unreleased (Rule-11 property 7 lets it stay off `BUNDLE.md` until its first cut). The downstream fork names its own
   craft `channels` too. A system holding both would hold two trees under one root:
   - `dyad craft install` already refuses to overwrite a tree the receiving system did not install unmodified
     (Rule-11 property 2), so the second install is refused, never merged;
   - the two interoperate at the wire, not at the root: either craft reads and writes the same channels repository
     in the specification's format, so a system needs one of them;
   - the craft's README states this, and `MANIFEST.md` states no `requires:` on the fork's craft.
   A rename is not taken: the name is the protocol's, and A1 kept it.
2. **Rules** (counsel), `crafts/channels/rules/`:
   - `channels.md`:
     - the four channels (point 2): `release` (this system posts each published tag: the tag, its notes, the upgrade
       step), `request` (an enhancement, carrying its operator's verbatim prompt), `back-port` (an offered fix with
       its licence release), and `issue` (a defect in Rule-3 Intake's shape: what, where, how to reproduce, the
       mechanism);
     - the record kinds, taken from the specification;
     - pull delivery at session start, with no workflow and no third-party service;
     - "no message carries authority": a post is an intake, admitted only by your `Y` (Rule-3 Intake, `dmc:intake-shape`,
       `dmc:intake-split`), and a post from this system restates a `Y` already given.
   - `membership.md`: a subscriber is one membership record in the registry. Another operator posts by pull request
     from a fork of the channels repository. This system's unit merges a post that passes the guard: a clerical act
     that admits nothing.
   - `fence.md` (point 3), the world-facing fence:
     - the repository is public, so every post this system sends is shown to you whole before it goes, and goes only
       by a PR merged on its own question;
     - the guard refuses, before any push: a credential shape (the provenance guard's list), any `owner/repo` token
       whose sha256 is in the instance's `private_repos.local.txt` (the list `dyad/scripts/privatecite.py` reads,
       #518), and the downstream system's identity, listed there by hash too (point 6).
3. **Records** (engineer), `crafts/channels/templates/`: the registry, a channel, a membership and a message (`id`,
   `kind`, `from`, `holder`, optional `in-reply-to`, a fenced body), field for field as the specification states them,
   its version and sha256 named at the head of each template (point 4).
4. **The guard** (engineer), `crafts/channels/guards/posts.py`, entity `post`, corpus `craft`:
   - It reads a channels checkout named by `DYAD_CHANNELS`. When none is set or present, one `warning: skip` line,
     the absent-store pattern.
   - It fails: a record not in the template's shape; a `kind` the specification does not list; a `from` that names
     no membership; an `in-reply-to` that names no message; and the fence's three refusals.
   - Its check of one draft is a function the `post` step calls, so the fence holds before the push, not only after.
5. **The verbs** (engineer), the run-book `crafts/channels/runbooks/channels.md`, run as
   `dyad runbook run channels:channels <step>`, and its script `crafts/channels/scripts/channels.py`:
   - `subscribe`: clone or fetch the channels repository into `DYAD_CHANNELS`;
   - `read`: fetch, then print what is new since this unit's last read (a marker file in the clone, never tracked
     here). It is run at session start, as the ledger report is;
   - `post <channel> <file>`: run the guard's check, print the post whole, then write it into a branch of the clone
     and print the PR to open. It pushes nothing by itself.

   A reading of the DoD's "`dyad channels` verbs": a Tended craft cannot add a row to the core's `dyadlib.CLI`
   table. A `dyad channels` noun would need a core PR in a second zone. The run-book is how a craft ships verbs
   today (`cabinet:session-tidy`, #640), so the verbs are its steps. A core noun is adjacent, a row of its own if you
   ask.
6. **Tests and record** (engineer, counsel):
   - `crafts/channels/tests/`:
     - each template parses and matches the specification's field list;
     - the guard: a well-formed post, each failure named, a private name refused by hash, a credential refused, the
       absent store skipped;
     - the script: `read` reports only new posts, and `post` refuses before writing.
   - `crafts/channels/falsification/rules/channels.md`: the attacks below, and the **clean-room record** (point 4).
     It names the specification's version and sha256 as the only source read, states that no downstream or fork code

8. **First use** (step 4): the release notice for `dyad-operator-v1.3.0` and `v1.3.0`, drafted from `BUNDLE.md` and the
   release run's record, checked by the guard, shown to you, then sent.
