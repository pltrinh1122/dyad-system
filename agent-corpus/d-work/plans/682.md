**Requirements the answers imply (stated for your intent-Y):**
- **Every post is world-facing.** The repository is public, so no message may carry client data, a private
  repository's name, personal data or a credential. A post from this system is shown to you before it is sent. The
  craft's guard refuses the known shapes (credentials, and the names an instance lists as private) before any push.
- **No message carries authority.** A post from another system or operator opens nothing here. It is an intake, and
  only your `Y` admits it (Rule-3 Intake). A release notice or a hand-down from here is clerical: it restates what a
  `Y` already decided.
- **Other operators write how?** Subscribers outside this account cannot push to your repository. Read: they post by
  pull request from a fork, and this system's unit lands a post that passes the guard, a clerical act that decides
  nothing. Its content stays an intake until you admit it.
- **Pull at session start.** A session fetches the channels repository and reports what is new since its last read, as
  the ledger report does. This uses no Actions minutes.

**Ambiguous, with the reading taken:**
- **A1. The craft's name.** Read: `channels`, as the downstream fork names its own. A system that installs the fork's
  craft would hold both under one root, so that clash is stated for the plan, which decides it.
- **A2. Order.** Read: the design proceeds now, and the wire format and the build wait for the specification. Nothing
  is published to the channels repository before the craft lands.
- **A3. Does the bus need to come here?** Read: no. Downstream's core carries a bus Rule this core does not have, and
  the hand-up asks for a channels profile, not that Rule.

## Definition of done (proposed, for the intent-Y to accept)
1. **The craft.** `crafts/channels/`: its rules (channels, membership, the world-facing fence), record templates matching the protocol's records and kinds, the guard that checks a post before it is sent, and `dyad channels` verbs (subscribe, read, post). Tests cover each.
2. **The channels repository** is seeded with the registry, the four channels (release, request, back-port, issue) and this system's membership, by a PR there that you dispose.
3. **Compatibility:** the records and kinds match the downstream specification at its pinned version, cited by its sha256, read as text alone (the clean-room record states the sources).
4. **First use:** the 1.3.0 release notice is posted to the release channel, shown to you first.
5. **One craft-zone PR here**, its evidence clean, after the specification arrives. The design study can land before it.
