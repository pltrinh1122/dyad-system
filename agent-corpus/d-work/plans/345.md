# Plan #345 — a cloud cabinet to streamline installation and back/forward-porting across the three repos

*Rule-15 phase 1. Base commit of `main`: 779e710 (2026-10-20). refs: 332 336 302 253 285 81.*

## Intent as read
The Operator asks for a cabinet whose goal is the path between three repositories: the authoring repo
**`pltrinh1122/dyad-system`** (public, this one), the installed client instance
**`ASG-Members/client-dyad-system`** (internal), and the ASG dyad **`asg-peter/dyad-system`**
(private) — `->` for installation (authoring → client), `<>` for back- and forward-porting between the
client and the ASG system. Read as #296/#299/#332's shape (#253 R29): the cos creates the session and
relays the Operator's verbatim prompt; the cabinet opens its own row `--relayed-via cos`, attaches the
two other repositories itself (`add_repo`; both are listed as reachable with push), plans in its own
session, and asks the Operator its plan-`Y` there. "Streamline" is read as: fewer hand steps, each step
mechanical and recorded, every port still a PR its receiving repo's Operator disposes — never an
automatic sync.

## What the cos reads into the brief (announcement of state, not an order)
- **Installation is Rule-11's path**: a bundle release (`vX.Y.Z` = `BUNDLE.md`'s version; the live tree
  is 0.14.0, last released `v0.12.1`), `dyad install` for the core craft and `dyad craft install` for a
  Tended craft, writing only under each craft's root plus the documented hooks; `crafts/REGISTRY.md`
  records every installed tree's sha256, the proof of an unmodified tree, and an install **refuses** to
  overwrite a tree the receiving system modified unless `--force` (property 2). The sysadmin craft's
  Tended rule `crafts/sysadmin/rules/host-install.md` (#81) states the host prerequisites. So the first
  streamlining question is whether the client and the ASG system install from a *release* or track
  `main`, and whether their trees are unmodified (the registry sha says).
- **Forward-port (authoring → client → ASG)** is an install of a newer release; what it cannot carry
  is instance state (ledger, preferences, host corpus — Rule-11 property 1), which stays each system's.
- **Back-port (ASG → client → authoring)** is never an install in reverse: a craft change made
  downstream is a modified tree the registry flags; the port is a PR to the authoring repo carrying the
  diff, with its provenance — an **enhancement** needs that system's Operator's verbatim prompt behind
  it, a **defect** its evidence (Rule-3 Intake; Rule-7 property 4, `relayed via`). The same Operator
  disposes on both sides here, which makes the form cheaper, not optional.
- **What exists to build on**: `dyad build | install`, `dyad craft export | install [--force]`,
  `dyad bundle build`, the registry sha, the release workflow (`dyad-release.yml`), `MANIFEST.md
  requires:` floors; `pltrinh1122/dyad-system-tools` (a repo of that name exists; its relation is the
  cabinet's to read). What does not exist: a port play-book, a diff of an installed tree against its
  registry sha by path, a check that a downstream change has an upstream PR.
- **Zones and seats**: core code and a play-book are agent zone here; anything written in the other two
  repos follows *their* Rules and zones; the cabinet is one seat with three checkouts, and its presence
  file here names only this repo's rows.
