# Plan #247 — decision record: where run-book trace events land

*Rule-15 phase 1. Base commit of `main`: 507562b (2026-10-08). refs: 242 229 234 246 223. This plan is the decision record the Operator asked for; the plan-`Y` is the disposition.*

## Intent as read
S1 of #242 left one decision to the Operator: at each Done-`Y` the Agent runs `DWORK=<id> dyad runbook run dwork-trace trace`, which writes the ledger-only
trace file *and* appends a 592-byte event line to `workstation-corpus/runbooks/events/dwork-trace.jsonl` — a workstation-zone file that cannot ride the
agent-zone Done commit. The Operator asked: *frame up a decision record for my disposition.* So: the question, the facts, every option attacked, one
recommended path, its strongest counter, and one `Y/N`. Research: workflow `wf_6b33dc81-dba` (4 read-only researchers, 5 skeptics, 1.78 M subagent tokens,
384 tool calls), at `origin/main` 15a6358 and later. Not in scope: any change to a Rule, a guard or the runner.

## The question
**Where should the event of a `dwork-trace` run land?** Today three events are tracked (#226, #229, #233: PRs #334, #345); three are only in the session
scratchpad (#234, #242, #246) and are lost when the session is archived; peers' events (≈19 more traces) are tracked nowhere. The untracked file also makes
the pre-push gate refuse the tree and the stop hook complain.

## Facts the options turn on (each verified by a researcher against `origin/main`; reproduced by the skeptic that used it)
1. **Nothing requires the event.** No Rule, guard or play-book says a trace step's event must be committed; Rule-3 and the `dwork-trace` preference ask for the
   *trace*. No guard fails when an event is absent (events dir absent: `ok [rule-19] 0 events`, one extra `skip changelog.event->event` warning).
2. **The event adds almost nothing the repo lacks.** Of 15 fields, `runbook_sha256`, `output_sha256`, `output_tail`, `role`, `exit`, `postcondition`, `cmd`,
   `class`, `scope` are constants or functions of the d-work id; `commit` is the parent of the Done commit (5 of 6); `ts` is 0–11 s before the Done commit (6 of 6).
   Only `duration_ms` (381–3947 ms) is not recoverable. The event does not even record the d-work id (`cmd` holds the unexpanded `${DWORK}`).
3. **The two paths give a byte-identical trace** (`dyad dwork trace <id> --out` against the runner: 1738 bytes, `diff` identical). The run-book's step is that very command.
4. **A and B cannot converge.** The event is born after the Done-`Y`, when the head is frozen (Rule-2 Binding), is workstation zone (Rule-1), and the banking PR must cite
   an open row (`prs.py`), so the banking d-work's own Done-`Y` makes one more event. Observed: 2 banking d-works for 3 events landed, 3 more unbanked.
5. **The cost of banking, observed:** #229 — 3 Operator `Y`s, 1 PR, 5 commits, 243 s agent-side, for 592 bytes. #234 — 2 `Y`s, 1 PR, 599 s.
6. **Volume:** about 6 trace events a day across all sessions (25 traced d-works in 4 days).
7. **Events pin the run-book:** the three tracked events make Rule-20 (`event.command->command`) fail if the `trace` step is renamed or removed. The step stays.
8. **Precedent already is C/D:** #204–#212 used the native command; #223 ran with `DYAD_RUNBOOKS` in the scratchpad and said so; no peer's trace has a tracked event.
9. **Any edit under `dyad/` is an agent-zone PR that bumps `dyad/VERSION`** (0.10.1 is released, `dyad/` equals its tag); the bundle row trails in an infra PR (a warning until the tag).
10. **Unsettled, not resolved here:** whether Rule-8 owes a CHANGELOG row for a step classed `reversible` that only writes a ledger file — the best reading is no (a repo write, not a host
    action), but no sentence says so. Whether anything will ever read these events: nothing does today.

## Recommended path: D
Run the trace natively and say so: `dyad dwork trace <id> --out` is the play-book's default, the trace file is the record, the completion reply cites its path (not an event id), and a trace
run through the runner by choice is stated as such (the play-book's own Evidence clause already allows it). Declared loss: `duration_ms` and the event id; the three scratchpad events
(#234, #242, #246) and the duplicates are dropped — everything in them but `duration_ms` is recomputable from git. The three tracked events stay (append-only); the `trace` step stays
(Rule-20 pins it).

### Why D over C and B
- **C** keeps the runner and hides its output behind an env var that must be set per command and never exported (exporting changes the evidence block's warning count); forgetting it
  fails loud at push but costs a hand-move, as at #226. Its events are then telemetry kept nowhere durable — evidence nobody can find, which is worse than none.
- **B** is the only option that keeps events *in the repo* without a Rule change, but the last event is always left over, it needs a trigger the Agent cannot observe (archive), and each batch is a
  d-work, a PR, and two `Y`s for bytes no guard or auditor reads.
- **E** is the only option that gives the repo what the written design intends (committed, fenced events) at zero per-d-work cost; but it needs a Rule-7 amendment, a runner route, a guard exemption
  and tests — a core release — for data nothing consumes.
