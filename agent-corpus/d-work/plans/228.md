## Why this and not something else
The sharpest fact is not "CI is red". It is this: **`cmd_guards` performs no install** — grep over its
body for `install`/`distribute` returns zero — and the install-into-a-scratch-repo step exists only in
`.github/workflows/dyad-package.yml`. Rule-11 property 5 says its own check is "CI installs the core
and a Tended craft into a scratch repo and runs the guards there (`dyad-package.yml`)". So that job is
the *only* verification property 5 has, including its idempotence claim that "a second install is
`0 changes`".

It has been failing for eleven days. Property 5 is therefore not merely uncorroborated — it is
**currently unverified**, and so is every release cut in that window, because `dyad build` and
`dyad install` share the one code path property 5 names. Nothing else open has that character: every
other check the system owns is green, and the local gate cannot see this one by construction.

The second item rides along for a reason Rule-1 settles rather than taste: `dyad/scripts/craft.py`,
its test under `dyad/tests/`, and `agent-corpus/audits/INCIDENTS.md` are **all agent zone**, so one
commit and one PR carry the fix and the six owed rows legally. That is the thing that blocked those
rows twice — they had no authorized PR of the right zone to ride. This is it.
