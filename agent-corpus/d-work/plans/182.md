# Plan #182 — switch the host's active `gh` account back to `pltrinh1122`

Base commit of `main`: 8fd77c1. Refs #178 (where the refusal surfaced), #8 (Rule-8, which classes
this), #175 (the host-path preference that now names where the change log lives).

## Intent as read
The host's active `gh` account is `asg-peter`, which is not a collaborator on
`pltrinh1122/dyad-system`, so `gh pr create` has been refusing since #178 and that d-work had to be
merged locally. The Operator asks for the active account to be `pltrinh1122` again. Both accounts
are already in the keyring, so this is a switch, never a re-authentication.

## The host action (Rule-8; classed by `crafts/sysadmin/rules/host-mutation.md`)
Read before planning, as Rule-8's Conditions require: the sysadmin craft's `host-mutation.md`
(classes, the change log's columns, `actor` naming hands only) and `ops-scripts.md`;
`workstation-corpus/` holds no rules of its own, only `INFRASTRUCTURE.md`.

| | |
|---|---|
| **action** | `gh auth switch --user pltrinh1122` |
| **class** | **reversible** — it changes state and has a stated undo (the craft rule's second class, beside `git config`) |
| **undo** | `gh auth switch --user asg-peter` |
| **postcondition** | `gh auth status` shows `pltrinh1122` as the active account, and `gh pr list` on this repo returns instead of refusing |
| **actor** | `agent` — my hands, my process; the credential afterwards is the Operator's |
| **not an ops script** | Rule-18 covers a command the *Operator* runs for the Agent (privilege, credentials the Agent lacks). Both accounts are already authorized on this host and the Agent can run this itself, so an ops script would be ceremony without a reason |

`gh` is a declared library row of the manifest (`dyad/infrastructure/INFRASTRUCTURE.md`, 2.45.0
observed, replacement "GitHub REST via Python, or LAN server API"), so nothing new enters The World.

## The record this action requires, and the file it needs
Rule-8's Conduct and the craft rule both require a change-log row in
`<host-path>/CHANGELOG.md` — and **that file does not exist**. The craft guard has been asking for
it by name on every run: "seed 'CHANGELOG.md' not copied to workstation-corpus/CHANGELOG.md". So
this d-work seeds it from `crafts/sysadmin/templates/CHANGELOG.md` and writes the first row. That is
not scope creep: a required record cannot be written into a file that is absent, and Rule-8's
Enforcement makes the absence itself a breach to report.

**Sequencing, and why the switch comes first.** The change-log row lands in a workstation-zone PR
(Rule-1), and a PR cannot be opened until the account is switched. So the order is: plan-`Y`,
switch, verify, then commit and open the PR that records it. The record follows the action by one
step, which Rule-8 permits — it requires the row in the same d-work, not before the action.

### Mutation proposed, revised — one workstation-zone PR (Rule-1)
1. **Seed `workstation-corpus/CHANGELOG.md`** from `crafts/sysadmin/templates/CHANGELOG.md`. The
   craft guard has asked for it by name on every run of this repo; until it exists, no Rule-8 row can
   be written into it, and Rule-8's Enforcement makes that absence itself a breach to report.
2. **Deliver the host action as an ops script**, `workstation-corpus/ops/182-h1-gh-auth-switch.sh`,
   in the craft's ops-script form (`crafts/sysadmin/rules/ops-scripts.md`, checked by
   `sysadmin/ops_scripts`): shebang `#!/usr/bin/env bash`; `set -euo pipefail`; the six headers
   (`d-work`, `class: reversible`, `undo: gh auth switch --user asg-peter`, `change-log`,
   `postcondition`, `destructive: none`); `git rev-parse --short HEAD` and `sha256sum "$0"` so the
   pasted output identifies the committed script; a `postcondition()` that tests
   `gh auth status` for the active account and is called both as the idempotence pre-check and as
   the final assert; the switch itself guarded by that check, so a second run is `already satisfied`.
3. **No change-log row yet.** The row records an action that has happened; writing it now would be a
   false record. It is written in this same d-work when the Operator pastes the script's output, and
   its `actor` is `operator`, not `agent` — the correction the context forces on the plan's own
   `actor` cell.
