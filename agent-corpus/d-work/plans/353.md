## Intent as read

**installed client** (`ASG-Members/client-dyad-system`) and the **ASG system** (`asg-peter/dyad-system`).
`->` is installation (authoring → client); `<>` is porting both ways between the client and the ASG
system, and back to the authoring repo. "Streamline" is read as: each direction becomes **one recorded
command** whose output is the record the receiving system's Rules already require — an install that
writes the registry row, a diff that is the port's patch, a PR that carries the port's provenance —
and never an automatic sync (a mirror merges with no disposer, Rule-2; cos plan #345 F1). What the
cabinet builds lives in the core craft (agent zone) so every one of the three systems has it after
the next install; what it does *in* the other two repositories follows their Rules and ledgers.

## What was verified here (WHAT, with evidence; #307's form)
1. **The install exists and is one code path** — `dyad install <repo>` (core, with hooks and bundled
   crafts, `package.py` `cmd_install`), `dyad craft install <src> [--force] [--dwork N] [--source
   <text>]` (`craft.py`), both through `distribute.install`. Both write `crafts/REGISTRY.md`:
   `sha256 = distribute.archive_sha256(tree on disk)`, the proof of an unmodified tree;
   `craft.unmodified()` is the yes/no; `dyad craft list` prints `installed <sha8> (modified)`.
2. **Two gaps in the install path, read from the code.** (a) `dyad install` installs **this
   checkout's tree** (`distribute.install(REPO, …)`): "install release vX.Y.Z" is today *clone the
   authoring repo, check out the tag, run that tree's `dyad install <target>`* — three hand steps the
   play-book makes one. (b) The core's registry `source` is `REPO.name` (`dyad-system`), never the
   tag or sha installed from; a Tended craft's is the archive name. Which release a system runs is
   therefore read from `version` alone, and `main` and a tag of the same `VERSION` are
   indistinguishable in the registry (Rule-11 property 4's drift guard runs only in the authoring repo).
3. **No by-path diff exists.** The registry holds a hash, not files; `unmodified()` says *that* a
   tree differs, never *where*. A back-port needs the diff of the installed tree against the pristine
   source at the registered version — not computable from the registry alone; it needs the source
   (the release archive or the authoring tree at its tag).
4. **Release state of the authoring repo** (`git tag`, `BUNDLE.md`, `VERSION`s): bundle live 0.14.0,
   last tag `v0.12.1` (74180d5, 2026-10-07); core 0.11.0 against `dyad-operator-v0.10.1`; sysadmin
   0.3.0 against `sysadmin-v0.2.1`; sysarch 0.3.0 and syseng 0.4.0 at their tags. So a forward-port
   "from a release" today ships a core two minor versions and 13 days behind `main`; a release is the
   Operator's own ratification event (Rule-11) and is **not** proposed by this plan — it is named as
   the precondition a forward-port from a release has.
5. **`pltrinh1122/dyad-system-tools` is an empty repository** — no commits on `main` (cloned
   read-only to `/home/user/pltrinh1122/dyad-system-tools`). Nothing there to build on or to conflict
   with; stated so no later reader assumes a tool exists.
6. **Receiving-instance upgrade order is already ruled**: `crafts/sysarch/rules/distribution.md`
   "Receiving-instance upgrade order (#178)" — core first, then every Tended craft its Rule text
   cites, `check --guards` clean against the pass, not each PR; `MANIFEST.md requires:` floors
   (`dyad-operator>=0.10.0/0.10.1`) refuse a craft on too old a core. The play-book cites it, never
   restates it.
7. **Host prerequisites and the record** are the sysadmin craft's `host-install.md` (#81): verified
   by running `dyad check --list`, every install step a reversible host action with its seven-column
   change-log row in the *receiving* system's host corpus, postcondition "registry sha equals the
   tree, second run `0 changes`, `check --guards` exits 0".

## Mutation proposed — Part A (agent zone, one PR, this repo)
A1. **`dyad craft diff <craft> --against <src> [--patch]`** (`dyad/scripts/craft.py`): the by-path
    diff of an installed tree (`crafts/<craft>/`, or the core when `<craft>` is `dyad-operator`:
    `dyad/`) against a source — a release archive or a tree (an authoring clone at a tag) — using
    `distribute.files`/`archive_modes`/`git_modes`, the install's own readers (Rule-13: imported, not
    re-authored). Prints `added`/`removed`/`modified`/`mode` per path and a one-line summary; `--patch`
    writes a unified diff (`difflib`, stdlib) of the text files to stdout — **the back-port's patch**.
    Exit 0 unchanged, 1 differing, 2 refused. Reads only; never the clock.
A2. **The registry `source` names what was installed from** (`package.py` `cmd_install`, `craft.py`
    `cmd_install` default): `<repo name>@<tag>` when the source tree is at an exact tag (`git describe
    --tags --exact-match`), else `<repo name>@<sha12>`; an archive keeps its file name. A
    `--source <text>` still overrides. Gap 2(b) closed; the Tended-craft row shape is unchanged.
A3. **`dyad install <repo> --from <src>`**: when `--from` names a release archive (`dyad-<ver>.tar.gz`,
    bundled crafts inside) or a tree, the install's source, version, roots and bundled list are read
    from *that* tree, not this checkout; default unchanged. Gap 2(a) closed in one command, through the
    same `distribute.install` (Rule-11 property 5: data, not a second path).
A4. **The port play-book**, `dyad/playbooks/port.md`, read by nothing in a Rule (a play-book is read by
    a Rule or cited by one; this one is cited from `distribution.md`'s upgrade-order paragraph, a
    sysarch craft rule — one line, in a separate **craft-zone** PR, A6). Three procedures, each a
    run-book step with its postcondition: **forward** (receiving repo: `dyad install <.> --from
    <release>`, then `dyad craft install` per cited craft in #178's order, `check --guards`, the
    change-log row per `host-install.md`; precondition: a tag exists for the version wanted);
    **diff** (`dyad craft diff` against the registered source; a non-empty diff is a port owed);
    **back** (the authoring repo: a branch carrying the `--patch` output, its row opened on the
    downstream row's own Operator prompt — the cheapest admissible same-Operator form, below — its
    PR body citing `d-work #<id>` and the downstream `<system>-<row>`). Never a mirror; every port a
    PR its receiving Operator disposes.
A5. **The run-book** `dyad/runbooks/port.md` (`# sections: Install, Crafts, Guards, Diff, Patch, Port`;
    `TAG`, `SRC`, `CRAFT`, `TARGET` from the environment, as `craft.md` reads `CRAFT`), checked by
    `sysadmin/runbooks` on every push; tests in `dyad/tests/test_craft.py` (A1, A2: a fixture install
    then a one-file edit → the diff names it; the patch applies), `dyad/tests/test_package.py` (A3:
    install from a built archive into a scratch repo = `0 changes` on the second run, registry row
    `source` naming the archive), `dyad/tests/test_playbooks.py` (A4/A5: sections pinned to the
    run-book's). `dyad/README.md` and the `dyad` usage docstring gain the verbs' lines.
A6. **One craft-zone PR**: `crafts/sysarch/rules/distribution.md` gains one sentence citing the port
    play-book under the upgrade-order paragraph; `crafts/sysarch/VERSION` 0.3.0 → 0.3.1 (a released
    craft changed: Rule-11 property 7's released-craft sentence; the bundle row warns until an
    infra-zone row update, which is a release-time act and is **not** in this plan).
A7. This d-work's ledger files; the seat's presence touched `-r 353`.
