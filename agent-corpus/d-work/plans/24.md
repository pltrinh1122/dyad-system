## Finding — the exec bit was not lost by accident, and the hook is the bug
`crafts/syseng/guards/naming_rules.txt` grants 100755 to exactly four path classes:

    mode: dyad/bin/<name>          = dyad/bin/*              = 100755
    mode: dyad/hooks/<hook>        = dyad/hooks/*            = 100755
    mode: crafts/<craft>/templates/*.sh = crafts/*/templates/*.sh = 100755
    mode: crafts/<craft>/server/*.sh    = crafts/*/server/*.sh    = 100755

Every tracked `.py` in the tree is 644, and the rule intends that: the entrypoint and the hooks are
executable, the modules they call are not. #6 was right. The bug is that one hook calls its module
the wrong way:

    pre-commit:  exec "$(git rev-parse --show-toplevel)/dyad/guards/infra/containment.py" staged
    pre-push:    exec python3 "$(git rev-parse --show-toplevel)/dyad/scripts/package.py" check --guards

The sibling hook already does it correctly. Reproduced before planning: staging one file and running
`dyad/hooks/pre-commit` gives `Permission denied`, exit 126.

Two Rule texts also print a bare-path invocation. Rule-11's (`dyad/scripts/package.py check`) names
the mechanism in prose; Rule-1's line 30 is an instruction to a reader — "print it with
`dyad/guards/infra/containment.py zones`" — and following it fails the same way.
