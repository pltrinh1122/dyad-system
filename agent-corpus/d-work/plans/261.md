## Incident, recorded on the plan-`Y` turn (Rule-3, written before the reply)
Re-verifying PR #366's head before asking its merge `Y`, I ran `check --evidence` from the
branch's worktree but through **the main checkout's** entrypoint
(`/mnt/shared_data/dyad/dyad-system/dyad/bin/dyad`). It exited 0 with `head=9ebc7fc`,
`tree=7973c782`, `dirty=no`, `evidence-sha256=614f8fab…` — an evidence block for `main`, produced
while standing in the worktree whose HEAD is `e06a3eb`. Nothing was pasted, posted or merged on it:
the mismatch was caught by comparing `head=` with `git rev-parse HEAD` in the same directory, and
the run was repeated with the worktree's own `./dyad/bin/dyad`, which reproduced
`head=e06a3eb`, `tree=0ea3d363`, `evidence-sha256=0273d2ae…` byte-for-byte against the block
already on the PR.

**Cause, read from the code.** `dyadlib.repo_root()` resolves the root as
`git rev-parse --show-toplevel` with `cwd=PKG` — the package directory of the *invoked script* —
and its own docstring says so: "The git work tree containing the package … in a linked worktree
too." The entrypoint is `exec "$(dirname "$0")/dyad-python" "$(dirname "$0")/../scripts/package.py"`,
so the checkout judged is the one the entrypoint lives in, never the caller's cwd. This is by
design and correct for a package that must find its own tree. The trap is that an evidence block
carries no trace of which entrypoint produced it: `head=` is the only tell, and a reader who
assumes the cwd was the subject has no other.

**Consequence.** None, caught before use. **Why it matters:** Rule-2's Binding rests on "the
kernel-only path … run by the main Agent on the exact head being merged", and this is a silent way
to produce a well-formed, 0-FAIL, correctly-signed block for the wrong head. It is adjacent to
incident 139 (`check --pr` dispatching on the checked-out branch name, `rows.py:169`) and has the
same shape: a command whose subject is decided by where it was invoked from rather than by what it
was asked about.

**The `INCIDENTS.md` row is owed, and deliberately not written yet.** The next agent-zone PR is
PR #366 itself, whose head is the head this turn's merge question names; appending to it would move
that head and break Rule-2's heads-unchanged condition on a question about to be asked. The row
therefore goes to the first agent-zone PR after PR #366 merges, together with #285's own owed row
(the two stray presence files). Stated here so the debt is in the corpus, not only in the reply.

## Correction to the incident above, verified after the plan-`Y` (clerical; the mutation is unchanged)
The cause as recorded names the wrong function, and the consequence understates the mechanism. Both
re-derived from the code; the section above stays as written and this is the correction.

- **`dyadlib.repo_root()` is never called on the `--evidence` path.** A grep for it over
  `dyad/scripts/package.py` returns nothing. The script resolves its own root at import instead:
  `PKG = Path(__file__).resolve().parent.parent` and `REPO = git rev-parse --show-toplevel` with
  `cwd=PKG` (`package.py:106-107`). `repo_root()` has the same shape and the same default
  (`dyadlib.py:250`, `cwd=start or PKG`), which is why reading it gave the right mechanism under the
  wrong name. The entrypoint line is `exec "$(dirname "$0")/dyad-python"
  "$(dirname "$0")/../scripts/package.py" "$@"` — it execs `dyad-python` *with* `package.py` as an
  argument, both paths from `$0`.
- **It is not only the three header lines.** Every guard is handed that same `REPO`
  (`package.py:606` for the package checks, `:628` for the transaction checks), so the whole block
  counts the entrypoint's corpus. Re-run over the same worktree during this d-work's verification,
  the two entrypoints differ throughout: 185 plans against 184, 273 rows against 272, 253 provenance
  records against 252, 1160 files classified against 1156, 6 run-book events against 3.
- **The worktree's own run was not even green.** Through `./dyad/bin/dyad` inside the worktree the
  same head exits **1** (`FAIL [guards] agent/prs [d-work]: PR body cites no 'd-work #N'`, an
  artifact of `e06a3eb` now being an ancestor of `origin/main`, so `origin/main..HEAD` is empty). A
  reader of the 0-FAIL block from the wrong entrypoint would never see it.
- **The push gate is immune, twice over** — which is what measures the gap. `dyad/hooks/pre-push:4`
  re-resolves `git rev-parse --show-toplevel` at run time rather than from `$0`, and
  `check --guards --pre-push` reads the checked-out HEAD (`package.py:556`), refuses a ref that is
  not it (`:570`) and refuses a tree holding changes the push does not carry (`:576`). The evidence
  path is handed no head, discovers one, and asserts nothing about it.

The owed `INCIDENTS.md` row is written now that PR #366 has merged (`a964e63`), as the section above
directs, in the agent-zone PR this plan's reply names.
