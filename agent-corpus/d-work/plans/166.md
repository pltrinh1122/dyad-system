# Plan #166 — `ds-report-incidents`: a play-book that groups the incident ledger and projects an anonymized, redacted report for a VAR

*Rule-15 phase 1. base commit: b888c5c (`main`, 2026-09-25). refs: 161 137.*

## Intent as read
A repeatable procedure that turns this instance's incident ledger into **one file that is safe to
hand to a third party** — a VAR such as Alchemic Solutions Group, Inc. — grouped so it is useful to
that reader, anonymized and redacted so it discloses neither this host's identity nor the practice's
proprietary substance, and downloadable as a single self-contained artifact that can be hand-carried
or emailed. The Operator's second message fixes the name: `ds-report-incidents`.

"IP content" is read as **both** senses, because either one left in would sink the deliverable:
*IP addresses and identity* (hosts, paths, users, emails, session ids, URLs) and *intellectual
property* (the practice's Rules, guards, modules, vocabulary, ledger ids, craft internals). The
plan covers both and says which class each belongs to; narrow it at the plan-`Y` if only one was
meant.

## Craft-instantiation play-book (Rule-3, Plan clause)
`dyad/playbooks/craft-instantiation.md` applied before this plan file was written.
- **Trigger: fires.** No installed craft practises *disclosure* — what may leave this system, in

  built, `syseng` is implementation discipline, `countersign` is a peer's craft under construction

- **craft-instantiation-criteria: none fire.** D1 — the data is this instance's own ledger, already
  here; the report's *destination* is external, its *source* is not, so no classification boundary
  is crossed. D2 — same Operator, same disposer; a VAR is a recipient, not a disposer. D3' — no such
  craft corpus exists to import, so it is authored here. D4 — its d-works `refs` this ledger's rows
  constantly. D5 — no lifecycle of its own. D6 — no zone beyond the five.
- **Outcome: the default — a new craft instance in this system**, `crafts/disclosure/`. The
  play-book and its run-book stay in the **core** craft, exactly as `incident-hardening` does.
- The run-book steps (`dyad runbook run craft new|check|registry`) belong to execution, after the
  plan-`Y`; their event ids go in the completion reply.

## The design decision that matters: allow-list, not deny-list
A deny-list can catch `192.168.`, `/home/`, `gh[pous]_…`. It cannot catch a sentence that reveals a
guard's internals in plain English — and 57 of 57 rows in this ledger are written in exactly that
English. So the report is assembled by **allow-list**: only fields the play-book names may appear in
it, and every one of them is either a date, a count, a controlled value, a stable pseudonym, or a
sentence the Agent wrote *for this audience*. The deny-list is a **second, fail-closed gate** over
the assembled output — if any forbidden shape survives, the projector refuses to write at all.

Three redaction classes:
- **Class A — identity. Removed.** Hostnames, `/home/…` and any absolute path, IPv4/IPv6 literals,
  email addresses, session ids and names, repository URLs, PR numbers, real names, and the credential
  shapes `dyad/guards/agent/provenance.py` already knows (reused, Rule-13).
- **Class B — proprietary substance. Pseudonymized, never deleted.** Rule numbers, guard and module
  names, file paths, craft names, vocabulary terms and ledger ids become **stable pseudonyms**
  (`SUBSYSTEM-3`, `COMPONENT-7`, `POLICY-K`) from a map that lives at
  `agent-corpus/disclosure/pseudonyms.md` and **never leaves the system**. This is what keeps the
  report useful: grouping, counts and co-occurrence survive — "7 incidents in SUBSYSTEM-3, 4 of them
  one failure mode" — while the substance does not.
- **Class C — retained.** The date, the *failure mode* class (vocabulary, Rule-3), the consequence
  shape (caught before commit / reached `main` / data lost), the mitigation status, and one
  Agent-authored **external summary** per group, written for this audience and passed through the
  Class A and B gates like everything else.

## Mutation proposed — two PRs (Rule-1: one zone each)

### PR 1 — core craft (**agent** zone)
- `dyad/playbooks/ds-report-incidents.md` — the play-book: trigger, parameters
  (`LEDGER`, `AUDIENCE`, `LEVEL`), the three redaction classes, the six steps, what the completion
  reply must cite, and the delivery gate below.
- `dyad/runbooks/ds-report-incidents.md` — its steps as `dyad-cmd` blocks run through the core
  runner (`dyad runbook run`), each with `class`, `role`, `undo`, `postcondition`, `scope`, and a
  declared `# sections:` set. Steps: **Survey** (row count, latest date, last report's watermark —
  the idempotence gate, copied in shape from `incident-hardening`), **Group** (failure modes; the
  same grouping, cited not duplicated), **Map** (pseudonyms allocated for anything new, stably),
  **Summarize** (the Agent writes one external summary per group), **Project** (`dyad project
  disclosure`), **Verify** (the fail-closed gate re-run over the written file, plus the redaction
  manifest). Every step read-only except Project, which is `reversible` with `undo: rm` — its output
  is generated and untracked, so it is not a repo transaction.
- `dyad/guards/agent/incidents.py` — the incident entity's parser and its guard (`ENTITY`, `CORPUS`,
  `FIELDS`, `TRANSACTION`, `check_package`, `describe`, `INVARIANTS`, per the naming guard's symbol
  row), checking only a row's shape: five cells, a parseable date, a d-work id column. It exists
  because **four modules already parse this ledger independently** — `references.py:incident_ids`,
  `project_instances.py:133`, `project_erd.py:151`, `project_countersign.py:_incidents` — and the
  guard contract makes the guard the entity's one parser, importable by projectors and by
  `references.py`.
- `dyad/tests/guards/agent/test_incidents.py` (Rule-12).
- `agent-corpus/disclosure/pseudonyms.md` — the map (instance, agent zone, tracked: it must be
  stable across reports so two reports are comparable, and it never leaves the system).

### PR 2 — the new craft (**craft** zone), `crafts/disclosure/`
- `VERSION`, `MANIFEST.md` (`requires: dyad-operator>=0.9.1`), `README.md`, `docs/`.
- `rules/redaction.md` — a **Tended** rule: the three classes, the allow-list-first principle, the
  fail-closed gate, the pseudonym map's location and confinement, the audience parameter, and the
  rule that **no craft or core file names any recipient** (Rule-11 property 1).
- `vocabulary/CRAFT.md` — `disclosure report`, `redaction class`, `pseudonym map`, `audience`,
  `deny-list`, namespaced as craft terms. **Not** Agent terms: `vocabulary.py` fails a term no Agent
  Rule mentions, and these are mentioned by a play-book and a Tended rule, not by a Rule.
- `guards/redaction.py` + `guards/redaction_rules.txt` — the redactor (the shapes and the
  substitution), its data beside it; the projector imports it as `project_events.py` imports
  `runbook`.
- `projectors/project_disclosure.py` — surface `disclosure` (registry `disclosure/disclosure`, the
  shape `countersign/countersign` already uses): one **self-contained, deterministic** HTML file at
  `<instance>/projections/disclosure.html` — inline CSS and JS, no external reference, so it
  hand-carries and emails as one file — carrying the audience, the level, the groups, the counts,
  and a **redaction manifest** (how many values of each class were removed or replaced) so coverage
  is checkable without the source. `generated: projections/*` already keeps it untracked
  (`dyad/scripts/package_rules.txt`), so no new pattern is needed.
- `tests/` — the redactor against a fixture corpus containing every forbidden shape (output must
  contain none), the manifest's arithmetic, determinism (two runs byte-identical), and a live run.

### Not in this mutation
- **No Rule change.** No Rule requires this report; an Operator prompt asks for it, and the
  play-book's own Trigger section says so — as `incident-hardening` is required by Rule-3 and this
  one is not. Rules 3, 4, 5 and 6 are untouched.
- **No conversion of the four existing incident readers.** A backlog row; converting them is its own
  d-work (Rule-12 Boundaries: a plan is never widened by its realization).
- **No report generated and nothing delivered.** The first actual report, and its delivery, is a
  separate d-work — see the gap below.
- No host action (Rule-8), no release, no preference change, no change to the hooks or CI.

### A gap this plan does not close, stated
Delivering a file to a third party is an outward, irreversible act, and Rule-11 already treats
"publishes to the world" as the Operator's to ratify. But only an **Agent Rule** may declare a
ratification event (Rule-2), a play-book is not a Rule, and a Tended rule may not bind the Agent's
process (Rule-4's guard warns on exactly that). So this plan does the conservative thing: the
play-book's last step requires the Agent to ask `Y/N: deliver <report> to <audience>?` as **conduct**
before any file leaves the system, and a **backlog row** proposes the Rule amendment that would make
it a declared ratification event. I am not smuggling a ratification event into a Tended rule.

## Rule-10
- **Path:** two PRs — the play-book, its run-book and the incident parser in the core; a new
  `disclosure` craft holding the redaction rule, the redactor and the projector. Allow-list first,
  deny-list as a fail-closed second gate, pseudonyms instead of deletion. No report generated and
  nothing delivered under this plan.
- **Counter:** a single core script writing a markdown file would deliver something today, with no
  new craft, no new guard and no projector — perhaps a tenth of the work.
- **Reconciliation:** that version has no mechanical check, and a redaction artifact without one is
  exactly the artifact you must not trust: the first time a paraphrase leaks an internal, it leaks to
  a company outside this system, and nothing would have caught it. The craft is also what makes the
  discipline exportable, which is the point of a VAR-facing report existing at all. What the counter
  is right about is sequencing — so the plan ships no report, and the first report is its own d-work
  with its own delivery question.
