# Plan #15 — craft-contributed data files for the syseng guards

Base commit of `main`: 0585f1e. Refs #1 (which deferred this and named it a follow-on), the sysarch
`references.md` property 6 (the same design, named as backlog there too).
Falsification: inline below; the record proposed as mutation item 6 carries it in full.

## Intent as read
"Plan #15." The row is the follow-on d-work #1 named in its own attack 3: the syseng guards'
data files hold rows that belong to *other* crafts, and the end state is that each craft ships its
own rows and the syseng guards merge them by discovery, so a craft's rows leave with the craft.
Plan means: deliver the mechanism that makes contribution possible, prove it mechanically, and say
plainly which rows can and cannot move in *this* repo.

## Findings — verified by reading the code and the tree, not inferred

**F1 — the rows that are foreign to syseng are, today, almost all from crafts that are not here.**
`crafts/syseng/guards/naming_rules.txt` carries rows whose `owner` column (the table in
`crafts/syseng/rules/naming.md`) names another craft's rule: the `<ops>/…` kind and the
`crafts/<craft>/templates/*.sh` + `server/*.sh` modes (the sysadmin `ops-scripts.md`), the
`<runbooks>/…` kinds (the sysadmin `server-instances.md`), the two `.github/workflows/lan-git*.yml`
allow lines (lan-git), and `env: DYAD_OPS@sysadmin`. `invariants_rules.txt` carries
`exempt: crafts/*/server/*.py` (lan-git). This repo has exactly two crafts — `sysarch` and
`syseng` (`ls crafts/`; `crafts/REGISTRY.md` is empty, both are authored here). **Neither sysadmin
nor lan-git is installed here**, so none of those rows can be moved to their owner in this repo.
This is what #1's attack 3 meant by "needs matching files authored in workstation at the same
moment."

**F2 — the file name #1 named trips syseng's own `beside` rule.** #1's attack 3 named
`crafts/<craft>/guards/naming_rules.txt` as the contributed file. `naming_rules.txt` itself carries
`kind: <entity>_rules.txt = crafts/*/guards/*.txt = crafts/[a-z][a-z0-9-]*/guards/(?P<beside>[a-z][a-z0-9_]*)_rules\.txt`,
and `naming.py:162` fails any such path whose `<dir>/<beside>.py` does not exist. `crafts/sysarch/guards/`
holds only `registry.py`; a `crafts/sysarch/guards/naming_rules.txt` would therefore **fail the very
guard it feeds**. The deferred design needs a distinct file name, not just a loader change.

**F3 — owner is not the same as contributor.** Several rows whose `owner` column names the sysarch
`guards.md` or `projection.md` select *core* paths — `dyad/guards/<corpus>/<entity>.py`,
`<entity>_rules.txt`, the `ENTITY CORPUS FIELDS …` contract symbols (whose constant,
`dyadlib.CONTRACT`, is core's). Those rows must **not** leave with sysarch: the paths they check
outlive it, and the check would vanish while its target remained. Only a row whose selected paths
exist *only when the craft exists* may be contributed by that craft.

**F4 — the loader is single-file today.** `naming.check_package` calls `load_rules(data)` on the one
`DATA` path beside the guard; `invariants.py` does the same. There is no discovery step, so
contribution is not merely unconfigured — it is unimplemented.

## Mutation
One PR, **craft zone** (`crafts/syseng/**` only; Rule-1), citing `d-work #15`:

1. `crafts/syseng/guards/naming.py` — a discovery step in `check_package`: for every installed craft
   (`dyadlib.craft_dirs`), read `crafts/<craft>/guards/naming_contrib.txt` if present and merge its
   entries with the guard's own, each tagged with its contributing craft. A malformed or stale
   contributed line is reported naming that craft, never syseng.
2. `crafts/syseng/guards/invariants.py` — the same discovery for `invariants_contrib.txt`.
3. `crafts/syseng/guards/naming_rules.txt` — one new `kind:` row for the contributed file
   (`crafts/*/guards/*_contrib.txt`, the `<receiver>` part naming a syseng guard module), so a
   contributed file is itself a named, checked path and F2's collision cannot recur.
4. `crafts/syseng/rules/naming.md` and `crafts/syseng/rules/invariants.md` — the contribution
   protocol stated as the rule it is: what a craft may contribute, where the file lives, that a
   contributed row's staleness belongs to the contributing craft, and that the `@<craft>` qualifier
   and the vacuous-`exempt` glob from #1 remain the interim for rows whose craft is absent, retiring
   per row as each craft ships its file. The `naming.md` table gains the row for item 3.
5. Tests (Rule-12 mapping): `crafts/syseng/tests/guards/test_naming.py`,
   `crafts/syseng/tests/guards/test_invariants.py` — a scratch craft that contributes rows; the
   contributed row is honoured; the craft removed, its rows are simply gone (no stale failure);
   a malformed contributed line names its craft; a contributed file whose receiver is not a syseng
   guard fails.
6. `crafts/syseng/falsification/rules/craft-contributed-data.md` — the record, attacks below.

**Deliberately not in this mutation, stated:**
- **No live row moves.** F1: the rows that should move belong to sysadmin and lan-git, neither
  installed here; F3: the sysarch-owned rows select core paths and must stay. The mechanism is
  therefore proved by tests against a scratch craft, not by a live migration — and it is precisely
  what unblocks the workstation system to author `crafts/sysadmin/guards/naming_contrib.txt` and
  this repo to drop the matching rows afterwards.
- **No `VERSION` bump.** A craft's version is bumped by its own release d-work (#13/#21 pattern;
  the #22 incident row records getting this wrong).
- **The interim mechanisms stay.** `DYAD_OPS@sysadmin` and `exempt: crafts/*/server/*.py` keep
  working exactly as they do now.

## Falsification
- **"#1 already named the file — `crafts/<craft>/guards/naming_rules.txt`. Use it."** Refuted, by
  reading the guard: F2. That path fails `naming.py:162`'s `beside` check in any craft without a
  `naming.py`, which is every craft but syseng. The deferral named a design that does not survive
  its own guard; `<receiver>_contrib.txt` is the smallest change that does.
- **"Contribute from the guard *module* — a constant — as `references.md` p6 words it ('each craft
  guard contributes its own rows')."** Survives, scoped — and it is the strongest alternative. It
  needs no new file kind at all, and it would make this mechanism identical to the one
  `references.md` p6 still owes. Chosen against for two reasons, both stated: it puts a list in
  code where this corpus keeps lists in data beside the guard (Rule-11 p1, and every `*_rules.txt`
  here), and it silently excludes a craft that ships no guard from contributing at all. If the
  Operator prefers the constant, this plan is the wrong one and should be re-planned, not patched.
- **"The mechanism has no user in this repo, so it is dead code."** Survives, scoped — the honest
  cost, and F1 is its whole shape. Two crafts are here and neither can contribute a row today. What
  it buys is that the workstation system can author its files without a second design round, and
  that this repo's data stops being the only place a foreign row can live. If the Operator would
  rather wait until sysadmin is installed here, `N` is coherent and nothing else depends on this.
- **"Prove it live by moving the sysarch-owned rows."** Refuted: F3. `owner` names the rule that
  owns the *pattern*; contribution must follow the *paths*. Moving the guard-contract symbol rows
  or the `dyad/guards/…` kinds to sysarch would delete a check on core paths the moment sysarch
  left, which is the opposite of what this d-work is for.
- **"Then retire `@<craft>` and the vacuous exempt now — they were only interim."** Refuted: they
  are the interim for exactly the rows that *cannot* move yet (F1). Retiring either before the
  owning craft ships its file would leave `DYAD_OPS` unchecked or falsely stale.
- **"The contribution protocol belongs to sysarch, not syseng — `guards.md` owns the guard
  contract."** Survives, scoped: what is being changed is the data model of syseng's own two
  guards, so the rule is syseng's. If it later generalises to every guard's data — `references.md`
  p6 included — that generalisation is sysarch's, and this is its first worked instance to
  generalise *from*.
- **Overlap (Rule-16):** read before writing this plan. `dev-main` (different root) holds no syseng
  rows with files named. `web-sysarch` is **live and records the same `root` string as this session**
  (`/home/user/dyad-system`) and holds #45 plus #27, whose plan touches
  `crafts/syseng/rules/failure.md` and `crafts/syseng/rules/README.md` — the same craft tree and the
  same zone as this plan, but not the same files. Two findings, neither a blocker: (a) if #27's
  craft-zone PR lands first, execution re-reads its base before touching `crafts/syseng/rules/`;
  (b) the identical `root` is the sharper signal Rule-16 names, but this session's working tree has
  never carried that peer's edits, so inference says a different container at an identical path
  rather than one shared checkout — stated, not assumed away.
