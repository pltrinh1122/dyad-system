# Plan #388 — the three organization modes, supported mechanically

base commit: 0e8963a (`main`, 2026-10-22)
refs: #386 (the finding), #385, #369, #368, #366 (M3/M4), #253 (R17–R18, the escalate edge), #314

## Intent as read
Three modes of attendance — pure M3 (only the program seat has an Operator present), pure M4 (every
seat does), hybrid (the program seat and some others) — and the escalation route that follows from
each, derived by code from records that already exist, shown on the board, and stated in the Guide.

## Mutation
1. **Attendance, derived, never declared.** A seat is *attended* when a provenance record whose
   `session:` line names that seat holds a disposition entry given in that seat — one whose note is
   neither `mandate #<id>, …` nor `relayed via …` — within the window the preference
   `attendance-window` sets (default 7 days; a preferences-zone row, the Operator's). The leader seat is
   attended by definition while any seat is. No field is written; the record is the proof (#295: a
   holder is what the process says; attendance is what the Operator did). `sessions.attended(seat)` in
   `dyad/guards/agent/sessions.py`, read from `provenance.py`'s parser; tests.
2. **Mode, derived.** Over the live seats (presence `seen` within the stale window): all attended → M4;
   only the leader → M3; otherwise hybrid. `dyad session list` prints the mode and each seat's
   attendance; `dyad dwork board`'s WHO column gains `attended`/`relayed`.
3. **Route, derived.** An escalation (a counter-prompt a seat owes the Operator) is asked in the seat's
   own chat when the seat is attended, and relayed to the leader otherwise — the leader asks it in the
   leader's chat, verbatim, with the seat named, and the answer is relayed back verbatim (R29). The
   relayed question is recorded: until the bus (#303) lands, the seat's plan file quotes it and the
   leader's provenance carries the Operator's answer (#314's shape). The board lists every outstanding
   question with its route (R17), so the Operator sees in one place what to answer where.
4. **Guide.** `crafts/cos/docs/operating-guide.md` gains the three modes, how attendance is earned (a
   disposition in the seat's chat) and lost (the window), and the route table; `rules/organization.md`
   gains the sentence that attendance is derived, never declared. Cos 0.1.x.
5. **Preference.** `attendance-window` row proposed in PR-B's PR or its own preferences PR.
Children (mandate scope: one row per seat, ceiling **2**): engineer (1–3, agent zone), counsel (4, craft
zone); the preference row rides PR-B.

## Falsification
| attack | result |
|---|---|
| Attendance should be declared (a line in the presence file), not derived; derivation lags. | Refuted: a declared line is a claim nobody verifies (#295); a disposition given in the seat's chat is the one act that proves an Operator was there, and it is already recorded by Rule-7. The lag is the window, a preference. |
| The leader cannot know a seat's chat holds an unanswered question. | Survives as #253 R17's requirement: the seat publishes its question by state (its row's plan file, the presence file's optional `waiting-on`, #316) and the board lists it; the mechanism here reads what is published. |
| Relaying the answer back makes the leader a courier, which R18 forbids of the board. | Scoped: R18 binds the *board*; the relay is the leader's act under R29, recorded in provenance both ends. The board stays a directory. |
| Hybrid is unstable: attendance flips as the window slides. | Conceded as the design: the mode is a reading, not a setting; the route is decided per question at the moment it is asked, from the records as they stand. |
