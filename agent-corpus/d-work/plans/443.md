# Plan #443 — a countersign/dwork back-end service: evaluated against the measured pattern; CLI batching first, the service gated on where it can be reached

## Intent as read
The Operator finds the cos's per-disposition git series wasteful as separate CLI calls: fetch, `reset --hard`,
`dwork state`, commit, a push to `main` through the pre-push hook with retries when `main` has moved, then a
mirror push of the session branch. The Operator asks for an evaluation of a `countersign`/`dwork` back-end service
behind an MCP-like interface, optimized for outcome ("a 'clean' repo without needing a full clone"), and for the
chat history and ledger to be mined for further mechanical work to move out. Verbatim prompt: provenance #443
entry 1, relayed by the cos. This plan is the evaluation. Its mutation is the part the evaluation supports now.

## Falsification (Rule-9)
| # | attack | result |
|---|--------|--------|
| 1 | The waste is the full clone and the full gate on every push. | **refuted, scoped.** A clone is 7.56 MiB. A ledger push runs guards only: Rule-12 p2's skip, 2.2 s measured. The waste is **calls**: ≈ 6 per record at ≈ 11.6 s of inference each, plus ≈ 2 gates per commit. Full gates fall only on branch pushes outside `d-work/`, and there the suite memo is per checkout, so it is not shared across containers. |
| 2 | A service removes the per-head evidence suite. | **refuted.** Rule-12 p2: `check --evidence` "never reads one [memo], so the merge evidence always observes". A service only moves where the suite runs. Sharing one run across seats would be a Rule-12 change, and this plan does not propose one. |
| 3 | A LAN `dworkd` (or a ledgerd on the workstation) serves the seats. | **refuted, decisive.** 6 of 6 live seats are cloud containers. Private ranges route inside the container, and the harness says a cloud session cannot reach the Operator's computer. A cloud seat can reach the service only by (a) a public HTTPS endpoint added to the environment's allowed domains, with a per-seat token as an environment secret, or (b) a claude.ai custom connector, which is remote MCP over HTTPS and also public, read at session start. Either way a **write-capable endpoint holding a GitHub token faces the internet**. That is the Operator's decision, and Rule-8 classes its exposure below. A LAN service serves only terminal seats, and today there are none. |
| 4 | MCP over stdio gives the gain without reachability. | **survives, scoped.** A stdio server is a process in the seat's own container, so it is the CLI behind a JSON schema. Its gain is exactly P1's, plus typed arguments, at the cost of the SDK's dependencies (attack 9). Not proposed now. |
| 5 | Extend ledgerd. | **refuted for writes.** ledgerd's invariant is "never a source", and its three PRs have waited 8 days, 384 commits behind. If a service is built, writes go in a sibling `dworkd`. A read-side MCP wrapper over `/board` and `/query` has the same reachability gap (attack 3) and waits for #336 to land. |
| 6 | A service doing writes is a subagent, which Rule-3 Scope forbids. | **survives, scoped.** A tool the main Agent calls is the main Agent's act, as `dyad dwork` is. But a service cannot tell the main Agent from a subagent calling the same tool. A sentence is needed in Rule-3 Scope ("a service's write tool is called by the main Agent only"), and so is Rule-2 *Not ratification* ("a service that executes a clerical act the Operator disposed executes it; it never disposes"). Both belong to P3, not here. |
| 7 | The service becomes the only enforcement (Rule-14 p3). | **confirmed as the risk; fenced by design.** The service runs `package.py check --guards` through the same hook on the kernel. Every seat keeps the hook and may push directly. Its manifest row names P1's verbs as its replacement, so the system loses nothing when it is down. Rule-14 p3 needs one sentence for P3: "a service that runs the guards for a seat is a library adapter; the hook is unchanged." |
| 8 | A server-side evidence run breaks the Operator's re-run (Rule-2 Binding). | **refuted, scoped.** The block is head sha, tree hash, results and a sha256 over them, and it can be re-run on any kernel. Rule-2's "run by the main Agent on the exact head" reads true of a tool call only with attack 6's sentence. A remote run should also name the host it ran on. P3. |
| 9 | The SDK meets the import criteria (Rules 13/14, `import-licenses`, `import-support`). | **survives, scoped.** MIT, released within 12 months, on PyPI. But it brings about 13 dependencies, including `opentelemetry-api`, which #336 kept out by pinning FastAPI. The alternative is MCP's stdio JSON-RPC written on the kernel's `json`. Rule-13 prefers import "whenever a fit candidate exists", so the Operator would choose between the dependency and authoring. Decided in P3, not now. |
| 10 | Batching in the CLI breaks Rule-7 verbatim or Rule-3's Done order. | **refuted.** `--land` calls the same `cmd_dwork` path: the words come from `--said-file`/`--prompt-file`, the fence is unchanged, and `done` is still refused until the head lands. It adds commit and push, which are clerical already (Rule-2: ledger-only commits). |
| 11 | Retrying on a moved `main` double-records. | **confirmed as the hazard; fenced.** A retry does not rebase. It rebuilds from the verb's own inputs on a fresh `origin/main`, re-allocating a `new` id. It refuses with `already landed` when the row already holds the entry (idempotence, syseng `idempotence.md` p1). At most 3 tries, then it stops and prints the state. |
| 12 | A single writer ends id collisions (`stores.md`: "only a shared allocator … changes" them). | **survives, weakened.** It does so only if every seat writes through it. The kernel-only path must stay open (attack 7), so collisions stay possible and are caught as today. |
| 13 | `relay(seat, text)` belongs in the service. | **refuted.** A relay carries the Operator's words between seats in one `send_message`. A service hop adds a party between the Operator's words and the seat (Rule-7 p4) and saves nothing. |
| 14 | P1 duplicates a future service. | **refuted.** P1 is the service's engine: a `dworkd` write tool would run `dyad dwork … --land` in its own worktree. P1 is also the replacement its manifest row must name. |
| 15 | `dyad ledger push` is the natural verb name. | **refuted.** ledgerd's PR #424 claims `dyad ledger init|serve|…`. The verbs go under `dwork`. |

## Recommendation (Rule-10)
**Path: phased, CLI first.** P1 (this plan's mutation, mandate below) puts the whole series into one call per
record:
- `dyad dwork new|state … --land [--mirror <branch>]`, and `dyad dwork land <paths…> -m <msg>` for plan files,
  presence and traces.
- `dyad check --evidence --at <head>` in a detached worktree.

The estimate is about 5 fewer tool calls per record and half the push gates. Over this window that is about
95 × 5 ≈ 475 calls, ≈ 1.5 h of agent time in two days (estimate). It also closes the #427 and #412–#414 incident
classes by construction. It adds no World dependency, no Rule text and no host action.

The service, P2 (read) and P3 (write tools), is **not built now**. Its first question is where it can be
reached, and that is yours.

**Strongest counter: build `dworkd` now.** That is what you asked for. A service gives one writer, one clean
worktree and server CPU for the suites. Its tools are typed. Seats would need no hook, no clone and no retry
loop. P1 polishes the pattern you called inefficient instead of replacing it.

**Reconciliation.** The cost measured is calls and gates, and P1 removes it. What only a service adds is a
single writer across seats and offloaded CPU, and both need an endpoint the seats can reach. Every live seat is
a cloud container that cannot reach a LAN host. Making one reachable means publishing a write endpoint that
holds a GitHub token. That is a decision about exposure, not engineering, and it should not ride a plan-`Y`.
P1 is also the service's engine and its named replacement, so nothing built now is thrown away.

**Concession.** If you want the service regardless, answer `N` with "service". The plan is then revised to P3,
and its first question is reachability: (a) public HTTPS plus allowed domain, or (b) a claude.ai connector, or
(c) terminal seats on the LAN.

## Mutation (mandate: one child per P1 deliverable, agent zone; ceiling 2)
Rule of the class: a child row per P1 deliverable named below, agent zone, its PR citing its own row, accreted
`--mandate 443`. **Ceiling 2.** P2, P3, any Rule text and any host action are outside the scope.
- **C1 — `--land`** (`dyad/scripts/land.py` new, dispatched from `package.py`'s `cmd_dwork`;
  `dyad/tests/test_land.py`):
  - It works in a tool-owned worktree, `<git common dir>/dyad-land`, detached at a freshly fetched
    `origin/main`, with `PYTHONDONTWRITEBYTECODE=1`. The seat's checkout is never reset.
  - It runs the verb there with the given words.
  - It refuses any written path outside `<instance>/d-work/`, because that would not be ledger-only.
  - It commits only the written paths, with a generated `ledger: …` subject that cites no `d-work #`.
  - It runs `git push origin HEAD:main [HEAD:refs/heads/<branch>]`: one push, one hook run, guards unchanged
    (Rule-14 p3).
  - On a non-fast-forward it rebuilds from the inputs, refuses when the entry has already landed, and makes at
    most 3 tries (attack 11).
  - It prints the landed sha.
  - Tests:
    - a record lands;
    - a racing commit is rebuilt, and a `new` is re-allocated;
    - an already-landed entry is refused;
    - a path outside `d-work/` is refused;
    - two refs are pushed in one hook run;
    - an ignored `__pycache__` in the seat's checkout does not reach the worktree.
- **C2 — `--at <head>`** (`package.py` `check`; `dyad/tests/test_package.py`):
  - `check --evidence --at <sha>` runs in a detached worktree under the common dir and removes it afterwards.
  - The block is byte-identical in form, and Rule-12 p2 is untouched (no memo read).
  - Tests: a run at a head other than `HEAD` leaves the seat's checkout and index unchanged, and the block names
    that head.
- **Not accreted.** These are surfaced at the Done question as candidate rows, each needing its own plan:
  - **P2/P3 `dworkd`.** Reachability first (attack 3). Then:
    - the Rule sentences of attacks 6–8 (Rule-2 *Not ratification*, Rule-3 Scope, Rule-14 p3);
    - the SDK-or-stdlib choice (attack 9);
    - manifest rows in `dyad/infrastructure/INFRASTRUCTURE.md`: `dworkd`'s libraries, `library`, with
      replacement "P1's `--land` and `--at`", profile `operating`;
    - a Rule-19 run-book `workstation-corpus/runbooks/dworkd.md` with a `/health` criterion.

    Deploying it is **reversible** (Rule-8; undo: stop and uninstall the unit). Exposing it publicly with a
    GitHub token is **destructive when in doubt**, since a leaked credential has no tested undo: it gets its own
    counter-prompt and is never accretable (Rule-2 Binding).
  - **The evidence-duration gap** (124–184 s measured against 10–20 min reported): trace one evidence run by
    duration.
- Evidence at Done: `dyad check --evidence` on each PR's head, verbatim. One live cycle of the cos or a
  secretary on `--land`, with its tool-call count against the 4–6 measured here. The trace (`dwork-trace:
  always`).
