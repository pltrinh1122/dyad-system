# Plan #114 — make the sysadmin craft part of the core release

Base commit of `main`: 25a1834. Refs #83 (the sweep that surfaced the craft's coupling), #155 (the
extraction that created the craft), #10 (backlog: core tests hardcode sibling-craft presence),
#178 (the receiving-instance upgrade order), #167 (per-craft reference resolution).

## Intent as read
`sysadmin` should ship **with the core release** — a system that installs the core gets the craft —
rather than only as a separately-installed Tended craft. The prompt asks for a **plan**, so this
d-work delivers the plan and its falsification; nothing is built.

## Why this is a real defect, not a preference (verified)
Four core Agent Rules cite `crafts/sysadmin/` **by path** — Rules 5, 8, 18 and 19, nine distinct
paths. Rule-8's kernel reads `crafts/sysadmin/rules/host-mutation.md`; Rule-18's reads
`ops-scripts.md`; Rule-19's reads `server-instances.md` and names two of its guards. So **what the
core ships and what the core's own Rules depend on already disagree.** The request closes that gap.

Two things were measured rather than assumed, and both changed the shape of this plan:

1. **A core-only install of `main` is already red.** Installed HEAD's core into a scratch repo
   (`package.py install`, 120 changes, no `crafts/` tree) and ran the runner there:
   `FAIL [Rule-12] tests failed (dyad/tests)` — `FAILED (failures=1, errors=1, skipped=21)`. The
   core does not stand alone *today*, before anything here changes. Backlog **#10** already names
   this class ("core tests hardcode sibling-craft presence and a minimum row count") and is the
   likely cause; **confirming which tests, and whether #10 covers both the failure and the error,
   is step 1 of execution** — not asserted here.
2. **Bundling one craft does not break the others' citations.** I expected `references.py`'s
   whole-tree `crafts_absent` flag to disengage once `crafts/` existed, turning sysarch's and
   syseng's citations red. It does not: #167 made resolution per-craft (`craft_state`), and an
   absent craft with no registry row resolves `skip`, or `warn` when a registry exists and omits
   it — never `FAIL` (FAIL is reserved for installed-then-deleted). So shipping sysadmin alone is
   safe for the siblings. **`crafts/sysarch/rules/distribution.md`'s paragraph claiming a one-craft
   subset leaves `check --guards` red predates #167 and is now stale** — a finding of this plan,
   filed as a backlog row rather than fixed here.

## Mutation (proposed)

**PR 1 — agent zone (core craft), the substance.** The change is a **Rule-11 amendment**, not a
build tweak, because property 2 forbids today what this asks for: a core install writes "only under
that craft's root plus … a documented, prefixed set of host-side hooks", and a Tended craft install
writes "only `crafts/<craft>/` and its row in `crafts/REGISTRY.md`". A core install that also writes
`crafts/sysadmin/` breaches p2 as written.
- `dyad/rules/RULE-11-distribution-structure.md` — a **bundled craft**: a Tended craft the core
  release carries and `dyad install` writes, declared in the core's own manifest, still its own tree
  and its own zone, still separately versioned and separately taggable. p2 gains the clause; p4 and
  p7 are untouched (the bundle stays what it is).
- `dyad/vocabulary/VOCABULARY.md` — the term `bundled craft`.
- `dyad/falsification/rules/rule-11-distribution-structure.md` — this plan's attack table as an
  amendment record.
- `dyad/scripts/distribute.py`, `package.py` — `dyad build` carries the bundled craft's tree and
  `dyad install` writes it, through the **one** distribution code path (Rule-11 p5): the difference
  stays *data* — which crafts are bundled — never a second mechanism.
- `dyad/tests/…` (Rule-12) — a scratch core-only install has `crafts/sysadmin/` present and the
  runner is green there; and a second install is `0 changes` (idempotence).

**PR 2 — infra zone.** `.github/workflows/dyad-release.yml` if the `core` kind must publish the
extra archive alongside `dyad-<version>.tar.gz`. `BUNDLE.md` is **not** touched.

**Craft zone — nothing.** `crafts/sysadmin/` does not move, does not change, and keeps its own
`VERSION` and its own `sysadmin-vX.Y.Z` tag. Only what the *core release carries* changes.

**Not in this mutation, stated:**
- **`sysarch` and `syseng` are not bundled here**, though the same coupling exists for both
  (sysarch: 7 paths across 8 core Rules; syseng: 7 across 4). Doing all three at once is the obvious
  next question and is deliberately left to the Operator — the prompt named sysadmin. Flagged, not
  assumed.
- **#10 is not fixed here**, only diagnosed; a core-only install cannot be proven green until it is,
  so #10 is this d-work's true blocker and the row should go `blocked` on it if execution starts
  before it lands.
- No release is cut. No tag. No version bump.

## Falsification

| # | attack | result |
|---|--------|--------|
| R1 | "The bundle already does this — Rule-11 p7, tag `vX.Y.Z`, names the core plus every Tended craft." | **refuted as sufficient, true as far as it goes** — the bundle releases them *together*, as a manifest over separate archives; the receiver still installs each craft in #178's order. A system that pins **the core tag** — which is what "the core Release" names — gets no sysadmin at all. The bundle solves co-release, not core-inclusion. |
| R2 | "Preference, not defect: the core is fine standing alone." | **refuted, and measured** — four core Rules cite the craft by path, and a core-only install of HEAD is red in the scratch test above. The dependency is already real; only the shipping is missing. |
| R3 | "Then merge `crafts/sysadmin/` into `dyad/`." | **refuted** — it reverses #155 and collapses Rule-4's Agent Rule / Tended Rule split (the core holds Agent Rules; these are Tended). It also puts host practice inside the one craft every system must have, which is exactly what #155 extracted to avoid. Ship the tree, don't absorb it. |
| R4 | "Forcing a host craft on every system breaks craft optionality." | **survives — the real cost, conceded** — `syseng`'s README states the principle, and **#60** (backlog) names a system with no host at all. Such a system would carry a craft it never uses. The concession: an unused tree, against a core whose Rules currently dangle. A bundled craft stays separately versioned and removable, which keeps the cost to disk rather than to doctrine. |
| R5 | "Fix the coupling instead: stop core Rules citing craft paths." | **survives as the honest alternative** — arguably more correct, and it preserves optionality. But it is a large Rule-text change across four Agent Rules, and it is not what was asked. Named so the Operator can take it instead; the plan-`Y` chooses between them. |
| R6 | "Rule-11 p2 forbids a core install writing another craft's root." | **confirmed — and it is the scope** — which is why the mutation leads with the Rule amendment rather than the build. A change that quietly made `dyad install` write `crafts/sysadmin/` without amending p2 would be a Rule breach dressed as a feature. |
| R7 | "Bundling one craft turns the siblings' citations red." | **refuted by measurement** — I believed this from `distribution.md` and checked: #167's `craft_state` resolves per craft; an absent sibling is `skip`/`warn`, never `FAIL`. The stale paragraph is filed as its own finding. |
