## Intent as read

The Operator observed that the turn ran very long. The observation is taken as a measurement
request, not as a complaint to agree with: measure the turn, say where the time went, say which
mechanism should have prevented it, and propose the fence. The instrument for this already exists
(`dyad dwork trace`, play-book `dyad/playbooks/dwork-trace.md`, d-work #213) and was run before
this plan was written rather than after.

tokens, 5 commits (all ledger-only), 0 PRs, 0 suite runs.

The trace's own Limits section names the thing that matters: *"1 agent-side segment(s) of 15 min or
more (7h59m18s): a restart, a sleep or a lost turn reads as that bucket — 16:58:13 inference
7h59m18s."*

So the 37.8% is not generation. Subtracting that one segment:

**real Agent inference ≈ 35m19s** — 35 minutes of model time produced the ADR's seven revisions and
the specification. The long part of the turn was a single 7h59m18s agent-side segment beginning
16:58:13 UTC, which the trace cannot classify further: a restart, a sleep or a lost turn all read
the same. The Operator's wait (61.6%) is the other large share and is not the Agent's to reduce.

## What held

Every byte of ADR revisions 3–7 was committed to `main` at **16:01:44 UTC**, 56 minutes *before*
the lost segment began. Nothing was lost. That is `concise-mode`'s record-before-narration clause
(Rule-10 Form, Rule-3 Incidents, amendment #113) and Rule-7 property 3 doing precisely what they
were written for: an interrupted turn loses narration, never record. The design survived the
failure it was designed for, and this is stated as a confirmed property, not a consolation.

## What went wrong — the finding

`delegation: plan-and-execute` never fired. The `subagent` bucket is **0 seconds** across the whole
window, while the two largest artifacts of the stretch — plan #252 at 783 lines and plan #253 at
249 lines — were drafted by the main Agent itself. A plan file is the exact artifact the preference
covers: *"subagents draft plan files and execution branches so the main Agent stays free for the
next prompt"* (`preferences-corpus/PREFERENCES.md`), and Rule-10's concise-mode clause says it
again: *"Execution longer than a few tool calls is delegated to a fork in its own worktree … so the
reply comes at once and the Agent stays free."*

A fork would not have made the model faster. It would have bounded the main Agent's turn: the
drafting happens in the fork, the main turn ends, and a turn that ends cannot be lost. The 7h59m
segment is a harness event; **the exposure to it was a choice, and it was mine.**

Second finding, stated and not fixed here: six of #252's eight prompts arrived mid-turn, each
growing the artifact, so the turn could not end while the deliverable kept moving. Under
`concise-mode: on` a mid-turn prompt is answered in the same reply — which is correct, and which
also means one turn can grow without bound. The refinements were the best part of the ADR (the
directed-graph principle arrived as prompt 3), so this is raised as a finding rather than proposed
as a change: detect, don't dispose.

## Behavioural change, which needs no disposition

From here, an artifact that will take more than a few tool calls — a plan file of this size above
all — is drafted by a fork in its own worktree, per the preference as written. That is not a
proposal; it is the preference, and it was not followed.

## Counter (Rule-10)

The honest case against this plan: it answers "the turn went long" with a *count*, and a count
changes nothing. The preference that would have bounded the turn already existed and was ignored,
so adding a line to a report is the weakest possible response — it makes the next failure legible
rather than impossible. The strong response would bound turn size directly: end the turn when the
artifact exceeds some size, and take further refinements as their own d-works.

Reconciliation: that strong response would remove the mid-turn refinement loop that produced the
ADR's best content, and it would need a Rule-10 amendment to a clause that is six d-works old and
working. So the plan concedes the point and takes the weak fence plus the behavioural change, which
is the part that actually binds — the preference was always the mechanism; what was missing was
compliance, and compliance is not bought with code. If the Operator wants the hard bound, that is a
Rule-10 d-work and this plan is not it.
