# Plan #108 — separate true unit tests (mocked) from integration tests (real subprocess/git)

Base commit of `main`: b1e07c8. Refs #107 (the profiling that surfaced this). Falsification: inline.

## Intent as read
"Remediate unittesting through separation of concerns — unittesting use mocks unlike integration
testing." #107 found the cost, not the fix: the suite doesn't distinguish the two kinds of test at
all — everything under `dyad/tests/` runs as one flat "unittest" tree, and several tests that
verify a *pure* property pay for a real subprocess or a real git repo to check it.

## Findings — what's actually mixed together
Beyond #107's own top three (`test_package.py`'s `test_evidence_block_deterministic`,
`test_pass_order_and_lines`, `test_evidence_block_shape_and_hash` — 16.7s across three tests,
17% of that file's wall time, verifying string-shape and hash properties via full external `check`
subprocess runs), the same *shape* of mixing recurs in two more places, checked directly:
- `guards.agent.test_rows.FenceTests.setUp` (12.22s total) builds a real `git init` repo — real
  `git config` x2, `git add`, `git commit` subprocesses — before *every* test method, to exercise
  `rows.py check_range`/`check_commit`, which themselves just run `git diff`/`git show` against
  `cwd` and parse the output. The guard logic is pure text-parsing; only the fixture is real git.
- `test_craft.CraftCliTests.setUp` (part of 17.66s) builds a fresh real "receiving" scratch repo —
  `git init` plus a full core-craft `install` — before every test method, on top of each test's own
  `dyad craft ...` subprocess call(s). Here the class's own purpose *is* verifying real CLI +
  filesystem + git behavior (install refuses a modified tree, a craft's `requires:` is enforced,
  etc.) — genuinely integration, not mixed.

## Mutation — staged, Stage 1 only in this d-work
**Stage 1 (this d-work), agent zone, `dyad/tests/test_package.py` only:**
1. Extract the evidence block's hashing/shape logic in `dyad/scripts/package.py`'s `cmd_evidence()`
   into one small pure function, `evidence_sha256(lines: list[str]) -> str` (the existing
   `hashlib.sha256(chr(10).join(lines).encode()).hexdigest()` line, named and reusable) — no
   behavior change to the CLI; `cmd_evidence` calls it instead of inlining it.
2. Rewrite `test_evidence_block_deterministic` as a true unit test: call `evidence_sha256` twice
   on the same fixed, fake `lines` list and assert equality — no subprocess, no real git, no guard
   traversal. This is what "deterministic" actually claims; a pure function is deterministic by
   construction once tested once, and two full external runs proved nothing past that.
3. Rewrite `test_evidence_block_shape_and_hash`'s *hash* assertion the same way (call
   `evidence_sha256` on captured `lines[:-1]`, compare to `lines[-1]`); its *shape* assertions
   (`head=`/`tree=`/`dirty=` regexes, the `[Rule-11]`/`[guards] infra/containment` lines present)
   stay against one real run — `load_package().cmd_evidence()` called in-process (via
   `contextlib.redirect_stdout`, matching the pattern `cmd_evidence` itself already uses
   internally) rather than a subprocess, since the property under test is "does the real CLI wire
   these lines together correctly," which does need the real guard traversal, just not a second
   *process*.
4. Rewrite `test_pass_order_and_lines` to call `pkg.cmd_guards()`/`pkg.cmd_check()` in-process
   (same redirect-stdout pattern) instead of two `self.run_py(...)` subprocess calls, keeping every
   existing assertion unchanged.

Net effect: three tests keep asserting exactly what they assert now; none needs a subprocess,
and only one (the CLI-wiring half of `test_evidence_block_shape_and_hash`) still needs an
in-process real guard traversal. Estimated savings against #107's own measurement: ~16s of the
96s total (the second `check --evidence` run, the `check --guards` run, and the `check` run this
removes), with zero loss of the properties each test actually names.

**Not in this mutation, stated (Stage 2, a separate plan if the Operator wants it pursued):**
- `guards.agent.test_rows.FenceTests` and `test_craft.CraftCliTests` are not touched here. Both
  build real git repos per test; genuinely converting either to mocks means either (a) giving
  `rows.py`'s `check_range`/`check_commit` an injectable git-command runner so a test can supply
  fake diff/show output instead of a real repo, or (b) mocking `subprocess.run` globally within
  the test module and hand-writing the exact byte sequences git would have produced — the second
  risks the tests passing against a fake git that no longer matches real git's actual output shape,
  which is a worse failure mode than the current cost (a false green, not a slow green). The first
  is real code work in `rows.py` itself (a guard `dyad/rules/RULE-3-d-work.md` and Rule-2's own
  Binding rely on), warranting its own falsification and plan, not a rider on this one.
- `test_craft.CraftCliTests` is correctly integration testing already (real filesystem/git effects
  of `craft install`/`export`/`new`/`check`) — "separation of concerns" for this class means
  *labeling* it as integration and leaving it alone, not mocking away the thing it exists to
  verify. Proposed here, not done: a one-line class docstring naming it Integration and pointing at
  this plan, so a future reader doesn't mistake its cost for the same defect Stage 1 fixes. Left
  out of this mutation because it's a docs-only craft-adjacent (`dyad/tests/`, still agent zone)
  change with zero risk, but bundling it here would blur what Stage 1 actually changed; a one-line
  follow-up if the Operator wants it, not gated on Stage 2.

## Falsification
- **"Extracting `evidence_sha256` is scope creep — the ask was about tests, not `package.py`
  itself."** Survives, scoped, and is the honest tension: refuted as *disqualifying*, though.
  Without the extraction, `test_evidence_block_deterministic` can only prove determinism by
  calling `cmd_evidence()` itself, which still runs the full guard traversal every time (in-process
  removes the subprocess cost, not the traversal cost) — the extraction is what makes the *pure*
  property actually testable as a pure property, not decoration. The change is two lines, no
  existing behavior moves.
- **"In-process is not the same isolation as mocking — this is still real git, real filesystem,
  just cheaper."** Confirmed, and stated as the honest boundary: items 3 and 4 above are
  *integration* tests made faster (subprocess removed, real guard traversal kept), not converted to
  mocked unit tests — only item 2 (`evidence_sha256` itself) becomes a true, mock-free unit test,
  because it's the only one of the three whose property is actually pure. Calling items 3–4 "unit
  tests using mocks" would be the same category error #107 found in the first place, just relabeled
  rather than fixed.
- **"Mock `rows.py`'s git calls now too — Stage 2 doesn't need its own d-work."** Refuted for this
  plan: `check_range`/`check_commit` are a mechanical fence Rule-3 and Rule-2's Binding depend on;
  changing their internals to accept an injectable runner is a real code change to guard logic, not
  a test-only change, and deserves falsification on its own terms (does the injected fake still
  exercise the same code paths a real `git diff` would hit) rather than riding in on a
  measurement-driven test cleanup.
- **"Just delete the second `check --evidence` call in `test_evidence_block_deterministic` instead
  of extracting a function — same time saved, one line, no `package.py` touch."** Considered,
  refuted: that leaves the *test* asserting nothing (an empty determinism claim with one call), and
  the underlying pure property (`evidence_sha256` is a function of its `lines` argument alone)
  would still not be independently checkable — the property this test names would simply stop
  being tested at all rather than being tested cheaply.
