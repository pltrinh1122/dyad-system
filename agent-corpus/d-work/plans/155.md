## What the audit measured, restated as the thing to fix
`python3 -m unittest discover -s dyad/tests` costs **120.06 s** by hand and **39.13 s** with
`DYAD_NO_NESTED_TESTS=1`, the variable `check_rule_12` sets for every suite it spawns
(`dyad/scripts/package.py`, the `env={**os.environ, "DYAD_NO_NESTED_TESTS": "1"}` argument). The
3x is the nested scratch installs running their own full suites. Across the session: **134 hand-run
suites, 3,894 s, required by no Rule**, and eight of the ten longest commands of the whole session
are that one command.

The habit is not "runs tests"; it is "reaches for `python3 -m unittest` because it is the shortest
thing to type". Rule-13 property 1 is exactly this case: the second occurrence of an inference task
yields a code path, and this is the hundred-and-thirty-fourth.

## Mutation (what a plan-`Y` authorizes)
One agent-zone PR, branch `agent/155-cheap-test-path`:
1. `dyad/scripts/package.py` — a new `check --tests [<target>]` verb and its `cmd_tests`:
   - no target: every root `test_suites()` returns, each as `unittest discover -s <root> -q`,
     printing the same `[Rule-12] <root>: Ran N tests OK` line `check_rule_12` prints;
   - a target that is a directory: that root only;
   - a target that is anything else: passed to `unittest` as a dotted module, class or method;
   - **always** with `DYAD_NO_NESTED_TESTS=1` in the child environment, which is the whole point;
   - exit non-zero if any root fails, so it is usable in a chain.
   The verb is added to the entrypoint's usage text so it is discoverable where the others are.
2. `dyad/tests/test_package.py` — its mechanical check (Rule-12 property 1): that `check --tests`
   with a dotted target runs that target and nothing else, that it sets the flag in the child
   environment, and that a failing target makes it exit non-zero.
No Rule, vocabulary, preference, play-book or craft change. No `VERSION` bump: `dyad/VERSION` is
0.9.0 and no `dyad-operator-v0.9.0` tag exists, so `bundle.check_drift` skips; `BUNDLE.md` already
reads 0.9.0, so no infra PR and no release. Re-verified in the completion evidence.

The completion reply must carry a **timing** of the new verb against both existing paths on this
tree, or the d-work has not delivered its own premise.

Outside the mutation, and stated rather than hidden: I will also write the habit into this
machine's memory cache, which is per-machine and not corpus (Rule-2, Not ratification), so a later
session reaches for the verb at its first test run rather than at its hundredth.

## Revision — 2026-09-24 (Operator's `N`: the local hooks, and tests at commit time)

### The question answered first
**Yes, there is a local CI check, and no, it does not run the tests.** Two blocking hooks:
- `dyad/hooks/pre-commit` → `containment.py staged`. One check: the commit touches one zone.
- `dyad/hooks/pre-push` → `package.py check --guards`. **61 checks, 1.75 s, no test suite** — the
  invariant pass and every guard over `origin/main..HEAD`, and `check_rule_12` is not in it.

So the suite runs in exactly two places today: when the Agent types it, and in GitHub CI *after* a
merge to `main`. The local gate never tests. That is the real gap the Operator's question exposes,
and it is larger than the habit #155 was opened to fix: the 134 hand-runs were the Agent standing
in for a gate that does not exist.

### Evaluation: unittest at commit time
Commits on `main`, 2026-09-21 to 24, both sessions — 133 non-merge:

| class | count | can a test outcome change? |
|-------|------:|----------------------------|
| ledger-only (`agent-corpus/d-work/**`) | 86 | no |
| other, no `.py` (audits, records, Rule text, play-books) | 40 | **yes — proven** |
| touches `.py` | 7 | yes |

The middle row is the finding that kills the obvious filter. In #137 a *markdown* file — a second
core run-book — broke the core suite, because a test pinned the run-book count. A `.py` filter would
have let it through. Any filter must therefore be "anything outside the ledger prefix", which is 47
of 133 commits, not 7.

Cost, at the measured 40 s per suite run:

| placement | runs | cost | what it buys |
|-----------|-----:|-----:|--------------|
| every commit | 133 | 89 min | nothing over the filtered form |
| commit, filtered to non-ledger | 47 | 31 min | the break is caught at the commit that caused it |
| push, filtered to non-ledger | ~47 pushes carry code | ~31 min | the break is caught before anything is shared |
| today | 134 hand-runs + 79 evidence + 80 bare `check` | **~176 min** | the same coverage, paid by hand |

Either gated placement costs about a fifth of what the session actually spent. The Operator's
instinct is right and the saving is real.

### Why push, not commit — the one place this plan disagrees
Two reasons, both from this session's own record.
1. **A blocking test at commit time manufactures the `--no-verify` pressure.** A commit is how work
   is recorded, including work in progress; Rule-3 requires a clerical commit at every disposition.
   A red suite that refuses a commit leaves the Agent with nothing to do but bypass the hook — which
   is exactly the incident of 2026-09-22 (#116–#125, ten commits made with `--no-verify` against a
   working hook), and Rule-1 forbids bypassing a hook that runs and fails. Push-time has an honest
   answer instead: fix it, then push.
2. **A commit is private; a push is shared.** Rule-14 property 3 already makes `check --guards` the
   gate "before anything leaves this machine", and Rule-2's Binding rests on that path. Tests belong
   at the same boundary as the guards they sit beside, not one step earlier.

The saving is identical either way (the same 47 ranges), so the choice costs nothing and avoids a
failure mode the log already carries.

### Revised mutation (what a plan-`Y` authorizes)
One agent-zone PR, branch `agent/155-cheap-test-path`:
1. `dyad/scripts/package.py` — `cmd_guards` gains the suite, **gated**: when `origin/main..HEAD`
   touches any path outside `<instance>/d-work/`, run `check_rule_12`; otherwise print one skipped
   line naming why. A ledger-only push stays at 1.75 s; a push carrying anything else pays ~40 s and
   the Agent stops hand-running the suite because the gate does it.
2. `dyad/scripts/package.py` — `check --tests [<target>]` as in the original mutation, for the case

3. `dyad/tests/test_package.py` — the mechanical checks for both: that a ledger-only range skips the
   suite and prints its line, that a range touching a non-ledger path runs it, that `--tests` with a
   dotted target runs that target only and sets the flag, and that a failing target exits non-zero.
Unchanged from the original: no Rule, vocabulary, preference, play-book or craft change; no
`VERSION` bump (no `dyad-operator-v0.9.0` tag exists, so `check_drift` skips); the completion reply
must carry timings of a ledger-only push, a code-carrying push and `--tests`, or the premise is
unproven.
