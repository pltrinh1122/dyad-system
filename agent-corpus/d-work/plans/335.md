## Pin convention (stated in the README itself)
The live tree is ahead of every release: `BUNDLE.md` names 0.14.0 and `dyad/VERSION` 0.11.0 while the
newest tags on `main` are `v0.12.1`, `dyad-operator-v0.10.1`, `sysarch-v0.3.0`, `syseng-v0.4.0` and
`sysadmin-v0.2.1`, all at `74180d5`; `countersign` 0.3.0 and `disclosure` 0.1.0 carry no tag (held, #232).
A tag alone therefore cannot pin what the README describes. The convention, written into the README as
one paragraph:
- one **pin line** names the `main` commit the README was written against (the base commit of this PR's
  final rebase) and the tree's `VERSION`s at that commit (bundle, core, each Tended craft);
- every footnote names the cited **path** and that path's **blob sha** at the pin (`git rev-parse
  <pin>:<path>`), so `git show <blob>` returns the exact text cited whatever `main` does later;
- where a **released tag** holds the same blob (`git rev-parse <tag>:<path>` equal), the footnote names
  the tag too — the "pinned version" the Operator asked for, given wherever a version exists; where no tag
  holds it, the footnote says *unreleased at the pin*;
- a row id (`#N`) or a PR number in a footnote resolves through the ledger (`agent-corpus/d-work/rows/N.md`
  at the pin) and the hosting respectively — the hosting reference is a `world` kind (Rule-20) and is
  stated as such.
Re-pinning is a later README d-work; the pin line makes the drift visible rather than silent (#332 F1).
