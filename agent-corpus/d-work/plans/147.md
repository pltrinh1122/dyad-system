# Plan #147 — the fit of each architecture across explicit, implicit and automatic modes

Base commit of `main`: aaac389. Refs: 145, 146. The Operator's `N` on the batch Done for #145 and
#146 asked for this synthesis. #146's survivor is the frame, restated here, so it can be read
alone.

## Intent as read
One synthesis, not a verdict per repo. For each of the three modes, and for the edges between them:
what each architecture provides, how well it fits, and what the combined architecture would need.

**The modes (#146's survivor):**
- **explicit**: an agent processes a *human prompt*; the human originates and disposes.
- **implicit**: an agent processes a *system signal*, under authority the human gave *in advance*
  (standing disposition); exceptions return to the human.
- **automatic**: a *non-inferring executor* processes a system signal; the human designed it
  beforehand and triages its exceptions.

The **edges**: *codify* (explicit or implicit → automatic: judgment written once into a
deterministic artifact), *delegate* (explicit → implicit: a standing disposition), and *escalate*
(automatic or implicit → explicit: the unexpected returned to a human).

## 3. Synthesis
1. **The two repos are strong in opposite corners.** dyad-system is strong in **explicit** mode,
   built and enforced, and in **automatic-for-its-own-repo** (guards as pre-authorized,
   zero-token checks). dsys is designed for **automatic** workflow execution and for the
   **escalate** and **delegate** edges, but is built only as far as a fixture-tested executor.
2. **Implicit mode is the gap in both.** Neither can yet let an agent act on a system signal under
   pre-given authority. dsys has the design (`set_standing`, three keys, coverage). dyad-system has
   the governance machinery a server would run on (ledger, guards, presence, run-books) but not the
   authority form (#145).
3. **Every edge that saves tokens runs toward automatic.** Explicit and implicit both spend
   inference; automatic spends none. So the architecture that fits the #143 client is the one
   whose *codify* edge is strongest and whose *escalate* edge is total. That is dsys's design,
   with dyad-system's enforcement discipline applied to it (block before the fact rather than
   judge after).
4. **A combined architecture, by mode:**
   - *explicit* ← dyad-system as is: d-work loop, provenance, blocking guards.
   - *implicit* ← new: a standing disposition (dsys's `set_standing` semantics) enforced by a
     dyad-system guard (scope checked mechanically, never by the agent), plus a per-signal token
     cap (#143 meter).
   - *automatic* ← dsys's executor, flows, totality invariant and disclosures, with production
     tools and an installed run-book path.
   - *escalate* ← dsys disclosures entering dyad-system as Intake rows (#145 S1), with a closure-bar
     guard (I-13 analogue).
   - *codify* ← dyad-system's Rule-13 trigger ("second occurrence") feeding dsys's authoring
     path, so repeated explicit work becomes automatic rather than merely scripted.
5. **Vocabulary is the first integration cost.** #142 §2: run-book is *inverted* between the repos,
   and so are event, role and the `dyad` command. A combined design must fix one meaning per term
   before any code joins the two.

## 4. Falsification of the synthesis
| # | attack | result |
|---|---|---|
| 1 | dyad-system's guards are not "automatic mode": they process the agent's own commits, not external signals. | **Survives, scoped.** They meet the mode's definition (no inference, a signal in, pre-given authority), but only for signals the dyad itself emits. Hence "strong but narrow" |
| 2 | dsys's explicit mode is as strong as dyad-system's, because its own decisions are made that way daily. | **Refuted as "as strong".** Its DecisionRecords are written in chat, and the model's validators are not run on them at decision time (#142 A8). dyad-system's loop is fenced by guards |
| 3 | Codify is really an implicit → automatic edge, not explicit → automatic. | **Refuted as exclusive.** Both repos codify from explicit work (Rule-13's recurrence; the playbook before automation). Implicit → automatic would also be valid once implicit exists |
| 4 | The combined architecture is two systems bolted together. | **Survives as a risk.** It stays one architecture only if one ledger and one authority model span all three modes. Otherwise a disposition in one cannot be cited in the other, violating both repos' own citation-integrity rules (I-11; Rule-20). The design choice of which ledger is canonical is the Operator's |
