## Intent as read
The Operator asks for the architecture of the d-work framework formalized in two parts: (a) its play-book
and its entity records; (b) d-work as a finite-state machine that carries state and completes a
countersigned work session. Read as: write the one place that states the framework whole. Today it is
spread across Rule-3 (states, forms, ledger), Rule-7 (the record), Rule-15 (phases, the plan file),
Rule-16 (the store, the transition table, presence), Rule-2 (what a `Y` binds), two play-books (trace,
disposition digest), `dyadlib` and the CLI help — and the one thing none of them holds is the machine's
*input alphabet*: `dyadlib.TRANSITIONS` is a successor relation (which state may follow which), not a
machine (which Operator act or Agent act moves a row along each edge, and which record that move writes).
"Entity records" is read as the records a d-work is made of — row, plan file, provenance record, presence
file, trace — and the records it references (incident row, falsification record, change-log row, PR).
"Completes a countersigned work session" is read as the countersign craft's explicit-mode lifecycle
(`crafts/countersign/rules/interaction.md` §4): Initiation → countersign proposal → countersignature →
execute → countersign report + proposal (done) → countersignature; a d-work is that lifecycle's dyad-system
realization, and reaches `done` through exactly two countersignatures when nothing is refused.
Not read as: changing any state, transition, form or guard semantics; a new store; a change to the
countersign projector (craft zone, its own d-work). The counter-reading — "entity records" as the event
records *of* the play-book entity — is stated under F7; an amend corrects the reading if it was wrong.

## The machine, as the play-book will state it (draft δ; the file is the deliverable)
| from | to | input | kind | writes | countersign |
|------|----|-------|------|--------|-------------|
| — | open | an Operator prompt; or the `Y` that admits an intake; or the mandate's plan-`Y` for an accreted row | prompt · disposition | row (`open`), record entry 1 (`prompt`, or `disposition` noted `mandate #m`), presence | initiation; or countersignature `yes`, basis `mandate` |
| — | backlog | an Operator disposition opening it (`Y backlog`) | disposition | row, record entry 1 (`disposition`) | countersignature `yes` |
| open | planned | the plan-`Y` (`Y plan`) | disposition | `disposed`, record entry, presence touch; the plan file already exists and is now bound | countersignature `yes`, basis `per-act` (the proposal is the plan file) |
| open | blocked | a deferral disposition naming the blocking d-work | disposition | `disposed`, record entry, `refs` | countersignature |
| open | done | the Done-`Y` (`Y done`) | disposition | `disposed`, record entry, trace; then the merges it ratifies | countersignature `yes` (the report precedes it) |
| planned | open | re-planning: `main` moved past a touched file (Rule-15 phase 2), or the Operator's amend of the plan | clerical · disposition | a plan revision; an `N` entry when there is one | none, or `amend` |
| planned | blocked | as open → blocked | disposition | as above | countersignature |
| planned | done | the Done-`Y` | disposition | as open → done | countersignature `yes` |
| blocked | open | the blocking d-work reaching `done` | clerical | the state line only | none |
| backlog | open | an Operator prompt for it | prompt | record `prompt` entry, state | initiation |
| backlog | archived | the retirement `Y` (`Y archive (sweep …)`) | disposition | `disposed`, record entry | countersignature `yes` over the named set |
| done | archived | the retirement `Y` | disposition | as above | countersignature `yes` |
A `no` (bare `N`) moves nothing and writes an entry; `amend` (`N` with text) writes an entry and a prompt
entry, revises the plan in place, and moves nothing (Rule-3 Answer grammar). Twelve edges, two births —
exactly `TRANSITIONS` and `NEW_STATES`; the test holds the two tables equal.
