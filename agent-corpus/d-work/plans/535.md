## Intent as read
The Operator, on the cos-as-a-mode destination (#531, roadmap P1–P5): "i've been using the older version of dyad-system
where `cos` is a seat versus a mode. while in that seat, the primary responsibility was orchestration and protecting
operator's attention. if `cos` is a mode, the orchestration needs to be continuous and seamless during seat-hops."
So the requirement for P1 is sharpened: a hop of the mode from one session to another must lose none of the
orchestration in flight, and must cost the Operator no re-explanation.

   #514 after season 1.

Only the rows, plans, provenance and presence are in the corpus today. Rule-3 calls the pending queue "conversational,
not a corpus file".

## Falsification
| # | attack | result |
|---|---|---|
| 1 | The rows and plans already hold the orchestration | **refuted by the inventory**: a row says `planned`. It says nothing of who holds the work, what it waits on, the next act, or the question outstanding. Items 1–6 are absent from every store |
| 2 | Write it all into each row file | **refuted**: rows are append-only and fenced (Rule-16), and this state changes many times a day and is overwritten, not appended. It belongs in a **board store** of its own: one file per open row, `<instance>/d-work/board/<id>.md`, rewritten freely, ledger-only commits. History is git's |
| 3 | A seat-hop mid-turn loses whatever the old holder had not yet written | **survives, with a discipline**: *write-ahead*. The cos writes the board entry before it sends the message or asks the question it records. So a hop at any point loses at most the reply being composed, never a dispatched act. The board is the cos's first write of every turn that changes orchestration |
| 4 | The Operator's attention: a new holder re-asks or re-explains | **survives, procedure**: each open question is stored verbatim (its last line and the evidence summary) with when it was asked. A new holder re-presents it unchanged, or reports it pending, and never re-derives it. The hop is invisible to the Operator except for one line: "cos resumed in <session>" |
| 5 | Seats address the old session id after a hop | **conceded to P2**: until the inbox (#536) lands, the new holder announces itself to every seat named on the board, and the board records each seat's session id, so the announcement is mechanical |
| 6 | Two holders write the board at once | **conceded to P3**: the lease (#537) arbitrates. Until then the board carries a `holder:` line, and `dyad board` warns when the last writer is not this session (Rule-16's writer pattern, #350) |
| 7 | It costs a ledger commit per orchestration change | **survives, priced**: ledger-only commits run no suite (Rule-12 p2). Today's turns already make 1–3 ledger commits each, and the board adds about one |
| 8 | Rule-3's pending queue is "not a corpus file" | **confirmed, so amended**: Rule-3 Batch disposition says the queue *is* recorded, in the board store. Counsel, with a falsification amendment |

## Survivor: the board store, written ahead, with a hop drill
- **Store.** `<instance>/d-work/board/<id>.md`, one per row not terminal that has orchestration in flight. `key: value`
  lines:
  - `holder` (the cos session);
  - `owner` (the seat doing the work, and its session id);
  - `waiting-on` (`operator` | `seat <name>` | `external <ref>`, e.g. `external run 41331223332`);
  - `next` (the next act, one line);
  - `since`;
  - `question` (verbatim, when the Operator owes one);
  - `promised` (follow-ups named to the Operator).
  A `board/_cos.md` holds the cross-row items: the pending queue counts, the seat table, the last question asked.
- **CLI.**
  - `dyad board set <id> key=value…` writes it, as a ledger-only land.
  - `dyad board` renders the Operator's board from rows plus board files: one line per program, the waits, the oldest.
    This also absorbs #304's surface.
  - `dyad board resume` prints, for a new holder, everything to resume: the questions owed verbatim, the dispatched work,
    the gates, the seats to announce to.
- **Discipline.** Write-ahead (attack 3). A cos turn that changes orchestration writes the board before acting.
- **Exit test, the hop drill.** Mid-flight, with a dispatched seat and an open question, a fresh session takes the mode
  (`DYAD_SESSION=program-…` and `dyad board resume`) and continues: it re-presents the open question verbatim, receives
  the seat's next report, and closes the row, with no lost item and no question to the Operator about state. The drill's
  transcript is summarized as an event.
