# Plan #231 — release readiness for the next release, by scanning every active branch

Base commit of `main`: 15948ad86e77f5bd835cc4621ebb7a7a959fde13

## Intent as read
Decide whether the next release can be cut now. The scan of every active branch is the method the
Operator named, not the whole question: a release is ready when nothing is waiting to be merged,
every component's version is the one its tree deserves, the order the tags must be cut in is known,
and the checks that verify what a release publishes are green. Report the verdict and what blocks it.

## Method (read-only, performed before this plan was written)
1. `git fetch --all --prune --tags`, then fast-forward `main` (it was 240 commits behind).
2. For all 160 remote branches: `git rev-list --count origin/main..<branch>`, and the three-dot diff
   of each branch that is ahead; `gh pr list --state open`; the one local branch.
3. Every `VERSION` against `git tag -l '<component>-v*'`; `BUNDLE.md` rows against the tree.
4. Every craft's `MANIFEST.md` `requires:` floor against the tags that exist.
5. `dyad check` (the Rule-11 runner, all guards) locally; `gh run list --branch main` for the hosted
   corroboration, and the failing job's step list.
6. For each component, the commits touching its root since its `VERSION` was last set.

The hold #198 placed on the release (PRs #223, #224) is discharged: both merged.

### 2. Every component is unreleased, and the core's number understates its tree

`dyad/VERSION` became 0.10.1 on 2026-09-25. Since then 21 non-merge commits touched `dyad/`: a new

invariant protocol, a new rule and changed guard behaviour. No drift guard fires for either, because
neither version is tagged — the number is simply not yet the one the tree deserves.

### 3. The order the tags must be cut in is forced, and the bundle's row set is a decision
Three crafts declare `requires: dyad-operator>=0.10.0` (sysadmin, sysarch, syseng) and disclosure
`>=0.9.1`. The floor resolves against tags, and the newest core tag is 0.9.0, so today every craft's
install is refused for an unmet `requires:` (Rule-11 property 2) — `dyad check` prints one warn per
craft saying exactly that. The core tag must therefore exist, at ≥0.10.0, before any craft tag, and
the bundle last.

`BUNDLE.md` holds four rows and omits countersign and disclosure. The bundle guard permits that only
while a craft is unreleased (#156). So releasing either of those two is not a detail of the release:
it forces an infra-zone `BUNDLE.md` edit plus a bundle version bump, in a craft-zone/infra-zone order
that Rule-1 cannot satisfy in one PR — the #170 class, already a backlog row.

### 4. Blocker: the only mechanical verification of what a release publishes is red
`rule-11 package` has failed on every push to `main` since 2026-09-25 — most recently at `0699b69`,
2026-10-06. The failing step is, verbatim: *install core, then export and install the sysadmin craft,
into a scratch repo; run the guards there; install both again (idempotent)*. The `check` and `build`
steps of the same job pass. That step is Rule-11 property 5's only mechanical check of the install
path, and an install of that path is precisely what a release publishes. Row #201 holds the
diagnosis — the core install writes a bundled craft's tree but no `crafts/REGISTRY.md` row, so the
subsequent `craft install` of the same craft is refused as locally authored — and row #228 is already
open to repair it.

Locally the runner is green: `dyad check` exits 0 with no `fail` line, 130 package files, warns only
(the craft floors above, the Rule-4 Agent-token warnings, the invariant follow-ups, two stale
`naming_rules.txt` allows, `pydantic` declared with no token). Local green and hosted red do not
disagree: the red step installs into a scratch repo, which the local runner never does.

## Verdict
**Not ready.** One blocker, two decisions, one correction owed:
- **Blocker** — `rule-11 package`'s install step (#201, repair open as #228). Releasing while it is
  red publishes an install path no check has verified for twelve days, and the known defect is in the
  core-then-craft upgrade every downstream system would take.
- **Correction** — the core's `VERSION` should be 0.11.0 before its tag is cut, and syseng's 0.5.0;
  each is a craft-zone (or agent-zone, for the core) PR of its own.
- **Decision** — whether countersign and disclosure join this bundle. If yes, the #170 ordering
  problem has to be solved first; if no, they stay out by #156's clause and the bundle releases four
  components.
- **Decision** — six tags or eight, and the bundle version. Unchanged from #198's answer except that
  the version numbers move.
