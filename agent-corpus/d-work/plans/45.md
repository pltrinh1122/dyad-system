# Plan #45 — stores.md's id-allocation bullet describes a mechanism that no longer matches the code

Base commit of `main`: cfc1d55. Refs #32 (the d-work that found the gap and spun this out), #42.
Falsification: inline below (Rule-9).

## Intent as read
`crafts/sysarch/rules/stores.md` states how ids are allocated and how a collision is caught. #32
proved that statement wrong and fixed the *code* (`check_id_collisions`, the allocator's fetch
warning) without correcting the *rule*, spinning the correction out as this row on its Done-`Y`.
Rule-6's Master record principle in its craft form: on divergence the text is the bug.

## The divergence, quoted

`crafts/sysarch/rules/stores.md:21-23` today:

> **Ids are allocated, never chosen.** `dyad dwork new` allocates `max(id on fetched origin/main,
> local) + 1`; **two sessions collide only on the same id, which the push rejects.** No session
> hand-edits a file.

Two claims in that middle clause, both false as written:

| claim | what the code does now |
|---|---|
| "the push rejects" it | True only of two **direct pushes to `main`** — git's own non-fast-forward. On the **PR path** the collision surfaces as an add/add conflict at merge, or silently as an overwrite if the branch was reset onto `main` first (#32 F2). |
| collision is the only failure mode | The allocator can also *degrade*: if `git fetch origin main` fails, `max()` runs over local ids alone. Since #32 F3 that prints a warning (`package.cmd_dwork`); before it, silence. |

And the mechanism the bullet does not mention at all: `dyad/guards/agent/rows.py`
`check_id_collisions` — on a branch, `check_transaction` checks that a row id this range adds or
modifies does not already exist at `base` under a **different title**, the signature of two sessions
racing the allocator. It runs before the push, which is the whole point: the fence proper only ever
runs on `main`, by which time the collision has already landed.

This session is the worked example twice over: #32's own INCIDENTS rows record `#24`→`#25`→`#30`
renumbered by hand, and the peer `web-sysarch-adh151` and this session collided on the name
`web-sysarch` on top of it.

## Mutation — one PR, craft zone (sysarch)
`crafts/sysarch/rules/stores.md`, the one bullet, rewritten to state the mechanism as it is: the
allocator's inputs and its warning when the fetch fails; that `main`'s push rejection covers only
the direct-push case; that the branch case is `rows.py check_id_collisions`, by name, running
before the push; and — the sentence #32 was careful about — that none of this makes a collision
*impossible*, because two sessions holding unpushed ids cannot see each other, which only a shared
allocator (the LAN git server, #24) changes.
No `VERSION` bump — a craft's version is its release d-work's (#22's lesson, #46's practice).
No code change: #32 already shipped it, and a single line of code here would make this a second
d-work wearing this one's number.

## Falsification
- **"A rule-text correction with no code is decoration."** Refuted, and this is the one case where
  the answer is sharp rather than conceded: `stores.md` is the **store pattern** every instance of
  the pattern is built against (Rule-16 delegates to it by name). A future store implemented from
  this text would reproduce the bug #32 just fixed, because the text still says the push catches it.
  The text *is* the artifact here, exactly as `guards.md` is for the guard contract.
- **"Then it belongs in Rule-16, not the craft rule."** Refuted: Rule-16's Boundaries hand the
  store pattern — "ids allocated `max(origin, local)+1`" among them — to `stores.md` explicitly
  (#159, #160). Rule-16 keeps the canonical path and the transition table. Correcting the allocation
  bullet in the core Rule would take the craft's concern back, the gap Rule-5 names.
- **"#32 should have done this; re-opening its work under a new number splits the record."**
  Refuted: #32 is `done`, and Rule-16 is explicit that a done d-work is never reopened — a new row
  refs it. `refs: #32` is that link, and #32's Done-`Y` created this row deliberately rather than
  leaving the correction unrecorded. The split is the mechanism working.
- **"Describe `check_id_collisions` and the text goes stale the next time the guard changes."**
  Survives, scoped — the honest cost of naming a mechanism in prose. Mitigated only by naming it
  *by symbol* (`rows.py check_id_collisions`), so a grep for the symbol finds the rule that
  describes it; not mitigated by anything mechanical, and no guard checks rule prose against code.
  This is the same exposure every craft rule carries and is not this d-work's to close.
- **Overlap (Rule-16) — a real one, stated as the Rule requires.** The peer session
  `web-sysarch-adh151` shares this session's **`root`** (`/home/user/dyad-system`) and its presence
  file lists `files: crafts/sysarch/rules/stores.md …` — *the exact file this plan touches* — under
  `rows: 32`, the very d-work that spun this one out. Judgment, which stays inference: #32 is
  `done` and merged (PR #26), so that `files` set is the residue of finished work rather than a live
  claim, and its `seen` is 17:25Z against `dev-main`'s 19:46Z. Acting anyway, because the row was
  created *by* that d-work's completion for this session to pick up. The same-root warning
  (`dyad session touch`) has stood all session and is unchanged: a raw git command from either
  session can still clobber the other's uncommitted state, which is #32's own unfixed residue, not
  this plan's.
