# Plan #462 — should a service's owner keep its run-book? (answer, falsified)

Base commit of main: ed5af7c

## Intent as read
Claim to falsify: the charters should let the seat that owns a service keep that service's run-book (distribute would
own `released`'s), instead of operate's fence holding every run-book under `<host>/runbooks/`.

## Mutation
None proposed: the claim is refuted as a charter rule; the survivor is the split #461 revision 2 already applies.
Files touched: none (this plan file only).

## Falsification
| # | attack | result |
|---|---|---|
| 1 | Owner-keeps lets the service and its run-book change together | **refuted**: Rule-1 puts the workflow (infra) and the run-book (workstation) in different zones, so they are two PRs whoever writes them; Rule-19's "revised in the same PR" is a same-d-work rule in practice, which the split already meets |
| 2 | The builder knows the service best, so its run-book is truer | **survives, scoped**: the knowledge is the commands, the health criterion and the request format — the spec — which the owner supplies in its own PR; transcription into the run-book form is operate's, and operate's run-book escalation ("a command that does not work as written") is the check that the spec was right |
| 3 | Owner-keeps ties a run-book's life to the builder's seat | **confirmed against the claim**: ledgerd (#336) was built by cab-8 and went stale with nobody operating it; operate is the standing seat that reads every run-book's events and runs the reconcile (#431) |
| 4 | Splitting `<host>/runbooks/` among owners shares ownership of one directory | **confirmed against the claim**: the charters' fences are paths, and orthogonality (Rule-5's sense, applied to charters) forbids shared ownership; a per-file carve-out in operate's directory is exactly that |
| 5 | Operate's health reading needs one form across services | **survives either way**: the `sysadmin/runbooks` guard checks the form whoever writes it, so this neither supports nor refutes |
| 6 | `released` runs on GitHub Actions, not on the host, so it may not be a Rule-19 server instance at all | **survives, scoped**: Rule-19's target is a service on the host; `released` is a run-book by analogy (its request store and events live under `<host>/runbooks/`), which keeps it in operate's directory either way |

## Survivor
Keep the charters as they are: **the owner of a service specifies, operate writes.** The service's owner states the
commands, the health criterion and any request/config format in its own PR; operate writes the run-book and owns its
location in a paired PR of the same d-work. No MANDATES change is proposed: the charter already reads this way, as the
Operator's correction to #461 found.
