Three things, in the Operator's order:

   is to ensure that operator's attention is scaled in the way that Operator chooses." It is a
   standing instruction: every reply of this session is judged by how much Operator attention it

The attention is not mostly spent *opening* accreted rows. It is spent reading a board that only grows.

- And `dyadlib.TRANSITIONS` is `{'backlog': ['open']}`: **a `backlog` row cannot be retired without being

Cheapening the inflow without opening a drain makes this worse, not better. The drain is in the mutation.

## Mutation this plan-`Y` authorizes (revision 5)

Three changes, in the order of what they are worth. The vocabulary is `crafts/countersign/`'s, adopted
rather than coined (Rule-13 property 1), and the Agent vocabulary references the craft's terms by craft
name as it already does for `sysarch` and `sysadmin`, never redefining them (Rule-6, Master record).

**(1) The drain — the largest single reduction, and it is not about accretion at all.**
`backlog → archived` added to `dyadlib.TRANSITIONS` and to Rule-16's Store sentence in the same commit
(`test_dyadlib_rows.py` already couples them), plus a **retirement form**: `Y/N: archive #a, #b, … #k?`,
one question over k rows the Agent proposes and the Operator disposes, which Rule-3's `archived` bullet
already describes ("by an Operator disposition naming the row(s)") and only the table forbade. And
`dyad dwork retire <id>…` to execute it. This is what 75 stalled rows, a 5.4% drain and zero uses of
`archived` in 280 rows cost today.

**(2) Implicit mode — the Operator's meta-disposition, in the craft's terms, with no code change.**
A row the Agent accretes while executing another, **whose existence the authorized plan describes by a
rule** ("one child per failure mode", "a row per surviving fence"), is born `open` in `implicit` mode:
`disposed: <date> Y plan (mandate #<id>)`, and its record's entry 1 is the mandate's own Operator words
verbatim, noted `mandate #<id>, <the mandate's date>`. It may carry a PR at once (the plan gate passes,
verified). Its Done rides the mandate's Done-`Y`. **Operator cost: zero.** Three fences keep it inside
Rule-2:
- **Scope.** Only a row the plan's **mandate scope** names — a stated rule and a stated ceiling — may be
  accreted. A plan with no mandate scope accretes nothing. Never accretable, whatever a plan says: a
  destructive host action (Rule-8 keeps its own counter-prompt), a release (Rule-11: it publishes to the
  world), a **Rule-3 Intake** (its words are another Operator's, Rule-7 property 4), a preference change,
  or any mutation outside the plan — which Rule-3 already calls a new plan.
- **The escalate edge.** An accreted row whose work departs from the mandate's scope returns to
  `explicit` mode: the Agent reports it and asks, rather than inheriting. Row **#249** is why — the
  Operator has used an accreted row's plan-`Y` as a veto, and this preserves it.
- **The report.** The completion evidence lists **every row accreted under the mandate** — id, mode,
  what it holds, what it cost — before the Done question, which also names them. The Operator verifies
  the set it got, not the set it was promised. An omission is a breach of Rule-3, as every other
  omission already is.

**(3) The three refactors `interaction.md` §7 already owes**, which make (2) data rather than prose:
a **`mode` field on rows** (`explicit` | `implicit`, default `explicit`; `dyadlib.FIELDS`, `rows.py`,
the fence, and its migration — this is also the answer to revision 4's "carry-forward has no home");
a **mandate record** so a standing authorization is parsed data and not preference prose (`ledger-pr-merge`
is the existing one); and **`amend` named in Rule-3's answer grammar** — `N` with text as a linked
re-entry, which is exactly the disposition this revision answers and which the Rules today leave inside
"any other response".

## What revisions 1–4 got wrong, corrected here

Seven claims this plan asserted and this revision's measurement refuted. They are listed because a plan
that has been answered `N` owes the Operator its own errors, not a smoother argument.

1. **"A standing disposition cannot be recorded as a `disposed` entry, so carry-forward can only ever be
   the absence of a new question."** The premise is true — an entry with no matching `disposition` entry
   fails Rule-7 property 5 — and the conclusion does not follow: the matching entry may be the Operator's
   own *earlier* words, copied, which Rule-3's Batch disposition already blesses across many records. This
   is the single inference revision 4 drew without checking the store, and it is what ruled out the design.
2. **"#96 and #97 are precedent for a row born under an existing plan-`Y`."** Half wrong, and the half
   that fails is the one the plan leaned on. Their `disposed: 2026-09-18 Y plan (named in plan 94.md,
   deferred)` does prove the **entry form** is writable and passes `rows.py` and property 5. But both are
   `backlog`, so `prs.py:44` refuses them on state *before* it ever reaches the `Y plan` test, and neither
   has a plan file. They have never passed the plan gate. The only real precedent for a row *working*
   under inherited authorization is #162–#165 under #199, and it is a better one.
3. **"`blocked` and `archived` have never once been used."** `archived`: correct, zero in 280 rows.
   `blocked`: wrong — used once, row **#185** (`N plan, blocked on #190`), and returned to `open` when
   #190 was done. The deferral route is therefore exercised and reversible, which prices the alternative
   for #259's 23 children honestly: 23 deferrals, not an impossibility.
4. **"Exactly two rows have ever used the `parent #N` form."** Four parents have: #259 (23 children),
   #116 (9), `parent-46` (4) and `parent-49` (2), plus one bare `parent`. Six of those child links use a
   hyphen form `references.py` cannot resolve (`hash_ids` needs the `#`), so if any mechanism is to key on
   the parent link, those six must be normalized first — `refs` is mutable where id and title are not.
5. **"105 rows opened in this chat, 67 accreted."** 139–142 rows, 82 accreted (band 69–83). The method was
   at fault, not the arithmetic: it could only see a `dwork new` whose printed id it parsed, and 9 rows
   (#102–#113) were never created by `dwork new` at all.
6. **"506 disposition entries, ≈409 distinct Operator questions."** 507 entries. And the question figure
   is unstable because the unit was never fixed: 431 if only `(batch …)` sets collapse, ≈409 if shared-act
   dispositions collapse too. The figure this revision uses instead is derived rather than estimated — walk
   every commit that touched the provenance store and group the entries it added by (commit, kind, verbatim
   text): **370 distinct Operator dispositions and 193 distinct prompts, 563 acts, from 708 entries.**
7. **"Accreted rows are where the cheap saving is."** Refuted, and it is the finding that reshaped this
   revision: accreted rows that were worked cost **more** — mean 2.65 disposed entries against 2.15 for

   the four that used the mandate shape. The large unpaid cost is the board's missing exit, which no
   earlier revision looked at.
