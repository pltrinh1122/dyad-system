Per ISO week W38–W42 the count is 0, 0, 0, 2, 1. The first 359 dispositions of a thirty-day ledger
hold none; two of the three are one row's; the question the Operator declined this turn would have
been that row's third. 184 of 189 merges rode a Done-`Y` — 97.4%. So this is a new and accelerating
mechanism caught at occurrence three, not a standing tax.

**Its generator is not the merge rule.** The sentence that compels the question is preference prose —
`preferences-corpus/PREFERENCES.md`, the `with-done` bullet: "A PR whose d-work is *not* yet done
still needs its own merge `Y`." Rule-2's Ratification events require only that *some* Operator
disposition ratify a merge, and name two shapes: its own counter-prompt, or the Done-`Y` of a
completion counter-prompt that names the PR. A d-work whose PRs all wait for its Done-`Y` therefore
costs two dispositions with no Rule changed at all.

**What forces a PR out of that shape is a d-work that cannot reach its Done question.** Rule-3's
Ledger clause: "The parent's counter-prompt is asked only when every child is `done` or `blocked`."
Exactly two rows have ever used the `parent #N` form:

| parent | state | children | children's states |
|---|---|---|---|
| #116 | done | 9 | 9 done |
| #259 | planned | 23 | 23 backlog |

`backlog` is neither `done` nor `blocked`, and `dyadlib.TRANSITIONS` (`dyadlib.py:448`) lets a
`backlog` row go only to `open` — `backlog → archived` is refused in so many words, which corrects
revision 3 of plan #259, where "archiving the ones whose exits are already recorded as unfenceable"
was offered to the Operator as an option it is not. `blocked → done` is refused too: a `blocked` row
returns only to `open`. **And in 278 rows `blocked` and `archived` have never once been used** — the
escape Rule-3's parent gate names has never been exercised by this instance.

So #259's Done question is mechanically unaskable, its four merged PRs had to be ratified some other
way, and PR #371 has nowhere to land. The merge counter-prompt is the symptom; **a parent gated by
`backlog` children is the mechanism**, with exactly one live instance — the row whose PR the Operator
was asked about. The cost of clearing it by hand: **47 dispositions** strictly one-per-question (23
prompts to open, 23 deferrals, one Done-`Y`), 70 if each child is worked to done, 93 by the archive
route — against 3 if the two batch forms are stretched to cover row-opening, which Rule-3 does not
today say they do.

## What this plan does not do

- **It does not make the plan-`Y` a merge ratification**, and that is now a refutation rather than a
  preference. The design was drafted in full as `merge-disposition: with-plan` — the plan-`Y`
  standing as the merge disposition of every PR whose whole `base...head` diff lies inside a fenced
  `plan-scope` block, checked in `prs.py` and printed into the evidence block inside its own
  sha256 — and it falsified itself on this store, four ways:
  - **The scope cannot be read from what the plans say.** A prototype of the fence, run over #259's
    own `files touched` line as written, matched **750 of 1177 tracked paths — 64% of the repo**.
    And 123 of 187 stored plan files carry no `files touched` line at all; the other 64 carry prose.
  - **The Agent could widen the scope after the `Y`.** The plan file lives under
    `agent-corpus/d-work/plans/`, so an edit to it is a ledger-only commit that needs no PR and no
    review.
  - **A fence that reads the live preference file is self-ratification by a one-line branch edit.**
  - **A standing disposition cannot be recorded as a `disposed` entry.** An entry with no matching
    `disposition` entry in the provenance record fails Rule-7 property 5's count check. So
    "carry-forward" can only ever be expressed as *the absence of a new question*, never as a
    synthesized record of one — which is exactly the shape PR-1 and PR-2 take.
  The one honest concession it also carries stands against it: merging on a plan-`Y` costs the
  sentence Rule-3's completion clause exists for — "asked on the output as it stands in the PR(s),
  before merge, so `main` never carries unverified output". Named here as the path not taken, with
  the measurement that closed it.
- **It does not build the fence that makes a standing disposition machine-readable.** Two standing
  dispositions are in force today (`merge-disposition: with-done`, `ledger-pr-merge: agent`) and
  **zero are stored as parsed data**: `disposed` is free text, and the one mechanically gated
  counter-prompt in the whole system is the plan gate's `"Y plan" in row.disposed`. The fence is the
  2026-10-08 audit's candidate 2, parsing `disposed` into kinded entries; this plan names it for its
  own `backlog` row in the opening batch rather than building it, because a Rule's text must say what
  the parser is for before the parser exists.
- **It does not touch Rule-2**, and removes no ratification event.
- **It does not shorten the evidence block.** Rule-2's Binding requires it "pasted verbatim in the
  completion reply"; at about 217 lines × 195 Done dispositions it is the largest single thing the
  Operator has ever been handed, and moving it to the PR body with its `evidence-sha256` in the reply
  is the largest single reduction available. A Rule-2 and Rule-14 property 3 change: surfaced, its own
  d-work.
- **It does not re-land PR #355** or work the 23 modes. Each needs a row the Operator opens, and both
  are candidates for the first opening batch this plan's own form would carry: one row to re-land
  #245's banking (its PR is refused by the plan gate against its own `done` row, and resolving the
  conflict would change the head and void the Done-`Y` under Rule-2's Binding), and the 23 mode rows
  prompted open or left where they are.
