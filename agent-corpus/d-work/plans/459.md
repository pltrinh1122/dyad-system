# Plan #459 — `dwork --land` takes several verbs in one commit; `dwork land` drops the caller's leftover copy

Base commit of main: 128cfdc

## Intent as read
The Operator's `Y` to "open rows for C … and A (engineer: multi-verb `--land`), each to plan?" opens candidate A of
plan #454. Today each `--land` record pays one push gate, so N closes cost N gates (the #443 live cycle: three
closes, three gates, where one hand commit had paid one). A batch of records should pay one gate. The same row
fixes the second #443 finding: after `dwork land <path>`, the caller's own copy of the file stays modified even
though it is identical to `main`, and that blocks the fast-forward.

## Evidence (main at 128cfdc)
- `dyad/scripts/land.py` `land()` (`:249-280`) runs exactly one `build(wt)` per call: one verb, one commit, one
  `push()` (`:232-234`). `main()` (`:312-352`) accepts one `new|state` verb or one `land <path>…`.
- `fast_forward()` (`:237-246`) skips any checkout that `status --porcelain` shows dirty. After `land <path>` the
  copied path is still modified in the caller, so the fast-forward is always skipped (#443 live cycle, presence
  file).
- The fence's Done order: `rows.done_order_problems` (`dyad/guards/agent/rows.py:128-141`) refuses a commit that
  both records a merge-naming `Y done` for a row and sets that row `done`. It judges per row and per commit, so
  one commit may hold row A's record and row B's close, never both for one row. `landing_problems`
  (`:143-…`) requires a close's named heads to be reachable from the base or the commit.
- `already_landed()` (`land.py:174-214`) judges one verb's entry against `origin/main`.

## Mutation (agent zone, one PR citing d-work #459; no mandate scope, accretes nothing)
1. **`dyad dwork batch <file>|- --land [--mirror <branch>]`** in `land.py`, dispatched from `cmd_dwork` like
   `--land`.
   - The file (or stdin) holds one `dwork` argv per line, shell-quoted (`shlex.split`). Blank lines and `#` lines
     are skipped. Each line is `new …`, `state …` or `land <path>…`; no other verb is allowed.
   - Words travel by `--prompt-file`/`--said-file` exactly as a single verb takes them. `-m`, `--land` and
     `--mirror` are refused on a line; the batch generates one subject and takes one `--mirror`.
   - **One worktree pass:** fetch, prepare, then run every line in order through the worktree's own runner.
   - **Lines already on `origin/main` are skipped**, each named on one `skipped (already landed): …` line, using
     the per-line `already_landed()` that exists today. A batch whose every line is already landed is refused, as
     a single `--land` is.
   - **One commit, one push.**
   - **Atomic:** a line the worktree's runner refuses stops the batch, and nothing is committed.
   - **On a moved `main`:** the whole batch is rebuilt from its inputs (TRIES = 3), the same rule as today. A
     `new` line re-allocates its id on a rebuild, so a later line may not name an id the same batch creates; the
     batch says so in its usage text.
   - **Subject:** `ledger: batch #a state done, #b Y done …, presence …`, cut to one line, citing no `d-work #`.
2. **The Done order is kept before running.** The batch parses every line first and refuses, naming both lines,
   when one row id has both a merge-naming `-d 'Y done (… merges …)'` and a `done` state. That is
   `done_order_problems`' condition, said where it costs a line instead of a push. The fence is unchanged and
   still judges the commit at the gate.
   - So a ratified set travels as the three acts in two batches: **record batch → merges → close batch**. That is
     2 gates for any number of rows, against 2N today.
   - A row whose `Y done` names no merge may record and close in one line, as today.
3. **The caller-copy fix** in `land`/`batch` `land` lines. After a successful push, if the caller's checkout is on
   `main` and its only changes are the landed paths, byte-identical to the landed blobs, those paths are restored
   from `HEAD` (`git checkout -- <paths>`) and the checkout is fast-forwarded.
   - Nothing is lost, because the content is the landed content. Any other change, or a different byte, leaves
     the checkout as it is, with the existing one-line notice.
4. **Tests** in `dyad/tests/test_land.py`, on the existing scratch bare-origin fixture:
   - a three-line batch, two closes and one presence `land`, is one commit and one hook run (the scratch hook's
     log counts runs);
   - a line the runner refuses lands nothing;
   - a line already landed is skipped and the rest lands;
   - a batch of only landed lines is refused;
   - one row with both a merge-naming `Y done` and `done` in one batch is refused before any push, with the fence
     message;
   - a racing commit rebuilds the batch;
   - `land` leaves the caller's checkout clean and fast-forwarded when its copy is identical, and untouched when
     it differs;
   - a line naming `-m`, `--land` or another verb is refused.
5. **Help and README:** the `dwork` help text in `package.py`'s docstring gains the batch form, and
   `dyad/README.md`'s `land.py` row says so. No new test module, so the levels seed is unchanged. No Rule text.
   `dyad/VERSION` stays 0.12.1, untagged: this rides it.

## Falsification (Rule-9)
| # | attack | result |
|---|--------|--------|
| 1 | A multi-id shorthand (`dwork state 447 448 443 done --mandate 443 --land`) is simpler than a batch file. | **refuted, scoped.** It covers only lines with identical flags. The cos's real batches mix a record (`-d … --said-file …`) per row with different words and refs, closes, and a presence touch. A file of argv lines covers all of them with one grammar, the verb's own. A shorthand can be added later over the same engine. |
| 2 | One commit holding several disposition events breaks Rule-7 property 3 ("appended in the clerical commit of the event it records"). | **refuted.** Each event's entry is still written by its own verb, in a commit that records it. A batch commit is the clerical commit of each event in it, as a hand-made ledger commit closing three rows always was (the #436/#437 closes at 751c627). The provenance transaction check judges each row's added entries against its added `disposed` entries, per row, whatever else the commit holds. |
| 3 | Batching lets a merge-naming record and its close ride one commit, the exact breach #202 fenced. | **confirmed as a risk, closed by mutation 2.** The batch refuses the pair before running, and the fence still refuses it at the gate. The three-act order becomes two batches with the merges between them. |
| 4 | Skipping already-landed lines hides a partial failure. | **survives, scoped.** A skip happens only when the entry is already on `origin/main` with the same words: the re-run after an ambiguous push (#443 attack 11). Every skipped line is printed by name, so a retry is idempotent per line and never records twice. |
| 5 | A `new` line's id cannot be named by a later line in the batch, so a "new then plan it" batch is impossible. | **confirmed, accepted.** The id is allocated in the worktree and may change on a rebuild. Stated in the usage. Opening a row and recording on it stay two calls, which is the rare case. |
| 6 | Restoring the caller's file is a write to the caller's checkout, which `land.py` promised never to make. | **survives, narrowed.** The promise was "never reset", against #427's shared-checkout loss. This restores only paths whose bytes equal the landed blob, on `main`, with no other change, so no content can be lost. Any other state is left untouched, as today. |
| 7 | One gate per batch loses the per-record gate's isolation: one bad record blocks the rest. | **survives, accepted.** The batch is atomic by design. The refused line is named, and the rest re-run as a batch without it. The cos chooses batch size. |
