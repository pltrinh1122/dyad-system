### Incident I5, in revision 2's own execution (Rule-3; row owed to M2 with I1–I4)

The refresh above warned, twice, and the first of the two **emptied the `files` field**:

```
warning: ds-cabinet-term-2.md was last written by a different, still-live process
(writer 3c74357b7815) under this same session id 'ds-cabinet-term-2' … recording only this
process's rows and files, not unioning the other's
```

There is no second session. `sessions._WRITER` is `uuid4().hex[:12]` computed **at import**
(`dyad/guards/agent/sessions.py`), and this harness runs every `dyad` invocation as a fresh
process, so *every* touch after the first inside the 6 h stale window presents a new `writer`
against a live `seen`. The guard reads that as #32's two-processes-one-seat collision and takes the
replacing branch — `row_set`/`file_set` from this call's flags only, no union with `prev` — so a
`touch -r 348` with no `-f` wrote `files:` empty, discarding the five paths the previous call had
recorded. Restored by re-running with the full `-f` list; the store is correct as it stands.

*Mechanism:* the F1 fence identifies a *process*, and for a seat whose every command is a new
process the normal case is indistinguishable from the collision it guards against. For such a seat
the fence is inverted: it warns on every touch and silently narrows the file unless the caller
re-passes everything. *Consequence here:* one field emptied and restored within seconds, and the
warning is noise that a reader of the board would reasonably take for a real collision.
*Not fixed here* (detect, don't dispose): the fix is a code change in the agent zone — identify the
writer by something that survives a process (the seat's holder id, which `holder()` already reads)
or union when the colliding writer's `holder` equals this one's. Named as a candidate row, not
opened; mandate scope is none.
