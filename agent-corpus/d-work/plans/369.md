## Intent as read
Make M4 — a tree of operator-agent pairs, each a cos with a cos-board, authority granted by
content-scoped mandates, every pair sharing the same ledgers — the organization every system runs
under unless its Operator says otherwise. Deliver (1) the preference, (2) an Operating Guide written
for Operators, not for the Agent, (3) a mechanism that names a seat's presence file and the Claude
Code session the Operator sees, and (4) a reasoned answer to which craft owns the preference.

## Evaluation: which craft (falsified first, Rule-9)
There is no `cos` craft today: `crafts/` holds countersign, disclosure, sysadmin, sysarch, syseng; the
cos's standing rules are backlog #306. So the question is whether to create one.
- Claim A, "core only": every system has at least one cos (the one seat beside its Operator), the
  presence store is Rule-16's (core), and a preference is read by a Rule. Attack: M4's content — a
  tree, boards, charters — is cos practice, which Rule-11 property 1 would put in a Tended craft, not
  the core. Result: survives for the *preference and the naming mechanism* (they bind Rule-16's store,
  which is core), refuted for the *Guide's organizational content* if that content ever varies per
  system.
- Claim B, "cos craft only": the organization is practice the Operator tends, like sysadmin's.
  Attack: a craft needs a second system to install it before it is a craft rather than a directory
  (craft-instantiation play-book, D5 lifecycle); and the authority half of M4 is already countersign's
  (`mandate`, `implicit mode`, adopted in #290), so a cos craft would re-define terms Rule-6 forbids
  defining twice. Result: refuted today; survives as the destination once #306 and #303–#305 give the
  cos a craft's worth of rules, vocabulary and guards.
- Survivor, "both, split by what binds": the **preference key and the seat-naming mechanism** are
  core (`dyad-operator`): they bind Rule-16's presence store and `dyad session touch`, which every
  system runs. The **Operating Guide** is a core play-book (`dyad/playbooks/organization.md`), read by
  Rule-3 the way `d-work.md` and `craft-instantiation.md` are, because the one-cos case is every
  system's default and the Guide must exist on a core-only install. The **charter content** (which
  functions, which fences) is instance: the bands table in `preferences-corpus/`, Operator-written.
  Nothing is written under `crafts/cos/` in this d-work; the plan names #306 as where a cos craft
  would be instantiated, and the craft-instantiation criteria are not run here because no craft is
  proposed. The authority vocabulary stays countersign's, cited not re-defined.

## Mutation proposed
Three PRs, one zone each (Rule-1); the preferences PR is the Operator's to dispose as a value change
(Rule-2, Not ratification) and is opened last so the Rule text it is read by exists first.

**PR-A (agent zone, core craft):**
1. `dyad/playbooks/organization.md` — the Operating Guide. Sections: the shapes (`flat`: one cos,
   one board, cabinets by row, today's default; `m4`: the tree of #368 revision 6); the precondition
   (shared ledgers; the one-repo default and the three multi-repo ways); seats and boards (every cos
   has a cos-board; a cabinet is on its cos's board and keeps none); charters (the band form: domain,
   fence, ceiling, escalations, revocation, the non-accretable list by reference to Rule-2); naming
   (below); what the Operator does at each moment (open a pair, grant a mandate, re-cut one, retire a
   seat, read the board); what the Operator never does through a cos (dispose another pair's row).
   Written to Operators; cites Rules by name, defines no term (Rule-6).
2. Naming mechanism, `dyad/guards/agent/sessions.py` + `dyad/scripts/session.py` (the CLI):
   - the **seat name form** `<role>[-<pair>]-<hp>` where `role` ∈ {`cos`, `cab`} (extensible by the
     Guide, never by code), `pair` a short function or number, `hp` the first 8 hex of the holder's
     `CLAUDE_CODE_SESSION_ID`; `cos-1-59cec502`, `cab-dwork-23d654aa`, `cos-ops-3283bd77`. Under
     `organization: flat` only `cos-<hp>` and `cab-<n>-<hp>` are checked; under `m4` the pair token is
     required on a cabinet and optional on the leader cos.
   - `dyad session name [--role cos|cab] [--pair <token>]` prints the seat name and the **Claude Code
     session title** to set, `<seat>: <kernel> (<system>) - <topic>`, from the environment (#294's
     `host_line`, `holder`), so the Operator pastes one line; never sets the title (the hosting is The
     World, Rule-14).
   - `touch()` warns, never fails (Rule-16 Presence: advisory), when the seat name does not match the
     form for the configured `organization`, and when the holder prefix in the name differs from the
     recorded `holder`; a bare `unnamed-*` file warns as today.
   - the presence guard's state check stays well-formedness only; the form check is a warning line.
   - tests in `dyad/tests/guards/agent/test_sessions.py` and `dyad/tests/test_session.py` (the mapping
     the syseng guard requires).
3. Rule-16 Presence: one sentence naming the seat-name form and the `organization` preference it is
   read under; Rule-3 Ledger: one sentence citing the organization play-book beside the d-work
   play-book. Vocabulary (Rule-6): `cos-board` (the board a cos projects over its scope),
   `member-cos`, `seat name`; `organization` is a preference key, referenced not defined.
   Falsification: `dyad/falsification/rules/rule-16-concurrent-sessions.md` amendment #369 and
   `agent-corpus/falsification/organization-preference.md` (the three claims above, this d-work's
   attacks); Rule-5 pairwise statement in the record.
4. `dyad/README.md` one line pointing at the Guide.

**PR-B (preferences zone):** `organization` key, value `m4`, allowed `flat | m4`, read by Rule-3
(play-book), Rule-16 (seat-name form); and an empty `mandates` table shape (seat, domain, fence,
ceiling, escalations, revocation) with the six charters of #368 revision 3/6 as its first rows,
each marked proposed until the seat is opened. Opened after PR-A merges; the Operator disposes.

**PR-C (agent zone, ledger-only, clerical):** nothing beyond this d-work's own rows and plan.

Not proposed: a `crafts/cos/` tree; any change to `prs.py`, `rows.py`, the fence; any rename of a
live seat's presence file (that is each seat's own row, as #351/#357/#358/#361/#363/#364 were);
any retirement of a session (yours, in the hosting).
