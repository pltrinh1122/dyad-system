# Plan #30 — evaluate the schema flow and pydantic vs zod for the syseng craft

Base commit of `main`: e56fffa. Refs #23 (open, same session), syseng craft.
Falsification: inline below (Rule-9); the record proposed as the mutation carries it in full.

## Intent as read
The Operator proposes a four-step flow for improving the `syseng` craft — (1) the d-work entity
mapped to a schema, hand-authored by the Agent; (2) the schema verified by code; (3a) the schema
mechanically transformed to a surface; (3b) the schema injected into a downstream prompt — and asks
whether the schema definition language should be pydantic or zod. The ask is **evaluate**, not
implement. So: does the flow hold, where does it already exist, where does it claim more than it
delivers, and which definition language survives this system's own constraints.

## Finding 1 — steps 1, 2 and 3a already exist; they are not called "schema"
`crafts/sysarch/rules/guards.md` property 3 names `FIELDS` "the schema constant". For the d-work
entity the pieces are all present in stdlib:
- **model** — `dyadlib.Row`, a frozen dataclass; `FIELDS`, `STATES`, `NEW_STATES`, `TRANSITIONS`.
- **verification** — `dyadlib.parse_row_file` (missing field fails), `rows.py check_package`
  (every row parses), `check_transaction` (the append-only fence and the transition table),
  and the `INVARIANTS` protocol (`row-fields-match-dataclass`, `transitions-keys-are-states`,
  `done-is-terminal`) run by the runner before any check (`crafts/syseng/rules/invariants.md`).
- **surface** — `rows.py describe()` emits `(name, type, allowed, required, example, source)` per
  field plus store, parser and transition prose; the entities projector consumes it, and
  `projection.md` property 1 already forbids a projector from hand-drawing an entity.
The proposal is therefore better framed as *promote the existing guard contract to a first-class
schema artifact* than as *adopt a schema library*. Reframed that way, steps 1–3a are a naming and
serialization change, not an architecture change — which is what makes the library question much
smaller than it looks.

## Finding 2 — step 2 conflates three checks, and the third is not mechanizable
"Schema verified by code" can mean:
  (i) the schema is well-formed — `dyadlib.CONTRACT` / `contract_problem`, exists;
  (ii) instances conform to the schema — `rows.py check_package`, exists;
  (iii) the schema is faithful to the Rule prose that owns the entity — **does not exist and
       cannot**. `guards.md`, Inference stated, already says it: *"Whether a guard's `FIELDS`
       matches its Rule's prose ... is inference."*
No schema library closes (iii). Rule-6's master record is the Rule text; a schema is its
restatement, and a restatement cannot verify its original. If the flow is adopted, (iii) is named
as inference in the rule that owns it, or the flow silently claims self-verification it does not have.

## Finding 3 — step 3b is the novel part and carries a no-self-ratify problem
Step 1 has the Agent author the schema; step 3b has the schema constrain the Agent's later output.
Author and subject are the same party with no disposal between — the Agent ratifies its own model of
the entity. Rule-2 does not catch it today because a schema is not a verdict, a merge or a direct push.
The fix is in-system and cheap: **the schema is corpus** — agent zone, in the core craft, changed only
by a d-work PR the Operator disposes, exactly as a Rule is. Then 3b injects ratified corpus and the
pattern is the memory cache's ("corpus wins"), not self-ratification. The failure mode to forbid
explicitly: generating the injected schema at prompt time from uncommitted working-tree code.

## Finding 4 — the schema must govern validation and projection, never the storage format
Rule-16's store is `key: value` lines, one file per row, append-only, *because* that makes two
concurrent sessions almost never merge; Rule-7's bodies are fenced Markdown *because* a prompt
containing a pipe or a backtick must not reshape its file. A schema library makes JSON storage the
obvious next step, and JSON re-serializes the whole object on every edit — line-granular merge, the
append-only fence and the fenced-body defence all go with it. This is the real risk of adopting a
schema library here, and it is a risk of the flow, not of either candidate.

## Finding 5 — zod is disqualified by the kernel, before merit
Rule-14 property 2's kernel is a CLI inferencing agent, Python 3.12 pinned, and Git. There is no
Node row in `dyad/infrastructure/INFRASTRUCTURE.md` at all. Rule-14 property 3 requires every guard
to run on the kernel alone (`dyad/hooks/pre-push` → `package.py check --guards`), and that same path
prints the evidence block Rule-2's Binding reads. Zod in this system means either the guards become
Node code — the kernel gains a runtime — or the schema is authored in TypeScript and re-parsed in
Python, which is two definitions of one model and exactly what Rule-6's master record and
`projection.md` property 1 forbid. `crafts/syseng/rules/imports.md` property 3 ("kernel ecosystem
first: Python packages before tools outside the kernel") settles it at step 0. Zod is a good library
losing on ecosystem, not on quality; the only case for it is a browser surface needing client-side
validation, and even there the TS types are *generated from* the Python model, never authored beside it.

## Finding 6 — pydantic passes the preferences and still costs the evidence path
Pydantic passes `import-licenses` (MIT) and `import-support` (released well within 12 months,
on PyPI, the kernel ecosystem). What it buys over the present dataclass: declarative validators,
coercion, error objects, and `model_json_schema()` — a *standard* serialization, which is precisely
what 3a and 3b want and what `describe()` (an HTML entity card) does not give.
What it costs: pydantic v2's core is `pydantic-core`, a compiled Rust wheel. Adopting it puts a
third-party binary wheel on the kernel-only path — so `dyad check --evidence`, the block the Operator
re-runs on the exact head to verify a merge, would stop reproducing on a bare kernel. Today that path
is stdlib only. Rule-14 property 3 says the package "must not depend on them to enforce a Rule"; a
compiled third-party import in the evidence path is that dependency in a new shape.
The gain is one method (`model_json_schema`); the price is the reproducibility of the merge evidence.

## The path (Rule-10)
**Neither library. Author the missing seam in stdlib: a schema emitter over the contract that exists.**
`describe()` already holds every field of a JSON Schema except the serialization; the emitter is a
small pure function in `dyadlib` turning a guard's `FIELDS` + `describe()` into JSON Schema — no
manifest row, no kernel change, no new zone, and it serves 3a and 3b from one declaration. If the
Operator later wants pydantic's validator ergonomics, that emitter is the seam to swap behind, and
the decision stays reversible.

**The strongest counter:** hand-rolling a schema emitter is Rule-13 property 1 inverted — the whole
point of "import over author" is not to write what a maintained library gives you, and pydantic is
the fit candidate `imports.md` property 1 says to take.
**Reconciliation:** `imports.md` property 1 conditions import on the candidate *meeting the
criteria*, and the criteria are not only license and support — Rule-14 property 3 is a constraint on
what may enter the evidence path, and pydantic fails it as long as that path must run on a bare
kernel. The counter is conceded in scope: if the Operator disposes that the kernel-only path may
require a pip install (a real and defensible choice — it is one `pip install pydantic` in a hook),
pydantic becomes the right answer and this plan is the wrong one. That disposition is the
Operator's, and it is the question this evaluation actually surfaces.
