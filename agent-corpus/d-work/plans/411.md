# Plan #411 — "only the program seat spins up sessions; members delegate to subagents": evaluation

## Intent as read
Evaluate, as pros and cons, a simplification rule: no seat other than `program` creates a session;
a seat that needs concurrency delegates to subagents. And whether it should be an invariant.

## Evidence from this instance
- The only member-spawned sessions so far: distribute's two cabinets under #345 (client, asg), created
  because each port runs in a *receiving repo's* checkout. They cost a three-hop relay (cabinet →
  distribute → program → Operator), could not write a presence file here, could not push this ledger
  (distribute wrote their registration rows for them), and one could not attach this repo at all.
- Rule-3 Scope already says a subagent's actions are the Agent's and that subagents never write a row,
  ask or answer a counter-prompt, push, open a PR or merge. `delegation: plan-and-execute` already has a
  fork draft in its own worktree while the main Agent stays free.
- A session can attach a second repo to itself (add_repo); the receiving checkouts a cabinet was made
  for are reachable from the member's own session.

## Pros
1. **One writer per function.** Every disposition-bound act of a function (row, push, PR, question)
   leaves one session; nothing a subagent does needs a presence file, a seat name or a relay hop.
2. **The board stays the charter.** Live seats = program + the members (≤ 7 lines); attendance and the
   M3/M4/hybrid mode read over exactly those; the `<topic>` slot and the cabinet form go unused, so
   #409's G2 (cabinets have no presence file here) disappears instead of being fixed.
3. **Two hops, not three.** A member's question reaches the Operator via program only; the relay
   fault of #407 has fewer places to recur.
4. **Credentials and scope stay with seats program opened.** No session exists whose repo scope the
   leader did not set at creation; the asg attach failure is not repeatable.
5. **Cheaper.** A subagent ends with the turn and leaves no stale presence file; thirteen `cab-*`
   files are the cost of the other way.

## Cons
1. **Long-lived parallel work is lost.** A subagent lives one turn and keeps no context across
   turns; a cabinet ran for days on one receiving repo. Work that spans turns re-briefs each time.
2. **Another system's Agent.** In a receiving repo the cabinet acted as *that system's* Agent
   (its ledger, its provenance, its Operator's Y by Intake). Under the rule the member's main session
   writes three systems' ledgers; the seat form of those stores and the "relayed via" note must say so.
3. **Serialization at the member.** Every disposition-bound act of N concurrent subagents queues at
   one main session; throughput of questions is bounded by it. (That is already the design: the
   main Agent is the one party the Operator disposes to.)
4. **Not an invariant that a guard can check.** The corpus holds no record of who created a session;
   presence files say holder, never spawner. Mechanically only one fence exists: drop `<topic>` from
   the seat form, so any cabinet-shaped name fails the seat guard. The rest is Guide conduct, inference.
5. **Program's charter says it accretes nothing.** Spawning a member's cabinet on request is a leader
   act with no row of its own; under this rule program would do so never, which is the simpler reading,
   but a member that truly needs a second long-lived session has no path but asking the Operator.

## Recommendation (Rule-10: path, counter, reconciliation)
Path: adopt it as conduct, not a Rule invariant — one sentence in the Operating Guide ("program opens
seats; a member opens none and forks subagents in worktrees for concurrency; a receiving repo is attached
to the member's own session") and the mechanical half: remove the `<topic>` group from
`crafts/cos/guards/seats_rules.txt` `form:` so a cabinet name fails the seat guard (a craft-zone PR,
cos VERSION bump; `naming.md` revised; the record amended). Counter: Con 1 — a receiving-repo port that
spans days loses its context each turn. Reconciliation: the plan file and the receiving ledger are the
context (Rule-15: execution resumes from the plan file in any session); what a cabinet kept in chat was
never corpus. Con 2 is answered by the "relayed via" note already in Rule-7 property 4.
