## Intent as read (independently re-derived from the current code, root cause verified)
`dyad/guards/infra/manifest.py`'s `check_manifest()` loads token->component mappings from exactly
one file, `dyad/guards/infra/manifest_rules.txt` (`load_rules(pkg / "guards" / "infra" /
"manifest_rules.txt")`, core-only). `craft_infra_rows()` already lets a craft contribute
*component rows* via its own `infrastructure_contrib.md` (Rule-11 property 2, #101's survivor) —
but nothing analogous exists for the *token map*: a craft's own files are scanned (`scan()`,
`craft_python_dirs()`) and their tokens must still resolve through the core-only `rules` dict.
Three concrete failure mechanisms follow, verified by reading `manifest.py` directly (lines cited
against this plan's base commit):

1. **A craft's own `guards/README.md` (or any non-`.py` file under a scanned craft dir) is swept
   as a shell script.** `scan()`'s file loop (`manifest.py:213-223`) dispatches every file that
   isn't `.py` to `shell_words(text)` — with no check for `.sh` or a shebang first. A markdown
   file's ordinary prose is not shell syntax, but any word `shell_words` extracts that isn't in
   `SHELL_SKIP` becomes an "invoked token", and with no manifest row it FAILs. Verified: this is
   latent in the core only because `dyad/guards/*/`, `dyad/scripts/`, `dyad/hooks/` currently hold
   only `.py` files, `.txt` (excluded) and two hook scripts (correctly shell); nothing stops a
   craft's `guards/` from holding a README, which every other craft convention (`vocabulary/
   CRAFT.md`, `rules/*.md`, `falsification/`) treats as normal.
2. **A craft's own `.sh` entrypoint invoking a tool the core manifest has no reason to know about**
   fails even after the craft adds an `infrastructure_contrib.md` row for it, because the row only
   declares the *component exists* — the *token* that names it in an invocation is still resolved
   solely against the core's `manifest_rules.txt`, which a craft cannot extend. This is the
   asymmetry `infrastructure_contrib.md` did not carry all the way through: rows are
   craft-contributable, the token map that maps a scan result to a row is not.
3. **`craft_python_dirs()` (`manifest.py:148-155`) scans a craft's `guards/, tests/, scripts/,
   projectors/` but not `server/`** — a craft-file location this repo's own `crafts/syseng/rules/
   invariants.md` already names as expected (`crafts/*/server/*.py`, its own `exempt:` pattern,
   confirmed live: `warn [guards] syseng/invariants ... exempt crafts/*/server/*.py matches no
   file here (a craft not installed); not checked`). `python_imports()`'s `internal` set is built
   only from the scanned dirs, so a test file's `import <server-module>` (a legitimate sibling
   import of the craft's own `server/` package) is invisible to `internal` and misclassified as an
   undeclared third-party import. The same class of gap PR2 already fixed once for `projectors/`
   (this session, d-work #100) — a third recurrence of "a new craft-file location isn't in the
   scanned-dirs tuple", after the `projectors/` gap itself.

Root cause (1 and 2 share it; 3 is narrower and independent): `infrastructure_contrib.md` gives a
craft an extension point for manifest *rows*; no equivalent exists for manifest *token rules*, and
separately, `scan()`'s file-type dispatch assumes every non-`.py` file under a scanned directory is
a shell script, an assumption only the core's own current file set happens to satisfy.

## Mutation
Two PRs, one zone each (Rule-1: the referent — Rule-14's own manifest.py and falsification record
— before the referrer — the craft rule's paraphrase — the same order `dyad/falsification/rules/
rule-14-system-infrastructure.md`'s own residue note already established for this exact file):

**Agent zone** (`dyad/guards/infra/manifest.py` is agent zone; first PR):
- **`manifest_rules_contrib.txt` mechanism** (mirrors `infrastructure_contrib.md` exactly, same
  extensibility pattern, #101): a craft ships `crafts/<craft>/manifest_rules_contrib.txt` (same
  `component: token token ...` grammar `parse_rules` already reads); a new `craft_infra_rules()`
  merges each installed craft's own file into `rules` in `check_manifest()`, keyed the same way
  `craft_infra_rows()` merges rows — a token a craft's own rules already map is never forced
  through the core file.
- **`scan()`'s file-type dispatch**: skip a file outright unless it is `.py`, has a shell shebang,
  or ends `.sh` — replacing the blanket `else: shell_words(text)` on every non-`.py` file. A `.md`,
  `.json`, or other data file under a scanned craft dir is no longer misread as shell text.
- **`craft_python_dirs()`**: add `c / "server"` to the scanned-dirs tuple, matching
  `crafts/syseng/rules/invariants.md`'s own already-anticipated craft-file location.
- New amendment in `dyad/falsification/rules/rule-14-system-infrastructure.md`.

**Craft zone** (second PR, after the first merges): `crafts/sysarch/rules/manifest.md` property 2
gains the craft-contribution sentence, alongside `infrastructure_contrib.md`'s existing one; craft
`VERSION` bump (the drift guard, #91) and a bundle-row follow-on, same pattern as #92/#103/#104.
