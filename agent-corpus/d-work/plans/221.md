## What the reference actually is (verified by hand, not from a delegate)
`build/half1` at `cdc5b9a`, 400 tracked files (the default branch, `397e6c8`/192 files, has no bus).

- `tax-prep/taxprep/bus.py`, 688 lines; 67 tests in `tax-prep/tests/test_bus.py` (37) and
  `test_bus_cli.py` (30); CLI `taxprep bus publish|listen|topics|tune|whoami` in `taxprep/cli.py`.
- **Two-repo topology.** The store is a *separate* repo, `github.com/pltrinh1122/dsys-store`;
  messages are one JSON file per message at `<store>/bus/<topic>/<ts>-<msg_id>.json`.
  `tax-prep/bus/README.md`: "Broadcast messages do NOT accrete here."
- **Envelope:** `{id, ts, from, topic, type, correlation_id, payload}`.
- **`publish()` writes a file; it does not commit and does not push.** `bus.py` shells out to git
  exactly once, `git pull --ff-only` in `poll_once`. The broadcast is a separate step, and the repo
  *does* automate it: `tax-prep/scripts/push-and-broadcast.sh` (160 lines) pushes the code branch,
  publishes via the bus CLI, then commits and pushes the store checkout (lines 108-155), verifying
  each remote head with `git ls-remote`. It is **Operator-run**: the GitHub device flow needs a
  human to open the link in an external browser per push (header line 30). `COLLABORATION.md:125`
  — "Pushing to origin is the Operator's separate explicit call (single-use device flow)." So even
  there, broadcasting is not autonomous; the Operator is at the push. (Revision 2 corrects this
  bullet — see the incident below.)
- **Delivery:** a per-session cursor in a local, never-committed file
  (`~/.config/taxprep/bus_cursor.json`, `{"sessions": {sid: {topic: last_msg_id}}}`). No ack, no
  retention, no delete. An unknown cursor reads everything (catch-up). A failed
  `git pull --ff-only` is a warning in the result, not an error — offline reads local.
  `exclude_from` tunes a session out of its own echo.
- **Hard PII guard** on the serialized payload (SSN/EIN, bare 9-digit runs, masked SSN, long digit
  runs, currency). Payloads are shapes only: ids, counts, enums, status strings.
- Motivation, `tax-prep/COLLABORATION.md:74-104`: "The Architect and Workstation sessions no longer
  relay through Peter." The human is not removed — he becomes one publisher of three
  (`tax-prep.review` → `{decision: "ratified", subject}`).

Two further designs on the same branch, both `specified-only` in `components.json` and neither
implemented: `doc/session-sync-spec.md` (a multi-writer hash-chained replication protocol over a
blind blob store, "approved for spec 2026-09-19; not implemented"; `dsys session` is a one-line
refusing stub) and `doc/dialog-protocol-spec.md` (a file-based request/reply mailbox,
"exploration … NOT approved for implementation", which names "another dsys installation" as a
legitimate peer). Neither has a topic, a subscriber or a broker. Both quotes verified in the files.

Against them stands an explicit architectural refusal, `doc/glossary.md:312-322`:
"**no supervisors, only checkers** … coordination and assurance come from checkable artifacts and
gates, never from a watching or guiding entity." And `doc/cli-interface-spec.md:276-280`: "There is
no node addressing" — so there is nothing to address a message *to*. The bus is a broadcast of
observations into a medium, and the refusal of a coordinating entity is the same conclusion
Rule-16's own record reached when it refuted locking.

## The three mechanisms dyad-system already has
The evaluation must beat these, not ignore them.
1. **Rule-16 presence store** — `<instance>/d-work/sessions/<id>.md`, one file per session, single
   writer, in-repo, advisory, read before a new plan. This is *state broadcast*: last value wins,
   no history, no topics, no delivery, no position. It caught nothing on its own; #185's near-miss
   was caught "only because a peer chose to message first".
2. **Rule-19 event store** — `<runbooks>/events/<instance>.jsonl`, append-only on `main`, with a
   guard and primitives already in `dyad/scripts/runbook.py` (`events_dir`, `events_path`,
   `read_events`, `all_events`, `event_line`). The closest substrate in the system, and Rule-13
   property 2 says reuse before authoring.
3. **Rule-3 Intake** — the governed channel: "A message from another agent opens no d-work: only an
   Operator prompt or disposition does." Two admissible shapes (a defect as an observation with
   evidence; an enhancement only with its Operator's verbatim prompt behind it). Deliberately inert.

## Revision 2 (2026-10-05, before any plan-`Y`) — the reference re-read in full
A second pass over `build/half1` corrected one claim of the first draft and added facts the
evaluation needs. Base commit unchanged (5d364bb); the mutation proposed is unchanged.

**The correction.** Revision 1 said "nothing in the repo commits or pushes the bus … the broadcast
half is unimplemented". False. `tax-prep/scripts/push-and-broadcast.sh:108-155` pushes the branch,
publishes, then commits and pushes the store, verifying both remote heads by `git ls-remote`. The
first grep missed it because the script writes `git -c credential.helper= push "$url"`, not
`git push`. What survives, and is the better fact: the script is Operator-run — a human completes a
GitHub device flow in an external browser per push — so the broadcast is gated on the Operator in
dsys too. Incident 3 below.

**Added to the attack table's evidence, each read in the files:**
- **The `from` field is self-asserted.** `publish(from_id=...)` takes any string; no signature binds
  a message to a sender, and `exclude_from` filtering trusts the field. Nothing re-checks on read.
  This strengthens A2 beyond a Rule argument into a mechanical one: **a bus cannot carry
  authorization because it cannot prove who sent anything.** Rule-2's proposer/disposer distinction
  would rest on an unauthenticated string. `doc/session-sync-spec.md:96` specifies session-key
  encryption for the *unimplemented* protocol; the implemented bus has none.
- **Delivery, precisely.** A per-(session, topic) high-water mark, local, never committed. No ack,
  no delivery receipt, no per-message read state, no sequence number and so no gap detection, no
  dedup on the consumer side, no retention, compaction or delete path. The cursor advances *before*
  the caller has processed what was returned (an at-most-once edge); an unknown or legacy cursor
  replays the whole topic (an at-least-once edge). Two sessions on one machine read-modify-write the
  whole cursor file, last writer wins, untested. This sharpens A6: the survivor is not merely "no
  cursor in the corpus" but **messages whose re-delivery is harmless by construction** — an
  observation may be re-read; anything with an effect may not.
- **Publish has no lock and no fsync** (`path.write_text` only); safety is the unique filename
  (microsecond timestamp + 48 random bits) plus `git pull --rebase` in the script, which **refuses
  and asks a human** on conflict rather than auto-resolving. This is exactly A8's survivor, and it
  is the same discipline as `doc/glossary.md:312` ("no supervisors, only checkers") and as
  Rule-16's refusal to lock.
- **Its own documentation is in tension.** The bus section says the two sessions "no longer relay
  through Peter" (`COLLABORATION.md:76`), while Branch discipline eleven lines earlier still says
  "If it finds a bug, it reports the shape through Peter" (`:110-111`). The migration away from the
  human relay is partial in the document itself — which is the honest version of A2's constraint,
  observed in the reference rather than argued from our Rules.
- **The bus carries no authority, by its own design.** The only machine-actionable instruction any
  payload holds is hardcoded: `"action": f"pull {branch} and re-run verify_all"` (`bus.py:388`).
  Topics are free-form, created by `mkdir(exist_ok=True)`; the three well-known ones are convention
  in a docstring and enforced nowhere. `COLLABORATION.md:42` — "the Operator is the sole decider".
- **It is live, not aspirational.** `doc/decision-records/DR-CMD-113-next-best-action-3.md:9-12`
  records a real inter-session message received and threaded by `correlation_id`, awaiting Operator
  disposition. Nothing in `bus.py` reads or indexes `correlation_id`; the threading is done by a
  reader.
- **And it was built outside that repo's own governance.** No decision record names the bus
  (`doc/decision-records/` has no `bus|store|broadcast|collab` entry) though every other feature
  there has one. Noted as an observation about the reference, not a judgment: it is that system's
  Operator's business, and it is why the design had to be read from the code rather than from a
  record.

**What this does to the recommendation:** nothing in shape, two things in emphasis. The recommended
store stays in-repo, append-only, Intake-shaped, on Rule-19's primitives — and the audit must now
state two properties as requirements rather than as nice-to-haves: every message must be
**re-readable without effect** (the delivery semantics above make re-delivery certain, not rare),
and the sender identity must be **whatever git already authenticates** (the commit's author and the
push), never a field in the message, because a self-asserted `from` cannot bear any weight a Rule
puts on it.
