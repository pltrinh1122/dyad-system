# Plan #206 — the commit-signing requirement, for Operator review

*Rule-15 phase 1. Base commit of `main`: 38b8c48 (2026-10-04). refs: 205 204.*

## Intent as read
Explain where the commit-signing requirement comes from, so the Operator can dispose whether it is
necessary. The 36 s attributed to signing in #205 is the trigger.

## Findings (read-only, observed 2026-10-04)
1. **Source.** `commit.gpgsign=true`, `gpg.format=ssh`, `user.signingkey=/home/claude/.ssh/commit_signing_key.pub`
   and `gpg.ssh.program=/tmp/code-sign` all come from `/root/.gitconfig`, the container's global
   config. `/tmp/code-sign` is a link to `/opt/env-runner/environment-manager`, the cloud
   environment's signer. It is not set by the repo, any Rule, any hook or any workflow.
2. **Repo.** No file on `main` sets, reads or verifies a signature. There is no `gpgsign`, no
   `verify-commit`, no `%G?` and no `--show-signature` in any `*.py`, `*.sh`, hook or workflow. No
   test checks a signature.
3. **GitHub.** Commits the session pushes carry an SSH signature that GitHub reports as
   `verified: true` (978efb5, 99e2229). Merge commits are PGP-signed by GitHub itself. Whether
   `main` requires signed commits could not be read: branch protection returned 403 to this session,
   and the rulesets endpoint returned `[]`.
4. **Test fixtures.** The suite's scratch repos (`tempfile.mkdtemp`, never pushed) inherit the
   global config by accident, so every fixture commit is signed: 99 ms against 11 ms unsigned
   (n=15). Nothing ever verifies those signatures.

## Mutation proposed
- In `dyad/scripts/package.py` `suite_env()`, the one environment every test child runs in
  (Rule-12; the spawn-site fence #199), append `commit.gpgsign=false` through
  `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`. Any count already present is extended,
  never overwritten.
- One test in `dyad/tests/test_package.py`: the child env carries the key, and an existing
  `GIT_CONFIG_*` entry survives.
- Real commits in the working repo are unaffected. They are made outside `suite_env`, so they stay
  signed and stay Verified on GitHub.
- An agent-zone PR citing d-work #206.

## Falsification
- **Attack: fixtures must be signed because the hosting requires signed commits.** Refuted. Fixture
  repos are never pushed. The requirement, if there is one, binds pushed commits only.
- **Attack: turning signing off globally is simpler.** Refuted as the proposal. It would also
  unsign the session's real commits and lose GitHub's Verified mark. That is the Operator's
  decision about the environment, not the suite's.
- **Attack: `GIT_CONFIG_COUNT` clobbers a user's own env config.** Survives as a constraint. Append
  at index n, never reset.
- **Attack: the suite memo key changes.** Checked: the memo keys on the instance's environment
  settings, not on `suite_env`. Re-verified at execution.
- **Attack: on the Operator's own host it saves nothing.** Confirmed. With no signing configured
  there, it is a no-op. The 36 s is this container's. The change costs nothing there.
- **Presence:** no other live session names these files.
