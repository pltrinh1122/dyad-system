## Falsification
1. **Claim: mock `rows.py`'s git layer (the option #108's plan literally named) is the right
   Stage-2 move for `guards/agent/test_rows.py`.** Attack: `rows.py`'s `check_commit`/
   `check_range`/`check_id_collisions` are themselves nothing but calls to real `git` plumbing
   (`diff-tree`, `show`, `rev-list --parents`) — this is the main fence Rule-2 and Rule-3 name by
   name as their mechanical enforcement. A mocked git layer could pass while the guard's actual
   parsing of real `git diff-tree --name-status` output (rename flags, path quoting, `--no-renames`
   behavior) silently diverges — the tests would keep passing on a guard that no longer says what
   they claim it says. Result: **refuted as the right move** — the risk (weakening the one
   mechanical fence a self-ratification rule depends on) is disproportionate to the payoff (this
   file alone measures 6.09s/25 tests, ~244ms/test, dominated by ordinary `git init`+commit
   subprocess cost, not by anything a mock would remove faster than a cheaper structural fix
   would). Not pursued.
2. **Claim: label `FenceTests` as integration and stop — no code change at all.** Attack: this
   matches #108's other named option and is zero-risk, but leaves the actual profiled cost
   (`guards.agent`: 12.64s across this file and its neighbours in #107's own measurement) entirely
   unaddressed, which is the reason Stage 2 exists. Result: **survives, scoped** — worth doing as
   documentation (a one-line module docstring note, already close to true given the file's own
   header), but not a sufficient answer on its own; see recommendation below.
3. **Claim: `test_craft.CraftCliTests`'s cost (24.08s/15 tests here, ~1.6s avg, #107's other named
   target) is inherent to what it tests and cannot be cut without weakening it.** Attack: measured
   directly — `setUp()` (`dyad/tests/test_craft.py:44-45`) calls `scratch()` fresh for *every* test
   method, which itself calls `package.py install` as a real subprocess (`scratch()`,
   `dyad/tests/test_craft.py:24-27`) into a brand-new `git init`. Every test in the class installs
   the identical core craft into an identical, disposable scratch repo before doing anything
   test-specific. Result: **refuted** — the repeated *install* is redundant, not essential; what
   each test actually needs varies (a receiving repo with the core craft present and committed),
   and that starting state is identical across every test in the class.
4. **Claim: a class-scoped install, copied cheaply per test (`shutil.copytree`, no subprocess),
   preserves what these tests are actually testing.** Attack: several tests mutate `self.dst` in
   ways that could interact if the underlying files were shared rather than copied (e.g.
   `test_install_refuses_modified_tree_unless_forced` deliberately dirties the tree). Result:
   **survives** — `shutil.copytree` gives every test its own independent directory and its own
   independent `.git`, byte-identical to what `scratch()` produces today, so no test's mutations
   are visible to any other; the *install itself* (property 5: one code path, deterministic,
   idempotent) is exercised once at class setup, still for real, never mocked — the redundant part
   removed is re-running it 15 times for input that never varies.

## Recommendation (Rule-10)
**Path:** two independent, both low-risk moves, not one — Stage 2 does not need to be a single
lump:
- (a) `test_craft.CraftCliTests`: replace the per-test `scratch()` (full `package.py install`
  subprocess) with a `setUpClass`-built template scratch repo, copied per test via
  `shutil.copytree` (`setUp`) — cuts ~14 of 15 `package.py install` subprocess invocations while
  every test still runs against a real, independently-mutable git repo with the real install in
  it. Expected to cut this file from ~24s to roughly the cost of one install plus 15 cheap copies
  (single-digit seconds, not measured yet — Stage 2's own plan would measure before/after as #108
  did).
- (b) `guards/agent/test_rows.py` (and `guards.agent` generally): no code change — keep real git
  subprocess calls (attack 1), add one docstring line making the "this is integration, by
  necessity" framing explicit rather than implicit, matching what #108 already did for
  `test_evidence_block_shape_and_hash`/`test_pass_order_and_lines`'s comments. Its cost (6.09s for
  this file) is not the dominant remaining one and buys real coverage of git-plumbing behavior a
  mock would remove.

**Strongest counter:** doing (a) now, in this same d-work, risks exactly the kind of drift-guard
miss #108 just caused (a green `check --pr` on the branch, a red `infra/bundle` only caught by a
peer session after merge) if this plan is treated as "just scope it" but then executes anyway
under momentum. A reasonable Operator could want the scope written now and the *code* done as its
own later plan-`Y`, keeping each d-work's diff and its own falsification separately reviewable —
exactly the shape #108 itself used for Stage 1 vs Stage 2.

**Reconciliation:** the counter is about sequencing, not substance — it does not dispute that (a)
is the right fix, only when to authorize writing it. This plan's mutation is scoping only (no code
touched); if `Y`, a second, small plan-`Y` (this same d-work, since the scope is already agreed, or
a fresh #111 if the Operator prefers a clean split) would cover implementing (a), running the full
check suite including `infra/bundle` explicitly (learning #108's own gap), and measuring the actual
speedup, the same way #108 measured `test_evidence_block_deterministic`'s.
