# Plan #232 — hold countersign and disclosure out of the release until the Operator says they are ready

Base commit of `main`: e51ef972ff5df122a46ca8f711e71c4798af652c

## Intent as read
The Operator has disposed one of the two open decisions #231 surfaced: countersign and disclosure do
not go into the next release. The instruction is to *not* act — so the work is to make sure nothing
acts on its own, and to leave the decision where the next session reads it instead of in the chat.
The plan also stops #231's Part A from presenting the two crafts as release content.

## What is already true (observed, not assumed)
- Neither craft has a tag: `git tag -l 'countersign-v*'` and `'disclosure-v*'` are both empty.
- Neither has a row in `BUNDLE.md`, which holds four: dyad-operator, sysarch, syseng, sysadmin.
- `dyad bundle build` sequences the one distribution code path **once per `BUNDLE.md` row**
  (`package.cmd_bundle`), so a craft with no row is never built and never published. The hold needs
  no mechanism; it needs no tag to be cut.
- `bundle.py` already enforces the other direction: a craft in the tree *with* a tag and no row is a
  **failure** (`'<craft>' is in the tree but has no bundle row`), while an unreleased craft with no row
  is a **warning** (`… unreleased … not yet bundled`). So the first tag on either craft would fail the
  guard until `BUNDLE.md` gained its row — the hold cannot be half-done by accident.

So the mechanical state already matches the instruction. The one thing missing is the record: the two
warnings `dyad check` prints every run read as an unfinished chore, and nothing in the corpus says they
are a disposed decision. That is what a later session gets wrong.

## Mutation proposed
1. **`BUNDLE.md`** (infra zone, its own PR): one sentence under the table naming countersign and
   disclosure as deliberately held out by Operator disposition, citing `#232`, so the file a release is
   cut from answers "why only four rows?" without the chat. No row added, no version change — the
   bundle's own version is untouched because nothing it names changes.
2. **`agent-corpus/d-work/plans/231.md`** revision 3 (ledger-only, no PR): Part A8 drops the two
   crafts from what the release delivers and records them as held by this d-work; Part B3's bundle
   decision is settled — four components, six tags, and the #170 ordering problem does not arise for
   this release; B5's open decisions reduce to the blocker and the two `VERSION` corrections.

Not proposed, and stated so the Operator can overrule: **the two warnings stay.** Suppressing them
would mean teaching `bundle.py` which absences are deliberate — a data file of held crafts, which is
exactly the kind of list Rule-11 property 2 refuses for bundling ("never by a list the core keeps").
A craft held out of a release is an instance decision, so if the noise becomes a problem the place to
fix it is the instance, not the core guard. Left as a finding, not a change.

Files touched: `BUNDLE.md`, `agent-corpus/d-work/plans/231.md`, and the ledger (`rows/232.md`,
`plans/232.md`, `provenance/232.md`, `traces/232.md`).
