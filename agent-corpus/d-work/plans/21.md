# Plan #21 — bundle release

Base commit of `main`: 3126a70. Refs #13 (per-craft releases), #17 (v0.4.0), #19 (hand-publish path), #20 (CI Release step).

## Intent as read
Two names for two things. `vX.Y.Z` (the GitHub convention: the repo's "Latest", the front-door
download) becomes the **bundle** — the whole distribution this repo authors: the core craft plus
every Tended craft in the tree, each at a pinned version, listed in one bundle manifest. Each craft
keeps its own version, its own prefixed tag and its own archive, so another system may pin
`dyad-operator 0.5.0 + sysarch 0.1.1` alone and compose its own bundle. The core craft therefore
gains the prefixed tag the Tended crafts already have: `dyad-operator-vX.Y.Z`.

## Design (falsified below)
- **Bundle manifest**: `BUNDLE.md` at the repo root, infra zone (a distribution artifact of this
  authoring repo — not core craft content, since a system without sysarch must not carry a bundle
  naming it; not instance state). A `version:` line and a table `component | version`, one row per
  craft in the tree (`dyad-operator` + every `crafts/<name>/`). sha256s are *not* tracked (they
  change on any craft edit; Rule-11 p6 generated data) — they are emitted at build time into
  `BUNDLE.sha256`, an asset, never a tracked file.
- **Versions**: the bundle carries its own version, independent of the core's (a craft-only change
  bumps the bundle, not the core). Seed: this d-work bumps the core to 0.5.0 (Rule-11 text and a
  new guard: minor), so the first bundle is `v0.5.0` = dyad-operator 0.5.0 + sysarch 0.1.1 +
  syseng 0.1.2. Existing tags `v0.3.1`, `v0.3.2`, `v0.4.0` never move; Rule-11 Provenance states
  they are core-only tags cut under the pre-bundle convention.
- **Guard** `dyad/guards/infra/bundle.py` (entity `bundle`, corpus `infra`, registry `infra/bundle`,
  tests `dyad/tests/guards/infra/test_bundle.py`, Rule-12): `BUNDLE.md` well-formed; every row's
  version equals that craft's `VERSION` in the tree; every craft in the tree has a row and every row
  names a craft in the tree (one bundle = the whole tree); absent file → one `skip` line, never a
  failure (a system that installed the core has no bundle — Rule-20 p2's pattern).
- **Build** `dyad bundle build [dir]` (`distribute.py`; one code path, Rule-11 p5): `dyad build` +
  `dyad craft export` for each row, then `BUNDLE.sha256`. Refuses if the guard fails.
- **Tags** (Rule-11 p4): `vX.Y.Z` = `v` + BUNDLE.md version; `dyad-operator-vX.Y.Z` = core;
  `<craft>-vX.Y.Z` unchanged. One `Y` per tag, as now.
- **Workflow** `dyad-release.yml`: `v*` → bundle path (all archives + `BUNDLE.sha256`);
  `dyad-operator-v*` → core; other `*-v*` → craft. Its Release step still 403s (#20); the
  check/build steps corroborate, hand-publish stays the delivery path.

## Falsification
- "Put the manifest in `dyad/` so every install has it" — refuted: the core must not name Tended
  crafts (Rule-11 p1: one craft, no instance; a core-only system would carry a lie). Root/infra.
- "Bundle version = core version, no second number" — refuted: a craft-only release would then need
  a core bump with no core change, or a bundle with an unchanged tag. Independent number survives.
- "Track sha256 in BUNDLE.md for verifiability" — refuted by Rule-11 p6 (generated) and by its
  own churn; the determinism guard already makes the archive reproducible from the tag; the
  sha file is an asset.
- "Just re-tag v0.4.0 as the first bundle" — refuted: tags never move, and v0.4.0's archive is
  core-only; the first bundle is the first tag cut under the new rule.
- "A bundle may list a subset of crafts" — refuted for this repo: "single bundle" = the whole tree;
  subsets are what individual pinning is for. The guard enforces tree == rows.
- Rule-5 pairs: 11–14 (the bundle names crafts, never World rows; manifest.md untouched); 11–1
  (one new infra path); 11–20 (bundle rows → craft VERSION is a new reference kind; resolver is the
  bundle guard, listed in `references.REFERENCES` as `guard:infra/bundle.py`). Others unchanged.
