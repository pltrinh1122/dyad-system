# Plan #185 — the bytecode suppression: close the one real coupling, then state and test the reason the suppression actually serves

*Rule-15 phase 1. base commit: 6a29e8b (`main`, 2026-09-29). refs: 184 187 183 190. Drafted by a
sub-agent under `delegation: plan-and-execute`; every load-bearing claim re-verified by the main
Agent before this file was written (Verification, below).*

## Intent as read
Row #185 found that `sys.dont_write_bytecode` in `dyadlib.load_module` and in `crafts.py`'s floor
script is neither load-bearing for the reason it claims nor covered by any check. This d-work
disposes of that: close the one place where bytecode on disk feeds a guard's computation, and then
either give the suppression a true reason with a test that fails without it, or delete it and let
`distribute.SKIP_DIRS` carry the concern. The "either/or" is read as a disjunction to be **decided by
measurement**, not a preference to be ratified — and measurement refutes both halves as stated.

## What measurement established before this plan was written
1. **The coupling is real, and the suppression neither causes nor closes it.** `manifest.py`'s
   `python_dirs` globs `dyad/tests/guards/*` and `python_imports` takes those directory *names* as
   internal module names, so `'__pycache__' in internal` is **True today with both suppressions in
   place**. That directory is written by the `unittest` child that imports the test packages;
   `load_module` never imports anything under `dyad/tests/`. #187's finding is real and its fix is
   owed — but it is **not** evidence for the suppression. This separation is the plan's load-bearing
   move.
2. **The suppression's stated reason is false.** Both counts the runner prints come from git
   (`distribute.files(tracked=True)`, `git ls-files`), so an untracked `.pyc` cannot move either.
3. **The reason proposed in its place is also false.** From a `__pycache__`-free clone with both
   suppressions present and the suite skipped, `dyad check --guards` leaves `dyad/scripts/__pycache__`.
   Every `dyad` command writes it, through `package.py`'s own `sys.path` imports, which `load_module`
   does not mediate. "A read-only command leaves no files behind" over-claims exactly as "file counts
   stay deterministic" did.
4. **What removal costs, and what it does not.** Removing both sites leaves the suites green, cold and
   warm, and turns 19 `__pycache__` dirs into 26 — 12 in craft trees into 15. Every one is excluded by
   `SKIP_DIRS`, by `.gitignore` and by `package_rules.txt generated:`, so craft identity
   (`archive_sha256(…, tracked=False)`), the registry sha, `install`'s prune and `instance_state` are
   untouched. Row #185's "26 instead of 7" compared a full gate run against a partial one; the honest
   delta is **+7 dirs, 3 of them in craft trees**.
5. **What `SKIP_DIRS` cannot carry is what *runs*.** Timestamp `.pyc` validation is
   (mtime-to-the-second, size). With the suppression removed, `dyadlib.load_module` returns
   `VALUE = 111` from a path whose source reads `222`. The guard registry is loaded **only** through
   `load_module`, so that is `dyad check` reporting on code that is not on disk — the one artifact
   Rule-2's Binding cannot tolerate, since the evidence block must be about the head being merged.

## Mutation proposed — one PR, agent zone
1. **`dyad/guards/infra/manifest.py`** — a `_code_dir(d)` predicate on both globs in `python_dirs`: a
   directory that can hold this package's Python, so a *generated* one is not, by

   that set to generated-or-VCS names and now protects this guard too). The `{d.name for d in dirs}`
   term in `python_imports` **stays** — it is load-bearing, and A1 is why.
2. **`dyad/tests/guards/infra/test_manifest.py`** — the check (Rule-12): a scratch package with
   `tests/guards/__pycache__` and `guards/__pycache__` planted and a module doing `import __pycache__`.
   Fails before the fix on two assertions, the second being the consequence — the token is swallowed
   as internal, so bytecode on disk changed the guard's verdict. Plus one regression test pinning
   `import guards.agent` internal, so the tempting version of this fix cannot land later.
3. **`dyad/scripts/dyadlib.py`** — `load_module`'s docstring replaced by the reason that survives
   (§5), naming both refuted reasons **as refuted** so neither is re-derived.
4. **`dyad/tests/test_dyadlib.py`** — `LoadModuleTests`: no bytecode beside the file and the flag
   restored; and, separately, that a same-size rewrite of one path under one mtime is not served from
   cache. `setUp` sets `sys.dont_write_bytecode = False`, so CI's own `PYTHONDONTWRITEBYTECODE=1`
   cannot make either pass vacuously.
5. **`dyad/guards/craft/crafts.py`** — one comment on `_FLOOR_SCRIPT`'s existing line: the target it
   loads is the *live* craft file, so the suppression keeps `.pyc` out of a craft tree and out of the
   next run's read. No behaviour change.
6. **`dyad/tests/guards/craft/test_crafts.py`** — the floor child writes nothing into the fixture
   craft's `guards/`, with `PYTHONDONTWRITEBYTECODE` popped from the inherited environment.

## Rule-10
- **Path:** one agent-zone PR, six files. Stop `manifest.py` scanning generated directories, so no
  guard's verdict depends on bytecode being on disk; keep both suppressions; replace `load_module`'s
  false reason with the one that survives — a by-path import executes the file on disk, never a cache
  whose one-second validation cannot see a same-size rewrite — and carry that reason in four tests,
  two of which fail on the consequence rather than the mechanism.
- **Counter:** drop the suppression. Untested defence-in-depth whose stated reason is false; the
  suites pass without it; three layers already exclude the files; and removing it deletes a
  process-global mutation from the hot path every guard load takes. The row's own second option, and
  the cheaper one.
- **Reconciliation:** the counter is right about everything it names and wrong about what it omits.
  `SKIP_DIRS` governs what is *counted*; the suppression governs what *runs*, and `dyad check`
  returning a verdict on code no longer on disk is the failure a guard system cannot have. So the
  suppression stays — but the counter wins the parts it asked for: the reason is corrected twice over,
  both refuted reasons named as refuted so neither is re-derived, and the line stops being unchecked.
  The manifest fix is not a concession to the suppression; it is the whole of the real defect, and it
  would be owed even under 2b.

## Revision 2 — 2026-09-29, after the plan-`N` (see #192)
The plan-`Y` was declined and the d-work deferred to the outstanding sub-agent tasks. The
deferral was falsified as #192 and holds. Three changes are owed to this file before it is asked
again; the mutation of §"Mutation proposed" is unchanged by all three.

1. **A5 is re-scored.** It read `confirmed as better, unavailable —
   "importlib.util.spec_from_file_location exposes no invalidation mode"`. That conflated the
   producer with the consumer. On the pinned kernel (3.13.12), over a source compiled with
   `compileall --invalidation-mode checked-hash`, the by-path loader `load_module` itself uses
   returned `222` after a same-size rewrite restored to the original mtime — the source's value,
   where the timestamp cache returned `111`. **A5 becomes: available, at the price of a
   `compileall --invalidation-mode checked-hash` step in the install path.** No environment
   variable substitutes: with `SOURCE_DATE_EPOCH` exported the import system still wrote flags
   `0`, a timestamp cache, on 3.13.12 and 3.11.15.
2. **A fourth option exists and is unpriced.** Keep the cache, compile it checked-hash at
   install, and drop the suppression: correct *and* cached. Its worth is the suppression's cost,
   which is what #190 is measuring and which today reads −0.4% unpaired against −6.4% paired on
   the core root, contradictory, with reverse-order pairs still running. This plan may not choose
   between option 2a and option 4 until that number is one number.
3. **`PYTHONPYCACHEPREFIX` is named and refused.** It empties the tree outright (0 `__pycache__`
   directories in the tree, 25 `.pyc` under the prefix) and so is a genuine alternative to the
   `python_dirs` filter. It is refused for the reason this plan already gives in §"Not in this
   mutation" against setting `PYTHONDONTWRITEBYTECODE` in `suite_env()`: a guard must not depend
   on an environment variable. Named here so it is not re-derived as a discovery.

**What stays.** The `_code_dir()` filter on `python_dirs` is owed under every option, 2b and 4
included — it is the whole of the real defect and nothing about the cache touches it. The
docstring correction stays owed, with both refuted reasons named as refuted, and now A5's
correction too.

**What the Rule-10 block owes.** It currently frames a three-option space with the fourth
scored out. It is rewritten, and the counter-prompt asked again, when #190 reports — not before.
