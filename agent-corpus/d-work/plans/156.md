# Plan #156 — a unifying Countersign schema: falsify "maps cleanly", then refactor both repos to it

Base commit of `main`: ee89625. Refs: 152 (Seed-0, on hold), 153 (modes are modes of an act; the
executor is the one mode-exclusive sub-system), 142 §2 (term collisions), 150 (countersign).
Compared: dyad-system `ee89625`, dsys-repo `37fc52e`.

## Intent as read
Two parts:
1. **Falsify** the claim that a unifying schema for the Countersign Architecture can be formed that
   maps cleanly to the existing dyad-system and dsys.
2. **Plan** the refactor of both repos, as far as necessary, so that each maps to that schema.

The Operator's standing constraints (#152 disposition) bound the refactor. dyad-system is deployed
to a commercial client, and dsys is research converging with workstation. Both keep evolving in
parallel; neither is merged into the other.

## 1. The candidate schema (Countersign core, v0)
Eight entities, derived from #153's survivor. Logical, not a storage format.

| entity | fields (core) | meaning |
|---|---|---|
| **Party** | id, kind ∈ {human, agent, executor} | who acts; only a `human` countersigns |
| **Act** | id, title, mode ∈ {explicit, implicit, automatic}, processor → Party, state, refs | one consequential unit of work, in exactly one mode at a time (#153) |
| **Proposal** | id, act → Act, author → Party(agent), body ref, artifact hash? | what is put up for countersignature |
| **Countersignature** | id, subject → Proposal \| Escalation, signer → Party(human), answer ∈ {yes, no, amend}, basis ∈ {per-act, mandate, release}, text (verbatim), bound hash?, at | the human act; `basis` is *how* it covers the act |
| **Mandate** | id, scope (event class, plan template, budget, rights), countersignature → Countersignature | a standing countersignature (implicit mode) |
| **Release** | id, definition ref (run-book / flow), version, hash, countersignature → Countersignature | a countersigned definition an executor runs (automatic mode) |
| **Event** | id, act → Act, seq, payload, at-or-seq | an append-only execution record |
| **Escalation** | id, from → Act, reason, opens → Act(explicit) | the unexpected, returned to a human |
| *(attribute)* **Check** | name, timing ∈ {before, after}, target entity | a guard or validator; timing is the axis the two repos invert |

## 2. Falsification: "maps cleanly"
| # | attack | result | evidence |
|---|---|---|---|
| F1 | **The spine**: do both repos' core records map onto Act → Proposal → Countersignature → Event → Escalation without loss? | **Survives.** dyad-system: d-work row → Act; plan file → Proposal; `disposed` entries plus provenance → Countersignature (answer Y/N/text; text is verbatim); run-book event → Event; intake or incident → Escalation. dsys: DecisionRecord / HarnessRun → Act; draft / CTA → Proposal; Disposition → Countersignature (CTA yes/no/counter → answer); AutomatonEvent → Event; Disclosure → Escalation | `dyadlib` rows; `schema.py:215-316` |
| F2 | **Mandate and Release**: do both have instances? | **Survives, thinly.** dsys: `set_standing` Dispositions → Mandate; PromotionRecord / AutomatonRelease → Release (both modelled). dyad-system: **the preference `ledger-pr-merge: agent` already *is* a Mandate**: a standing Operator authority for one class of act, which this session has exercised seven times today. Release tags cut on `Y/N: release <tag>?` → Release. But dyad-system has no *record* type for either; they live in preference prose and git tags | `PREFERENCES.md`; Rule-11 |
| F3 | **Mode and processor fields.** Does either repo record them per act? | **Refuted as "cleanly".** Neither does. dyad-system's acts are all explicit by construction, so a mapping can *derive* `mode=explicit, processor=agent`. dsys stores the mode implicitly in the entity *type* (AutomatonRun is automatic; HarnessRun is explicit or implicit) and never marks implicit. A mapping can derive both, but only by rule, not from data |
| F4 | **Vocabulary.** Does any term mean opposite things? | **Refuted.** dsys's `DispositionMode` (ratify, authorize, set_standing, overrule, triage) uses **"mode"** for what Countersign calls a countersignature's *basis or kind*. Countersign's "mode" is explicit / implicit / automatic. Mapping without renaming collides on the schema's central field. #142's inverted terms (run-book, event, role, `dyad`) collide the same way | `schema.py:215` |
| F5 | **Extension entities**: does everything map? | **Refuted for the whole, survives for the core.** dsys's Principal, Hat, R, Fleet, CoS Directive, GateCheck, Application, LocalVeto, Claim and IFF gates have no dyad-system counterpart. dyad-system's zone, craft, presence file, plan gate and evidence block have none in dsys. A schema of *core plus per-system profiles* maps; a single flat schema does not |
| F6 | **Timing.** Checks before (dyad-system guards block) against after (dsys referee judges). Representable? | **Survives** as the `Check.timing` attribute. It is a *policy* difference, not a structural one |
| F7 | **Representation.** Markdown `key: value` stores against pydantic `SystemState` JSON. | **Survives by projection.** Both can be *projected* to the schema. dyad-system already has a projector mechanism (sysarch `projection.md`) and a declared-but-unused pydantic kernel row. dsys *is* pydantic. Mapping is code in each repo, not a storage migration |

**Verdict:** "a unifying schema maps cleanly to both" is **refuted as stated** (F3, F4, F5).
**Survivor:** *a Countersign **core** schema (the eight entities) maps to both repos **by projection**,
after two renames on dsys's side and two derivation rules on both; each repo keeps its extension
entities as a profile outside the core.*

- **no change to dyad-system's core Rules, guards or stores**, because the commercial client runs

## Rule-10 framing
- **Path:** additive projection, in a new unbundled craft and a dsys mapping module. Both repos map
  to one core schema, and nothing either repo already does changes.
- **Strongest counter:** projection hides the gaps. Deriving `mode` by rule (F3) and renaming at the
  boundary (F4) makes the repos *look* unified while their stored models stay divergent. A real
  refactor, with stored fields and renamed enums, is what "refactor as necessary" literally asks.
- **Reconciliation:** the stored-field refactor touches dyad-system's core stores and guards (the
  client's runtime) and dsys's validated model (the research baseline). Projection first *proves*
  the mapping with tests against real data. The stored-field changes can then be justified one by
  one by what the projector could only derive. It concedes the literal reading for now.
