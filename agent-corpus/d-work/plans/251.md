# Plan #251 — audit the Operator-disposition chain of authority, down to git and GitHub

*Rule-15 phase 1. Base commit of `main`: 507562b408af892f54992b22c75a53f2a06c6fa3 (2026-10-08). refs: 249 250 241 24.*

## Intent as read
Trace one thing end to end: an Operator `Y`, from the words that arrive in the chat to the bytes
that land on `github.com`. At every hand-off, ask two questions — does the authority survive the
hand-off, and does the hand-off cost a human question it did not need. Report both as findings with
evidence, not as changes.

**"cabinet session" is not a term of this corpus.** It appears nowhere in `dyad/`, the crafts, the
instance or the memory cache. Read as: a session of several seats, each auditing one link
independently, their findings synthesized by the main Agent — a council, not a single reader. The
reading is stated here rather than guessed silently; if `cabinet` carries a definition from another
system, the Operator says so and this plan is revised before any seat is filled. Mechanically the
seats are subagents, which Rule-3 Scope confines to reading, searching and drafting: no seat writes
a row, asks or answers a counter-prompt, commits, pushes, opens a PR, merges, or touches the host.

## The chain, as the links the audit will cut it into
One seat per link, each given the same brief — what the chain *asserts* here, what a mechanism
*checks* here, and the gap between them — and each required to cite path and line, a commit, or an
observed run for every claim:

1. **Capture.** The Operator's words to the corpus: `dwork new|state`, the provenance record,
   the row's `disposed` column, Rule-7 property 5's one-to-one count, the legacy list, the
   transaction check that fails the gap in the session that wrote it.
2. **Authorization to mutation.** The plan gate (`dyad/guards/agent/prs.py`): a PR body's
   `d-work #N` resolved at the base commit, the state set, the `Y plan` key, the ledger-only
   exemption (#191) — and #250, already open: the key is a substring search over the whole column.
3. **The direct-push fence.** `dyad/guards/agent/rows.py` on `main`: ledger-only or refused,
   the first-parent walk, each merge commit against both parents, the transition table.
4. **The hook layer.** `core.hooksPath dyad/hooks`, `pre-commit`, `pre-push` and the kernel-only
   path (Rule-14 property 3): what the refs-from-stdin judgement covers, what `--no-verify` and an
   unset `core.hooksPath` leave uncovered, what a lost exec bit does (#23), and what the suite memo
   and installed-root skips mean for the gate's coverage.
5. **The git-to-GitHub boundary.** Who merges, with which credential, and what the hosting checks:
   no required status checks (#24 open since 2026-09-15), CI detecting-only and never on a branch or
   a PR event (#168), the `gh` token's scope, and the plainest question of the audit — whether a PR
   merged in the web UI, by anyone holding the token, would leave any trace that no disposition
   authorized it.
6. **Tag and release.** A release `Y` to a tag to a published archive: whether anything mechanical
   ties a tag to the disposition that authorized it (#70 records that three past tags have no such
   disposition at all), what `check_drift` does and does not cover, and the five `gh release create`
   calls this session ran by hand (#20).
7. **The counter-prompt inventory** — the main Agent's own seat, not a subagent's, because it is a
   read of the Rules plus this session's own transcript. Every `Y/N` the Rules require, classified:
   **adds authority** (the only disposer decides something undecided), **duplicates** (the same
   authorization already given, asked twice), **friction** (a human keystroke that decides nothing).
   Named starting points: `merge-disposition` and `ledger-pr-merge`, both already tuned away from
   duplication; the five per-tag release questions of #241 against Rule-11's own release-batch form,
   which was unavailable only because its precondition is a Done-`Y` that comes after the tags; and
   the `backlog` -> `open` prompt requirement, which in this session turned four consecutive `Y`s
   into four banked rows and no work, because a bare `Y` can open a row but never start one.

## Mutation proposed

`agent-corpus/audits/2026-10-08-disposition-chain-of-authority.md` — the seven links in order; one
findings table per link (`link | what the chain asserts | what is mechanically checked | class |
evidence | proposed fence or recorded impossibility`); a falsification table (Rule-9: every finding

Operator disposes each.

No Rule text, no guard, no preference and no workflow is edited by this d-work. A fence the audit
proposes is a later d-work with its own plan-`Y`.
