## Intent as read: the intent reading (`intent-reading: on`, Rule-3 Plan)
Prompt: provenance #676, entry 1 (the same words open #677). The hand-up it introduces is held in
`plans/677.md`, Appendix.

**What exists.**
- **`dmc:intake-shape`** (core, Rule-3 Intake) decides whether a message is **admissible**: a defect, an enhancement,
  or returned to the sender.
- **Nothing decides what happens after admission** when the sender is a downstream system of the same operator. That
  is: which part upstream builds, which part stays downstream, and what is said back down.
- **The craft/instance line** (Rule-11 property 1) and `dmc:bundled-craft`'s purpose ground say what a craft may hold
  (no instance state, and purpose judged on the craft's own tree). They are never read as one decision for a hand-up.

| portion of the prompt | class | consequence |
|---|---|---|
| "need a formal `dmc` for intaking work" | new | a core record, `dmc:intake-split`. For an admitted hand-up, it decides per requirement where the work lives: **upstream core**, **upstream craft**, **downstream instance**, **both** (an upstream mechanism with a downstream configuration or data), or **asked back** (an open question the sender must settle first). Its inputs are read from the requirement, never from the sender's code: whether every installing operator needs it, whether it needs instance data (another party's records, credentials, one client's domain), and which Rule or craft already owns the concern |
| "that can be shared with downstream as well" | new | the record is core (`dyad/dmc/`), so it ships in the next core release and downstream reads the same record when it frames a hand-up. Its home is Rule-3 Intake, which gains one sentence naming it after `dmc:intake-shape` |
| "we'll communicate back down whatever we decide to implement here versus what's left for them" | new | the record's output is a **hand-down**: one line per requirement with its outcome and ground. The home drafts it and shows it to you first, and it reaches downstream only on your `Y` (every communication outside this system is shown to you first) |

**Ambiguous, with the reading taken:**
- **A1. Granularity.** Read: per requirement and per constraint of the hand-up, so one hand-up can split. The parts
  are the sender's own numbered items (R1–R9, C1–C5).
- **A2. Privacy as an input.** Read: a requirement whose data is another party's (C4's client mail and transcripts) can
  put the **mechanism** upstream but never the **data**. The record states that as a rule of its outcomes, not as a
  case-by-case judgement.
- **A3. Mechanical or inference.** Read: inference, judged by the home, with the outcome and ground stated per item.
  Each outcome's `dyad:effect` is declared: `asks` for "asked back", `shapes` for the rest, so a precedent may
  settle them later.
