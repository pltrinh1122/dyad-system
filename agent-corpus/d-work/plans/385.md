Nothing lands before #385's Done-`Y` (the Operator's invariant, #384: one execution review, merges ride
it), and four children cannot be *delivered* until another child has *landed*. V → C5, C7 → PR-B, #393,

the plan's own order, which assumed "lands" where the Rules give only "delivered".

### Two ways out
**(a) One parent per dependency layer** — the tranche-1 pattern again: L1 = {V, G, #392}, L2 = {C5, C7}
after L1 lands, L3 = {PR-B, #393, C6} after L2, each layer its own row and its own Done-`Y`. Three
execution reviews for one tranche, and every future program would need its layers counted in advance.
**(b) Stack within the tranche.** A child that needs a predecessor's *output* builds on the
predecessor's *branch*, not on `main`: C5's branch on V's (#449), C7's #448 rebased onto V's, PR-B
drafted on #448's, #393 on #448's, C6 on C5's. Every child is then deliverable now with an evidence
block on its own stacked head; one Done-`Y` names every head; the seats merge in stack order (base
first; the hosting retargets each child to `main` when its base lands — and where it does not, the seat
merges locally at the named head, as engineer did for #442, plan 378 attack 11). The add/add hazard
counsel hit on #441 is the known cost: a stacked PR is merged only after its base, never before, and
never rebased past a merged base without re-asking.

### The rule, for this tranche and for the Guide
*Within one mandate, a child that depends on another child's output stacks on that child's branch;
merge order is stack order; a head that moves is re-asked.* Stated in #385 here, and as one sentence in
the Operating Guide (#392's PR #451 or the next Guide child), so the next program does not plan "after
X lands" where it means "on X's branch".
