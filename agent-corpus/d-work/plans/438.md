## The problem as it stands
- Operate runs `dyad runbook run sessions health` at every reply (`workstation-corpus/runbooks/sessions.md`).
- The runner appends one event per run to `workstation-corpus/runbooks/events/sessions.jsonl`, as the sysadmin
  craft's `server-instances.md` property 7 requires ("every execution of a run-book command leaves an event"). The
  store is committed and append-only on `main`.
- An event is a workstation-zone path. Committing it today needs:
  - a PR, because the fence (`rows.py`) admits only ledger-only commits to `main`;
  - an `open` or `planned` row carrying a `Y plan`, because of the plan gate (`prs.py`);
  - the full suite at the pre-push gate, because Rule-12 property 2 runs it on any range outside `<instance>/d-work/`
    (about four minutes).
- #431 is `done`, so the plan gate refuses it. Operate holds the events uncommitted, and that dirty tree then blocks
  its own ledger pushes (the pre-push hook refuses a dirty tree, Rule-14 property 3).
- On a cloud kernel nearly every reading is identical by construction. Every other live seat reads `no harness
  session` and the seat's own reads `title differs (no title recorded)` (the run-book's Pass, #434). So most events
  record nothing new.

## What monitoring is, as a class
| | d-work (Rule-3) | monitoring |
|---|---|---|
| opened by | an Operator prompt or disposition | a cadence or a request, with no prompt |
| authorized by | a plan-`Y` naming a mutation | nothing to authorize: read-only (Rule-8 class) |
| changes | the repo or the host | nothing; it observes |
| output | a delivered change, Done-`Y` verified | a reading of current state, and at most a finding |
| ends | Done-`Y` | never; it is standing |

A standing row would be a d-work that never completes and whose plan-`Y` authorizes no mutation. That is the shape
Rule-3 is built to exclude: "terminates only when the Operator disposes `Y` to the Agent's counter-prompt of
completion". Monitoring's only write is its record. The question is whether that record is a decision (needs a
row), clerical (like the ledger), or unnecessary.

## Survivor
Monitoring is its own activity class, not d-work: read-only, standing, with no plan-`Y` because there is nothing to
authorize. Its record is an observation, which Rule-2 already treats as clerical in kind. Three parts:
1. **(c) Record only changes.** A read-only health command appends an event only when its reading's digest differs
   from the last event of that command. A heartbeat is not an event.
2. **(b) Events-only commits are clerical.** A range touching only `<host>/runbooks/events/` goes to `main` directly,
   as a ledger-only range does: no row, no plan gate, no suite. The events guard's append-only check and the fence
   judge it. One zone per commit stays.
3. **(e) as a finding.** Operate's run-book cadence becomes "at session start and on the program's request". That is
   operate's run-book text and needs no Rule.

The current reading is always on the board, computed on demand, as in (f). The committed record is the history of
changes, which audit grades.

## Rule-10
**Path.** Adopt (b)+(c). No standing row; monitoring is a clerical, append-only record of changes in reading.
**Counter.** (f) is cheaper and needs no Rule text. Audit's recurrence grading could instead come from operate filing
a finding when a mismatch persists, and widening the clerical class is a precedent: the next class asking for the
exemption will cite this one.
**Reconciliation.** (f) keeps nothing of the harness side, which no one can recompute. "Persists" needs a memory of
the earlier reading, which is exactly the record (f) drops, and operate's filed finding would be a row per finding: a
heavier record than an event. The precedent is bounded by the test Rule-2 already states, "records … never a
decision". An observation passes that test; anything that chooses does not. The counter's cost argument stands for a
reading no one grades, and the Rule sentence should say so: the exemption covers events of read-only commands only.
