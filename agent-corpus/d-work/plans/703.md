Definition of done (proposed; the plan-`Y` accepts it, since no intent question was asked):

- Each desk is a reference: to that system's `paired-units` preference at a commit, or to a provenance entry for a pairing no one system holds.
- A drift line appears for each system whose preference and ledger disagree, naming the preference as the one that stands.
- Nothing in the ledger pairs a unit or changes a route.
- Tests cover each case.

The `attention.py` change in detail:
- **`derive` (the sync side).** It reads this system's `paired-units` from its own preferences file at `HEAD`, through `dyadlib.preference`. Each named unit becomes one `paired` entry, `what: paired-units`, `ref: <preferences path>@<HEAD>`. A name no longer listed gets `unpaired` at the next sync.
- **`attention pair <system>/<unit> --ref <path>@<commit>` (new verb).** It records a pairing that no single system's preference can hold, `what: declared`. It refuses a `--ref` that does not resolve in the reader's checkout of the system the path belongs to. The ref is the provenance entry of the operator's words, so the entry references a record and asserts nothing of its own. It also refuses a `<system>` whose checkout holds a `paired-units` row: that system's preference is the authority, so the pairing goes there instead. `--drop` writes the `unpaired` entry.
- **`fold` (the display side).** The header gains `desks <n>`, the count of paired desks across systems, and `--full` lists them. One drift line appears per system whose preference, read from the reader's checkout of that system, differs from the ledger's `paired-units` entries: `drift: <system> paired-units names X, the ledger holds Y; the preference stands (the next sync of <system> corrects it)`. A system the reader cannot read gets no drift line and no judgement. Drift lines count against the seven-line bound before item lines, at most one line per system, plus a single `+n systems drift` overflow line.
- **No closing-line change.** Pairing is not a question, so `board.awaiting_line` is untouched.

The tests:
- the sync emits `paired` and `unpaired` from a fixture preference;
- `attention pair` refuses a ref that does not resolve, and refuses a system that holds its own `paired-units`;
- `--drop` writes `unpaired`;
- the drift line appears and names the preference as the one that stands;
- no drift line for a system with no checkout;
- the header counts desks;
- the seven-line bound holds with drift lines present;
- no entry holds a unit's text or a preference value beyond the unit name.

### Additions to `dyad/scripts/attention.py`

1. **A `registered` kind, written once per checkout.**
   - When sync runs in a checkout that names a clone and the store holds no `registered` entry for this (system, unit), it writes one entry: `kind: registered`, `unit` = `DYAD_SESSION`, `row: -`, `ref: <instance>/d-work/sessions/<unit>.md@<HEAD>`, `what: checkout`.
   - The ref points at the unit's presence file, so the entry is a reference to a record, as every other entry is.
   - It opens nothing and has no closer, so it is never in the open set. The aggregate desk's header counts registered units per system.
   - The home's own registration (program-59cec502, 2026-11-14 16:26 UTC) is the first such entry. The home's first sync after this lands writes it, ref'd at the commit the home names.
2. **History replay in place of deriving the present only.**
   - Sync reads this system's watermark: the newest commit any of this system's entries references (its `registered` entry's commit on the first run).
   - It walks `git log --reverse <watermark>..HEAD -- <instance>/d-work/board <instance>/d-work/rows` and derives the open set at each commit (board and row files read by `git show <c>:<path>`).
   - It appends the events that take the store's open set to each commit's state in turn, each `ref`'d `path@<c>` and named by that commit's committer time (`<stamp>` = the commit's UTC time).
   - A question asked and answered between two syncs is therefore an `asked` and an `answered`, not nothing. The first run backfills from the home's registration on, which recovers #704's backlog question and its answer and the openings of #704 and #705, as the home's falsification names.
   - The walk stops at `HEAD`, so its last state is the present. Every entry stays keyed by (system, row, what), so a second run appends nothing (idempotent).
3. **Cross-row and held questions.**
   - Derivation no longer skips the cross-row file (`_cos[-<operator>]`). Its `question` becomes `asked` with `row: _cos`, and its kind comes from `dmc:disposition-request`: the retirement form, the precedent question and the home's other asks.
   - A held entry (`phase: held`) whose `question` holds a `Y/N:` line is classed by the question's form, as an unphased entry is. A question asked by hand on a held entry is therefore recorded too.
   - The closing line is unchanged: it still reads this system's own questions from its board, and only other systems' from the ledger.
4. **The home warns when unregistered.**
   - `dyad session touch` and `dyad board resume`, run by the home (`sessions.is_leader`), print one line, `attention: this home's checkout names no central repository (git config dyad.attention.clone <path>); the operator's desks are not logged`, when no clone is named.
   - The line is a warning, never a refusal. A unit that is not the home prints nothing, since only the home was asked to log.

5. **Rule-2 names an attention-ledger write as not ratification** (the operator's prompt recorded on #703: "each attention logging doesn't require operator disposition because the registration action is the disposition that is carried forward ... falsify."; the home's falsification B1–B4, below).    > - Attention-ledger writes (`dyad attention sync`; Rule-3 Batch disposition): each entry references a record the
   >   system already holds, under a kind the code defines, and decides nothing, so no disposition is asked for it. A
   >   kind that would add content enters only by a plan-`Y`'d change, as every kind does. Registering a checkout with
   >   the operator's central repository is the unit's setup, which owes the log; it is not a disposition and carries
   >   none forward (#703).

   Its Provenance line names #703. Amendment #703 in Rule-2's record holds B1–B4 and the pairwise statements 2–3, 2–7 and 2–16. No code change follows from this item, because a write already asks nothing; item 4's warning is what makes the obligation checkable.
