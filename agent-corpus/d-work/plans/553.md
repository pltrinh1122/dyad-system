## The four decisions, with a recommendation each (the plan-Y accepts these unless amended)
1. **Capital Y in plan-Y / done-Y: keep it.** `Y` is the literal answer token, the same character the ledger records
   (`Y plan`, `Y done`) and the guards match. The standard's rule becomes: terms are lowercase, a literal answer token
   keeps its case, so `plan-Y` and `done-Y` (with `Done-Y` → `done-Y`). *Counter:* one more exception. *Reconciliation:*
   lowercasing it would make the term disagree with the 800+ ledger entries it names, which history keeps.
2. **operator / agent: lowercase in prose.** They are kinds of party, like `holder` and `unit`, and the standard
   lowercases terms. *Counter:* capitals marked the two parties as proper roles. *Reconciliation:* the vocabulary row is
   the marker, and capitals were applied inconsistently anyway (prose, Rules and guard messages differ).
3. **Kind by pairing: yes, a unit changes kind when paired or unpaired.** A unit's name and holder stay; `dyad` or
   `solo` is derived from attendance, which `pair`/`unpair` (today the `attended-seats` preference) declares, and the
   records check it (Rule-16). *Counter:* a question in flight could change route mid-row. *Reconciliation:* the board's
   `question` line records where it was asked, so a mid-row pairing reroutes only later questions.
4. **Uppercase files: keep them, as listed exceptions** in the standard. *Counter:* the standard says lowercase.
   *Reconciliation:* renaming 80 files and about 1,250 references, plus the `RULE-*` patterns in `rules.py`,
   `references.py` and the CI wrapper, changes mechanisms, which scope 2 excludes. The exception list is closed, so a
   new uppercase name fails the guard. A rename can be its own later d-work.
