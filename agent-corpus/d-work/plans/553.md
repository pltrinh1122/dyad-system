## The four decisions, with a recommendation each (the plan-Y accepts these unless amended)
1. **Capital Y in plan-Y / done-Y: keep it.** `Y` is the literal answer token, the same character the ledger records
   (`Y plan`, `Y done`) and the guards match. The standard's rule becomes: terms are lowercase, a literal answer token
   keeps its case, so `plan-Y` and `done-Y` (with `Done-Y` → `done-Y`). *Counter:* one more exception. *Reconciliation:*
   lowercasing it would make the term disagree with the 800+ ledger entries it names, which history keeps.
2. **operator / agent: lowercase in prose.** They are kinds of party, like `holder` and `unit`, and the standard
   lowercases terms. *Counter:* capitals marked the two parties as proper roles. *Reconciliation:* the vocabulary row is
   the marker, and capitals were applied inconsistently anyway (prose, Rules and guard messages differ).
3. **Kind by pairing: yes, a unit changes kind when paired or unpaired.** A unit's name and holder stay; `dyad` or
   `solo` is derived from attendance, which `pair`/`unpair` (today the `attended-seats` preference) declares, and the
   records check it (Rule-16). *Counter:* a question in flight could change route mid-row. *Reconciliation:* the board's
   `question` line records where it was asked, so a mid-row pairing reroutes only later questions.
4. **Uppercase files: keep them, as listed exceptions** in the standard. *Counter:* the standard says lowercase.
   *Reconciliation:* renaming 80 files and about 1,250 references, plus the `RULE-*` patterns in `rules.py`,
   `references.py` and the CI wrapper, changes mechanisms, which scope 2 excludes. The exception list is closed, so a
   new uppercase name fails the guard. A rename can be its own later d-work.

## Revision 2 (2026-11-02, on the Operator's prompt: the decision criteria for labeling, and when capitalization is critical, given that operators misspell, so precise case in operator prompts should be required only in rare conditions)

### The principle: the operator's text is read, the agent's text is written
Case and spelling matter only where a **machine compares a string literally**. The operator's prompts are read by the
agent, an inferring reader, so they never need precise case or spelling. The agent is the **normalizer**: it reads the
operator tolerantly and writes canonical forms into every place a machine reads. Provenance stays verbatim (Rule-7):
the operator's words are recorded as typed and never "corrected". The canonical reading lives in the agent's own text
(the plan's intent as read, the row, the board).

### Decision criteria for a label (the DMC record `dyad/dmc/label-case.jsonld`, inputs L1–L6)
| # | question | if yes |
|---|---|---|
| L1 | Does an outside system define the case (an environment variable, a Python identifier, a schema.org or JSON-LD key, a git hex sha)? | keep the outside system's case; it is listed in the standard's exceptions |
| L2 | Is it ledger grammar the agent writes (`Y plan`, `Y done`, `N amend`)? | exact case, written only by the agent's tooling, never typed by the operator |
| L3 | Is it an ecosystem file name (`README.md`, `LICENSE`, `CLAUDE.md`) or on the closed uppercase list (decision 4)? | keep, as a listed exception |
| L4 | Otherwise (files, keys, flags, unit names, tags, branches, terms) | canonical lowercase kebab-case; stored lowercase |
| L5 | Could two labels differ only by case? | forbidden: labels must be unique under casefold. A case-insensitive filesystem (macOS, the Operator's second workstation) would merge them |
| L6 | Is the label compared by a machine at a point where the operator types it directly, not through the agent? | the comparing tool casefolds the input and warns when it is not canonical, unless L1 makes case meaningful |

### When the operator's case or spelling actually matters (the rare conditions)
Only where the operator's own keystrokes reach a machine without the agent in between:
1. **Values the operator enters in a settings UI or file** (a preference value, a repository variable such as
   `RELEASE_APPROVAL`, a branch name typed in GitHub's editor). GitHub's expression comparison of strings already
   ignores case, so `Tap` works for the release gate. The preferences guard will casefold values and warn on a
   non-canonical one (L6).
2. **Credentials and secrets.** These are exact by nature, and never typed into a prompt.
3. **Commands the operator runs.** The agent delivers these as ops scripts (Rule-18), so the operator pastes them and
   never types them.
In every other place the operator writes — prompts, dispositions, quoted names — the agent normalizes:
- `Y`, `y` and `yes` are one answer, as are `N`, `n` and `no`;
- `Done-y`, `done-Y` and `done y` name one term;
- `Cos` and `COS` name the home.
A misspelling ("minimimum", "agian") is read as the nearest defined term when only one reading leads to the same act.
The agent asks only when two readings would lead to different acts (a blocking question, Rule-8's form), and never
about spelling alone.

| R1 | Tolerant reading lets an ambiguous prompt be "normalized" into the wrong act | **survives, procedure**: normalization is allowed only when every reading gives the same act. Otherwise the agent asks. The plan's intent-as-read line shows the operator the reading before the plan-`Y` |
| R2 | Normalizing a disposition (`yes` read as `Y`) is the agent putting words in the operator's mouth | **refuted**: provenance keeps `yes` verbatim, and the row records `Y`, the token the answer grammar defines (Rule-3). That is a reading, not an edit |
| R3 | Casefold-uniqueness (L5) breaks an existing pair of labels | **checked when built**: the guard reports any existing collision once, warning; none is known |
| R4 | Case-insensitive matching of terms in tooling could match the wrong thing (`Agent` vs `agent`) | **survives**: decision 2 lowercases them, so there is one form. Where case carries meaning (L1) the tool compares exactly |
