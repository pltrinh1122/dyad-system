## Revision 2 (2026-11-05): test timers first, to triangulate
The operator's prompt on this row: "test it by setting up test timers, e.g. to triangulate issues with GitHub actions
scheduling." Revision 1's fix (hourly with `--if-due`) is a guess until the scheduler's behaviour is measured, so the
plan measures first and fixes on the evidence.

**Step 1, the test timers (distribute, infra zone).** Two probe workflows, each read-only (`permissions: contents:
read`), no checkout, no commit, no inbox post: a job that prints `github.event.schedule` and exits. A probe run's
delay is its `created_at` minus the nominal slot of the cron that fired it, read from the API, so the probes write
nothing to `main` and add no noise to the ledger. Each file carries the same four timers, each testing one variable:
| timer | cron (UTC) | tests |
|---|---|---|
| T-15 | `*/15 * * * *` | frequent short slots: delay distribution and drop rate |
| T-07 | `7 * * * *` | hourly, early in the hour |
| T-37 | `37 * * * *` | hourly, mid-hour: whether minute of the hour matters |
| T-sweep | `17 14,2 * * *` | the sweep's own slots, beside its own runs |
- `dyad-probe-app.yml` lands as one PR merged by the home through the Claude GitHub App, the route #672 took.
- `dyad-probe-user.yml` is the identical file under another name, landed by the operator's own merge on GitHub.
Two registrations, one by the app and one by the operator, otherwise identical. If only the operator's probe fires,
the app-registration suspect holds. If both fire with the same delays, registration is ruled out and delivery is the
cause.

**Step 2, the reading (distribute).** After 24 hours, a table per timer and per probe: slots due, runs arrived, delay
percentiles (median, p90, max), drops, and the sweep's own schedule runs in the same window. Then a verdict naming the
cause, one of:
- (a) delivery, best-effort delays and drops;
- (b) registration by actor;
- (c) something else the data shows.

**Step 3, the fix, chosen by the verdict.**
- On (a): revision 1's hourly `--if-due` sweep, if the hourly timers show at most a few hours' worst delay. If the
  data shows long blanket outages, the reading says so, and an external trigger is put to the operator as a new plan.
- On (b): the sweep's schedule is re-registered by the operator's push, and Rule text states that a workflow file's
  last push must be a user's.
The fix's code and workflow PRs, revision 1's steps 2 and 3, are carried as written when (a) holds.

**Step 4.** The probe workflows are removed by one PR once the reading is in, merged by the home through the app.
H2 restarts from the first `schedule`-triggered clean sweep after the fix lands (revision 1's step 4). No hand
dispatch meanwhile.

**Definition of done, revised (proposed):**
- the 24-hour probe table with its verdict;
- the fix the verdict selects, landed;
- four consecutive 12-hour windows each with a `schedule`-triggered sweep and no hand dispatch;
- the probes removed;
- each PR's check clean.

Order: required. The probes run before the fix is chosen.
