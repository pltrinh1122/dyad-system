## Terms, so the attacks have targets
- **harness session**: what the kernel CLI calls a session — one transcript, one
  `CLAUDE_CODE_SESSION_ID` (here `59cec502-…`, one `.jsonl` under `~/.claude/projects/`), resumable,
  compactable, restartable (`CLAUDE_CODE_WORKER_EPOCH=5` in this very session: the worker process
  has restarted five times under one id). Subagents inherit the id (#285 rule 1).
- **dyad session / seat**: what Rule-16 calls a session — a presence file
  `<instance>/d-work/sessions/<id>.md`, `id` = `DYAD_SESSION` when set, else a fresh
  `unnamed-*` **per call** (`sessions.py:50-58`). `cos` and `cabinet` are roles a seat plays (#253 R28).

## Survivor
A `cos` or `cabinet` is a **seat**: a role name (`cos`, `ds-cabinet-term-1`) bound to one presence id,
held by one harness session at a time and by many over time, never verifiable by the dyad. The
registration record therefore names the seat, and records *beside it*, as the process reports them,
the harness session id and host (#294) of the current holder — "who holds the seat now", refreshed
at every touch, not "which session the seat is".

## Consequences for #293 and #294 (what changes)
- #293: the seat is `ds-cabinet-term-1`; the hand-carried prompt sets `DYAD_SESSION` to the seat name
  in *every* harness session that terminal runs (a shell profile line, not a one-off), so the seat's
  file survives restart and resume; the cabinet's row is opened once, by the first holder; later
  holders touch, never re-register. This cos's own seat is unnamed today — the same defect; plan
  revision 3 of #293 names it `cos` (`DYAD_SESSION=cos`), so the board has two named seats, not one
  name and one UUID.
- #294: the `host` line is "the current holder's host", and `touch()` also writes the harness session
  id when the kernel exposes one (`CLAUDE_CODE_SESSION_ID`, else absent) — one more optional line,
  `holder:` — so "who holds the seat now" is in the record. Its plan gains that line (revision 2).
