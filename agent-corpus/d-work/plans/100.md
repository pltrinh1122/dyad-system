### PR 2 — agent zone: the three contribution mechanisms + D1–D3's core side + one SEMVER
- **Zone contribution.** `crafts/<craft>/MANIFEST.md` gains an optional `instance-zone: <prefix>`
  line (`dyadlib.manifest`, already parses `key: value`). `dyad/guards/infra/containment.py`:
  `ZONES` becomes `ZONES + zones_contrib(pkg)`, the latter reading every installed craft's
  `MANIFEST.md` for `instance-zone:` and yielding `(craft, f"{prefix}-corpus/*")`; a prefix
  colliding with a core zone or another craft's fails (`craft/crafts`, not here — Boundaries).
- **Infra (World-dependency) contribution.** `crafts/<craft>/infrastructure_contrib.md`, same six
  cells as `INFRASTRUCTURE.md`, parsed by the same `parse_manifest`. `manifest.scan` gains
  `python_dirs` entries for every installed craft's tree (`dyadlib.craft_dirs`, not just `dyad/`)
  and `check_manifest` reads the core table's rows plus every contributed file's, concatenated,
  duplicate-component-name a fail naming which craft. Closes #51 structurally; the Anthropic API
  row itself is `automaton`'s own file to write, at workstation, once this ships.
- **Reference contribution.** `dyad/guards/agent/references.py`: a craft guard may export
  `REFERENCES_CONTRIB` (same 6-tuple shape as a `REFERENCES` row); `Corpus`'s reference list
  becomes `REFERENCES + [row for craft in installed for row in craft's REFERENCES_CONTRIB]`,
  discovered via `dyadlib.guard_files()`'s craft half. `CRAFT_ENTITIES` and the sysadmin-specific
  `GUARD_KINDS` special-casing in the register are retired in favor of the sysadmin guards
  declaring their own `REFERENCES_CONTRIB` rows (this PR moves `changelog.*`, `ops.*`, `event.*`
  out of the core file into `crafts/sysadmin/guards/*.py`, craft zone — see PR 4).
- **D1, the floor check.** `dyad/guards/craft/crafts.py`: for each `requires: dyad-operator>=X`,
  if `dyad-operator-vX` resolves locally (`git rev-parse -q --verify`), load that tag's
  `dyad/scripts/dyadlib.py` via `git show <tag>:dyad/scripts/dyadlib.py` into a scratch module
  (`dyadlib.load_module` on a temp file, or `exec` into a fresh namespace — no on-disk artifact)
  and evaluate the craft's own `INVARIANTS` (every guard and projector module) against it; a false
  invariant fails "floor dyad-operator>=X: <invariant> is false against X — raise the floor". No
  local tag → one skip line, the #91 pattern.
- **D2, one grammar.** `dyadlib.SEMVER = re.compile(r"\d+\.\d+\.\d+(\+[0-9A-Za-z.-]+)?")`; `crafts.py`,
  `package.check_rule_11`, `bundle.py` import it; `crafts.semver()` and any comparison strip the
  `+...` suffix before the tuple compare. `bundle.check`'s row-equals-VERSION test is unaffected
  (a `+local` `VERSION` simply never equals a clean bundle row, which is correct: it cannot be
  released from here).
- **D3, core side.** `package.projectors()` keys the registry `f"{craft}/{surface}"`;
  `PROJECTORS` follows; `cmd_project` resolves a bare `<surface>` when exactly one entry's suffix
  after `/` matches it, else lists the qualified candidates and exits 2 (mirrors
  `dyad check --list`'s `<group>/<entity>` resolution, no new pattern). `dyad project --list`
  prints the qualified key. `references.registry_modules` follows the new key shape.
- `dyad/VERSION` 0.7.0 → 0.8.0 (new mechanism surface in four guards + the runner).

- "PR 2 is too large — split the three contribution mechanisms into three PRs." Considered:
  refuted for now. All three are core/agent zone, share the discovery primitive
  (`dyadlib.craft_dirs`), and a reviewer reads them together faster than three times the PR
  ceremony for one theme; if any one needs its own iteration, it splits out then.
- "Moving sysadmin's `REFERENCES` rows out of the core file (PR 2/5) is scope creep beyond
  #101's survivor." Refuted: it is the survivor's own worked example — `references.md` p6 named
  exactly this move as the fitting design and it was never done (#155 debt, cited in the record).
  Leaving `CRAFT_ENTITIES`/`GUARD_KINDS` in place while adding a *parallel* contribution path for
  every craft but sysadmin would be the actual inconsistency.
- "The floor check (D1) needs no `git show` — read the tag's `dyad/VERSION` alone and compare
  against a hand-maintained 'feature added in version N' table." Refuted: that recreates D1's own
  bug (a second hand-maintained table to drift). Running the craft's own already-declared
  `INVARIANTS` against the floor tag's real code is the only check that can't drift from what the
  craft actually needs.
- "Disjunctive naming (D4) could hide a genuinely wrong path if two kinds both wrongly accept it."
  Survives, stated: true in principle; no installed craft's `naming_contrib.txt` demonstrates it,
  and the failure message still lists every pattern tried for a path neither accepts.
