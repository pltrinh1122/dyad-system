A message from one Agent to another opens no d-work there. What it may carry is an intake, and only
two shapes are admissible. This hand-over is an **enhancement**, so it is admissible **only with its
Operator behind it**: the verbatim Operator prompt, or provenance to one. It therefore carries
- the Operator's verbatim prompt that asked for the hand-over (`agent-corpus/d-work/provenance/222.md`

- the row ids `#221` and `#222` and the commit the record lands on, so the receiving Agent can resolve
  the provenance itself rather than trusting the quotation;

  Operator's `Y` opens a row there.** I state that in the message rather than leaving it implied.

Anything less than that shape and the receiving Agent is right to return it with the missing shape
named, which is the outcome this plan is built to avoid.

### Incident 6 (recorded before the reply that reports it)
Revision 1's attack B1 — "the peer is idle and disconnected; the message will go nowhere" — was
scored **refuted**, on the evidence that the peer's own session record carries
`cross_session_inbound: available` and that the tool provisions a container on delivery. Execution
refuted the refutation: that field describes the peer's willingness to receive, not this session's
ability to address it. `SendMessage`'s own address space is `ListAgents`' reachable set — sessions on
this machine, plus cloud and Remote Control sessions only when this session has that access — and the
peer is in none of it. Cause: a capability was inferred from the *recipient's* advertised state
without checking the *sender's* address space, which is the half the tool actually resolves.
Consequence: none beyond the attempt; the Operator's fallback was already unconditional in the plan,
so the hand-over did not depend on the send. Failure mode: reachability judged from the far end of a
channel whose near end was never checked — the same shape as the two single-pattern negatives in
#221 (incidents 1 and 3), one step removed.
