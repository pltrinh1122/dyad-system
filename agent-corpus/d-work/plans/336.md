## Revision 2 (2026-10-17, after the Operator's amend: "evaluate CLI-based query versus "SQL-like" syntax (e.g. `dyad work query {sql-like query}`)")

### The evaluation
Two shapes for the mechanical query over d-work records: **A, CLI flags** — a fixed verb (`dyad dwork board`)
with a fixed column set and a few filters; **B, a query language** — `dyad dwork query "<query>"` over the
records as tables. Criteria are the Rules', not taste.

| criterion | A: flags | B: query language | reads |
|---|---|---|---|
| Rule-13 import over author | nothing imported; ~60 lines authored per verb | a *custom* "SQL-like" dialect is authored code with a grammar to maintain — the worst case; **real SQL via the stdlib `sqlite3`** (3.45.1 under the kernel's Python 3.13.16; stdlib, so no manifest row — `imports.md` line 20) is imported, not authored | B, only as real SQLite |
| recurrence (Rule-13 p1) | every new question is a new verb or flag — the fourth board request already changed the columns (#298 → #324 → #327 → WHO as holder id) | one verb answers every question over the same tables; the board is a named view, not code | B |
| Rule-12 verifiability | a verb's output is tested by fixture | the **loader** (files → tables) is tested by fixture; SQL semantics are SQLite's, tested upstream; a saved view is one asserted query | B (less authored surface to test) |
| determinism (syseng) | reads only; no clock | the same: an in-memory DB built from the parsed files at the base commit, read-only (`?mode=ro` is moot in memory; no write statements are exposed — the connection runs one `SELECT`/`WITH` and refuses anything else) | tie |
| the entity model (sysarch `projection.md`: parsed data is the source) | the verb re-composes rows/plans/presence by hand | tables **are** the guards' parsers: `rows` (`dyadlib.read_rows`), `plans` (`plans.parse` + `PLAN_PARTS` as columns), `sessions` (`sessions.read_all`, with a junction `session_rows(session, row)` for the space-list and `holder`/`host` columns), `provenance` (entries), `traces`; a schema the Operator can print (`--schema`) | B |
| the Operator's cost | one line to type, no schema to know | SQL to type, schema to know — mitigated by named views (`board`, `unheld`, `stale`) and `--schema` | A for the first question, B for every later one |
| naming (syseng `naming.md`, `cli-pattern`) | `dyad dwork <verb>` — the existing noun | the Operator's example `dyad work query` introduces a second noun for the same entity; the noun stays **`dwork`**: `dyad dwork query "<sql>"`; `work` would be the first alias in the CLI | `dwork`, either way |
| #304 / #253 R19 (`cos/board` surface) | the verb is the text rendering | the HTML projector renders a view's result set; one composition, two renderings — and the bus's announcements become one more table when #303 lands | B |
| injection / safety | n/a | the DB is built from the repo's own files and holds no secret the files do not; provenance bodies are already credential-scanned (Rule-7); a query that is not a single read statement is refused before execution | tie |

**Verdict:** B, as real SQLite over tables built by the guards' parsers, never a bespoke "SQL-like" dialect;
with named views so the one-line board stays one line. A is kept only as that view's alias.

## Revision 3 (2026-10-17, after the Operator's second amend: "spin up a cloud cabinet session to take on expanded work of a persistent SQL-lite server/service to be used rather than for a single command")

### Intent as read
The Operator widens #336 and moves it: the query mechanism is to be a **persistent SQLite
server/service** — a running instance the seats query — rather than an in-memory database built for one
command, and the work goes to a cloud cabinet. Read as #302's shape (revision 2 there): the cos hands
the row over on the Operator's words; the cabinet holds #336, reads revisions 1–2 (the falsified claim,
the flags-versus-query evaluation, whose verdict for real SQLite over the guards' parsers stands), and
**plans the service itself in its own session** — this revision is the handover and the brief, not the
service design, because a persistent service is a Rule-19 server instance with host actions (Rule-8)
the cos cannot plan on the cabinet's behalf; the cabinet's plan-`Y` for the service is asked there.

### What the cos reads into the brief (state, not an order)
- **Rule-19**: a server instance needs a run-book at `workstation-corpus/runbooks/<instance>.md` with a
  health command, a supervisor named, events through `dyad runbook run` (the sysadmin craft's form); its
  deploying d-work is not Done until the health command passes as observed. **Rule-8**: every start, stop
  or install is a classed host action with a change-log row (workstation zone); a cloud container is
  ephemeral and is nobody's host — where the service *persists* is the first thing the cabinet's plan
  must say (the Operator's host, `workstation-corpus/`, is the one place with a run-book store; a
  cloud container can prototype but not persist).
- **Rule-14**: SQLite is stdlib for the client; a *server* (a process answering over a socket — SQLite
  has none of its own; candidates are a thin HTTP/JSON service around `sqlite3`, or a file-backed DB on
  a shared path with the loader as a daemon) is a library row in the manifest with license and
  replacement, and its World dependencies declared.
- **Rule-16 / `stores.md`**: the row, plan, provenance, presence and trace files on `main` stay
  canonical; the service is a **projection kept current** — rebuilt from the files on every push to
  `main` (or on demand), never written to by hand and never a source. Revision 2's R1 survivor holds
  for a persistent instance only if that is true; the cabinet's plan states the refresh trigger and the
  staleness signal (#253 R19's `seen`/`--asof` discipline).
- **Determinism / verifiability**: the loader, views and refusal of non-read statements are the same
  code whether in memory or persistent; the cabinet keeps the single-command path (`dyad dwork query`
  against the files) as the fallback that needs no service, so a seat with no network to the service
  still has the board.
- **Seats as clients**: cloud cabinets reach a host service only through what the hosting allows
  (network policy); term-1 reaches it locally. The cabinet's plan says which seats can query it and
  how the rest fall back.
- Zones: core code is agent zone; run-book, change-log and ops scripts are workstation zone; a manifest
  row is agent zone; one zone per PR (Rule-1) — the cabinet sequences its PRs.
