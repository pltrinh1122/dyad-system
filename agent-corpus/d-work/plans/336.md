## Revision 2 (2026-10-17, after the Operator's amend: "evaluate CLI-based query versus "SQL-like" syntax (e.g. `dyad work query {sql-like query}`)")

### The evaluation
Two shapes for the mechanical query over d-work records: **A, CLI flags** — a fixed verb (`dyad dwork board`)
with a fixed column set and a few filters; **B, a query language** — `dyad dwork query "<query>"` over the
records as tables. Criteria are the Rules', not taste.

| criterion | A: flags | B: query language | reads |
|---|---|---|---|
| Rule-13 import over author | nothing imported; ~60 lines authored per verb | a *custom* "SQL-like" dialect is authored code with a grammar to maintain — the worst case; **real SQL via the stdlib `sqlite3`** (3.45.1 under the kernel's Python 3.13.16; stdlib, so no manifest row — `imports.md` line 20) is imported, not authored | B, only as real SQLite |
| recurrence (Rule-13 p1) | every new question is a new verb or flag — the fourth board request already changed the columns (#298 → #324 → #327 → WHO as holder id) | one verb answers every question over the same tables; the board is a named view, not code | B |

### Intent as read

d-work queries over tables built by the guards' own parsers (revision 2's verdict stands) — such that:

### What was measured before designing (Rule-9: the premise, attacked first)
A scratch run over this instance at 8be32c4 parsed every store the service will load — 324 rows, 224
plans, 73 presence files, 311 provenance records (848 entries), 83 traces, 6 run-book events — in
**0.30 s**, and loaded them into an in-memory SQLite in **0.02 s**. The in-process query of revision 2
therefore costs a third of a second per command; a persistent service buys **no speed** that matters.
What it buys is stated in P1 below and nothing else is claimed for it. The Operator chose the service
knowing the single command existed (revision 3, S3); this revision keeps that choice and the honest price.

### Persistence host and process shape
- **Host:** the Operator's workstation. A cloud container is nobody's host (revision 3); this one
  prototypes and tests, deploys nothing that outlives it.
- **Instance name:** `dwork-query` (run-book `workstation-corpus/runbooks/dwork-query.md`; unit
  `dyad-dwork-query.service`; the noun stays `dwork`, revision 2 R3).
- **Process:** one Python process, kernel only — `dyad dwork serve` (`dyad/scripts/dwork_query.py`),
  a `http.server.ThreadingHTTPServer` over the stdlib `sqlite3`, bound to `127.0.0.1:8736` by default
  (`--bind` for a LAN address; never a public one). Endpoints: `GET /health` → `{"ok": true,
  "built_from": <40-hex sha of main>, "tables": n, "rows": n}`; `GET /schema`; `POST /query` with
  `{"sql": "..."}` → `{"columns": [...], "rows": [[...]], "built_from": sha}`; `POST /refresh`. No
  authentication: it serves a projection of a public repository on a loopback socket, and refuses
  every write (below), so there is nothing to protect that the repository does not already publish.
- **Supervisor (server-instances rule, property 1):** a systemd **user** unit
  `~/.config/systemd/user/dyad-dwork-query.service`, `Restart=always`, enabled, with
  `loginctl enable-linger` so it starts at boot without a login. The unit file is instance
  (`workstation-corpus/server/dwork-query/dyad-dwork-query.service`), written with systemd's `%h`
  specifier so no `/home/` string enters any tracked file (`package_rules.txt` forbids it in the
  package; the convention is kept in the instance too). Docker (already an operating row) is the
  replacement named in the manifest row; not chosen because the service is one stdlib process and an
  image would add a build, a registry pull and a second copy of the kernel's Python for nothing.
- **Where state lives (`Data`):** `~/.local/state/dyad/dwork-query/` — `dyad-system/` (the service's
  own clone of the repository, code checked out at a pinned ref, data fetched from `origin/main`) and
  `dwork.db` (the projection). All of it is generated: a fresh deployment needs nothing restored, it
  rebuilds from `main`. The repository is public (`visibility: public`, observed via the hosting's API
  2026-10-17), so the clone and every fetch need no credential — nothing of the Operator's `gh` login
  is read by the unit.

### The projection and its refresh (Rule-16, `stores.md`, R1 of revision 2 kept)
- **Build:** `dyad dwork build --db <path> --at <sha>` exports `<instance>/d-work/` and
  `<host>/runbooks/events/` from the clone at `origin/main`'s sha (`git archive <sha> <paths> | tar
  -x` into a temporary tree — never a working tree, so no seat's dirty checkout is ever the source),
  runs the existing parsers over it, writes a new SQLite file beside the old one and `os.replace`s it
  — atomic for every reader, which opens a connection per request. The `meta` table holds
  `built_from: <sha>` and `schema: <n>`; no clock, no timestamp enters the database
  (`determinism.md` property 3): two builds from one sha give one `iterdump()`, which the test asserts.
- **Refresh trigger:** the server's own loop — every `--refresh-every` seconds (default 300) it runs
  `git fetch origin main` in its clone, compares the sha to `built_from`, and rebuilds only on a
  change; `POST /refresh` (the run-book's `refresh` command) does the same at once. A push to `main`
  from any seat therefore reaches the service within one interval or on demand. No hook on the host
  checkout, no timer unit: one unit, one process, one run-book.
- **Staleness signal:** every response carries `built_from`; the client prints `asof <sha>` on every
  result and, when the sha differs from its own `origin/main`, one line `stale: service at <a>,
  origin/main at <b>`. The board renders `seen` verbatim (#253 R19) and takes `--asof <iso>` to flag
  a presence file older than the stale window; the service never reads the clock for it.
- **Never a source:** the database accepts no write from any client. Two fences: the SQL text must be
  one `SELECT`/`WITH` statement (the friendly refusal), and the connection is opened `mode=ro` with
  `set_authorizer` denying every action but `SQLITE_SELECT`, `SQLITE_READ` and `SQLITE_FUNCTION` (the
  mechanical one, SQLite's own). A client that wants to change a row edits the row file through
  `dyad dwork state` as today.

## Revision 6 (2026-10-17, after the Operator's amend on revision 5: "`ledgerd` - is the name but the design and architecture should contain adapters to git as the underlying store or any other store. In fact, the adapters should be generalized such that a ledger schema of any kind can use the `ledgerd` as long as it's been initialized with the schema of the ledger.")

*Base commit of `main` unchanged: 8be32c4 plus this d-work's own ledger commits. The name `ledgerd` is
disposed. Revisions 4 and 5 stand — host, supervisor, projection-never-a-source, the 60-second refresh,
the generated views, the read-only fences, the host actions, the two PRs — and this revision replaces
their *architecture*: one daemon, two seams.*

### Intent as read
`ledgerd` is not the d-work service; it is a daemon that keeps a queryable projection of **a ledger**
current, where a ledger is any store of records. Two seams make that true: a **store adapter** (git as the
first; any other store behind the same contract) answers "what is the latest pin, and give me the ledger's
files at it"; a **ledger schema** (the dyad's d-work ledger as the first; any other once written) answers
"what records those files hold, as tables and views". A `ledgerd` instance is **initialized with a schema
and a store** and serves that pair; the dyad-system instance is `dwork` over `git+https://github.com/
pltrinh1122/dyad-system.git`. "Ledger" here is the general sense; the vocabulary's own term (the d-work
row store) is the first schema, and no Rule text changes (G6 below).

### Architecture
```
   store adapter ──pin, tree(pin)──▶  ledgerd core  ──tables, views──▶  SQLite file + rendered views
   git | dir | <module>              build · refresh loop · fences · serve        /health /query /views/<v>
                                         ▲
                                   ledger schema
                               dwork | <module>  (STORES, TABLES, VIEWS, load(tree))
```
**Store adapter contract** (`ledgerd.STORE_CONTRACT`, the shape of `dyadlib.CONTRACT`): `SCHEME`;
`open(url, state) -> store`; `store.pin() -> str` — an opaque string that changes if and only if the
ledger's content changed (a commit sha for git, a content digest for a directory); `store.tree(pin,
paths) -> Path` — the named paths at that pin materialized under a temporary directory; `store.describe()`.
The daemon performs one operation on a pin: equality. Adapters shipped:
- **`git`** (`git+https://…`, `git+ssh://…`, `git+file:///…`, with `#<ref>`, default `main`): a bare clone
  under the instance's state directory, `git fetch` per tick, `pin` = `rev-parse <ref>`, `tree` = `git
  archive <sha> -- <paths> | tar -x`. Never a working tree (a seat's dirty checkout is not `main`).
- **`dir`** (`file:///…` or a bare path): a directory as it is on disk; `pin` = sha256 over the sorted
  relative paths and contents under the schema's `STORES`; `tree` = that directory itself. This is the

`{name: sql}`; `RENDERED` — the views rendered to files on every refresh; `load(tree) -> {table: rows}`;

instance's conf (G2). Shipped: **`dwork`** (`dyad/scripts/ledgerd_dwork.py`): revision 4's schema and

them where a guard already owns the parser (Rule-13, one parser per entity).
