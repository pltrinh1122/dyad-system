# Plan #23 — diagnose the inferred conflict; disambiguate the rules

Base commit of `main`: e56fffa. Refs #22 (where the conflict surfaced).
Falsification: inline below (Rule-9); no separate record proposed until a Rule text actually changes.

## Intent as read
In #22 I stopped and escalated, claiming a conflict between the harness's one-branch restriction
and the dyad's rule that a ledger-only commit goes directly to `main`. The Operator disposed the
push *and* asked me to diagnose that inferred conflict and disambiguate the rules. So: was it a
real conflict, where does it actually live, and what text — if any — should change so the next
session does not have to stop and ask.

## Finding 1 — inside the dyad's own rules there was no conflict, and no ambiguity
Three mechanisms agree, and interlock:
- Rule-2, *Not ratification*: "Ledger-only commits to `main` (touching nothing outside
  `agent-corpus/d-work/`) ... never a decision." The Agent may do it freely.
- Rule-3, *Ledger*: "Ledger-only commits ... are clerical and **go directly to `main`** without a
  PR." Not merely permitted — prescribed.
- `prs.py check_transaction`: returns `[]` when HEAD is `main`, and on any other branch reads the
  cited rows **at the base**. So the direct-to-main ledger push is not a convenience; it is what
  makes the plan gate satisfiable at all. A new d-work's row *cannot* reach `main` through a PR,
  because that PR is gated on the row already being there.
Verified live: the first attempt to push branch `claude/sysarch-backlog-filter-wat8mz` failed
`agent/prs [d-work]: #22 not in ledger`, and passed only after the ledger commit landed on `main`.
The rules were unambiguous. My escalation was not caused by them.

## Finding 2 — the conflict was between authority layers, and one Rule already names that pattern
The dyad's Rules bind the Agent's process *inside the corpus*. The harness instruction ("develop on
branch X; never push to a different branch without explicit permission") binds *this session's
runtime*. They are different layers, and the dyad already has a sentence for exactly this shape —
Rule-8, Boundaries: "The harness permission mode: an Operator-side fence outside the corpus, per
command; it neither replaces nor is replaced by this Rule."

That sentence is declared **only for host actions**. Nothing says it for repo transactions, which is
where I hit it. That is the real gap: the corpus tells the Agent how to reason about an
Operator-side fence over *the host* and says nothing about an Operator-side fence over *the repo*.

**Proposed disambiguation (a):** one Boundaries bullet in Rule-1, mirroring Rule-8's wording — a
session-level restriction on which branches may be pushed is an Operator-side fence outside the
corpus; it neither replaces nor is replaced by this Rule; where it forbids what a Rule prescribes,
the Agent does the corpus-legal part it can, states the rest, and asks. Rule-1 is the right owner:
it owns the repo transaction, and this is a fence over repo transactions.

## Finding 3 — the escalation was right anyway, for a reason that is not ambiguity
Even with the rules unambiguous, the harness text could be read either way: its four numbered items
are headed *Git Development Branch Requirements* and concern where **development work** goes, and a
clerical ledger push is arguably not development. "Arguably" is the point — I could not settle it
from the text, and the costs are asymmetric: guessing "allowed" wrongly writes to a published
branch; guessing "forbidden" wrongly costs one question. **Survivor:** asymmetric-cost escalation is
the decision procedure where corpus and out-of-corpus fence disagree, and it is conduct, not a Rule.
Nothing to encode. (Attack: "then the bullet in (a) is useless." Refuted — (a) tells the next
session *which layer it is in*, which is what I lacked; it does not promise an answer.)

## Finding 4 — a genuine ambiguity inside the corpus, found mechanically on the way
Rule-3, Ledger: "**PR bodies** cite `d-work #<id>` ... The phrase is a claim of work on that d-work,
not a mention — cross-reference other rows as plain `#<id>`."
`prs.py check_transaction`: "On a branch: **the commit messages** of base..head are the body."

The Rule binds a PR body. The guard binds every commit message in the range. Nothing in Rule-3 tells
the Agent that the claim/mention distinction governs commit messages too. Demonstrated, not
speculated: an incident sentence in a commit message reading "since d-work #6" failed the push with
`agent/prs [d-work]: #6 is done, not open`. The fix in #22 was to write plain `#6`.

**Proposed disambiguation (b):** extend that sentence in Rule-3 to name its real target — "PR bodies,
and on a branch the commit messages the guard reads as the body, cite `d-work #<id>`". One clause;
no mechanism change; the guard is already right and the Rule is what is under-specified.

## Finding 5 — Rule-1's enforcement is currently vacuous, and the Rule says nothing about that
Rule-1: "these hooks are the only *blocking* enforcement of Rule-1; CI only detects." On current
`main`, `dyad/hooks/pre-commit` execs `dyad/guards/infra/containment.py` by path and that file is
mode 100644 (since #6), so **every** commit fails `Permission denied`. I improvised: run
`containment.py staged` by hand, commit `--no-verify`, state both in the commit message. That
improvisation is unwritten, and the obvious alternative — chmod the file — would have silently
undone #6 on a file I do not own in this d-work.

**Proposed disambiguation (c):** one sentence in Rule-1's Enforcement — when a hook cannot execute,
the Agent runs the guard by hand, records the observed line and the bypass in the commit message,
and reports it as an incident; it never repairs the hook inside an unrelated d-work.
*Separately and not part of this d-work:* the broken exec bit is a one-line fix (the hook calls
`python3`, or the file keeps +x) and belongs to its own row.

- **"(a) imports a harness concept into the corpus, which Rule-11 says never to do."** Refuted,

- **"(b) is a style nit; the Agent should just know."** Refuted mechanically: I did not know, the
  guard failed, and one push cycle was lost. A rule whose text names the wrong artifact is a bug by

  #3 incident was a `--no-verify` *push* withdrawn before execution, with no compensating check. (c)

  output recorded, and only as a reported incident. If the Operator would rather the Agent stop and
  ask instead, that is the one-word change to make here and it needs no other edit.
