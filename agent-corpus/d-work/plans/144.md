# Plan #144 — which architecture fits a server model: event-driven work, human disposition of the unexpected

Base commit of `main`: 028906f. Builds on #142 and #143. Compared: dyad-system `028906f`,
dsys-repo `37fc52e`.

## Intent as read
Which of the two is more aligned with a **server model of operation**: most work starts from
**events**, not from a person prompting, and humans **oversee** it and **dispose** of the unexpected
events it raises?

## Mutation
None beyond the ledger (the #127 pattern): this row, this plan and provenance #144. Host actions:

## Answer
**dsys, by design.** dyad-system is misaligned by construction: its work opens only on a human
prompt. dsys's alignment is mostly specified and modelled, not running.

| server-model property | dsys-repo | dyad-system |
|---|---|---|
| **What starts work** | Events. Flow transitions fire on the closed trigger set `timer \| run_completed \| run_aborted \| external`. A wrapper (cron or script) owns the schedule and calls `dsys automaton advance`; the executor validates the trigger and mints the event. The updater is a worked release-monitor automaton (9 states, 16 transitions) | A person. "Every Operator prompt opens a d-work. There are no exemptions" (Rule-3). The Agent never originates work, and another agent's message is only an *intake* the Operator must accept. There is no scheduler or daemon actor: `RUN_ROLES` is `operator \| agent`, and the gap is on record as backlog #54, "no scheduled/daemon actor model across Rules 3/8/19" |
| **Routine work without humans** | Zero-inference execution of run-books and flows, append-only events, deterministic replay (built, but on fixtures only) | Every step passes through the inferring Agent inside a live chat session. Run-books are shell commands a person or the Agent chooses to run |
| **Detecting the unexpected** | Mechanical and total. I-14, flow totality: every non-end state must route every fate, or the definition is refused. An unhandled trigger aborts and emits a fixed-template `automaton-exception` Disclosure (flow id, run id, state, trigger, no prose) (`automaton-executor-spec.md` §7) | The Agent notices a departure while working and reports it as an *incident* (Rule-3) in its reply. Detection lasts only as long as a session is open, and nothing watches between sessions |
| **Getting it to a human** | Disclosures queue with a sequence number, in a verification view independent of any agent's presentation. The Chief-of-Staff "drain duty" triages them serially, kind-ordered, one proposal per disclosure. I-13 refuses to close a governance run with undisposed backlog, and flags an open queue with no governance run as a violation | The human is already present: the incident appears in the reply they are reading. No queue survives the session except the incident log and ledger rows |
| **Human disposition** | A typed `triage` mode (acknowledged / escalated / converted / dismissed), with every non-open disclosure cited by exactly one triage disposition (I-2). Standing policies (`set_standing`) pre-authorize recurring classes of events | `Y/N` counter-prompts, or a new d-work. There is no standing disposition for a class of events except preferences |
| **Stance on "server"** | The executor is explicitly "a step function, not a server". No daemon, no clock in the model, and the loop belongs to an outside wrapper. Server-*like* operation is the wrapper plus the executor, which keeps its trust boundary honest | The dyad itself is not a server. It *operates* servers (sysadmin craft: supervisor, run-book, health command), and the one server-shaped dyad craft seen, workstation's `automaton` ("a server performing instructions from other dyad systems"), lives outside this repo |

## Falsification
| # | attack | result |
|---|---|---|
| 1 | dyad-system's run-book runner and event log make it event-driven. | **Refuted.** Its "event" is a *record* of a command someone chose to run (`<runbooks>/events/*.jsonl`); nothing is *triggered* by one |
| 2 | dsys is event-driven in running code today. | **Refuted as "running".** The executor and the triggers are built and tested on fixtures. There are no production tools, no wrapper deployment, and no Harness. The CoS drain is a role prompt and validators; with `execute` refusing, no agent performs it (#142 A7) |
| 3 | dsys's human-in-the-loop is only for authoring, not for runtime exceptions. | **Refuted.** `automaton-exception` disclosures route to the DR-5 drain, and I-13 enforces that the queue is drained |
| 4 | dyad-system could become event-driven by configuration. | **Refuted.** It needs Rule changes: Rule-3 Scope (only an Operator prompt opens work) and the actor model of Rules 3, 8 and 19 (#54). Those are Operator-disposed amendments, not settings |
| 5 | The server model contradicts dsys's "no daemon". | **Survives, scoped.** dsys wants the always-on part *outside* the architecture (the wrapper) and verifiable steps *inside* it. That is a server model with a clean boundary, but the wrapper, delivery of disclosures to people and alerting are unbuilt and unspecified |

**Survivor:** dsys's architecture is shaped for event-driven operation with human disposition of
exceptions: triggers, flow totality, exception disclosures, a drain with a closure bar, a triage
mode and standing policies. Most of that is modelled and specified; the executor is built on
fixtures. dyad-system is shaped for prompt-driven, human-initiated work, and moving it to events
takes Rule changes.

## What remains for dsys to run as a server (observations)
1. The wrapper: a supervised scheduler or event intake calling `advance`, with the trigger payloads.
2. Delivery of disclosures to humans: notification, a triage surface, and the agent performing the
   CoS drain (needs an agent backend).
3. Production tools, installed run-books and the Harness module (#142 A7).
4. The budget meter from #143, so unattended event handling stays inside a budget.
