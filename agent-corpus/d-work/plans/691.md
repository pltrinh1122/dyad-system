- not-due: none holds, or the same condition set was already posted (one notice per state, folded like the sweep's other findings).
The sweep posts `audit due: A1, A3 …` to the home's inbox once per changed state; the home asks the question; nothing runs on a clock.

## Plan revision 2 (A4's timing)

Found answering the operator's question "explain how the audit trigger will be triggered unless we have a recurring scheduled sweep for audit condition?". A1, A2 and A3 read what only a merge changes (the code tree, `agent-corpus/audits/INCIDENTS.md`, `dyad/rules/`), and the full sweep that computes `audit due` runs after every landed merge (`dyad-sweep.yml`: a code push to main, or the automaton's dispatch when its run landed a merge), so no clock is needed for them. A4 is the exception: a release tag is published by the `released` workflow from a ledger push (the `Y release` line), which starts no full sweep, so A4 would wait for the next merge; and revision 1 says A4 rides "that release's own Done reply", which comes before the tag exists.

Change: A4 is read by the home, not the sweep — at the moment the home lands a `Y release` line, the audit-due state is recomputed from the newest sweep report plus that tag, and presented in the reply that reports the release published (the release's own report, not its Done). The record's A4 outcome names that moment; the sweep's `audit due` line covers A1–A3. No other change.
