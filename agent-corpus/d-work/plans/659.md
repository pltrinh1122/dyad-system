## Mutation
1. **`dyad/guards/agent/board.py`, the stored sets.**
   - `PHASE_SUBKEYS` gains `retires` and `releases`, each single-valued and comma-separated (`retires: 640, 641`,
     `releases: dyad-operator-v1.2.1, v1.2.1`). `PAIR_KEYS` gains `retires=` and `releases=`.
   - `parse_advance` admits the two as optional pairs on `asked --expect done-ready` alone (a new `ASK_OPTIONAL`, beside
     each event's required fields). Every other event refuses them, as it refuses any pair it does not take.
   - Before any fetch or write, the pairs are refused if:
     - a `retires` value is not `#<n>[,#<n>…]` or `<n>[,<n>…]`, or names a row twice;
     - a `releases` value is not a list of tags in a release-tag shape (`vX.Y.Z` or `<craft>-vX.Y.Z`, the forms of
       Rule-11 property 4 and 7), or names a tag twice.
   - In the builder, on the tree it writes, a retired row must exist, must be `backlog` or `done`, and must not be the
     row itself or another named row. These are the refusals `dwork state` already makes (#574 G2), said at the ask, so
     a question naming an unarchivable row is never asked.
   - The `asked` builder stores both sets in the entry's phase (`done-asked`), so `answered-Y` and `board draft` read
     what was asked, never a re-parse of the question.
2. **`question("done", …)`**: the clauses in Rule-3's and Rule-11's order, each only when non-empty:
   - one row: `Y/N: Done with #<id> <title> (accreted #c, retires #r, merges PR #a, releases <tag>)?`;
   - batch: `… #a <ta> (accreted #c, retires #r), #b <tb> (…) (merges PR #w, #x, releases <tag>)?`. Each row's
     `accreted` and `retires` go in its own clause; the `merges` and `releases` unions go last (A2).
   - `releases` is composed under `merge-disposition: with-done` as `merges` is. A release names no PR of its own;
     under `separate` the existing refusal stands.
3. **`ledger_lines` (`answered-Y`)**: each row's `Y done (…)` entry carries its retired rows and the release union:
   `Y done (accreted #c, retires #r, merges PR #a at <head>, releases <tag>)`. This is the entry form `release.py`
   already reads (`releases …` after the merges clause) and `dwork state`'s retires check reads. The drift check
   (`q != question(...)`) now also covers `retires` and `releases`, since `question` reads them from the phase. The
   close's archiving of retired rows is unchanged: `close_landed` and the no-PR `done` path already archive what the
   entry names.
4. **`board draft <id>`**: the Question section shows the full form. A `retires` or `releases` slot comment tells the
   agent to pass them at `asked`. The draft takes no new flags.
5. **Tests**, `dyad/tests/guards/agent/test_board.py`:
   - `question` with `retires`, with `releases`, with both, and in the batch form, each against the exact string;
   - `asked` stores the sets and refuses, before any write:
     - a bad `retires` (shape, an `open` row, the row itself);
     - a bad `releases` tag;
     - either pair on any other event;
   - `answered-Y` writes `Y done (… retires #r, merges PR #a at <h>, releases <tag>)`, and the rows guard and
     `release.py`'s reader both accept it;
   - a phase holding `retires` survives `head-moved` and `withdrawn` (the sets stay; the question is withdrawn, as
     today).
   `dyad/tests/test_replays.py` gains no case; its replays hold no retires or releases.
