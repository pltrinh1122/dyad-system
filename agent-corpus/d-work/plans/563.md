## Measured (one full suite run under a profiler, 4 cores, at #561; then the base)
- **Totals.** Suite wall time is 208 s. Summed test time is 738 s; the 252 test children sum to 772 s.
- **The critical path.** The runner gives each test class its own child.
  - `test_package.PackageTests` is one child of **203.5 s**, which is the whole suite's wall time.
  - The other cores finish their share sooner (772 s / 4 cores is about 193 s).
  - Wall time is about max(the largest class, total / cores). Shrinking either one alone barely moves it.
- **CLI children: 780 processes, 1,183 s of wall time summed.**
  - Each start costs about **0.34 s** (`dyad dwork` usage takes 342 ms; bare Python takes 30 ms).
  - About **0.21 s** of that is `package.py` building the guard registry at import (`CHECKS.update(…registry())`,
    line 885). It loads and compiles all 30 guards from source on every CLI call, even a `dwork` call that runs no
    check.
  - The compile itself is 0.12 s. It is deliberate (#185: no bytecode, so a check never reports on code that isn't on
    disk), and this plan keeps it.
- **`git update-index`: 9,039 calls, 87 s summed.** These are not the tests' own calls. `distribute.install` calls
  `git update-index --add --chmod=±x -- <one path>` once per file written into a work tree (`distribute.py` 221), about
  445 calls per scratch install. Every scratch install of every test pays that.
- **One `check` child takes about 11 s without the suite.** `check --guards` takes about 15 s.
  - In that check, `agent/merges` state takes about 3 s in process (6.6 s under cProfile).
  - Of that, 4.4 s goes to `rows_at`, which re-reads the whole row store at every merge it judges: 37 merges, 337
    git subprocesses.
  - That cost grows with `main`'s history.
- **Duplicated runs.**
  - `test_evidence_block_shape_and_hash` (39 s) and `test_check_runs_and_reports_rules_and_guards` (19 s) run
    `check --evidence` and `check` separately in clones of the same tree.
  - `EvidenceAtTests.test_e_brief…` (19 s) re-runs the full `--at` block that `test_a_head_other…` (13.6 s) already
    ran on the same revision.
- **Copies: the 176 s I reported at #561 is overcounted.** My wrapper counted recursive `copytree` calls inside each
  other: 29,447 calls. The real figure is unmeasured. Nothing here acts on it.

## Candidates and their falsification
| # | candidate | attack | result |
|---|---|---|---|
| C1 | **Batch the install's index writes.** One `git update-index --add --chmod=+x` call and one `--chmod=-x` call over all the written paths (chunked under the argument limit), in place of one call per file | Does coverage drop? Is the index state different? The old per-file call ignored its exit code, so is failure handling changed? | **Survives.** The resulting index is identical (the same paths and modes), and the install's mode tests pin it. Failure handling is unchanged: the batched call ignores its exit code exactly as the per-file one did. It speeds every real `dyad install` too. |
| C2 | **Build the guard registry lazily.** `CHECKS` is built on the first call that needs it (`check`, `check --list`, `--guards`, `--evidence`, the invariant pass), not at import | #185: does it reintroduce bytecode? Does any import-time path need `CHECKS`? | **Survives, scoped.** No bytecode change: guards still load through `dyadlib.load_module`. Which import-time readers of `CHECKS` exist is checked in the PR. Each one becomes a call to the builder; a reader that must stay at import keeps the eager build and is reported. No test changes what it asserts. |
| C3 | **Share identical runs.** One `check --evidence` in a hermetic clone per test module, read by the evidence-shape test and the check-report test. One full `--at` block per `EvidenceAtTests` class, read by the brief test | Is test isolation lost? Do side-effect assertions disappear? | **Survives, scoped.** The shared run is made once in `setUpClass` or `setUpModule`, and its output is read only, never mutated. A test that asserts a side effect of its own run keeps its own run: the stored file, the untouched checkout, the worktree removed. Every assertion is unchanged. |
| C4 | **Judge each merge only on the rows its entry names.** `agent/merges` reads only the rows a judged merge's `Y done` names, with one `git cat-file --batch` over the commits judged, not the whole store per merge | Does a verdict change? | **Survives.** The judgement reads the same rows' same lines. The guard's own tests (`dyad/tests/guards/agent/test_merges.py`) pin every verdict, and one is added: the guard's subprocess count stays constant as merges grow. Every push saves the same time, and the saving grows with history. |
| C5 | **Split `PackageTests` (146 tests, 203.5 s, one child) into several classes by theme, in the same file** | The Rule-12 mapping. Shared fixtures. | **Survives.** The mapping is module to test file (`syseng/tests`). The tests stay in `dyad/tests/test_package.py`, the same root, so nothing moves between roots. A `setUpClass` fixture shared today is duplicated per new class only where measured as cheap, else the classes are grouped by fixture. Without C5, C1–C4 cannot lower the wall time, because this one child would remain the critical path. |
| R1 | Hardlink or reflink scratch-install copies in place of `copytree` | Tests write into their copies | **Refused.** A shared inode makes one test's write corrupt another's copy, which is lost isolation and so lost coverage. The cost is also unmeasured (the overcount above). |
| R2 | Turn the CLI's end-to-end tests into in-process calls | They test the entrypoint path (`bin/dyad`, `dyad-python`, argv) | **Refused.** That drops the entrypoint coverage the operator's rule protects. C2 makes each start cheaper instead. |
| R3 | More parallel test jobs | `SUITE_JOBS` already equals the core count, and the summed time already saturates 4 cores | **Refuted.** It gains nothing without C5, and nothing beyond the core count with it. |
| A1 | Presence overlap with #562 (PR #628 touches `package.py`) | Shared file | **Confirmed, priced.** This PR is built after #628 lands (the relay's order) and rebased onto it. Nothing here touches the memo code #628 changes. |

  C5). If a verdict changes, the cause is harder to isolate, and C2 touches the module every check runs through.
