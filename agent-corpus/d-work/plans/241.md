## Mutation proposed
Four stages. Each PR is one zone (Rule-1); stage 2 branches from `main` only after stage 1 has
merged, because #228's patch touches `package.py` too.

**Stage 1 — clear the install blocker (d-work #228, already authorized; not re-authorized here).**
1. Apply the test half of the banked patch first and run it: it must fail. If it passes, the
   diagnosis is wrong and #228 stops for a fresh `Y` (its own plan step 3 says so).
2. Apply the fix half; the test must pass. Append the nine `INCIDENTS.md` rows per the restore note.
3. `dyad check --evidence` on the head; one agent-zone PR citing `d-work #228`; its own Done-`Y`
   merges it (`merge-disposition: with-done`).
4. After the merge, read `rule-11 package` on `main` as observed. Green is the condition for stage 4.
   Red stops the sequence and re-plans — no tag is cut against a red install check.

**Stage 2 — the corrections owed (#241, two PRs, two zones).**
5. Agent zone: `dyad/VERSION` 0.10.1 → **0.11.0** (#231 B2: a new guard, amendments to Rules 1, 3, 7,
   11, 12 and 14 and changes to the one distribution code path are minor-level change wearing a patch
   label), and in the same PR the `cmd_bundle` fix — split `check_bundle`'s messages on the `warning:`
   prefix exactly as the runner does, so warnings print as `warn` and neither `check` nor `build`
   refuses on them — with its own test under `dyad/tests/` (Rule-12 property 1), failing before and
   passing after.
6. Craft zone: `crafts/syseng/VERSION` 0.4.0 → **0.5.0** (#231 B2: `0.4.0` predates the invariant
   protocol it now carries).

**Stage 3 — the bundle manifest (#241, one infra-zone PR).**
7. `BUNDLE.md`: rows `dyad-operator 0.11.0` and `syseng 0.5.0`; `version: 0.12.1` → **0.13.0** (two
   component minors; `0.12.1` itself was never tagged). The guard warns between stages 2 and 3 and is
   green after (Rule-11 property 7, #230 amendment) — the ordering #170 names, legal in this
   direction because neither new version is tagged yet.
8. `dyad check --evidence` on the final head; #241's Done-`Y` merges the three PRs of stages 2–3.

**Stage 4 — the Release itself (each tag the Operator's own disposition).**
9. `dyad bundle build <scratch>` on the merged head: four archives — `dyad-0.11.0.tar.gz`,
   `sysarch-0.3.0.tar.gz`, `syseng-0.5.0.tar.gz`, `sysadmin-0.2.1.tar.gz` — plus `BUNDLE.sha256`,
   generated files, never tracked. The one distribution code path once per row, no second mechanism.
10. Five tags on that head, in the forced order, each on its own `Y/N: release <tag>?` unless the
    Operator takes Rule-11's release-batch form: `dyad-operator-v0.11.0`, then `sysarch-v0.3.0`,
    `syseng-v0.5.0`, `sysadmin-v0.2.1`, then the bundle's `v0.13.0`.
11. Publish each tag's archive as its GitHub Release, as past component tags were, and the bundle's
    release carrying `BUNDLE.sha256` — clerical execution of each release `Y` (Rule-11: "creating and
    pushing the tag, exporting the archive, publishing any artifact it names").
