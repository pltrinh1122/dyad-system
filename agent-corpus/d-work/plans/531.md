# Plan #531 — cabinet across several workstations: a cos per Operator, a desk per workstation (falsified)

Base commit of main: (main at opening)

## Intent as read
The Operator works across a Linux workstation and a MacBook, and asks:
- whether the cabinet should run several cos, or keep one cos on one workstation with a new subordinate seat;
- that the organization support multi-workstation work for one Operator as well as for several;
- for decision criteria to choose between the options.

## Facts the evaluation rests on
- The cos (`program-59cec502`) is a cloud session. It is bound to no machine, and the Operator reaches it from either
  workstation through the Claude app.
- What is bound to a machine: host actions (Rule-8), local files and credentials, terminal-only tools, and the change log
  of that host (`workstation-corpus/`). A cloud session reaches a machine only through Remote Control, one computer per
  session (`request_computer_folder`). A terminal session runs on its machine and cannot receive `send_message`.
- Presence already records `host` (kernel, OS, arch) and `holder` for every seat (Rule-16). The naming form already has a
  member-leader form for a second Operator, `program-<operator>-<hp>` (`crafts/cabinet/rules/naming.md` §1). The
  precondition is one set of ledgers on one `main` (`organization.md` §2).

## Options
- **A. One cos per workstation**, peers.
- **B. One cos on one workstation**, plus a subordinate "workstation cos" on the other.
- **C. One cos per Operator, bound to no machine (cloud), plus one desk per workstation**: `operate-<host>-<hp>`, a desk
  on the operate secretary's board. It holds that host's rows and runs its host actions, as a terminal session there or a
  cloud session attached to it by Remote Control.
- **D. Several Operators**: C for each Operator, the Operators' leaders as `program-<operator>-<hp>` under one cos —
  the extension of C, not an alternative to it.

## Decision criteria (proposed as DMC record `crafts/cabinet/dmc/seat-topology.jsonld`)

**Selection rule:**
1. K1, K2, K6 and K7 are gates: an option failing any one of them is out.
2. Among the survivors, K3 and K4 decide.
3. K9 breaks a tie.

Under this rule A and B are out (K1/K2/K7 and K7, respectively), and C is selected.

**The principle:** a cos belongs to an Operator's attention, never to a machine. A workstation is a place where acts run,
so it gets a desk.

## Revision 2 (2026-10-30, on the Operator's amend: "N: did we miss a permutation, a D or E?")
Revision 1 is kept above. Its option list varied the number and placement of the cos, and the subordinate seat's shape
only within the function-first tree, so it missed four permutations.

The space has four axes:
1. how many cos;
2. where the cos runs (bound to no machine, on a fixed workstation, following the Operator);
3. how a workstation enters the tree (as a desk under a function, as a secretary of its own, as a seat that attaches per
   act, or as a separate system);
4. how long a workstation seat lives (standing, or opened per act).

Revision 1's D, several Operators, is not a permutation of these: it is C's extension, and it is kept as such.

Four options are added:
- **E. Host-first secretaries.** One cos, plus one *secretary per workstation* (`mac-<hp>`, `linux-<hp>`), each with its
  own desks per function on that machine. The tree is grouped by place, where C groups it by function.
- **F. Roaming seats.** One cos, no standing workstation seat. Whatever seat an act needs attaches to the machine by
  Remote Control for that act.
- **G. A cos that follows the Operator.** One cos, re-seated onto whichever workstation the Operator is at, as a terminal
  session there.
- **H. A system per workstation.** Each machine runs its own dyad system with its own ledgers, linked by intake (Rule-3).

## Revision 3 (2026-10-30, on the Operator's prompt: G as the destination — "the `cos` follows me everywhere so it's not a stand-alone session but perhaps a 'mode'")
Revision 2's G was scored as a *session* moved between machines, and it failed K7 and K3 for that reason. The Operator's
G is different: a *mode*. Restated, so it can be falsified:

### G, fleshed out: the cos as a mode
- **Any session can be the cos.** The cos is a role, not a session: whichever session the Operator is talking to (cloud,
  phone, Mac terminal, Linux terminal) takes the cos mode and becomes the cos for as long as it holds it.
- **Continuity lives in the corpus, never in a chat.** Everything a cos knows must be readable from `main`: the board, the
  pending queue, every question in flight and whose it is, every relay and its answer, every seat and its state. A fresh
  session that takes the mode reconstructs the cos exactly, with nothing told to it. Today part of this state is
  conversational: the pending queue (Rule-3 says so), in-flight `send_message` relays, and the cos's own context. That is
  the gap.
- **One holder at a time.** The mode is a seat, `program` (`program-<operator>` with several Operators), held by one
  harness session at a time. Taking it is an explicit act (`dyad cos take`) that records the new holder and makes the old
  one yield. A second live holder is warned on (K2). This uses Rule-16's seat and holder exactly: "held by one harness
  session at a time and by many over time".
- **Seats reach the mode, not a session.** A seat addresses the cos through the store, an inbox on `main`, which the
  holder reads every turn. So a terminal holder, which receives no `send_message`, is reachable, and a hand-off loses
  nothing in transit.
- **The mode's acts are unchanged.** Receive, route, present, relay back, board (Guide §2). Host actions stay with the
  host desks (C′). When the mode sits on the Mac, it can open a Mac desk locally, but it does not become one.
- **Authority unchanged.** The Operator disposes wherever the mode is. Provenance records the words with the session that
  received them.

Re-scored as a mode: K1 ✓ (one board, derived from the corpus); K2 ✓ (lease); K3 ✓ (the cos is wherever the Operator is,
and the corpus is the continuity); K4 ✓ (via C′ desks); K5 ✓ (a store inbox); K6 ✓; K7 ✓ (a mode per Operator); K8 ✓;
K9 high, paid in phases; K10 ✓. **G-as-mode passes every gate.** Its cost is the roadmap.

Ordering rationale:
- P1 comes before everything, because without the state in the corpus, a hand-off loses the cos.
- P2 comes before P3, because a lease is useless if seats can only reach a session id.
- P4 is packaging, and is cheap once P1–P3 hold.
Each phase is useful alone: P1 alone makes the current cos crash-safe, and P2 alone gives terminal desks (C′) a way to
hear the cos.

Risks, stated:
- **Rule-3 calls the pending queue "conversational, not a corpus file".** P1 changes that, which is a Rule-3 amendment
  (counsel, with a falsification record).
- **Two holders during a take race.** The lease is advisory as presence is (Rule-16). The guard warns. It is never a lock,
  because git push order is the only arbiter this kernel has.
- **The harness may never let a terminal session be addressed.** P2 removes the need.
