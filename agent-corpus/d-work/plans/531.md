# Plan #531 — cabinet across several workstations: a cos per Operator, a desk per workstation (falsified)

Base commit of main: (main at opening)

## Intent as read
The Operator works across a Linux workstation and a MacBook, and asks:
- whether the cabinet should run several cos, or keep one cos on one workstation with a new subordinate seat;
- that the organization support multi-workstation work for one Operator as well as for several;
- for decision criteria to choose between the options.

## Facts the evaluation rests on
- The cos (`program-59cec502`) is a cloud session. It is bound to no machine, and the Operator reaches it from either
  workstation through the Claude app.
- What is bound to a machine: host actions (Rule-8), local files and credentials, terminal-only tools, and the change log
  of that host (`workstation-corpus/`). A cloud session reaches a machine only through Remote Control, one computer per
  session (`request_computer_folder`). A terminal session runs on its machine and cannot receive `send_message`.
- Presence already records `host` (kernel, OS, arch) and `holder` for every seat (Rule-16). The naming form already has a
  member-leader form for a second Operator, `program-<operator>-<hp>` (`crafts/cabinet/rules/naming.md` §1). The
  precondition is one set of ledgers on one `main` (`organization.md` §2).

## Options
- **A. One cos per workstation**, peers.
- **B. One cos on one workstation**, plus a subordinate "workstation cos" on the other.
- **C. One cos per Operator, bound to no machine (cloud), plus one desk per workstation**: `operate-<host>-<hp>`, a desk
  on the operate secretary's board. It holds that host's rows and runs its host actions, as a terminal session there or a
  cloud session attached to it by Remote Control.
- **D. Several Operators**: C for each Operator, the Operators' leaders as `program-<operator>-<hp>` under one cos —
  the extension of C, not an alternative to it.

## Decision criteria (proposed as DMC record `crafts/cabinet/dmc/seat-topology.jsonld`)
| # | criterion | test | A | B | C |
|---|---|---|---|---|---|
| K1 | one board | the Operator reads exactly one roll-up per Operator | fails (two boards; the Operator integrates them) | passes | passes |
| K2 | one relay, one merger per question | no question or merge can be asked or executed by two seats | fails (two cos can both relay, both merge, race on `main`) | passes | passes |
| K3 | availability | the cos survives either workstation being asleep or offline | partial | fails (the cos dies with its machine) | passes |
| K4 | locality | every machine-bound act has a seat on that machine | passes | passes on one machine only, unless the subordinate is a cos | passes (a desk per host) |
| K5 | reach | the cos can reach every seat, and a seat that cannot receive messages reports through the ledgers | n/a | partial | passes (cloud↔cloud by message; terminal desks by row, presence and events on `main`) |
| K6 | the same ledgers | every seat pushes to the one `main` (§2) | passes | passes | passes |
| K7 | generalizes to N Operators | the single-Operator case is unchanged when a second Operator arrives | fails (a cos per machine × per Operator) | fails (the cos's machine is one Operator's) | passes (D: a leader per Operator, a desk per workstation) |
| K8 | span | the Operator's attended seats and the leader's seven lines are unchanged | fails (two attended leaders) | passes | passes (desks are unattended unless `attended-seats` names one, so they never count against span) |
| K9 | cost | new terms, guards, a Rule change | high | medium (a second kind of cos) | low (a topic on an existing function, a guide section, one advisory check) |

**Selection rule:**
1. K1, K2, K6 and K7 are gates: an option failing any one of them is out.
2. Among the survivors, K3 and K4 decide.
3. K9 breaks a tie.

Under this rule A and B are out (K1/K2/K7 and K7, respectively), and C is selected.

**The principle:** a cos belongs to an Operator's attention, never to a machine. A workstation is a place where acts run,
so it gets a desk.

## Falsification
| # | attack | result |
|---|---|---|
| 1 | The cloud cos cannot touch a workstation's files | **survives, scoped**: it never needs to (§1, the five acts), and the host desk does |
| 2 | A terminal desk cannot receive messages, so the cos cannot route to it | **survives, procedure**: routing goes through the ledgers. The desk reads its rows and presence at start and on each prompt, and reports by row state and events on `main` (§2's precondition already says this). A cloud desk attached by Remote Control receives messages |
| 3 | The Operator sitting at the MacBook wants to talk to the Mac seat directly | **survives**: `attended-seats` names that desk while the Operator is there, as communicate is today. The cos still holds the board |
| 4 | Two checkouts on two machines collide | **refuted**: each workstation has its own clone (a different `root`, Rule-16), and both push to one `main` through the fence. The id allocator's contiguity fence (#560) rejects a true collision |
| 5 | A second cos is needed when the cloud is down | **conceded, scoped**: the leader may be re-seated on a workstation by its own row (a seat re-homed, `organization.md` §1). That is a re-seating, never a second cos. The cabinet `seat` guard warns on two live `program` seats of one Operator |
| 6 | Host facts per workstation | **procedure**: each host's facts and change log are in the host corpus under its own name (operate's charter). The sysadmin craft's per-host files are out of scope here |
