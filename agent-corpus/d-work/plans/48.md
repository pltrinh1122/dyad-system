## Falsification
**Claim: "dyad/tests contains a corpus-level flaky test."**
- Attack: two kills at two unrelated stall points (`test_evidence_block_deterministic`,
  `test_check_runs_and_reports_rules_and_guards`) — if one specific test were broken, both kills
  landing on *different, unrelated* tests would be a strange coincidence; an external OS-level
  kill striking whatever happens to be running at that instant explains both trivially. Result:
  refutes "one broken test"; supports "external interruption."
- Attack: run 1 (2 fail) and run 2 (0 fail) are the *identical command against the identical,
  unchanging tree*, seconds apart — no corpus change between them. A deterministic corpus-level
  bug cannot produce this; transient resource contention (a subprocess timing out or scheduling
  oddly under CPU/memory pressure, e.g. in `check_rule_12`'s own subprocess-spawning tests) can.
  Result: refutes "deterministic corpus bug"; consistent with "environmental."
- Attack: "confirm definitively with more runs" — not pursued further: two OOM-kills already
  imposed real cost on a shared, multi-session machine; a third risks killing something a peer
  session or the Operator needs. Named as untried, not claimed as ruled out.
- Survivor, scoped: this workstation exhibits real, recurring memory/CPU contention (confirmed:
  two independent process kills) capable of destabilizing test runs; this is a host/infrastructure
  condition of the shared machine, not a dyad-system corpus defect. No code change proposed;
  recorded as an incident, not a falsification-record amendment (it falsifies no Rule or
  mechanism — Rule-12's tests are not wrong, the machine running them is contended).
- Presence: `web-sysarch`/`web-sysarch-adh151` run at a different root (`/home/user/dyad-system`,
  a separate host per Rule-16's own presence data); neither can be the source of this machine's
  local contention. Host actions: none (observation only, Rule-8 read-only).
