## Intent reading (revision 1)

Prompt (entry 1): "the home communication strategy needs to account for operator load from context-switching for when  multiple concurrent operator  of dispositions are being asked: intent-Y, proceed-Y, done-Y.  we need a strategy to not overwhelm the operator and depending on criticality of the disposition, some can be batched while others should be presented solo.  basically, we need to establish the `dmc` for how you present dispositions."

Read against: `dyad dwork intent 706` (top: #705, #559, #207, #307, #292, #290); Rule-3 Batch disposition (one kind per
question, the batch forms, the mandate form, the closing line); `batch-disposition-mode: always`; `dmc:disposition-request`
(the kinds: intent, plan, done, retirement, precedent, merge, release, destructive); `dmc:re-present` (void, full,
remind, pending; #694); `dmc:batch-engagement`; `dmc:release-batch`; `dmc:message-overhead`; `relay-form: brief`;
Rule-10 (one `Y/N`, last line, one per reply); Rule-8's destructive question, always its own; Rule-11's release question;
#705's attention order (plan revision 1).

| portion | class | against |
|---|---|---|
| (a) the operator's load when several questions are open at once | overlap, partial | Rule-10 already bounds a *reply* to one `Y/N`, and Rule-3's batch forms already compress questions of one kind. What nothing bounds is the number of questions **outstanding** across replies: Awaiting you counts them (`d-work 2 intent (#1; #9 in <unit>)`), but nothing stops a fourth kind being asked while three are unanswered. The cost the prompt names is switching between *kinds*, each a different mode of reading: an intent-`Y` reads a reading, a plan-`Y` reads a mutation, and a done-`Y` verifies output against evidence. The prompt's "proceed-Y" is the plan-`Y` |
| (b) "from industry practice", implied by "strategy" | new, a synthesis | the candidates: **ITIL change types** (standard changes are pre-approved and batched, normal changes are reviewed one by one, emergency changes go alone); **incident severity levels** (a SEV-1 interrupts, lower severities queue); **task-switching cost** (the known penalty of moving between task modes, which argues for grouping by kind); **WIP limits on decisions** (Kanban applied to questions, not work); **notification digests** (low-stakes items batched to a cadence). The proposed synthesis is criticality tiers (solo, batch, defer) and a bound on outstanding question **kinds** rather than on questions. Within a tier the order comes from #705's attention order |
| (c) criticality: some batched, some solo | new | today, solo is decided by Rule only (destructive by Rule-8, release by Rule-11 unless its batch form or gate applies) and batching by kind alone (Rule-3). Nothing weighs criticality for intent, plan and Done questions. The proposed inputs: **irreversibility** (a host action of class destructive, a release, a publish); **reaches the world** (a release, an announcement, a public front door); **money or credentials** (a spend, a key, a grant of access); **binding size** (the number of PRs, merges, carried or retired rows and the mandate ceiling a `Y` binds); **verification** (a Done the operator must check against the output, as against an intent or plan that is read only); **novelty** (the first question of its record, or one with no precedent); and **coupling** (a `Y` that would change another question already queued) |
| (d) a `dmc` for how the home presents dispositions | new | proposed `dmc:disposition-presentation` (core), deciding, for each question ready to ask, one outcome:
  - **solo**: asked alone, with nothing else asked until it is answered, when any irreversibility, world, money or credentials input holds, or when binding size passes a threshold;
  - **batch**: asked with others of the same kind and tier, in Rule-3's batch form, when none of the solo inputs holds;
  - **defer**: kept in the pending queue and not asked, while the bound is reached or a solo question is outstanding. Shown in Coming as `deferred <n>`;
  - **re-present**: an outstanding question whose matter moved, handed to `dmc:re-present`, which this record consumes and does not restate.
  
  Its bound is on the kinds outstanding (`open-kinds-max`, default 2), with a solo question counting as the only one. Within an outcome, the order is #705's (obligations, goal alignment, focus, urgency). It authorizes nothing: it orders and times questions, and every `Y` still binds only what its own question names (Rule-2) |
| (e) the shared mechanism versus each operator's rules | new, the #705 split | **Shared, in the core**: the record, its inputs and outcomes, and the rule that destructive and release questions stay solo (they are Rule-8's and Rule-11's, never weakened by a setting). **Per operator**: the thresholds and the bound (`open-kinds-max`, the binding-size threshold, whether a Done is solo by default), kept in #705's per-operator store (central repository, else `preferences-corpus/`), and an operator's own overlay record admitted on #705's terms (it may add an order, never skip a question) |
| (f) fit with `batch-disposition-mode: always` | overlap, a wording to settle | `always` reads "never singly: the first pending item already opens the queue". A solo outcome is a batch of one, so the two agree in substance. Rule-3's sentence that the batch forms are "one kind per question" needs one clause: "and a question the presentation record makes solo is asked alone" |
| (g) consume #705, never duplicate it | overlap | the order inside each outcome is #705's attention order; this record adds the tier and the timing, never a second ranking |

The proposal adds no limit on what the home may present. It limits how many kinds wait on the operator at once: a reply still asks one question (Rule-10), and the closing line still counts every question outstanding.

Ambiguous, with leans:
- **(h) the bound's unit.** It could be outstanding kinds or outstanding questions. Lean: kinds, since the switching cost is between modes, and a batch of five plans is one mode.
- **(i) whether every Done is solo by default.** Lean: no. A Done is solo when it ratifies merges, a release or retirements past the threshold, or is the first of its record; otherwise Dones of one tier batch, as today.

Definition of done (proposed):
- `dmc:disposition-presentation` in the core, with the inputs (c), the outcomes solo, batch, defer and re-present, and the per-operator tunables (`open-kinds-max`, the binding-size threshold).
- `dyad board` computes, for every question ready to ask, its outcome and the next question to ask, and the closing line's Coming shows `deferred <n>`.
- Rule-3 Batch disposition's clause for the solo outcome, the play-book's step for presenting, and the template preference rows.
- Tests:
  - destructive and release questions are always solo, whatever a setting says;
  - two plan questions with no solo input batch;
  - a Done ratifying merges past the threshold is solo;
  - a third kind waits while two are outstanding;
  - an operator's setting changes the outcome with no code change;
  - the order within a tier is #705's.

## Intent reading (revision 2)

Prompt (entry 2): "for example, right now, i'm having to scroll the chat history to identify the outstanding disposition and its details to reduce the token expenditure of asking you again.  perhaps there's a better UI mechanism to cache and present outstanding dispositions while being token efficient."

Revision 1 is kept above and stands. Revision 2 adds portion (j) and changes nothing else.

| portion | class | against |
|---|---|---|
| (j) a place to read every outstanding question and its details without scrolling or asking again | new, a presentation surface | the board already records every question asked, verbatim and write-ahead (#535, #587), and the closing line counts them (#646, #670). But the closing line holds only ids and kinds, and the question's text and its WHAT/WHY/HOW live only in the reply that asked it, so the operator scrolls. The home's lean, falsified below: a **standing page of outstanding questions**, a private Artifact the home publishes and updates after each question is recorded or answered |

The page, as proposed:
- **One card per outstanding question**, generated by code from the board (`dyad board cards`; `--full` prints the same text in chat), so its content is deterministic and costs no inference to compose. Each card holds:
  - the exact `Y/N` line, to paste as the answer;
  - the unit whose chat holds the question (#670);
  - WHAT, WHY and HOW in three lines;
  - the counter and the reconciliation;
  - pointers: the row, the plan file, the PR and head, and the evidence sha256. It never holds the full evidence.
- **Ordered and grouped by the presentation record (a)–(i):** solo first, then batches, with deferred items listed below as `deferred`.
- Headed by the board commit it was rendered from and its time.
- Other systems' items from the attention ledger (#700) are listed by reference only, as the ledger holds them.

Falsification of the lean:

| id | claim | attack | result | survivor |
|---|---|---|---|---|
| U1 | the page is a cache, never the record | the operator answers from a stale card | survives, scoped | each card carries the board commit it was rendered from; the home re-renders after every recorded ask or answer, write-ahead order kept (board first, page second); the answer is still given in chat, where the home checks it against the board before recording (Rule-2: a `Y` binds the question it answers, and a voided one, `dmc:re-present` `void`, is re-asked) |
| U2 | it holds no `Y` | an Artifact can collect input (a button, a form) | survives, scoped | the page offers no answer control: the disposition is the operator's words in chat, entered verbatim in provenance (Rule-7). A page that recorded answers would be a second channel of authority. If wanted, that is a later row, not this one |
| U3 | it saves tokens | every publish rewrites the page | survives, scoped | the cards are generated by code, so a publish costs the page's bytes and no composition. The page is bounded by `open-kinds-max` and the batch forms, so it stays short. It is updated only on a recorded change, through an edit when one card changes. Against it stand the operator's scroll and the home's restatement, a full reply each time |
| U4 | it is private | it leaks a goal or the central repository's name | survives, scoped | an Artifact is private by default. The card text is the same text the chat already shows the operator. The central repository is never named (#700), goals appear by id unless the operator's store is read in chat (#705), and the page is never published to anyone else without the operator's own act |
| U5 | it works on every surface | a terminal session has no Artifact tool | survives, scoped | the cards are the core's (`dyad board cards`), and the Artifact is one renderer. Where none exists, the closing line gains one pointer, `details: dyad board cards`, and the operator reads the same text on request |
| U6 | it adds no channel to the operator (`message-overhead`) | a new page to watch | survives | it replaces messages rather than adding them: re-asks, restatements and scrolls. It sends nothing on its own, and the closing line gives its URL once, and again only when the URL changes |
| U7 | it fits #700's references-only rule | the page holds summaries | refuted as a conflict | #700 entry 4 binds the central repository. The page is a separate, private presentation that copies nothing into any store. The ledger stays references-only, and the page lists other systems' items by their references |
| U8 | it duplicates `dyad board` | the board already prints questions | survives, scoped | the board prints them only on request, in a tool call the operator cannot see without asking; the page is the same rendering, standing |

Alternatives weighed:
- **`dyad board` on request:** it costs the operator a prompt and the home a reply each time. It is kept as the fallback (U5).
- **A rendered file in a repository:** this repository is public, and the central one holds references only (#700), so neither can hold the cards.
- **The harness's own UI:** a panel beside the chat (a plugin or mod) is per-machine and does not reach a phone. The Artifact reaches a browser and a phone.

Shared versus per operator, as #705 has it:
- **Shared, in the core:** the card's form, `dyad board cards`, and the write-ahead order.
- **Per operator:** whether the page is published (a form preference, `question-page`, `on` | `off`, the template shipping `off`), with the home's checkout and harness deciding whether an Artifact can be made at all.

Definition of done (revision 2): revision 1's, plus:
- `dyad board cards [--full]`, generating one card per outstanding question in the presentation record's order, from the board alone;
- the home's publish of those cards as one private page after each recorded ask or answer, under `question-page: on`;
- the closing line's `details:` pointer when no page exists;
- tests:
  - a card is generated per question with its exact `Y/N` line;
  - a card the board has moved past is dropped;
  - no card holds the full evidence or the central repository's name;
  - the order is the presentation record's.
