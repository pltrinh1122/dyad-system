## Intent as read

The Operator's `Y` disposed one counter-prompt with two halves, in this order: **write the records
this system owes**, then **run the incident-hardening play-book over the result**. The second half
is the reason the first is worth doing now rather than whenever a later d-work happens to carry a
row: a ledger is hardened from its rows, so rows that exist only in replies cannot be grouped,
cannot be counted in a population, and cannot be fenced.

Read as a single d-work with a parent/child shape, not as two: the writes are phase 0's input.

### Part B — the hardening exercise (phases 0 to 2, and 4)

Run through the core runner, `LEDGER=agent-corpus/audits/INCIDENTS.md dyad runbook run
incident-hardening <step>` — **except** where the runner's event write would block the push that
must follow it, the condition candidate I records; there the native command is run and the
departure is stated in the completion reply rather than silently taken.

- **Phase 0, survey.** Derived already, before this plan: **no index audit carries a `covered
  through:` line for this ledger** (the 2026-10-05 audit states it at line 297), so this is the
  first exercise on it — full derivation, phases 1 to 4. Population at that moment: 119 rows
  (`incidents.py`), 85 beyond the last grouping's 34; ~134 and ~100 after Part A.
- **Phase 1, group.** Every row read and assigned one observed failure mode — the mechanism that
  would have to change for it not to recur, never the Rule breached and never the harm. **Modes are
  re-derived from the ledger, not read off the 2026-09-22 index**: the play-book requires it, and
  #128's attack 7 found a tenth mechanism one day after that index was written. Output: one index
  audit carrying the watermark line, the population and the mode table; one record per mode with
  its definition bounded against its neighbours, its rows by date and d-work, the pattern, and one
  remediation candidate under attack; one child row per mode, `refs: parent #259`.
- **Phase 2, inventory and falsify.** Per mode, every live mitigation read **from the code and the
  Rule text, never from an audit's prose**: path and identifier, the moment it fires, which of the
  mode's rows it reaches and which it does not, shipped or candidate, and whether anything of that
  mode recurred after it shipped. Then one falsification record attacking *this mode is addressed*,
  one attack per mitigation and per gap. Only survivors reach phase 3.
- **Phase 4, verify.** Ungated: each shipped fence named with its moment, and whether a fault of
  that shape presented at that moment would now meet it. Each mode closes by exactly one of the
  play-book's three exits — fenced at a named moment, a `backlog` row naming the fence to build, or
  recorded unfenceable on this kernel naming the Rule that makes it so — or it stays open in the
  index whatever its record says.

**Phase 3 is not in this mutation.** The play-book puts each survivor under its own plan-`Y` on its
own child row; a plan-`Y` here cannot authorize mutations whose content does not yet exist.

### Delegation

`delegation: plan-and-execute`, and candidate H's own row is the measurement of what happens when
it is ignored: the mode records are the archetypal fork work. One fork per group of modes, each in
its own worktree, drafting that mode's record and its mitigation inventory from the code; the main
Agent writes every row, commits, pushes, opens each PR and asks every counter-prompt. A fork reads
the sentinel back before it drafts.

### Ordering, and why it is not the obvious one

`INCIDENTS.md` is a tail-append file every session appends to, and that is exactly how #242's
conflict appeared after its Done-`Y`, when the branch could no longer be changed (candidate J's
mechanism, second occurrence). So **PR-1 is cut, opened and merged first and alone**, before any
mode record exists, rather than riding one large agent-zone PR at the end: a small diff with a
short life. PR-3 carries only new files, which no peer appends to. PR-2 is workstation zone and
must be separate anyway (Rule-1).

## Revision 2 — the ordering this plan wrote is unsatisfiable as written

Added after Part A was executed, PR #363 and PR #364 opened. The mutation set is unchanged; what
changes is one sentence about *when* a PR merges, and nothing here needs a fresh plan-`Y` to
continue — it needs one Operator merge-`Y`, which the preference already provides for.

**The defect.** The ordering section says PR-1 is "cut, opened and **merged** first and alone,
before any mode record exists", and phase 1 groups the ledger including Part A's own rows. Under
`merge-disposition: with-done` a PR merges at its d-work's Done-`Y`, and #259 cannot be done until
phases 1 and 2 are delivered — which this plan says come after PR-1 merges. Read literally, nothing
can happen next. It is the same shape as plan #256 revision 1 (F11) and as candidate J: an ordering
written without asking what authorizes each step.

**The resolution, already available.** `preferences-corpus/PREFERENCES.md`, `merge-disposition`,
names this case in as many words: *"A PR whose d-work is not yet done still needs its own merge
`Y`."* So PR #363 and PR #364 merge on their own merge counter-prompt, before #259 is done, and the
plan's reason for the ordering — a tail-append file with a short-lived diff — survives intact. It
costs one counter-prompt, which is what the preference's own sentence is for.

**What this does not change.** Phases 1, 2 and 4 stay exactly as planned and stay authorized by the
plan-`Y` already given. Phase 3 stays out. The forks of phase 1 read the ledger as merged, so the
population is 137 rows (119 live plus Part A's 18), not the ~134 the plan estimated.
