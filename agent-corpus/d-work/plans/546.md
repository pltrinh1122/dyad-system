# Plan #546 — stress-test seat-hops by simulation, across cabinets and hosts (falsified)

Base commit of main: (main at opening; executes after #535's three PRs land)

## Intent as read
The Operator: "stress test the seat-hops through simulation - cover all scenarios across cabinets and hosts". The
subject is #535's board store and `dyad board resume`, the P1 mechanism for the cos as a mode, plus the cabinet rules a
hop touches (#531's desks per workstation, attendance, merges by seats).

## The scenario matrix
**Axes:**
- (a) where the hop goes from and to: cloud→cloud, cloud→terminal (Mac, Linux), terminal→cloud, terminal→terminal
  across hosts;
- (b) when it happens: idle; mid-turn before the write-ahead; mid-turn after it; during a `dyad merge`; during a gated
  release run;
- (c) what is in flight: a question owed to the Operator, a dispatched seat, an external gate, a relay unanswered,
  promised follow-ups;
- (d) who else is live: secretaries (cloud), a terminal desk (no inbound messages), an attended seat (communicate);
- (e) how many cabinets: one Operator, or two (`program-<operator>` leaders under one cos);
- (f) failure conditions: two holders, a stale board, a lost push (non-fast-forward), the hosting unreachable, clock
  skew between hosts, a board file for a terminal row.

**Scenario set** (each a script with an expected outcome; about 24, pairwise-covering the axes, with every value of
every axis at least once):

| # | scenario | expected |
|---|---|---|
| S1 | cloud→cloud hop, idle, nothing in flight | resume prints nothing owed; the new holder writes `holder` |
| S2 | cloud→cloud hop with one open Operator question | the new holder re-presents it verbatim, with no re-derivation |
| S3 | hop mid-turn **before** write-ahead (cos crashed between deciding and writing) | the act was never dispatched, so nothing is lost and nothing is duplicated |
| S4 | hop mid-turn **after** write-ahead, message not yet sent | resume shows the dispatch pending; the new holder sends it once (idempotent by board `next`) |
| S5 | seat reports to the **old** session id after a hop | the report is lost to the new holder, then **detected**: resume lists the seat as owing a report, and the new holder re-asks. Measured: the time to detect |
| S6 | cloud→terminal hop (Mac): the new cos cannot receive `send_message` | seats' reports must reach it by row, board or events only; measure what is lost |
| S7 | terminal desk on Linux (operate-linux) dispatched by a cloud cos, then the cos hops | the desk reports by ledger; the new holder sees it on its next read |
| S8 | two holders at once (the old session not dead) | the `writer` warning fires on the second write; measure whether any act is double-executed |
| S9 | stale board: an entry for a terminal row | the guard warns; resume skips it; `--drop` cleans it |
| S10 | hop during `dyad merge` (push raced) | the merge is either landed or not, with no half-state; resume reads the row's operative entry |
| S11 | hop while a gated release run waits for approval | resume shows `waiting-on external run <id>`; the new holder does not record `Y release` until the run completes |
| S12 | hop with an attended seat (communicate) mid-question | the attended seat's question stays in its own chat; the new cos does not relay it (attendance unchanged) |
| S13 | two cabinets: Operator B's leader dispatches, Operator A's cos hops | A's board never claims B's rows; B's leader is unaffected |
| S14 | hosting unreachable at hop time | resume works from the local clone; writes queue until reconnect (Rule-14 p3); a conflict on reconnect resolves by id fence |
| S15 | clock skew (a host 10 min fast) | `since` ordering and the stale window still judge correctly, or the skew is reported |
| S16–S24 | pairwise fill: the remaining combinations of axes (a)×(b)×(c) not yet covered, listed in the harness | per the oracle below |

**The oracle, for every scenario:**
- no item of (c) is lost;
- no act is executed twice;
- no question is asked of the Operator about state;
- at most one line, "cos resumed in <session>", is visible to the Operator.

## Method
1. **Harness (engineer, agent zone):** `dyad/tests/sim/` holds a scratch-repo simulator.
   - A bare origin and N clones, one per session and host. The host is set by env (`CLAUDE_CODE_REMOTE`, OS label) and
     holders by `CLAUDE_CODE_SESSION_ID`.
   - Messages are modeled as a mailbox that a terminal holder cannot read.
   - Each scenario is a scripted sequence of `dyad board set/resume`, `dwork`, `merge` and push races, followed by the
     oracle. It runs in CI like any test, but is marked `integration`.
   - What cannot be simulated (the real harness classifier, a real Remote Control attach) is stated as such.
2. **One live hop (the cos):** #535's planned drill on real sessions. A fresh cloud session takes the cos role while a
   seat's work is in flight and a question is open, and the result is reported. Mac and Linux terminal hops are
   simulation-only, since no session here can reach the workstations.
3. **Findings (audit):** the audit seat runs the matrix and writes `agent-corpus/audits/2026-11-<dd>-seat-hop-stress.md`:
   each scenario's pass or fail, and for each fail its failure mode.

## Falsification
| # | attack | result |
|---|---|---|
| 1 | Simulation proves nothing about real harnesses | **scoped**: it proves the corpus-side protocol (board, write-ahead, resume, fences). Harness behaviour is covered by the one live hop. Terminal reachability is a stated limit, not claimed |
| 2 | "All scenarios" is unbounded | **scoped**: every value of every axis appears at least once, with pairwise coverage. The harness lists the exact set, so "all" means that list |
| 3 | P2 and P3 are not built, so S5, S6 and S8 must fail | **expected, and the point**: they measure what P1 alone loses. Their failures become the acceptance tests of #536 (inbox) and #537 (lease), not new rows |
| 4 | A test suite grows heavy | **survives**: the scratch repos are local and seconds each; marked `integration` |
