# Plan #421 — the attendance fence's false `undeclared`: what, why, how

## WHAT
After #412 closed, the board (`dyad session list`) prints
`undeclared: engineer-1537d8fb holds an own disposition of 2026-10-25 but attended-seats does not declare it`.
The Operator gave no disposition in engineer's chat; every Y of 2026-10-25 was given here and relayed. The
line is false.

Traced to the records: #412's record carries no `session:` line (opened by the program, so it is not
counted at all). #413's and #414's records (`session: engineer-1537d8fb`) hold entry 2
`Y done (mandate #412, 2026-10-25)` — the close form this program has used for every accreted row since
#369, because `dyad dwork state <id> done` refuses an accreted row without a `Y done` entry of its own.
`sessions.own_disposition()` excludes a note only if it *starts with* `mandate #` or *contains*
`relayed via`; `Y done (mandate #412, …)` starts with `Y done`, so it counts as engineer's own.

## WHY it is an issue
1. The fence #412 just built reports the Operator as attending a seat they do not. The leader is its sole
   reporter (attack 45), and a false line at every reply is noise that trains the reader to ignore the
   true one — the #407 case the fence exists to catch.
2. Routing follows attendance: a seat read as attended asks its questions in its own chat (#388). Today it
   is only a printed line, but the Guide says the route follows the reading.
3. The cause is structural, not engineer's: every mandate's close writes this entry on every accreted row,
   so the line will recur on every secretary after every mandate — and the `relayed via` exclusion can never
   fire on a disposition either (counsel's attack 44: the CLI attaches `--relayed-via` to prompts only).
   Two of the three exclusions the fence relies on are unreachable by the CLI's own forms.

## HOW (one engineer row, agent zone; no preference change)
1. **A close form for accreted rows.** `dyad dwork state <id> done --mandate <parent>` writes the entry
   with the note the fence already reads, `mandate #<parent>, <date>` (Rule-7 property 4's own note form),
   and the body is the mandate's Done-`Y` words. The `Y done (mandate #N, date)` workaround retires.
2. **`--relayed-via` on a disposition.** `dwork state … --said Y --relayed-via <seat>` writes the note
   `relayed via <seat>` on the disposition entry, as it already does for a prompt; the vocabulary row
   `relayed prompt` and Rule-7 property 4 gain the sentence (a relayed disposition is still the
   Operator's words; the note says where it was given).
3. **The reader matches the forms.** `own_disposition()` excludes a note that starts with or contains
   `mandate #` and one that contains `relayed via`; the records written under the old close form
   (`Y done (mandate #…)`, 2026-10-21 → 25) read correctly without rewriting — provenance records never change.
4. Tests: the three note forms × declared/undeclared; a fixture with #413's exact entry reads silent.
5. Rule-16 record attack 46; the Guide's §8 names the two CLI forms as the convention attack 44 said was
   unchecked — now mechanical.
Cost: one PR, ~150 lines with tests; the board reads clean on the next `session list` after merge.
