# Plan #81 — sysadmin craft scope: host-side packaging and installation, and the host platform abstraction

Base commit of `main`: b000af1. Refs #155 (the extraction that made sysadmin a craft), #179 (the
d-work that gave syseng `host-facts.md` and `dyad/scripts/hostadapter.py`), #71 (planned; it holds
`BUNDLE.md` and `crafts/syseng/VERSION` — see Falsification, overlap). Craft play-book
(`dyad/playbooks/craft-instantiation.md`) applied: **craft-instantiation-criteria: none fire**;
D3' decides extend-an-existing-craft, since sysadmin is the host-facing craft already installed here.

## Intent as read
Two scope declarations about the `sysadmin` craft, to be recorded as the craft's own Tended rules:
1. **Packaging and installation of the Dyad System** is sysadmin's scope.
2. **Maintaining and operating the host infrastructure abstraction** — portability on top of macOS
   and Windows — is sysadmin's scope.

Read as a *scope* prompt, not an implementation prompt: it says what the craft owns, not that macOS
and Windows work today. The mutation records the ownership and cuts its seam against the three rules
that already hold adjacent ground; making the dyad actually run on macOS or Windows is named as
follow-on work, not delivered here.

## The collision this plan exists to resolve
Both declarations land on ground that is already owned, so a literal reading breaks Rule-5
(orthogonality: ownership is never shared).

| today's owner | what it owns | verdict |
|---|---|---|
| Rule-11 kernel | craft/instance split; what an install *writes*; VERSION, tag, bundle | keeps it |
| `crafts/sysarch/rules/distribution.md` | the *design*: archive shape, version seed, entrypoint, upgrade order | keeps it |
| `crafts/syseng/rules/idempotence.md`, `determinism.md` | the *implementation discipline*: scripted, idempotent, byte-identical | keeps it |
| `crafts/syseng/rules/host-facts.md` | "this rule is about *portability*" — one place per host fact, `hostadapter.py`, two functions not a framework | **direct collision on (2)** |
| Rule-8 / `crafts/sysadmin/rules/host-mutation.md` | classes and records *any* host action, an install included | keeps it |

**The seam this plan cuts:**
- Rule-11 + sysarch say **what is distributed and what an install writes**. sysadmin says **what a
  host must provide for that install to succeed, and how the act is performed, authorized and
  recorded on a live host.** Different targets; no shared ownership.
- syseng's `host-facts.md` says **how a host fact is read in code** (one place, no inline call
  sites, two functions). sysadmin says **which host platforms this system supports and what each
  one demands.** The first is a property of the code; the second is a property of the practice.

The leftover is real, not invented. Evidence found in this session, on this host: `dyad/bin/dyad`
execs `python3`, which here is 3.11.15, while the kernel pin (Rule-14 property 2) is 3.12+ — the
documented entrypoint fails outright, and `python3.12 dyad/scripts/package.py` has to be used
instead. No rule today owns that failure: Rule-14 declares the dependency, Rule-11 says what an
install writes, and neither says what a host must provide or what happens when it does not.
