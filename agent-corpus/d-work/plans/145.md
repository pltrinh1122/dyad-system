## 1. The design constraint that shapes everything
dyad-system's core invariant is **the Operator originates and disposes; the Agent proposes**
(Rules 2 and 3). A server mode cannot drop it without becoming a different system (the
craft-instantiation play-book's D2 logic). So the question is not "remove the human from the loop".
It is **how an event can do what an Operator prompt does today without the Operator being present,
and how the Operator's disposition can be given ahead of time**. dsys answers the same question
differently: it moves routine work *out of inference* altogether.

## 2. Sketch: dyad-system server mode (S1–S7)

| # | element | what it would be | what already exists | what changes (Operator-disposed) |
|---|---|---|---|---|
| S1 | **Event intake** | A non-inferring receiver (webhook, cron, queue poller) writes each event as a `backlog` row, `refs: event:<source>-<id>`, with the payload in its plan file. This is a clerical ledger write: no inference and no decision | Rule-3 *Intake*, whose defect shape is an observation with evidence, is already the shape of a machine event. Row store, `dyad dwork new --backlog`, conflict-free ids (Rule-16) | Rule-3 Intake extended from "another agent's message" to "a registered event source". Rule-7: an event is not the Operator's words, so it goes to the plan file, never to provenance |
| S2 | **Standing disposition** | The Operator pre-authorizes *classes* of events: "for event class X, plan template P is authorized, up to budget B, merge allowed if guards pass". A row matching a standing disposition moves `backlog → planned → done` without a live `Y` | Preferences are the only standing Operator decisions today. `batch-disposition-mode` already shows that disposition *forms* can be changed by preference | **The biggest change.** A new ratification event in Rule-2 ("a standing `Y` binds every row matching its scope"), and Rule-3's plan-`Y`/Done-`Y` read "or covered by a standing disposition". It is the analogue of dsys's `set_standing` mode and its coverage rule (`dialog-protocol-spec.md` §16.4) |
| S3 | **Server actor** | A headless agent session (`claude -p` with `dyad/CLAUDE.md` loaded, kernel per Rule-14 p2) that wakes per event, works only rows a standing disposition covers, and otherwise stops at the plan | Subagent limits in Rule-3 Scope. `delegation: plan-and-execute`. Presence files (Rule-16) | A third actor beside `operator \| agent` (backlog #54: `RUN_ROLES`, changelog `ACTORS`). Rule-8's actor and host clauses (#60). A Rule-14 row for headless or API use (#51) |
| S4 | **Exceptions to a human** | Anything a standing disposition does not cover stays `backlog` and notifies the Operator. The Operator answers in chat, which is today's loop | `dyad dwork list --state backlog`, the kanban projection, the incident log | A *closure bar* guard, the analogue of dsys I-13: fail or warn when event rows sit undisposed past a window. Plus a notification adapter (a library row) |
| S5 | **Supervision** | dyad-system in server mode *is itself a server instance*: supervisor, run-book, health command, per Rule-19 and the sysadmin craft | The sysadmin craft already defines supervisor, run-book and health for servers the dyad operates | Apply Rule-19 to the dyad itself. There is no Rule change, but #60 (which host records its actions) must be answered first |
| S6 | **Budget per event** | Each standing disposition carries a token cap, and a run that exceeds it stops and becomes an exception (S4) | Nothing (#143 R1 = 0) | The meter from #143 is a prerequisite, not an add-on: an unattended inferring server with no meter is exactly the unbounded spend a client fears |
| S7 | **Evidence and audit** | Every server-worked row keeps plan, evidence block and merge commit; its Done is recorded as `Y done (standing #N)` | Ledger, evidence blocks, guards blocking at commit and push, provenance checked against rows | Rule-7 property 5 must accept a standing disposition as the matching entry, cited by reference rather than repeated |

**Precedent in the family:** workstation's `researcher` craft (plan 51 addendum) is already an
inferring server of exactly this shape. It takes requests from other dyad systems, is registered in
a repo, and is gated by governance rules restricting its activity. Its Operator's own motive:
"I don't want to be the human-in-the-loop hand-carrying prompts across dyad-system." It had to
work around the missing manifest row (#51) and actor model (#54). Those are S3's and S7's gaps,
already observed in use.

## 3. Compared with dsys

| concern | dyad-system server mode (sketch) | dsys (design; #142, #144) |
|---|---|---|
| Who does routine work | An **inferring** agent on every event, bounded by a standing disposition | A **zero-inference** executor walking pre-authored run-books and flows |
| Cost per routine event | Tokens every time (#143 F2) | ~0 tokens. Inference is paid once, when the run-book is authored (factory, spec) |
| Handling the *novel* event | Strong: the agent can reason about an unforeseen event and propose a plan, with the Operator disposing | Weak by design. An unrouted trigger aborts with a fixed-template disclosure, and a human (via the CoS drain) must decide |
| Pre-authorization | Standing disposition (to be built, S2) | `set_standing` mode plus the coverage rule (specified, and in the model) |
| Exception queue and closure bar | Backlog rows plus a new guard (S4) | Disclosures, the verification view, I-13 (in the model and validators) |
| Enforcement timing | **Before** the fact: guards block commit and push, so a server-agent cannot land unchecked work | **After** the fact: the referee "enforces nothing at invocation time"; the executor's zero-inference path is structural |
| Replay and determinism | None. Work is reproducible only through its git record | Deterministic replay from the event log |
| Always-on part | Inside the system: a supervised headless session (S3, S5) | Deliberately *outside*: a wrapper (cron) calls a step-function executor. "No daemon" |
| Maturity | Ledger, guards, intake, presence and server run-books all built. S2, S3, S4 guard and S6 missing | Executor built on fixtures. Wrapper, disclosure delivery, CoS agent, production tools, Harness and budget missing |
| Rule surgery needed | Rules 2, 3, 7, 8, 14 (and 19 applied to itself) | None to its principles. Its design already *is* event-driven |

## 4. Falsification
| # | claim | result |
|---|---|---|
| 1 | Server mode is a configuration of today's dyad-system. | **Refuted.** Rule-3 Scope ("every Operator prompt opens a d-work… no exemptions") and the two-member actor tuples need amending (#54). That is Operator-disposed Rule work |
| 2 | A standing disposition breaks no-self-ratify (Rule-2). | **Survives, scoped.** It holds only if the standing `Y` is itself Operator-given, scoped (event class, plan template, budget, merge rights) and recorded verbatim, and the server-agent cannot widen it. That is the same answer dsys gives (`set_standing` plus coverage validation). Without a mechanical scope check it becomes "self-ratification by template" |
| 3 | An inferring server is too expensive for the #143 client. | **Survives as a warning, not a refutation.** The cost is acceptable for *novel* events and wasteful for routine ones. It is the argument for a hybrid (§5), and for S6 before any deployment |
| 4 | dsys already provides server mode, so dyad-system need not. | **Refuted as "already".** dsys's always-on half is unbuilt (#144). And by design it can only *abort and disclose* on a novel event, never reason about one: that reasoning is exactly the dyad loop dyad-system runs |
| 5 | The two cannot combine. | **Refuted.** Their boundaries line up. dsys's CoS drain (disclosure, triage, proposal, human disposition) is functionally a dyad-system d-work loop, and dsys's executor is the zero-inference runner dyad-system lacks. No code joins them today (#142), and the vocabulary collides (#142 §2: run-book, event, role and others) |

## 5. Reading
- **dyad-system server mode = an inferring governor.** It is good at the unexpected, pays tokens
  on every event, enforces before the fact, and needs Rule changes to Rules 2, 3, 7, 8 and 14.
- **dsys = a deterministic operator with a human exception desk.** It is cheap on the routine,
  helpless on the novel by design, enforces after the fact, and is architecturally ready but unbuilt.
- **The natural composition:** dsys's automaton for routine events; its exception disclosures
  becoming intake rows (S1) in a dyad-system server whose standing dispositions (S2) and budget
  (S6) govern how far the agent may go before the Operator is asked. That puts tokens only on the
  unexpected, which is also #143's budget argument. It is a design direction, not a plan; its first
  prerequisite, in either repo, is still the meter.
