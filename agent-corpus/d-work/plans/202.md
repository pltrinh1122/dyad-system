## Intent as read
Four Rules are each correct and jointly leave a ratified merge that still needs one push with no
admissible sequence. Rule-3's completion clause orders the Done record before the merge it ratifies — the
converse is self-ratification, an incident three times (#47, #58, #67). That record is written by
`dyad dwork state <id> done`, which sets the state. `done` is terminal (Rule-16's table, invariant
`done-never-reopens`). And the plan gate refuses every commit citing a row that is not `open`, `planned`
or `blocked` (`dyad/guards/agent/prs.py:43-45`). So from the Done record onward, a rebase onto a moved
`main`, a conflict resolution, or the second PR of a sequenced set cannot be pushed at all. Mode M, *no
legal order, no verb* (`agent-corpus/audits/2026-10-10-incident-mode-m.md`, the `gate-after-Done`
cluster).

Eleven landed instances in sixteen days: `INCIDENTS.md:89` (#196, for #185/#186), `:91` (#200, the
recurrence inside its own recovery), `:123` (#242), `:136` (#256), `:156` and `:178` (#245 / PR #355, a
`Y` spent on a merge that never ran), `:170` (#249), `:175` and `:176` (#243), `:180` (#310), `:181`
(#322), `:182` (#297) — plus #321's I3 today, in `plans/321.md` and owed a row. Four recovery rows were
paid for it (#196, #200, #246, #245→#239) and three more rows exist only because of it (#321, #322,
#323). The quieter half is that `done` then *lies*: 164 rows' `disposed` claims `merges PR #n`, rows are
append-only, and nothing reads the claim — a git-only reconciliation run while planning this found a
fifth false one not in the log, **row #309**, `state: done`, `2026-10-15 Y done (merges PR #394, #393)`,
while PR #394 is CLOSED with `mergedAt: null`, its head `f6980e6` is no ancestor of `main`, and the
incident row it carried (a three-way id collision in which one row took four ids) is on `main` nowhere.
Surfaced for the Operator, not disposed: it is `ds-cabinet-cloud-1`'s row (#252 D3, authority does not
travel).

What this row does: make the state follow the merge, and make the claim checkable. What it does not do:
prevent the tail-append conflict that triggers most instances (the hold protocol's item 1 owns that), or
stop a Done question being asked on a PR already known unmergeable (#297's own cause).

## Mutation proposed — one agent-zone PR, one merge
Every path is agent zone (`dyad/` is the core craft's tree in the agent zone, Rule-11 property 1;
`agent-corpus/` likewise), so this is one PR and one merge — deliberately, because two PRs under one
Done-`Y` is the sequenced-merge shape row #200's own title names: "one PR, one merge, nothing to push
after it".

**1. Rule-3's completion clause becomes three ordered acts** (`dyad/rules/RULE-3-d-work.md`). Replacing
"The reply that receives the Done-`Y` merges, as clerical execution, after recording the disposition
(`dyad dwork state <id> done`)": (1) the disposition is recorded with the state left as it is — the
`disposed` entry and its provenance entry in one clerical ledger commit, the commit that carries the
trace, each entry naming the head its `Y` was given on (`Y done (merges PR #402 at 0fa99a7)`); (2) the
merges execute; (3) a second, dispositionless ledger commit sets `done`, once every head those entries
name is on `main`. "The ledger's own record of the `Y` precedes every merge it ratifies" is kept word for
word and stops being conflated with the state: that record is the `disposed` entry plus the provenance
entry. A Done-`Y` naming no merge is recorded `done` at once, so nothing costs more where nothing is in
flight. Also amended: the Ledger bullet that says when `done` is written, the trace bullet (it names the
*record* commit now, the first of the two), and Mechanisms (the two new fence clauses).

**2. `done` means more** (`dyad/vocabulary/VOCABULARY.md`): the Operator answered `Y` *and* every merge
that `Y` named has landed. One row changes; no term is coined, so Rule-6's add-a-term trigger does not
fire.

**3. The fence** (`dyad/guards/agent/rows.py`, the main fence Rule-3 owns, at
`check_commit`'s modified-row branch — every commit pushed to `main` and every commit of a ledger-only
branch, on the kernel-only path):
- `done_order_problems` — a commit that moves a row to `done` while adding an entry matching
  `\d{4}-\d{2}-\d{2} Y done\b.*\bmerges? PR #\d+` is the old order and FAILs, naming the split. The cure
  is always available: both commits are ledger-only, which the plan gate skips (#191).
- `landing_problems` — on the commit that sets `done`, every sha an `at <hex>` of its `Y done` entries
  names must be an ancestor of that commit (`git merge-base --is-ancestor`). A sha unknown to this clone
  prints one line and is skipped, never failed — the sixteen-minute cross-clone wedge of `:184`/#321's I7
  is exactly what a hard failure on an unresolvable sha does. A squash- or rebase-merging hosting records
  `landed <sha>` in the entry instead.
- `done_recorded_not_closed` — in `check_package`, a row whose `disposed` holds a `Y done` entry while its
  state is not terminal prints one `warning:` line naming the owed command. It runs at every push and
  inside `check --evidence`, so the open interval sits in the pasted evidence block and inside its
  `evidence-sha256`, in front of the Operator at the moment they dispose the next Done. Zero such rows
  today (measured while planning).
- **No new entry in `rows.INVARIANTS`**: `crafts/sysarch/tests/test_project_entities.py:319` pins that
  list to exactly `["fields-are-dyadlib-fields"]`, so a second invariant turns a craft-zone test red
  inside an agent-zone PR — mode M's own version/zone closure, met from the guards side and avoided.

**4. The CLI makes the same refusals before the first write** (`dyad/scripts/package.py` `cmd_dwork`,
beside the existing `backlog`→`open` refusal, Rule-7 property 3): a `-d` naming `merges PR #` with no
`at <sha>` is refused; a `-d` naming merges together with `state done` is refused with the split; the
`done` call takes no `-d` and runs the ancestor check, with `--landed <sha>` as the explicit override.

**5. `dyadlib`'s machine is re-described, not re-shaped** (`dyad/scripts/dyadlib.py`): the two `INPUTS`
descriptions for `("open","done")` and `("planned","done")` gain ", written when it is given; the state
follows once the merges it names have landed". The `kinds` stay `frozenset({"disposition"})` and
`TRANSITIONS`, `STATES`, `NEW_STATES`, `TERMINAL_STATES` are untouched, so every import-time invariant
still holds — `only-the-operator-closes` (`dyadlib.py:653`) above all.

**6. The procedures that tell the Agent what to do** — `dyad/playbooks/d-work.md` (the machine table's

## Falsification (Rule-9)

every landed instance, two independent fence designs, and an adversarial attack on the leading one. The
attack's own survivor and the second designer's independent proposal converged on the same thing — a

## Rule-10
- **Path:** one agent-zone PR. Rule-3's completion clause becomes record → merge → `done`; the `Y done`
  entry names the head it was given on; the fence refuses the old one-commit order and refuses a `done`
  whose named head is not an ancestor; the open interval warns at every push and in every evidence block;
  the play-books, the run-book, the trace prose, the vocabulary's `done` and the falsification record
  follow; the three rows #321 owes ride along.
- **Counter:** the named state `verified` — a seventh ledger state, admitted at the plan gate, in the
  parent clause and in the retirement form, with `verified → done` and `verified → open` declared in
  Rule-16's table. It puts the interval on the board instead of in a warn line, and it gives a row whose
  merge will never run an honest exit. It is the stronger design on visibility, and it is what one of the
  two independent designs proposed and the adversarial pass concluded.
- **Reconciliation:** its exactness is adopted here (the head sha and the ancestor test are the whole of
  it); what is declined is its cost — four PRs across three zones in a fixed order, a craft projector
  relaxed first so a core PR does not turn a craft test red, a transition-table edit weakening "state
  never regresses" by one clause, and a kanban column. That cost is the version/zone closure of the same
  failure mode, so paying it to fix this one risks the fence needing the discipline it supplies. What this
  path concedes: the interval has no name, so it is read rather than seen, and a ratified merge that will
  never run leaves a row non-terminal with no retirement exit — visible and unclosable, where today it is
  closable and false. If the Operator prefers seen over read, the state is one `N` away and this plan's
  fence is the half it needs anyway.
