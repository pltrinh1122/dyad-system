# Plan #106 — release gets its own narrower batch form, split from destructive's unconditional one

Base commit of `main`: a6d4a94. Refs #17 (the d-work that wrote the clause being amended), #92
(the concrete sysadmin-v0.1.1/#92-collision precedent for "tags do not move, only supersede"),
#100 and #105 (both cut several release tags in sequence, each individually named beforehand —
the precedent this plan formalizes rather than invents).

## Intent as read
Falsified in the immediately preceding reply (reproduced here as the record; the full attack
table lives in the falsification section below, not repeated in prose): the claim "release isn't
destructive, therefore not subject to the no-batching clause" does not survive whole, because
Rule-11 already gives release an independent, non-destructiveness-based reason for one-per-
question ("publishes to the world"). But a real, narrower survivor falls out of the attacks: the
two kinds (release, destructive) were bundled under one shared "batched or not" bullet as if they
rested on one risk, when they rest on two different ones — and a batch of *several release tags
belonging to one already-Done d-work's own already-surfaced output*, each individually named
before the question (exactly Rule-3's own Done-batch discipline), carries none of the risk the
original clause was written against (an item disappearing, unnoticed, inside a heterogeneous
batch of unrelated approvals).

Destructive-action counter-prompts are untouched: Rule-8's own criteria (no undo / loses data /
untested undo) genuinely apply there, independent of this analysis, and stay unconditional.

## Falsification (the attack table this plan encodes into the two records above)
| # | Attack | Result | Survivor |
|---|--------|--------|----------|
| 1 | A superseding release is a true undo, like Rule-8's reversible examples (`git config`, a kept-copy edit, stopping a service). | Refuted | Those restore the *prior* observable state; a superseding release doesn't — the erroneous tag stays forever resolvable (Rule-11 property 4: tags "never retagged," "do not move"). Forward patch, not a reversal. |
| 2 | Even without a true undo, if remediation is accepted, release fails Rule-8's own disjunctive test (no undo / loses data / untested undo) on its own terms. | Survives, scoped | Fair reading, but reveals release was never a Rule-8 *class* to begin with — Rule-8's Target is "a host action"; release is Rule-11's own domain. Asking "is release destructive" is a category error either direction. |
| 3 | Since release isn't Rule-8-destructive (or isn't Rule-8's business at all), and the no-batching clause's stated purpose (#17's record, attack 4) was specifically about destructive actions riding along, the clause has no surviving basis against release. | Refuted | Rule-11 gives release an independent reason, unconnected to destructiveness: "A release publishes to the world, so it is the Operator's to ratify however few d-works it gathers." Holds regardless of later fixability. |
| 4 | The original text (Rule-3 Boundaries) bundles release with destructive under one shared "batched or not" bullet, as if one risk. | Confirmed | Split: destructive stays unconditional (its criteria genuinely apply); release gets its own narrower form, scoped to tags of one already-Done d-work's own already-surfaced output. |
| 5 | Any carve-out invites scope creep — "these releases were all just named" is a judgment call, not a mechanical gate. | Survives, scoped | The gate is conservative by construction: a batchable release must already appear, unmerged, individually named, in the *same reply's own completion evidence* — exactly Rule-3's existing Done-batch pattern (#17's record, attack 2's survivor), extended to the one case it was arbitrarily excluded from, not invented fresh. |
| 6 | Tonight's own instance (three releases batched, no visible loss of scrutiny) is one sample; it doesn't prove safety in general. | Survives, scoped | Not offered as proof by itself — the *gate* (already-named, already-Done, same d-work) is what made it safe, and is now the formal requirement rather than an ad hoc reading of one bare `Y`. |
