*Rule-15 phase 1. base commit: (see the commit that carries this file) `main`, 2026-09-29. refs: 180 185 192. files touched: see §Files touched. ## Intent as read
"Perform a fresh execution performance profile of the testing where 'pyc' are not removed" — measure
the suites with bytecode retained, and again with the write suppression off, so that #185's keep-or-
drop question has a price attached instead of an argument. The measurement is done. What is left is
to put it where a later session will find it, and to spend it on #185.

## The result
**The suppression is not buying or costing measurable time.** Of six roots and two gate paths, one
effect replicated across two independently built clones: `crafts/sysarch/tests` runs **0.33 s
(−12.5%) faster** with bytecode written — 10 of 10 paired trials negative, and **0.3% of total suite
time**. Everything else is inside its own within-condition spread: `dyad/tests` +0.4%,
`check --guards` +1.6%, `check --evidence` −6.3%, all smaller than the ±5–7 s that root varies by
between identical runs.

**A −6.9% result was found and then withdrawn by the sub-agent itself.** Four interleaved paired runs
in both orderings gave −7.95, −5.51, −7.45, −7.77 s — same sign, both orderings, exactly the shape
that survives a careless profile. A third clone with the identical two-line edit then ran
indistinguishably from baseline, and the two same-code clones differ by 3.1 s while the faster one
carries the largest internal spread of any condition (11.55 s over nine runs). The effect was a
property of one clone's history, not of the flag. The withdrawal is the most valuable thing in the
report and is why this audit is worth publishing rather than summarising.

**Retaining bytecode does not make later runs faster.** On a clone that starts with zero bytecode,
run 1 is the *fastest* run on four of six roots (`sysadmin` 5.07 → 5.52 → 5.45; `sysarch` 2.61 → 2.88
→ 2.66; `syseng` 1.45 → 1.51 → 1.47; `countersign` joint-fastest). Nothing resembling the 195.9 s
first run #180 saw. The sub-agent's slowest single observation across 23 `dyad/tests` runs was
108.64 s, so **195.9 s was not reproduced and stays unexplained**; what this profile establishes is
only that bytecode is not its cause, now from both directions — #180 deleted caches before a warm run
and saw nothing, #190 started with none at all and saw no first-run penalty.

## Verified by the main Agent (not the sub-agent's word)
- **The 7 directories / 24 files.** The clones are still on disk: baseline `19 __pycache__ / 68 .pyc`,
  suppression-off `26 / 92`. The difference is exactly 7 and 24. Baseline holds no `__pycache__` under
  any *guard module* directory; suppression-off adds `crafts/{sysadmin,sysarch,syseng}/guards/` —
  **three inside craft trees** — plus the four under `dyad/guards/`. The suppression's effect is
  exactly what it claims, and no more.
- **The empty-range gate finding is real.** `package.py` `ledger_only_range` ends
  `return bool(paths) and all(...)`, so an **empty** range is `False` and the full suite runs: a push
  gate on an empty range pays ~115 s. This is backlog row **#164** (`#161` candidate C1) reaching the
  same line from the opposite direction — an independent corroboration, not a new row.
- **`suite_env()` sets no `PYTHONDONTWRITEBYTECODE`.** Confirmed at the source: it returns
  `DYAD_NO_NESTED_TESTS` and drops `GIT_VARS`, nothing else. Only `test_package.py:20` and the CI
  workflow set the variable.
- **Not verified, carried as the sub-agent's word:** the individual timings of all 23 `dyad/tests`
  runs and the five craft roots (re-running them costs ~40 minutes of suite time and #190's own
  finding is that the differences are inside noise), the contended-block numbers, and the peer-session
  contention diagnosis. The raw TSVs are on disk (`/tmp/claude-0/prof190-out/`), so the audit cites
  them as provenance rather than asserting them from memory.

## What this settles for #185
#185 is `blocked` on this d-work. The price is now known, and it kills the option the wait was
opened for:
- **Option 4 (compile the cache checked-hash at install, drop the suppression)** — correct *and*
  cached, at the price of a new `compileall` step in the install path. It buys back **0.3 s per full
  gate**. Refused on price: a build step in the one install code path (Rule-11 property 5) for a
  third of a second is the worst trade in the plan.
- **Option 2b (drop the suppression)** — buys the same 0.3 s, gives up the property verified in #192
  (a by-path import returning `111` from a source reading `222`) and writes bytecode into three craft
  trees. Refused.
- **Option 2a** — keep both suppressions, fix `python_dirs`, correct the docstring — survives, now
  with a measured cost rather than an assumed one. #185's revision 3 records it.
The deferral paid for itself twice: it priced the option, and #192's experiments corrected A5's
scoring. Neither would have happened after a plan-`Y`.
