# Plan #465 — a `Y done` entry travels with its trace (R2); `dyad release` keeps the bundle Latest (rider)

Base commit of main: 66ebfd3

## Intent as read
The Operator's `Y` to "open #465 (engineer: R2 + `--latest=false`) … to plan?".

**R2** (audit's index note, PR #502; row 232; modes E/Q). Rule-3's Completion clause already says, under
`dwork-trace: always`, that the trace is written to `<instance>/d-work/traces/<id>.md` before the Done **record**
commit and is carried by that commit. Nothing enforces this. Six Done records (#455–#460) carried none, because a
refused `dwork trace` went unseen. R2 makes the record impossible to write without its trace: the fence refuses the
commit, and the CLI refuses before its first write.

**Rider** (distribute's finding at dyad-operator-v0.12.2). `dyad release` lets `gh release create` mark every new
Release Latest, so a core or craft release took Latest from the bundle. The fix passes `--latest=false` for every
non-bundle tag.

## Evidence (main at 66ebfd3)
- Rule-3 Completion (`dyad/rules/RULE-3-d-work.md:266-273`): the trace is written "before the Done **record** commit —
  the first of the two above — which carries it". Preference `dwork-trace: always` (`PREFERENCES.md:23`).
- The fence is `rows.check_commit` (`dyad/guards/agent/rows.py:279`), run on direct commits to `main`, on each commit
  of a ledger-only branch, and on merges (`check_merge`, against each parent). The trace store's guard
  (`traces.py`) is state-only (`TRANSACTION = False`), and it checks a trace's form, never its presence.
- An accreted row's close is written by `dwork state <id> done --mandate <P>` as
  `Y done (mandate #<P>, <date>)` (`package.py:1263`), with the words copied from the mandate.
- A batch Done writes `Y done (batch #a,#b, …)` into each named row.
- `dyad/scripts/release.py:224` runs `gh release create … --verify-tag --title … --notes …` with no `--latest`.
  `want_tag()` gives `kind` ∈ {bundle, core, craft}.
- `dyad/VERSION` is 0.12.2 and `dyad-operator-v0.12.2` exists, so this change bumps it to **0.12.3** (Rule-11 p4).

## Mutation (agent zone, one PR citing d-work #465; no mandate scope, accretes nothing)
1. **Fence** — `rows.py`: new `trace_problems(path, before, after, label, sha, cwd)`, called from `check_commit` (A and
   M rows) and from `check_merge` (against each parent).
   - **When it fires:** the commit adds a `Y done` entry (`DONE_Y`) to row N, the entry is *not* a mandate close (its
     note does not hold `mandate #`), and the preference `dwork-trace` read at the commit's tree is `always`.
   - **What it checks:** that `<instance>/d-work/traces/N.md` exists in the commit's own tree
     (`git cat-file -e <sha>:<path>`). Either this commit carries it, or it is already on the base.
   - **What it does not touch:**
     - Rows whose entries were added before this fence: it judges only added entries.
     - The closing commit: that commit adds no entry.
     - Ranges on code branches: the fence does not run there.
   - The docstring sentence is updated to match.
2. **CLI** — `package.py` `cmd_dwork`.
   - `dwork state <id> … -d 'Y done…'` refuses before its first write, under the same conditions, when the trace is
     not in the working tree. The message names the fix: `dyad dwork trace <id> --out`, then re-run.
   - `dwork batch --land` (`land.py`) gets this refusal for free, because each line runs through the same runner in
     the worktree. A batch whose earlier line is `land <instance>/d-work/traces/N.md` therefore passes. The batch
     usage text gains one line saying so.
3. **Rider** — `release.py` `publish()`: `gh release create … --latest=false` when `kind != "bundle"`. The bundle
   keeps gh's default, so it becomes Latest.
4. **Tests**
   - `dyad/tests/guards/agent/test_rows.py`:
     - a direct commit adding `Y done` without the trace fails;
     - with the trace in the same commit, it passes;
     - with the trace already on the base, it passes;
     - a mandate close (`Y done (mandate #3, …)`) passes with no trace;
     - a batch `Y done (batch #a,#b)` needs both traces;
     - under `dwork-trace: on-demand`, it passes;
     - a merge commit that resolves an entry in without its trace fails.
   - `dyad/tests/test_package.py`: `dwork state -d 'Y done …'` is refused, and writes nothing, when the trace is
     absent; it passes when the trace is present.
   - `dyad/tests/test_land.py`: a batch with a `land traces/N.md` line followed by the `Y done` line lands; one
     without it is refused.
   - `dyad/tests/test_release.py`: the `gh` shim's argv carries `--latest=false` for a core and a craft tag, and not
     for a `v…` bundle tag.
5. **Rule-3 Mechanisms**: one sentence naming the fence's trace clause (`rows.trace_problems`), which keeps the
   Completion clause's "the Done record commit carries it". Rule-3's record (`dyad/falsification/rules/rule-3-d-work.md`)
   gains amendment #465 with the attacks below. Rule-5/Rule-6 statements go there; no new term.
6. **`dyad/VERSION` 0.12.3.** The bundle row lag (0.12.2 → 0.12.3) is a warning until the next release's
   infra-zone row PR.

## Falsification (Rule-9)
| # | attack | result |
|---|--------|--------|
| 1 | A mandate's accreted rows each get a `Y done` entry, so each would need its own trace. | **refuted, scoped.** Rule-3 asks for "the d-work trace of the d-work it completes", and an accreted row's Done rides the mandate's Done-`Y` (Scope), so the mandate's own trace covers the set. The fence exempts an entry whose note holds `mandate #`. That is the note `--mandate` writes and Rule-7 p4 prescribes, the same discriminator `sessions.py`'s attendance reading uses (#422). The mandate's own `Y done` still needs its trace. |
| 2 | A Done-`Y` that names merges is recorded first and closed after the merge (three acts). Which commit must carry the trace? | **answered by the Rule:** the **record** commit, the one that adds the entry. The close commit adds no entry and is not judged. A re-asked Done (a moved head voided the first `Y`) adds a second entry, and that passes because the trace is already on the base. Re-writing the trace for the new head is the play-book's concern, not the fence's. |
| 3 | A batch Done names several rows in one entry shape, so one trace might be taken to cover all of them. | **refuted.** Rule-3 Batch disposition writes "the same entry into every named d-work's own record", and the completion evidence carries each d-work's own trace. Each named row needs `traces/<id>.md`. |
| 4 | The fence turns `main` red for history. | **refuted.** It judges only entries a commit *adds*. Rows #455–#460's late traces are already on `main` (55c9a21), and earlier rows are never re-judged. |
| 5 | Reading the preference at the commit's tree is wrong if a commit flips `dwork-trace`. | **survives, accepted.** A preference change is its own preferences-zone PR, never in a ledger commit, so a ledger commit's tree carries the value it is judged under. `on-demand` disables the clause, which is the preference's meaning. |
| 6 | `dwork state --land` (single) cannot carry the trace, because it lands only what the verb writes. | **confirmed, by design.** The trace is written by `dwork trace --out` in the caller's checkout, so the single form refuses with the message naming `dwork batch` with a `land traces/N.md` line. That is the documented path, and test 4c covers it. |
| 7 | `--latest=false` on a core tag leaves no Latest when a core is released alone. | **survives, accepted.** Latest stays on the last bundle, which is what the repo's "one front door" (Rule-11 p7, the unprefixed tag) means. gh's `--latest=false` leaves the existing Latest as it is. |
| 8 | VERSION 0.12.3 is owed. | **confirmed:** `dyad-operator-v0.12.2` exists (Rule-11 p4). The bundle row lags with a warning until its row PR. |

legacy list. The transaction clause judges only new records, refuses where the record is written, and needs no list.
