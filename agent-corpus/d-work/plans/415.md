# Plan #415 — renaming the craft `cos` to `program`: evaluation

## Intent as read
Evaluate renaming the Tended craft at `crafts/cos/` (the organization craft, version 0.1.2, tag
`cos-v0.1.2`) to `program`.

## Why a rename is on the table
#406's port found a name collision: client-dyad-system and asg-peter carry a different craft named
`cos` (their chief-of-staff craft, no common ancestor). A craft install refuses to overwrite a tree the
receiving system authored, so under one name ours can never be forwarded there (Rule-11 property 2).
The collision is real and a rename is the only fix on our side; the other fix is theirs.

## Falsification
| # | attack | result |
|---|--------|--------|
| 1 | `program` names one seat's function (the leader); the craft defines six functions, charters, boards, naming and attendance for all of them. Naming the whole after one member conflates the craft with the leader seat, and the seat-name form `program-<hp>` would then read as "the program craft's seat" where `counsel-<hp>` is also that craft's. | **confirmed** — `program` is a worse name for the craft than for the seat |
| 2 | The core already calls it "the organization craft" in Rule-3 (2×), Rule-16 (2×) and the craft's own vocabulary `rule` column (`organization`); only the directory and the tag say `cos`. | confirmed — the name the Rules use is `organization`; the directory lags it |
| 3 | `cos` is also a core vocabulary concept (`cos-board`, `leader-cos`, `member-cos`: chief-of-staff as a *role a seat plays*, #295). Renaming the craft does not touch those terms, and keeping `cos` as the craft's name while `cos` is also the role is the ambiguity #410/#411 kept tripping on ("cos" the craft, "a cos" the seat). | confirmed — a rename to anything else *reduces* ambiguity |
| 4 | Cost. The tag `cos-v0.1.2` never moves (Rule-11 property 4): the renamed craft is a new craft name with a fresh tag line (`organization-v0.2.0`), the old tag stays as history, the unpublished archive `cos-0.1.2.tar.gz` is never published. Three zones, three PRs in referent-first order (Rule-1): craft (`git mv crafts/cos crafts/organization`, MANIFEST `name:`, 11+6+17+2 in-tree mentions, VERSION bump), agent (Rule-3 ×2, Rule-16 ×3, vocabulary ×2 paths), infra (BUNDLE row `cos` → `organization`; the bundle guard fails a released craft without a row, so the infra PR lands last and the old row is removed only then), preferences (`PREFERENCES.md` line 120 path, the Operator's PR), plus `crafts/REGISTRY.md` rewritten by the next install. About 50 edits, one day of one seat. | survives — the cost is bounded and mechanical |
| 5 | Receiving systems: after the rename our craft forwards to client and asg as a new craft beside their `cos`; their Operators decide whether to install it, by Intake (Rule-3). Nothing of theirs changes. | survives — the rename unblocks decision (b) of #406 without touching their trees |

## Survivor (Rule-10)
Path: rename, but to `organization`, not `program` — the name the Rules already use, the whole the
craft covers, and no overlap with a seat's function or the `cos` role. Counter: `program` is the word
the Operator reaches for ("the board of programs", the leader seat) and is shorter. Reconciliation:
`program` stays the leader seat's name and the board's name; the craft that defines all six seats takes
the name of what it defines. If the Operator still prefers `program`, the same three PRs do it; attack 1
is the cost, not a blocker.

## Mutation
None in this row: evaluation only. The rename, on the Operator's word, is its own row (engineer; three
PRs, craft → agent → infra; the preferences line the Operator's).
