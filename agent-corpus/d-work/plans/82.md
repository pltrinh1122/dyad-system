# Plan #82 — cloud session instantiation does not reach the Rule-14 kernel

Base commit of `main`: b284769. Refs #81 (this is the concrete case its `host-install.md` would
own), #155, #179 (`host-facts.md`, `hostadapter.py`).

## Intent as read
The pasted output is an environment condition observed at cloud-session instantiation, submitted as
an incident, to be troubleshot, remediated, and falsified first. Two symptoms were pasted: a list of
installed interpreters (`python3` resolving below the kernel pin) and a `ModuleNotFoundError` for
pydantic. Falsification below finds these are **not one fault** — one is real, one is not a fault at
all — so the remediation addresses only the real one.

## Troubleshooting: what was actually observed

| observation | verdict |
|---|---|
| `python3` is 3.11.15; the Rule-14 kernel pin is 3.12+ | **real, and the whole fault** |
| `/usr/bin/python3.12` and `/usr/bin/python3.13` are installed | the host **does** meet the kernel; nothing is missing |
| `dyad/bin/dyad` fails (rc=1) | consequence: it `exec python3` unconditionally |
| `dyad/hooks/pre-commit`, `pre-push` inert | same cause; both `exec python3` |
| `dyad check --evidence` fails (rc=1) | same cause — and this is the Rule-14 p3 merge evidence |
| `ModuleNotFoundError: pydantic` | **not a fault** — see F2 |

Root cause, one sentence: **the system's own launchers hardcode `python3` instead of resolving an
interpreter that satisfies the pin, so a host that fully meets the kernel is treated as one that
does not.**

Failure behaviour is *correct*: every gate exits non-zero with a named message
(`package.py: Python 3.12+ required (kernel pin), found 3.11.15`) — `crafts/syseng/rules/failure.md`
("fail early and loud") is satisfied. Verified directly, rc captured without a pipe in the way.
Nothing fails silently; the defect is purely in interpreter selection.

## Mutation

**PR 1 — agent zone** (core craft):
- `dyad/bin/dyad-python` (new, mode 100755) — one POSIX-shell helper that resolves the first
  interpreter satisfying the pin (candidates `python3.13`, `python3.12`, `python3`; each probed with
  `sys.version_info`, never by parsing a version string) and `exec`s it; if none qualifies it exits
  non-zero naming the pin, the candidates tried and what each was. One place, because three callers
  need it — Rule-13 property 1 (the second occurrence of an inference task yields a code path).
  Shell, not Python, of necessity: the thing being located is the interpreter, so this cannot live
  in `hostadapter.py`. Stated in the plan as `host-facts.md` property 2 requires of a third host
  fact ("earns its own, new function, justified in the plan that adds it").
- `dyad/bin/dyad`, `dyad/hooks/pre-commit`, `dyad/hooks/pre-push` — call the helper instead of
  `exec python3`.
- `dyad/tests/test_entrypoint.py` (new) — the mechanical check Rule-12 requires of code entering the
  package: the helper picks a conforming interpreter when one exists under a PATH whose `python3` is
  older; it exits non-zero with a named message when none does; and **its pin constant equals the
  Python-side pin** (`package.py`'s `(3, 12)`), so the two can never drift.

**Not in this mutation, stated:**
- **pydantic is not installed.** F2: its absence is the manifest's own declared state.
- **No Python is installed and no host package is touched.** F3: nothing is missing. This d-work
  takes **no host action at all** — it is repo-only.
- **No `.claude/` SessionStart hook.** F6: it is symptom-level, and `.claude/*` is claimed by no zone
  in `containment.py`'s table, so adding it is a zone-table change first (Rule-1: unclassified paths
  are forbidden). Its own d-work, proposed as a backlog row.
- **No CI change.** `actions/setup-python@v5` already makes `python3` conforming there; the fix is
  for hosts, and CI keeps corroborating exactly as Rule-14 p3 says.
- **No change to the version gates themselves.** They behave correctly.

**Backlog rows this opens:**
1. `.claude/` SessionStart configuration for cloud sessions, preceded by a `containment.py` zone-table
   row claiming `.claude/*` (today unclassified ⇒ forbidden).
2. Every shebang in the tree is `#!/usr/bin/env python3` — the same defect wherever a script is run
   directly rather than through the entrypoint. Out of scope here; the entrypoint and hooks are the
   paths a session and a transaction actually use.
3. `agent/prs` FAILs on an empty commit range (observed this session): with `origin/main..HEAD`
   empty it still reports "PR body cites no 'd-work #N'" instead of skipping.

## Falsification

| # | attack | result |
|---|--------|--------|
| F1 | "This is an incident" (Rule-3: an action or outcome **a plan did not name**). A standing environment condition present before any plan existed is not one. | **survives, split** — as a *condition* it is a Rule-14 conformance defect of the launcher, not an incident. As it *manifested* in this session it genuinely was one: two `--no-verify` bypasses and by-hand guard runs, already reported. Both records are warranted, and they are different records — hence one `INCIDENTS.md` row for what happened, and this plan's code fix for the cause. |
| F2 | "pydantic is missing, therefore broken." | **refuted, decisively** — `dyad/infrastructure/INFRASTRUCTURE.md` says verbatim: *"2.13.5 pinned … not yet installed — adopted when a plan first imports it"*. Absence is the declared, expected state. Nothing imports it; the manifest guard itself warns *"'pydantic' declared but no token maps to it"*; `package.py check` is 0 FAIL without it. The traceback came from a probe command of mine, not from any system code path. **Half the pasted evidence is not a defect.** |
| F3 | "The host does not meet the kernel." | **refuted** — `/usr/bin/python3.12` and `/usr/bin/python3.13` are both installed. The host meets it. Only the name `python3` does not. This is the attack that changes the remediation: installing anything would have been the wrong fix, and would have looked like it worked. |
| F4 | "Remediate by pinning the harness — install 3.12 as `python3` in the container." | **refuted as the fix, useful as a stopgap** — it repairs one harness and leaves the launcher wrong everywhere else (a macOS with system Python, a Debian stable, any host meeting the kernel under a versioned name). The system ships the bug; the environment only exposed it. |
| F5 | "Remediate in `hostadapter.py` — it is the one place per host fact." | **refuted on mechanism, accepted in spirit** — the fact being read *is which interpreter to run*, so it cannot be read from inside Python. It must be shell, upstream of the interpreter. `host-facts.md` property 2's "two functions, not a framework" is respected: this is a third host fact earning its own place, justified here, not a generic hook. |
| F6 | "Remediate with a `.claude/` SessionStart hook." | **survives as secondary, refuted as primary** — symptom-level for one harness, and blocked anyway: `.claude/*` is in no zone of `containment.py`'s table, and Rule-1 forbids unclassified paths. Backlog row. |
| F7 | "Low severity — CI is green, so the system is fine." | **refuted, and it inverts** — CI is green *because* `actions/setup-python@v5` gives it a conforming `python3`. Rule-14 property 3 makes the **kernel-only path** the merge evidence and says CI "corroborates and never replaces" it. The broken thing is exactly the kernel-only path, and CI's green is what hides it. Severity is higher than the symptom suggests, not lower. |
| F8 | "Fails silently — `--evidence` returned 0." | **refuted, my own error** — rc=0 was `head`'s, through a pipe. Re-run without the pipe: rc=1, named message. `failure.md` is satisfied; there is no silent-success defect. Recorded because the wrong version of this finding nearly went into the report. |
| F9 | "Out of scope — this is core-craft code, and #81 just proposed that host installation is sysadmin's." | **survives, and it is the strongest argument for #81** — this is precisely the class of fault `host-install.md` would own ("what a host must provide for the system to run, and what happens when it does not"), found by accident hours after that scope was proposed. But the *code* is core-craft (`dyad/bin/`, `dyad/hooks/`), agent zone, and #81 is unauthorized. So: fix the code here, under Rule-14 which already owns the kernel, and let #81 decide the rule that should have caught it. No dependency either way. |
