Base commit of main: de08534

## Definition of done (proposed; amend with N and text)
A report you read in one pass:
1. The transition table, one page: phases, events, the effect of each transition, and who or what fires it.
2. **Today's orchestration replayed through it** (rows #564–#586, 2026-11-04). Each of today's slips, listed below,
   is shown as either refused or prevented by a transition, or put on the ring list home is shown. Each with the
   command output.
3. The tests that pin the table.
Nothing in it depends on a merge's aftermath.

## Intent as read
Orchestration between units is unreliable because its state is free text: the board's `waiting-on` and `next`, and
inbox bodies. It is advanced by memory. Make it a finite-state machine, mechanized. Falsify first, then implement what
survives.

## The machine (survivor)
- **Phases:** `planning` → `plan-asked` → `dispatched` → `building` → `pr-up` → `verifying` → `done-ready` →
  `done-asked` → `recorded` → `landing` → `closed`. Escape edges: `held` and `amending`.
- **Events and who fires them:**
  - home's record of a `Y` (plan or done) and home's asking;
  - a unit's typed report (`plan-landed`, `pr-up`, `done-drafted`);
  - orchestrate's `evidence-verified`;
  - the automaton's `merged` and `closed`.
- **Effects, in the same commit as the transition:**
  - `owner`, `waiting-on` and `next` derived;
  - the relay to the next unit posted;
  - the ring list updated.
- **Fired by** `dyad board advance <id> <event> [fields]`, which refuses an illegal event. The automaton fires the
  ones its own records decide.
- **Data, not prose:** `dyadlib.ORCH_PHASES` and `ORCH_TRANSITIONS`, with invariants (every phase reachable, every
  non-terminal phase has a next actor).
