# Plan #107 — profile dyad/tests to find slower-than-necessary tests

Base commit of `main`: a5ce4fb. Falsification: inline below.

## Intent as read
"Profile existing unittest to determine which of the tests are taking longer than necessary."
Measure, don't guess: per-test wall time across every unittest root, attribute the cost, name what
makes the slow ones slow.

## Method
`unittest.TestLoader().discover()` refuses `dyad/tests` as a start dir directly (no `__init__.py`;
it only works via `python3.12 -m unittest discover -s <abspath>`, no `-t`, matching how
`package.py`'s own `check_rule_12` invokes it). Ran that exact form with `-v`, `DYAD_NO_NESTED_TESTS=1`
(test_package.py's own scratch-install tests shell out to `package.py check` themselves; without
that env var each one recurses into the whole suite again — the first run, without it, never
finished in 120s and was killed, unstarted rather than reported as a finding), and timestamped each
stderr line as it arrived — the gap before a line is that test's (setUp+test+tearDown) wall time.
Scratch script: `/tmp/.../scratchpad/time_tests2.py` (session scratchpad, not part of this plan's
mutation).

## Finding
`dyad/tests`: 96.19s, 464 tests. The other three roots are negligible by comparison: `sysarch`
1.73s, `syseng` 1.00s, `sysadmin` 4.05s (every individual test in all three under 15ms). All the
cost is in `dyad/tests`, concentrated:

- 25 tests (of 464) >=1s: 56.77s, 59.0% of total.
- 79 tests >=200ms: 81.53s, 84.8% of total. The other 385 tests together cost under 15s.
- By class: `test_package.PackageTests` 37.44s, `test_craft.CraftCliTests` 17.66s,
  `guards.agent` (mostly `test_rows.FenceTests`) 12.22s, `test_package.InvariantPassTests` 7.37s —
  four classes account for ~75s of the 96s total.

Two root causes, both structural, neither a correctness bug:

**1. `test_package.py` shells out to a full `check` subprocess 23 times** (`self.run_py(...)`),
against the *real* repo, each run walking every guard and invariant. The single most expensive
test in the suite, `test_evidence_block_deterministic` (8.04s), runs `check --evidence` *twice* —
a full guard-suite traversal, twice — solely to assert the two outputs are byte-identical.
`test_pass_order_and_lines` (4.52s) runs `check --guards` *and* `check` for the same reason:
comparing subprocess output against values already computable in-process. `test_evidence_block_shape_and_hash`
(4.11s) is a third full run checking the block's own shape. Three tests, three-plus full suite
runs, ~16.7s — 17% of the whole file's wall time — verifying properties `dyadlib`'s own functions
could assert directly, in-process, without a subprocess at all.

**2. `test_craft.CraftCliTests.setUp` builds a fresh real git scratch repo for every test method.**
`setUpClass` correctly shares one "authoring" scratch repo across the whole class; `setUp`
(instance-scoped) creates a brand-new `git init` "receiving" repo — real filesystem, real git
process — before *each* test, even for tests that do not need a fresh receiving tree. Combined
with each test's own `dyad(...)` subprocess call(s), this is why ordinary-looking tests like
`test_check` (2.01s) or `test_usage` (1.08s) cost as much as they do.

## Falsification
- **"434 tests in a few seconds is what this session has always observed; 96s must be an artifact
  of this measurement method, not the suite's real cost."** Refuted, checked directly: the
  `DYAD_NO_NESTED_TESTS=1` run (the same env `package.py check` itself sets) reproduces the same
  ~96s; the first, much-worse hang (>120s, killed) came specifically from *omitting* that variable
  and letting `test_package.py`'s own subprocess calls recurse into the whole suite again --- a
  measurement-setup mistake, caught and corrected before being reported as a finding, not the
  finding itself.
- **"The other three roots might hide a slow test this sampling missed."** Refuted for now:
  every individual test in `sysarch`/`syseng`/`sysadmin` timed under 15ms; no test came close to
  `dyad/tests`' slowest even at that root's own top end.
- **"Subprocess-heavy tests are the point — they're integration tests, and 'slower than necessary'
  doesn't apply."** Survives, scoped: true for coverage *that requires* the CLI/subprocess
  boundary (does `check --pr` actually reject the right things when invoked as a real process).
  False for `test_evidence_block_deterministic` specifically — determinism of a pure function's
  output is not a claim about the subprocess boundary, and asserting it via two full external runs
  buys no coverage a single in-process call plus a hash comparison would not also give.
- **Overlap (Rule-16):** presence read at session start (`dev-main` stale; `web-sysadmin-scope`
  stale, `files=32`, none under `dyad/tests/` or this plan's own three files; `web-sysarch{-adh151}`
  stale, no overlap). No overlap found.
