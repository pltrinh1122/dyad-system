### Decision 1: the deadlock fix
**Choice: (a).** On a ledger-only or events-only push, a missing core tag is one `skip [pre-push]` line, not a
`FAIL`. Every other push keeps the refusal, and `check --evidence` keeps it everywhere.
- **Where:** `package.clone_lines(repo, clerical=None)`. `package.cmd_guards` computes `clerical_paths(base, pushed)`
  before the clone check (today it does so after) and passes it in. The guard loop reuses the same value.
- **Its line:** `skip [pre-push] no dyad-operator-v<v> tag while BUNDLE.md names dyad-operator <v>: a ledger-only or
  events-only push runs no check that reads tags (d-work #621)`.
- **Unchanged:** a shallow clone still prints its `warn` line. A range git cannot read is not clerical
  (`range_paths` returns None), so it keeps the refusal: the strict side. `bootstrap.py` is not touched.

The three candidates, against the pushes after a cut, in the order they come:

| push after the cut | class | (a) clerical skip | (b) release-ready entry admits | (c) both |
|---|---|---|---|---|
| the automaton's close of the row, same run | ledger-only | passes | refused: no entry yet | passes |
| its notice to the home, on any refusal | ledger-only | passes | refused | passes |
| the stores step's notice (since #617) | ledger-only | passes | refused | passes |
| the dispatched sweep's events commit (since #617) | events-only | passes | refused | passes |
| a unit's inbox read, board write or row entry | ledger-only | passes | refused | passes |
| the release-ready lines | ledger-only | passes | passes | passes |
| a unit's code push | code | refused | refused, then passes after the entry | refused, then passes after the entry |
| anything, once the tag exists | — | passes | passes | passes |

- **The decisive attack on (b):** the first five rows. (b) leaves refused every clerical push that comes before the
  release-ready entry, and the automaton's close comes first. That is the half of the deadlock the 2026-11-06 record
  shows: #570 had to be closed by hand.
- **The decisive attack on (c):** it adds to (a) only (b)'s admission of a code push after the entry. That buys
  nothing: `check --evidence` still refuses in the window, so no Done can be asked on that code. It also lets a line
  an agent wrote, which no fence checks against the hosting, widen the gate for code.
- **`check --evidence` keeps refusing.** Its block would differ with and without the tag. `check_drift` prints `skip
  'dyad-operator': no tag … here` without it, and nothing with it. So a block taken in the window would not match your
  re-run after the tag (Rule-2 Binding). The automaton's evidence act reads that refusal as no verdict and tells the
  home once (`evidence_event`).
- **The automaton's hosted job is covered.** `fetch-tags: true` fetches only tags the hosting holds, and the
  publishing run makes the tag only after your approval. Its close, its notices and its stores step push through
  land's worktree at the fetched tip, so they run the post-cut code, which holds the fix. All are ledger-only.
- **The fix may land in the same push as the cut.** The hook runs `$(git rev-parse --show-toplevel)/dyad/scripts/
  package.py`, and the gate refuses any ref but the checked-out HEAD. So every push is judged by the pushed tree's
  own code. The cut push itself passes as a proposed release (#526), under the old code or the new. So the fix
  needs no earlier push, and "on `main` no later than the cut" holds with the fix inside the cut.
- **The replay test** (new): `dyad/tests/test_package.py`
  `ReleaseWindowTests.test_after_a_cut_clerical_pushes_pass_before_the_tag`. A scratch origin holds a row 0.1.0
  tagged `dyad-operator-v0.1.0`. A cut moves `dyad/VERSION` and the row to 0.2.0 and lands on `origin/main`, with no
  0.2.0 tag. Then, in order, `cmd_guards(pre_push=True)` judges:
  1. the close (a row set `done`): passes, one `skip [pre-push]` line, guards reached;
  2. an inbox post: passes;
  3. an events-only commit: passes;
  4. the release-ready line on the row: passes;
  5. a code commit: `FAIL [pre-push] no dyad-operator-v0.2.0 tag …`, no guard reached;
  6. `check --evidence` on the ledger head: `FAIL [evidence]`, nothing run;
  7. the tag made: the code push reaches the guards with no `[pre-push]` line.
- **The guard that keeps (a) true** (new): `PrePushStdinTests.test_no_guard_that_reads_tags_runs_on_a_clerical_push`.
  It reads every registered guard's source for a tag read (`"tag"` as a git argument, `refs/tags`). It asserts each
  such guard is `swept()` on a ledger-only push of a row file and on an events-only push. Today that is
  `infra/bundle` and `craft/crafts`. A future guard that reads tags and runs on a clerical push fails the suite, so
  the skip never becomes a false pass.
- **The Rule.** Rule-14 property 3 says "a clone missing the core's release tag fails before any guard runs". It
  becomes: "…fails before any guard runs, except on a ledger-only or events-only push, which runs no check that reads
  tags and prints one skip line instead (#621)". `dyad/surface.md` S1's `--pre-push` row says the same. Nothing is
  removed or renamed, so it is not a break (release play-book Q1, Q3).
