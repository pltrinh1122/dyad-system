## Intent as read
"Audit the chat history and the incident log for incidents and errors that a pydantic-defined
schema plus mechanical verifiers would have prevented; then evaluate migrating to pydantic
schemas." Two deliverables, one d-work: a classification of what is and is not in a schema's
reach, evidenced per incident, and a verdict on migration that is honest about what it costs.

## Findings — from all 25 rows of `INCIDENTS.md` plus this session's own unrecorded errors

**F1 — two recurrence families sit squarely in a schema's reach, and Rule-13 p1's trigger has
already fired on both.**
- *A doubled date in a `disposed` entry*, twice: `#1` (2026-09-14, "its `-d` disposition text
  carried a doubled date"; cause: "`dwork state -d` already prepends a date") and again in this
  session on row 45 (`2026-09-16 2026-09-17 Y spinout`, caught and corrected in-flight, not yet
  an incident row). Both are the same mechanism: `package.cmd_dwork` builds the entry by string
  concatenation — `disposed = (disposed + "; " if disposed else "") + f"{today} " + <text>` —
  into a field typed `disposed: str`.
- *An id assumed rather than read from the allocator*, three times: `#26, #34` (twice in one hour;
  a peer's real #27 plan and provenance overwritten on `origin/main` for about a minute) and `#27`
  (the provenance record written as `26.md`).

**F2 — the corpus already has a schema in all but name; what it lacks is typed values and
construction through the model.** 21 modules declare a `FIELDS` tuple; `dyadlib.Row` is a
dataclass; `STATES`, `TRANSITIONS`, `CONTRACT` and each module's `INVARIANTS` are declared data;
`describe()` already projects an entity card. But every `Row` field except `id` is `str` —
`opened` is a date-shaped string, `disposed` an entry list, `refs` a reference list — and
`parse_row_file` validates nothing at all (state membership, reference resolution and entry
counts are checked *later*, in `rows.py`, `references.py` and `provenance.py`). 20 modules
hand-roll `key: value` / line parsing.

**F3 — every class-A incident is a construction-time failure; every guard is an
inspection-time check.** That is the whole gap: a wrong value is *built* at a call site, written
to disk, and only then met by a guard — or, for a doubled date, met by nothing, because no check
owns the shape of a `disposed` entry.

**F4 — the majority of incidents are out of a schema's reach, and saying so is the audit's job.**
Environment and CI (`#1` red Actions, `#13/#16` the 403 release, `#22` the 3.11 kernel pin,
`#25/#27/#35` the `--no-verify` pushes, `#48` flakiness), concurrency (`#3`, `#30`), process
ordering (`#18`, `#35`, `#47`, `#32` — a disposition recorded or a merge performed before it was
asked), analysis error (`#6`, `#22`'s references misdiagnosis), prose (`#15`, and the incident row
that reproduced it), and store *shape* (this turn's `INCIDENTS.md` append conflict — solved by one
file per instance, as Rule-16 already does for rows, not by a schema).

## Falsification
- **"The audit's counts overstate the case: the class-A incidents stopped recurring anyway."**
  Survives, scoped — and it is the honest counter. The assumed-id family stopped because conduct
  changed ("never write `<id>.md` before the id is printed") and the doubled date was caught by
  eye both times. Conduct is exactly what Rule-13 p1 says should become code on the second
  occurrence; it fired at two and three. But the marginal prevention is smaller than 6-of-25
  suggests, and the audit must say so rather than sell the number.
- **"Then migrate the storage to JSON and get validation for free."** Refuted, and this turn
  supplied live evidence: the `INCIDENTS.md` append conflict resolved line-by-line because the
  file is text. #30's record attack 4 already stands — JSON re-serializes the whole object per
  edit, dropping Rule-16's line-granular merge and append-only fence and Rule-7 p1's fenced-body
  defence. The survivor keeps `key: value` files and puts pydantic only in the model.
- **"pydantic is kernel now (#31), so the cost is already disposed."** Survives, scoped: the
  *membership* is disposed, the *dependency of the evidence path* is not. `dyad check --evidence`
  is stdlib-only today; `pydantic-core` is a compiled wheel, so a migrated model makes the block
  Rule-2's Binding reads depend on a wheel being installed in the verifying environment. Named as
  a cost, not a blocker.
- **"Rewrite the 20 hand-rolled parsers — that is where the duplication is."** Refuted for this
  verdict: the parsers are the *inspection* layer, which F3 shows is not where the incidents come
  from, and #1's attack 3 already named a two-guards-at-once data-model change as the hazard.
  The recommended path touches construction, not parsing.
- **"An audit that recommends a migration should just do the migration."** Refuted: Rule-3 — the
  verdict is this d-work's output and the Operator's to dispose; a migration is a separate plan.
- **Overlap (Rule-16):** read before writing this plan. `dev-main` (different root) and
  `web-sysarch` (same recorded root, `rows` and `files` both empty as of 22:43Z) declare no files;
  this session's own file declares the #15/#32 craft and guard paths, none of which this d-work
