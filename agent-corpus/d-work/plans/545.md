# Plan #545 — the hosting's release approval is the release question (falsified)

Base commit of main: 856eaea

## Intent as read
The Operator, choosing option 1 of the cos's two shapes after asking why the release needs a tap beyond the chat `Y`:
"1. a release question". With the release gate on (`RELEASE_APPROVAL=tap`), the Operator's approval of the paused
publishing run on the hosting *is* the release question's `Y`. The chat carries the evidence, never a second question:
one act per release, and the strong one.

## Falsification
| # | attack | result |
|---|---|---|
| 1 | Rule-11 says a release is `Y` to `Y/N: release <tag>?` in chat | **confirmed, so amended**: Rule-11 Ratification events gains a form. | 3 | A tap has no words, so what does provenance (Rule-7) store? | **amended**: a disposition given on the hosting is recorded by reference, with the approval's run id, approver and time as the entry body. | 6 | The cos cannot read the approval record (the proxy refuses the environments API) | **survives**: a run that waited and then completed was released by a required reviewer, and only the Operator is one. | 8 | Rule-2 Binding: a `Y` binds to what the question named | **survives**: the run is started by the commit naming exactly those tags at that cut, so the approval binds to that set and nothing else |
