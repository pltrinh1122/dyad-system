## Revision 2 (after `2026-09-29 N plan`): the counter, taken as the path

The Operator's `N` names the counter as closer to the intent: a missing record should **fail**, and the
guards may be refactored so they serve that intent. What follows is how the guards work today, where they
conflict, and a refactor that makes the failure land on the right push.

### How the guards run today (read from code at 209dd2a)
- **The pre-push hook** (`dyad/hooks/pre-push`) runs `package.py check --guards` before every push, on any
  branch. It runs two kinds of check:
  - *State checks* (`check_package`) judge the whole tree as it stands.
  - *Transaction checks* (`check_transaction`, guards with `TRANSACTION = True`: `rows`, `prs`,
    `containment`, `events`) judge only the commits being pushed.
- **`provenance.py` is state-only** (`TRANSACTION = False`).
  - Property 5, the disposition count, runs only when a record exists.
  - A missing record warns when the row id is at or above `SINCE_ID`.
- **`rows.py`, the main fence, is a transaction check.** On `main` it checks each direct commit's paths and
  transitions; on a branch it checks id collisions and, since #133, the shape of added `disposed` entries.
- **`prs.py`, the plan gate, is a transaction check on branches only.** It reads the commit messages as the
  PR body and fails unless they cite a `d-work #N` that has a `Y plan` at the base. It returns early on `main`.
- **Hosted CI** runs on `main` after the fact. `dyad-d-work.yml` has `paths-ignore: agent-corpus/d-work/**`,
  so ledger-only commits get no CI at all.

### Why "missing record fails" was judged a red `main` in Rule-7 (attack 13)
Rule-7's hazard is real only for a **state** check. A state check judges the whole tree, so one bad row that
reaches `main` fails the pre-push hook of **every** session afterwards. Every session is blocked until someone
repairs the row — and a missing record cannot be repaired honestly, because the words are gone (property 3).
A **transaction** check has no such hazard: it fails only the push that adds the row, on the session that
wrote it, before it leaves the machine. The reasoning behind "warn, never fail" belonged to the state check
alone, and nobody built the transaction form.

### The conflict that lets a bad row through anyway: the plan gate forces a bypass
On a session whose harness forbids a direct push to `main` (Rule-1's #23 case), a ledger-only commit must
travel as a PR branch. The plan gate then fails it, because a row being opened or planned has no `Y plan` at
the base yet ("FAIL [d-work]: PR body cites no 'd-work #N'" — seen today on #133 and on #191's own opening).
The only route left is the GitHub API, which skips **every** local guard. #204, #207 and #208 all took it.
Rule-2 and Rule-3 already class a ledger-only commit as clerical, never a d-work claim, so the plan gate
applying to it at all is the conflict. Rows born without a disposition, and without a record, get through by
this route, and no CI catches them afterwards either (`paths-ignore`).

### The path (supersedes Mutation items 1–2; items 3–4 stand, widened below)
1. **Close the bypass.** `prs.py` `check_transaction` skips a range that `ledger_only_range` accepts — the
   same prefix test Rule-12's suite skip already uses (d-work #155).
   - The plan gate stays for every range that touches anything else.
   - `rows.py`, `provenance.py` and `containment` still judge the ledger-only range.
   - The ledger path then goes through the hook like everything else; the API route is no longer needed.
2. **Fail at the cause.** `provenance.py` becomes a transaction guard (`TRANSACTION = True`,
   `check_transaction`). Over base..head, on any branch including `main`:
   - A row the range **adds** must have its record added in the same range, carrying at least one entry: a
     `prompt` for a row born `open`, a `disposition` for a row born `backlog`.
   - A row whose `disposed` gains *k* entries must gain *k* `disposition` entries in its record in the same
     range. This is property 5 per transaction, so a record created later cannot catch up by accident.
   - `rows.py` keeps row shape; `provenance.py` owns the row↔record correspondence. That keeps one owner per
     concern (Rule-5), and #191's first plan (a backlog-without-disposition check in `rows.py`) is withdrawn
     in favour of this.
3. **Make the right thing the easy thing.** `package.py dwork` writes the provenance entry in the same step as
   the row:
   - `dwork new <title> --prompt-file <f>` (or `--backlog -d <summary> --said-file <f>`) creates both files.
   - `dwork state <id> <s> -d <summary> --said-file <f>` appends the disposition entry to the record.
   - `--said "Y"` accepts short text inline.
   - Without the verbatim text, `dwork new`/`state -d` refuse, naming Rule-7.
4. **State check, severity reversed: fail, not warn.** A row with no record fails `check_package`, **except**
   the 24 rows that predate this enforcement. Those are named in a data file beside the guard
   (`provenance_legacy.txt`, one id and reason per line, like `package_rules.txt`), replacing `SINCE_ID`.
   - With items 1–3 in place, a row without a record can reach `main` only through a hook bypass. The state
     failure is then the alarm for a bypass, not for ordinary work.
   - Leaving such a row is an explicit, reviewable act: a PR adding its id to the legacy file. It is never a
     silent drift.
   - The file's own invariant: every id it names exists and has no record.
5. **Rule text.**
   - Rule-7 Conditions and Enforcement: the transaction check, the fail severity, the legacy file; attack 13's
     survivor is restated for the state/transaction distinction.
   - Rule-3 Mechanisms: the plan gate exempts a ledger-only range.
   - Falsification amendments #191 to `rule-7-provenance.md` and `rule-3-d-work.md`, each with the pairwise
     coherence statement (Rule-5).
   - The vocabulary gains no term: `provenance record` and `ledger` cover it.
6. **`INCIDENTS.md`:** one row for the 24 legacy rows, recorded rather than repaired, and one for the API
   bypass on #204, #207 and #208 (this session's own ledger PRs).

Out of scope, reported:
- countersign `rules/interaction.md`'s "164" sentence (craft zone, its own PR).
- Adding the `dyad-d-work.yml` `paths-ignore` exception back into CI for ledger commits (infra zone, its own
  PR): with item 1 the hook covers them, and CI stays corroboration only (#168).
