## Intent as read
The Operator refused #100's plan on an architectural ground, not a technical one: the four fixes
were *patches* to core, sysarch and syseng, made because a downstream craft could not extend the
system without them. The claim to falsify is about the architecture: **it does not support
low-friction extensibility, and patching — the highest-friction path — is what it leaves.** Rule-9:
attack the claim, keep what survives; the survivor decides what #100 becomes.

## Falsification of the claim
| # | Attack (against the claim) | Result | Survivor |
|---|---|---|---|
| 1 | The system *is* extensible: ten discovery mechanisms, and a craft install writes only its own root (Rule-11 p2). | Refuted as a whole, confirmed for the *first* craft | Discovery covers what sysarch/syseng/sysadmin needed *when they were extracted from this repo*. The first craft authored *elsewhere* (workstation's `lan-git`, `surfacer`, `automaton`; dsys-repo's `cos`) hit a patch-only point within days. | 3 | Some points are closed **by design** and should stay closed: Agent-process Rules (Rule-4: a rule that binds the Agent belongs in core), `STATES`, the kernel-only path. | Confirmed | Not every closed point is a defect. | 4 | The D-shape recurs because the fixes were one-offs: #46 derived `KNOWN_CRAFTS`; #98 is the identical hard-code two files over. | Confirmed | A patch fixes the instance and leaves the class. | 5 | The cross-cutting note is right and generalises: D3/D4 are "extension points the design anticipates and the implementation does not complete" — so is `references.md` p6 (written as design, never built), so is `requires:` (checked but never verified). | Confirmed | The architecture already *names* the missing mechanisms; it has not built them. That is the most damning and the most hopeful finding: the design is not wrong, it is unfinished. |
| 6 | A general contribution mechanism is over-engineering; an `.local` overlay per table is enough (the #192 pattern). | Survives, scoped | An instance overlay answers the *installing* system's need (its zone, its allow lines) but not the *craft's*: a craft must carry its own contribution so it leaves with the craft (p6's own words). Both are needed; overlays alone recreate the 29-`allow`-lines cost. |

**Survivor (the claim, scoped):** dyad-system supports extension by *discovery* wherever the
extracted crafts needed it, and by *patching* everywhere else; the "everywhere else" is exactly
where a craft authored outside this repo needs to write craft-varying data into a core-owned
table — zone, dependency, reference kind, surface key, naming shape, version form, floor, command
— and the design already names the mechanism for most of them without having built it.
Patching is the highest-friction path because it moves the act from the extending system to this
one. The remedy is one shape applied ten times, not ten patches: **every core-owned table that
holds craft-varying data accepts a craft-shipped contribution by discovery, keyed by craft, that
leaves with the craft** — the p6 design, generalised; the `*_contrib.txt` / `<craft>/<name>`
pattern that already exists, completed.
