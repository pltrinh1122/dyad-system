**The procedure as read (steps):**
1. **records:** list the agent-side inference records that the gate could admit. That means outcomes whose
   consequence names no ratifying act (#644's finding), so the operator-side are dropped before any work.
2. **structured:** `backfill.py` produces candidates from cells holding outcome names.
3. **prose cases:** the agent assembles cases from plans, rows, falsification records and the change log, each as
   neutral decisive facts, a label quoted from its source, and its covering row, in a fixed form the run-book states.
4. **readers:** `dyad precedent prompt` builds the blind prompt. Two readers answer it, the cheap model and the
   default model. `dyad precedent score` keeps a case only when both match the label, and arbitrates the rest: one
   reader missing means a model limit; both missing means a context gap, so refactor the record or overrule the
   label.
5. **gate:** `similar.admit` runs over the kept cases. Only admitted ones go forward.
6. **question:** the `precedent-Y` over the admitted list, with the set-aside and refused lists beside it, written
   by `dwork state … --decisions`.
7. **convert or wait:** `similar.agreement` per record; a record at the bar converts as its own row, otherwise the
   count it lacks is reported.

**Ambiguous, with the reading taken:**
- **A1. Core or a craft.** Read: the core, because the precedent kind, the store and the gate are core (#642, #644).
- **A2. Which readers.** Read: the run-book names the two roles, cheap and default, not model ids. Each instance
  picks its own, and the event records which.
- **A3. The gate question** (precedent narrow, (a), or a proposal-only outcome admitted, (b)) stays out. The
  play-book cites the gate as it stands, and a later change reaches it through `dmc:precedent-admission`.

**Adjacent, out:** the gate question (A3), the direct-API route, and conversions themselves (step 7 proposes them).
