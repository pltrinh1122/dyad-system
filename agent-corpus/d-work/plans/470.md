# Plan #470 — the `dyad release` verb: `released.py` into the core; then dyad-operator-v0.12.2 and v0.16.2 through `released`

Base commit of main: 0534c2c

## Intent as read
The Operator's `Y` to "open a row for engineer to plan the `dyad release` verb (released.py into the core) and then
dyad-operator-v0.12.2 + v0.16.2 through `released`?". Plan #469 found that the published core `dyad-0.12.1.tar.gz`
ships the `released` workflow (`.github/workflows/dyad-release.yml`) but not its code (`.github/released.py`), so every
installing system runs a red `scan` job on each push touching the rows. Fix: put the code in the core as a `dyad`
verb, point the workflow at it, and release the fixed core and bundle through `released` itself.

## Evidence (main at 0534c2c)
- `.github/released.py` is 174 lines, stdlib only. It invokes `git`, `gh` (`gh api …/releases/tags`,
  `gh release create`) and the package's own builders (`python3 dyad/scripts/package.py build|bundle build`,
  `python3 dyad/scripts/craft.py export`).
- It hardcodes `ROWS = agent-corpus/d-work/rows`. It reads `BEFORE`, `ONLY`, `GITHUB_REPOSITORY`, `GATE`,
  `GITHUB_OUTPUT`, `GITHUB_STEP_SUMMARY`, `GITHUB_SERVER_URL`, `GITHUB_RUN_ID` and `GITHUB_SHA` from the
  environment. `--scan` is read-only.
- `.github/workflows/dyad-release.yml` (61 lines) runs `python3 .github/released.py --scan`, then
  `python3 .github/released.py`. Its trigger path is `agent-corpus/d-work/rows/**`.
- **Zones** (`containment.py zones`): `.github/*` is **infra**, `dyad/*` is **agent**. The core's distribution roots
  are `dyad/` plus the `dyad-*` workflows (`distribute.py:3`), so the workflow ships with the core but is authored in
  the infra zone.
- **Manifest** (`dyad/infrastructure/INFRASTRUCTURE.md`):
  - `gh` is a library row with profile `authoring` (`:20`). Its token is mapped (`manifest_rules.txt:18`).
  - `actions/setup-python@v5` already names `dyad-release.yml` (`:19`).
  - Once the code is under `dyad/scripts/`, Rule-14's scan sees its `gh` invocation. It also runs in every installing
    system's CI, so the `gh` row's profile becomes `both`.
- `dyad/VERSION` is 0.12.1 and `dyad-operator-v0.12.1` exists, so any change under `dyad/` needs 0.12.2 (Rule-11 p4,
  the #350 incident). `BUNDLE.md` holds `version: 0.16.1` with the core row at 0.12.1.

## Mutation (two PRs, one zone each; no mandate scope)
**PR-A (agent zone, engineer, cites d-work #470; lands first, as the referent):**
1. `dyad/scripts/release.py`: `released.py` moved in.
   - Rows are read through the instance (`dyadlib`'s `DYAD_INSTANCE` resolution, default `agent-corpus`), not a
     hardcoded path.
   - Builders are called as `sys.executable <tree>/dyad/scripts/package.py …`, as `land.py` and `--at` do, under
     `dyadlib.git_env()`.

     for module constants.

     and it writes nothing to the repo.

   - an entry refused for a cut not on `main` or a tag ≠ VERSION;

   - a tag elsewhere is refused;

   - one `livetest.ScratchInstalls` case: install the core into a scratch repo and run `./dyad/bin/dyad release --scan`
