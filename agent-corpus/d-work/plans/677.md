## For upstream's agent: how to read this
This is an **enhancement** in the sense of your Rule-3 Intake. It is a need, with its operator's own words behind it,
and it opens nothing until your operator disposes it.

**Sources.** Every requirement and constraint below cites the entry of provenance record #194 in [a downstream dyad system]
whose words it rests on (`#194/<n>`), and quotes those words where they are short.

**Answers to questions.** Some entries are answers to questions asked in the eliciting chat, such as "(c) both" or
"1. a". The questions themselves were the eliciting agent's options, which made them proposals, so they are not
reproduced here. Each such need is restated in plain words and marked *answer*.

**Edits to quotes.** Personal data is replaced by a bracketed role, such as `[an individual's mailbox]`, and each
replacement is marked. Nothing else in a quote is edited.

**What is decided and what isn't.** A point the operator has not settled is listed under Open questions, never as a
requirement.

**Why now.** The operator has a live first use case shaping this need, and asks that upstream weigh it while that
is so. This system's own work on it is paused until a future upstream release has been evaluated.

## Problem
An operator accumulates knowledge in artifacts that sit outside any dyad system: email, meeting transcripts, and
documents met along the way. Several dyad systems, each with its own purpose, would each benefit from the part of
that knowledge that concerns them. Today nothing turns those artifacts into knowledge a dyad system can consume.

The operator's framing:
- **What it is.** "a transformation engine that maps from source to destination via a schema mapping" (#194/6).
- **What it is for.** "ingesting and harvesting artifacts that are useful knowledge for the dyad-system" (#194/1).
- **Scope.** Its scope is "any set of knowledge base artifacts" (#194/2), not one client's records.

## Requirements
- **R1 Ingest once, consume many.** Every artifact is ingested once into one intermediate form. Several downstream
  consumers each take from it "for their specific purposes" (#194/9).
  > "i'll ingest every email and transcript files and artifacts; however, downstream,[a downstream dyad system] would
  > only be harvesting and ingesting matters specific-to, related-to [that system] or [that system]'s work." (#194/9,
  > system name replaced)
- **R2 A generic intermediate record, made specific per install.**
  > "a generic knowledge record format .json-ld; however, a `harvestd` needs to be instantiated/installed with a schema
  > defining the specific knowledge records" (#194/3)

  Each installed instance is "configured for specific instances/uses" (#194/4).
- **R3 Every record traces to its source.** Each record must lead back to the artifact it came from. This follows
  from R1 and R6, and #194/7 assumes it.
- **R4 Knowledge changes over time.** A value can expire, be refreshed, or be "overturned later". The operator's
  example is the "current decision for a specific matter" (#194/7).
  - *Answer* (#194/8): a value can be overturned both by a newer source and by a person's ruling.
  - *Answer* (#194/8): how long a value stays fresh before it is reviewed is set per record type, not per record.
- **R5 Consumers select by relevance, not only by exact match.** A consumer takes what is related to its work, not
  only what is tagged for it.
  - *Answer* (#194/10): a cheap first selection, with a judgement step only for the cases it cannot settle.
  - The first selection "is more likely an embedding space search (e.g. cosine similarity) rather than a hard filter"
    (#194/10). That phrase is the operator's example of the kind of selection meant.
- **R6 Several knowledge bases, one owner each, consumed as a union.**
  - A consumer combines several knowledge bases. The operator's example is an individual's mailbox and transcripts
    together with a shared mailbox and shared transcripts (#194/12, mailbox addresses replaced).
  - Each knowledge base runs its own ingester under its own owner: "`[a shared mailbox]` would run its own ingester as
    `[an individual's mailbox]` would run my own" (#194/13, addresses replaced).
  - Sources overlap, so the knowledge bases hold "some duplicate informations". The consumer wants their "union" with
    the duplicates resolved (#194/12, #194/13).
- **R7 The owner decides sharing.** "each 'owner' of its knowledgebase can elect their own 'sharing' permission"
  (#194/13).
  - *Answer* (#194/14): sharing is all or nothing for a whole knowledge base, at least at first.
  - Any dyad system can be a reader (#194/14).
- **R8 Transcripts from anywhere, one place to put them.** Transcripts "can be files that i come across from any
  sources, including attaching them to the chat session. if there is a standard location for ingestion, i'll make the
  effort to put them there, e.g. google-drive" (#194/17).
- **R9 The first use case first.** "at launch, i want to prioritize having my first use-case working solidly" (#194/16).
  Generality the first use case does not need can wait.

## Constraints
- **C1 The record format is JSON-LD** (#194/3). This is the operator's stated constraint.
- **C2 Embeddings are computed on a host the operator controls.**
  - *Answer* (#194/11): not on a third-party embedding service.
  - Placement: "on an embedding host that is either in the cloud or local+ngrok proxy" (#194/11).
- **C3 Access follows something every dyad system already has.** The operator asks whether permission can be "by
  github repo access" (#194/14). The operator's own example is "the embedding server URL + key is stored in a github
  repo and if you can access it to read the file, then you can have access". That is an example, not a decision.
- **C4 The sources include client mail and transcripts.**
  - The intermediate form and every shared copy carry other people's correspondence, so R7's owner choice is a hard
    boundary, not a preference.
  - This constraint is inferred from R6 and R7, not quoted.
- **C5 How much is configurable at launch should itself be decided by a stated criterion.** The operator asked what
  that criterion is (#194/15), which presumes one. None existed when asked.

## Open questions (not settled by the operator)
1. Which consumer is first, and what it uses the knowledge for, for example current decisions, open actions, people
   or terms.
2. Which record types the first use case needs on day one.
3. What "working solidly" means in checks the operator can evaluate: schedule, completeness on a sample, correctness of
   quotes, timeliness of overturns, cost.
4. Where ingest runs, and how often.
5. Whether any source is in a language other than English, and if so whether translation belongs in the first version.
6. Whether the access mechanism of C3 is the one wanted, or only its intent: access by repository, with no key
   to rotate.
7. Which criterion decides what is configurable at launch (C5).
8. Who reads a shared knowledge base, beyond "any dyad system can be a reader".

## What this is not
- **Not a design.** It names no schema, no store layout, no file, no module and no algorithm. The phrases quoted as
  examples are the operator's, offered as examples.
- **Not an offer of code.** A craft exists in [a downstream dyad system] (`crafts/harvester/`, 0.1.0, unreleased). It was
  built for one client's records and is not offered here. The operator asked that the hand-up "only frame the problem
  and requirements/constraints and not the solutions" (provenance #202 entry 1).
- **Not complete.** This system's elicitation (#194) is paused, not finished. A later hand-up may follow when
  the open questions above are settled.
