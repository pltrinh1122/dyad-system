# Plan #561 — local automaton runner for comparison: replay the #558 cut merges locally and time them

Base commit of main: 133ef15

## Intent as read
The operator saw the d-work automaton's run #31 (the #558 cut) take 13m11s on GitHub Actions and asks: "set up a
local automaton runner for comparison".

## What the GitHub run spent (read from job 125635629458's log)
- Set up, checkout and Python: 3 s.
- `automaton scan` and the start of `run`: 2 s. All three merges were planned by 00:04:52.
- **13m01s in one act:** the three merges were made locally and pushed together, and the push went through the
  pre-push gate (`core.hooksPath dyad/hooks`, as every unit's push does). The range carried code, so the gate ran
  Rule-12's whole suite on a fresh 2-core runner. A fresh runner has no suite memo: the evidence distribute had
  already run on the same trees was on another machine.
- The close (row `done`) and its ledger push took under a second.

So the cost is the suite inside the gate, not the automaton.

## Falsification
| # | claim | attack | result |
|---|-------|--------|--------|
| A1 | A local runner is faster | Does the local machine run the suite faster? This container has 4 cores and the GitHub runner 2. The suite's roots run as one child each. | **Survives, unmeasured**: that is the comparison asked for, and the replay below measures it. |
| A2 | Speed is the runner's hardware | A local runner that keeps its checkout keeps its suite memo, so a tree whose code already passed evidence in that checkout skips the suite. The GitHub runner never does. | **Confirmed as the bigger lever**: the gap is state, not cores. It is the memo fix engineer drafted (code-tree memo), still unasked. The replay measures with the memo cold and warm. |
| A3 | Replaying is safe | A replay must not touch the real `origin` or the ledger. | **Survives, scoped**: it runs against a scratch bare clone of `origin` at `bccbfcb9` (main before the cut), with the three PR heads as branches. The automaton's push goes to that scratch remote. Nothing reaches GitHub. It is a read-only host action outside the repo (the sysadmin craft's class), with no change-log row. |
| A4 | "Set up a runner" means a standing service | A standing local runner is a server instance (Rule-19: a run-book and a health command). It would also have to hold a GitHub token on a machine that runs unattended. | **Deferred, not refused**: this plan measures first (Rule-9: measure before claiming, #560 D5). Whether to stand a runner up, and where (your workstation, or a cloud unit of kind `auto`), is a decision for after the numbers. |

## Mutation (engineer, the machine's charter; no PR unless the replay needs a script)
1. Build a scratch origin and replay `dyad automaton run` there, timing each phase:
   - (a) memo cold, which is the GitHub equivalent;
   - (b) memo warm: run `check --evidence` on #626's head in the same checkout first, then replay.
2. Report one table, back to the operator through the home:
   - GitHub: 13m01s in the gate;
   - local cold;
   - local warm;
   - the gate's split between suite and guards.
3. If the replay needs a reusable script, it lands as `dyad/scripts/` code with a test, in one agent-zone PR citing
   d-work #561, so the comparison can be re-run.
- Mandate scope: none.

## Files touched
None required. At most one script and its test under `dyad/scripts/` and `dyad/tests/`.

## Decision for after the numbers (not bound by this plan)
- If warm local beats GitHub by an order of magnitude, the next question is the memo fix (engineer's draft): make the
  gate memo carry to the automaton, either by running it where the evidence ran or by keying the memo on the code
  tree.
- If cold local is also fast, the next question is a standing local runner.
