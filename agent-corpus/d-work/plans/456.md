# Plan #456 — `suite_env` drops `GIT_CONFIG_PARAMETERS` (row 153's fix)

Base commit of main: 9f8f116

## Intent as read
The Operator's `y` to "open a row for the `GIT_CONFIG_PARAMETERS` suite-env fix, engineer to plan it?". Row 153 of
`INCIDENTS.md` (ported by #455, PR #495) traced the gate's 29 suite errors to `git -c core.hooksPath=… push`: git
exports every `-c` to its children as `GIT_CONFIG_PARAMETERS`, and the suite's fixture repos inherit it. The fix makes
a caller's `git -c` unable to reach the fixture repos. The caller's `GIT_CONFIG_COUNT/KEY/VALUE` entries, which #206
keeps and tests, are left alone.

## Evidence (main at 9f8f116)
- `dyadlib.GIT_VARS` (`dyad/scripts/dyadlib.py:247`) is `GIT_DIR, GIT_WORK_TREE, GIT_INDEX_FILE, GIT_COMMON_DIR`.
  `git_env()` (`:250-252`) drops exactly those, and `suite_env()` (`dyad/scripts/package.py:478-492`) is
  `git_env()` plus `DYAD_NO_NESTED_TESTS`, a `commit.gpgsign=false` entry appended after the caller's
  `GIT_CONFIG_COUNT` entries (#206), and the temp root (#326).
- git 2.43 (this kernel) exports `-c` as `GIT_CONFIG_PARAMETERS` and leaves `GIT_CONFIG_COUNT` alone. Observed:
  `git -c foo.bar=1 -c alias.x='!sh p.sh' x` printed `GIT_CONFIG_PARAMETERS='alias.x'=…'foo.bar'='1'`, and beside it
  this cloud container's own `GIT_CONFIG_COUNT=3` entries (`credential.interactive`, two `url.…insteadOf`). Those
  container entries are a live reason why the COUNT path must survive.
- Reproduced on 2026-10-26 (#455): `dyad check --tests dyad.tests.guards.infra.test_containment` gives 27 OK bare,
  and 24 FAILED (errors=1, in `setUpClass`) with `GIT_CONFIG_PARAMETERS="'core.hookspath=dyad/hooks'"`.
- The other places a caller's environment reaches a child (all checked):
  - **`evidence_env()`** (`package.py:819-824`, the `--at` child, #448) is `git_env()` plus no-bytecode. That child
    runs `check --evidence`, whose suite spawns through `suite_env()`, so it is covered by this fix. Its own guard
    calls run in a worktree of this repo, where a relative `dyad/hooks` resolves correctly.
  - **`land.py` `env()`** (`dyad/scripts/land.py:53-56`, #447) is `git_env()` plus no-bytecode. Its push runs the
    real hook in `.git/dyad-land`, a checkout of this repo. The hook's suite goes through `suite_env()`, so it is
    covered.
  - **`dyad/hooks/pre-push`** runs `package.py check --guards --pre-push`. Its git calls read the live repo, where the
    caller's `-c` is the caller's intent.
  - **`livetest.ScratchInstalls`** (`dyad/scripts/livetest.py:148, 160`) uses `git_env()`. It runs only inside a test
    child, which after this fix no longer carries the variable.
  - **`distribute.py` `_git_env`** (`dyad install <repo>`, `craft install`) runs git in a *target* repo with the
    caller's `-c`. That is the same class of leak, but into an install target rather than a fixture. It is surfaced
    below, not fixed here.

## Mutation (agent zone, one PR citing d-work #456; no mandate scope, accretes nothing)
1. `dyad/scripts/package.py` `suite_env()`: drop `GIT_CONFIG_PARAMETERS` from the child's environment, with one
   docstring sentence citing #456 and row 153. Everything else is unchanged: `GIT_VARS`, `git_env()`, the
   `GIT_CONFIG_COUNT/KEY/VALUE` append (#206) and the temp root.
   - **Why only `suite_env`, not `GIT_VARS`/`git_env`:** `git_env()` serves every git call aimed at the *live* repo
     (dyadlib's range readers, provenance, trace, the suite memo, the hook's guards). There a caller's
     `git -c safe.directory=…` or `-c core.hooksPath=…` is the caller's deliberate setting for that repo, and dropping
     it would silently change what those calls see. The gap is specific to fixture repos, which are other
     repositories built by the suite, and `suite_env()` is the one environment every fixture inherits.
   - `GIT_VARS` keeps its meaning ("a hook's per-invocation variables that redirect git to another repository"),
     which `GIT_CONFIG_PARAMETERS` is not.
2. `dyad/tests/test_package.py`: one test beside #206's two (around `:1383-1400`, untouched).
   - With `GIT_CONFIG_PARAMETERS="'core.hookspath=dyad/hooks'"` in `os.environ` (patched), `suite_env()` has no
     `GIT_CONFIG_PARAMETERS`.
   - The caller's `GIT_CONFIG_COUNT` entry still survives, followed by the signing entry.
   - A scratch repo with a `dyad/hooks/pre-commit` that exits 1 commits successfully under `suite_env()`, and fails
     under the raw environment. This is the mechanism, in miniature, with no nested suite.
3. Evidence:
   - `dyad check --evidence` on the PR head.
   - The row-153 reproduction re-run: `GIT_CONFIG_PARAMETERS=… dyad check --tests dyad.tests.guards.infra.test_containment`
     gives 27 OK on the PR head, against 24 FAILED (errors=1) on `main`.
   - `dyad/VERSION`: this is a core change after the #451 cut, and the drift guard (Rule-11 p4) requires a patch bump.
     `main` is at 0.12.1, untagged, so **no further bump** is needed: 0.12.1 is unreleased, and this change rides it.
     I will check that before pushing.
   - No Rule text changes. Rule-12 p2 names `suite_env` only as "the environment the runner sets", and that
     sentence still reads true.
