## Intent as read

The Operator will not adopt an architecture from an ADR's prose. What is needed before adoption is
a specification: a numbered, normative statement of the mechanism — what exists, what each part
is, what is forbidden, what is not solved — such that each requirement can be adopted or struck on
its own, and such that building it is clerical afterwards.

This document specifies only the **mechanism**. The ADR (plan #252) holds the reasoning, the
falsifications and the 36-case edge-case register; this document holds the result. Where the two
disagree, this document is the later one and the ADR is the record of how it was reached.

## Scope

In scope: how a session of any dyad system, on any host, makes something known to another; how the
Operator's control reaches a session; what is recorded; what a `cos` is; what standing authority a
node may hold.

Out of scope, by construction and not by omission: any transport for a disposition; any mechanism
by which one node directs another; authentication of a sender; and the harness's own interrupt
mechanism, which this system specifies records for and never replaces.

## Mutation this plan-`Y` authorizes

**Only the document.** One agent-zone PR landing this specification where the corpus keeps a
design record, plus the two owed `INCIDENTS.md` rows (F5's and #241's). Nothing in §9's build
sequence is authorized by this `Y`: S1–S5 are each their own d-work with their own plan and their
own plan-`Y`. Adopting a specification and building it are two dispositions, and a `Y` that did
both would be the authority leak R25 names.

## 0. Terms (Rule-6 rows this specification would add)

- **node** — one dyad-system session, of any system, on any host.
- **edge** — a directed Operator→node relation across which one authorization passes. The unit
  authority travels on. It is not a channel and has no address.
- **announcement** — an undirected, unaddressed message with zero or many readers, carrying no
  authorization.
- **store** — the git repository the announcements live in; one per practice, distinct from every
  dyad-system repo.
- **topic** — a path segment of the store, the unit a node tunes to.
- **tuning** — the set of topics one node reads. Node-local, untracked, never published.
- **band** — a standing disposition pre-authorizing a class of edges, held by a role, content-scoped.
- **board** — a projection surface rendering, in one place, every node's state and every
  outstanding question.

## 1. Planes

**R1.** Traffic divides into exactly three planes, typed by graph shape. No message is on more
than one.

| | shape | what travels | carrier | record |
|---|---|---|---|---|
| **Announcement** | undirected | intake, status, questions, notes | the store (§2), or the presence store within one system (§3) | the store itself |
| **Command** | directed | counter-prompt, disposition, band supersession, stop | **none** — the session's own chat | row `disposed` + provenance (Rule-3, Rule-7) |
| **Interrupt** | directed, preempting | the Operator entering a node mid-turn | the harness's mechanism | provenance (R20) and status (R21) only |

**R2.** Nothing on the command plane has a transport. The edge is the session; its carrier is that
session's chat. A disposition is given only in the session that asked for it. This is the whole
answer to "is the control channel the same as the primary channel": for **status**, yes, the same
store; for **commands**, there is no channel to be the same as.

**R3.** The interrupt plane is the harness's. No store, no poll and no notification can serve it:
a node mid-turn is not reading. This specification adds records for it, never a mechanism.

**R4.** **Agent-to-agent control is excluded.** No node may send another node an instruction, a
disposition, or a question that obliges an answer. A node may only announce. A channel on which one
node commands another is authority routing under a new name, and is refused here once so that no
later requirement has to refuse it again.

## 2. The announcement store ("the bus")

**R5.** One store per practice: a git repository distinct from every dyad-system repo, reachable by
any host that can reach a git remote. It is a Rule-14 **library** row, never kernel (Rule-14
property 2: a hosted git service is never kernel).

**R6. Degradation is a requirement, not a nicety.** With the store unreachable, every node remains
fully operational: every Rule, guard, gate, counter-prompt and disposition works exactly as today.
Only consolidation is lost. No Rule, guard or disposition may be made to depend on the store. R6 is
what makes R5 admissible at all, and it is the first thing to test on any implementation.

**R7.** Append-only, one file per message, at
`topics/<topic>/<utc-date>-<system>-<session>-<n>.md`. Never edited, never deleted. Collision-free
by construction — the sender owns its own path segments — which is the same property that makes the
row store collision-free (Rule-16), and for the same reason.

**R8.** A fixed envelope: `id`, `topic`, `system`, `session`, `kind`, `subject`, `refs`, then
exactly one fenced body. The fence is what makes the body data: a message containing a heading, a
pipe or a backtick cannot reshape the file that stores it (Rule-7 property 1's reason, unchanged).

**R9.** `kind` is a closed set: `status`, `question`, `intake-defect`, `intake-enhancement`, `note`.
A new kind is a d-work, not a convention.

**R10. The one new fence: the store refuses a disposition at publish.** The store's guard fails,
at publish and at check, any payload that carries an answer — a body that is a bare `Y` or `N`, a
body holding a line in the disposition forms, or any `kind` naming disposal. A `kind: question`
carrying a verbatim `Y/N:` line **is** admissible, and the distinction is the point: a question
creates no authority, an answer is the authority. Refusal is at publish, so the store never holds
one; a reader-side check would already be too late, and a reader that chose not to look would be
the authority leak.

**R11.** The same guard refuses credential shapes, reusing the provenance guard's predicate rather
than restating it.

**R12. Tuning is node-local and never travels.** The topics a node reads are an untracked instance
file. Consequence, stated and accepted: **who is listening is not computable from the store.** A
sender learns nothing about its audience, which is what makes this a tune-in filter rather than
addressing.

**R13.** Reading is pull-only. No node is notified and no node is addressed.

## 3. Status

**R14.** Status is an announcement. It has two homes by reach, and neither needs a frozen invariant
to move:
- **Within one dyad system** — the presence store already in place (Rule-16): `state`, `working`,
  `suspended` and `waiting-on` as **optional** fields, checked only when present. The precedent is
  the guard's own `writer` field, which already sits outside `FIELDS` and is checked only when
  present; `fields-are-five` pins the five that are *required* and is untouched.
- **Across systems** — a `kind: status` announcement on the store (§2), the only reach a presence
  file in one repo does not have.

**R15.** A node publishes status at the moments it already commits: session start, each plan-`Y`,
each counter-prompt asked, each disposition received, and session end (best-effort). No new write
moment, so status costs nothing it does not already cost.

**R16.** Idleness is made **visible**, never prevented. Four computed states per edge: node
working; node waiting on the Operator; Operator waiting on a node; both idle. Only the last is a
defect, and the board reports it; nothing here resolves it, because resolving it would mean a node
acting without an edge.

## 4. Questions and the board

**R17.** A node publishes its outstanding counter-prompt as `kind: question`: the row id, the
verbatim `Y/N:` line, and the session that asked. This is the mechanism that serves a `cos` — the
Operator sees every outstanding question across every node in one place.

**R18.** The answer does not travel (R2). The board is a **directory, not a courier**: it tells
the Operator which session to enter. A `cos` therefore reduces the channels the Operator
**watches**, never the channels the Operator **uses**; the number of edges is unchanged, and only
#251's friction findings can change that.

**R19.** The board is a projection surface, `cos/board`, over the ledger rows, the presence files
and the store's announcements; its output is untracked like every other surface. It never reads the
clock (`crafts/syseng/rules/determinism.md` property 3): it renders `seen` verbatim and takes an
optional `--asof` for staleness.

## 5. Intervention and interruption accounting

**R20.** A prompt the Operator gives a node mid-turn is already a provenance entry (Rule-7). No new
record for the words — this is the half that already works, eight times in d-work #252 alone.

**R21.** Suspension is recorded: status (R14) names `working` and `suspended`, so a row suspended
by a newer prompt is distinguishable from one abandoned. Today they are identical from outside.

**R22.** Abandonment stays inference, stated: no terminal status plus a stale `seen`. No requirement
here claims more than that.

## 6. Sovereignty bands

**R23.** A band is a standing disposition, so it lives in the preferences corpus and nowhere else —
never in a reply, never in a row. Form: name, the role that holds it, the edge class it
pre-authorizes, a machine-checkable predicate, and a revocation condition.

**R24. Content-scoped only.** A band's predicate is over the content of the act, never over who
performs it. Identity is the one predicate this system cannot check: one shared credential, no
per-session identity, 52 of 58 presence files `unnamed-*`. An identity-gated band would be a band
in name only.

**R25.** A band whose predicate cannot be checked mechanically is not a band. The precedent is
`ledger-pr-merge: agent` — scope is a path prefix, the whole diff is checked before each use, and
the merge commit cites the preference and the file list, so `git log` alone shows why no
counter-prompt preceded it. The counter-example is the plan gate's substring test (#250), which is
exactly a predicate loose enough to admit what it was never meant to.

**R26. The ceiling.** No band may contain a Rule-2 base event, a Rule-8 destructive action, or a
Rule-11 release. Bands narrow; they never widen.

**R27.** Supersession is the Operator changing the preference, by the ordinary preferences-zone PR.
There is no in-band supersession, no emergency path, and no node supersedes another's band.

## 7. The `cos`

**R28.** A `cos` is an ordinary dyad-system session, distinguished by exactly three things: tuning
across every topic (R12), the `cos/board` surface (R19), and a band permitting it to publish
relayed prompts and nothing else. It holds no authority of its own; it holds attention.

**R29.** A `cos` delegating to a cabinet uses the mechanism that already exists: it publishes the
Operator's verbatim prompt as `kind: intake-enhancement` (Rule-3 Intake's enhancement shape, which
already requires the Operator's own prompt behind it), and the cabinet opens its row with
`--relayed-via cos` — the asymmetry already in the code, where `--relayed-via` attaches to
`--prompt` and never to `--said`. Work with no Operator prompt behind it is an intake the
Operator's `Y` opens: **a `cos` may propose, never open.**

## 10. What this specification does not solve

- **Identity is unverifiable** (E7, E9, E26). Accepted; R24 is the concession that follows.
- **Who is listening is not computable** (E36, R12). Accepted; it is the price of a tune-in filter.
- **The interrupt plane has no record of its own** (E35). Partially mitigated by R20–R21, no further.
- **A band cannot be narrower for one role than another** (revision 6, L2). Content-scoping is the
  only scoping this system can check, so this stays unexpressible.
- **The counter-prompt count is unchanged.** Nothing here removes an edge. §11's counter.

## 12. The counter (Rule-10)

The strongest case against this specification: it builds a craft, a surface, a guard and a
preferences table to serve **attention**, while the thing the Operator actually feels — too many
counter-prompts, each one a stop — is untouched by every requirement in it. R18 says so outright.
A specification that makes the Operator's queue *visible* without making it *shorter* could be the
more elaborate way to stay just as busy.

Reconciliation: the ask was "ensures no idleness in actors, including the operator" — visibility is
what was asked for, and R16 delivers exactly that and claims nothing more. But the concession is
real and should be stated when adopting: the edge count falls only through #251's friction class,
and **this specification is the substrate that makes #251's findings landable, not a substitute for
them.** If only one of the two is to be built, #251 is the one that shortens the queue.
