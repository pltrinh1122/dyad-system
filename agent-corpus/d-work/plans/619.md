   - executable bits on hooks and the entrypoint;

   - the newest record's two watermark lines;

### Decision 1: how the audit gathers one report
**Choice: no new command and no new flag.** `dyad automaton sweep` run with no `--row` *is* the report, as item 1
says.
- Every mode now prints its findings in two groups:
  - `standing`: findings already told to the home;
  - `new`: findings not yet told.
- Every full sweep also prints `reading:` lines. A reading is never posted and never counted as a finding.
- With no `--row`, it also prints:
  - the stall block (`stall_lines`, every cabinet), which now includes the delivery lines (Decision 4);
  - `checks-sha256=`: a digest of the tree's own check lines, in the order `check` printed them;
  - `report-sha256=`: a digest of the whole text.
- The full text is stored at `<git common dir>/dyad-sweep/<report-sha256>.txt`, never tracked, as the evidence block
  is stored (Rule-14 property 3's pattern).

Why not a separate `dyad audit report`: item 1 names `dyad automaton sweep` with no `--row` as the first act. Item 2
says the checks run in the automaton and are classed in the check-trigger table, and only sweep parts and guards
enter that table. A separate command would run them only when an audit is prompted. (The counter, below.)

**The health event: not landed, as today.** Without `--row` nothing lands (F1), so an auditor's checkout never
lands an event recorded `role: automaton`. The audit's own record of the run is its run-book event: the `report`
step runs the sweep through the runner, under the auditing party's role.

### Decision 2: where each delegated check goes
**Placement.** One new sweep part, `sweep_audit`, in `automaton.py`. It calls a new module,
`dyad/scripts/audits.py`, the way `hygiene` is called.
- It runs in the full sweep only: after each landed merge, and in the auditor's own run.
- Its checks read the code tree, so its row in `CHECK_INPUTS` is `(CODE,)`.
  `<instance>/audits/` lies outside the d-work store, so it is code tree.
- Why not a guard: a guard also runs in the pre-push gate and in every evidence block. "An audit is due" is never a
  defect of a push. A sweep part keeps it out of both.
- Why not absence: these checks read files, which only a merge changes. Time plays no part.

**Severity.** Every finding is `warn`. None fails the sweep.

**No growing count in a finding.** A finding names a record, a label, a mode or a sha, and finding_key masks
shas. Counts go in readings, which are never compared.

**Reuse (Rule-13).**
- the tree listing and prune of `package.code_digest`;
- `incidents.parse` and `incidents.by_year_month`;
- `levels.check_instance` and `levels.summary`;
- the guard discovery `dyadlib.guard_files` and `dyadlib.guard_key`;
- the tag reading of `infra/bundle`.

### Decision 4: the delivery check
**Input: absence.** A sweep that did not run is a stall: nothing changes when it fails to happen.

**Where it runs:** in `sweep_ci`, which already reads the hosting's run lists for corroboration. So it prints in the
home's read at each prompt, and in the report's stall block.

**What it checks.** The `sweep-ci-hours` window is reused, and no new preference key is added. Only the newest push
of each kind needs a run, because a later run checks the whole tree or the whole store.
- *Full sweep*: the newest landed merge on `main`'s first parent has a `d-work sweep` run at it or at a later
  first-parent commit.
- *Stores sweep*: the newest ledger-only or events-only push has a `d-work automaton` run at it or later.
  - Commits pushed by the workflow's own identity are skipped. The automaton's own pushes are swept by the same
    run's stores step, which fetches after them (F11).
- A run counts when it is queued, in progress, or completed (success or failure). Cancelled and skipped runs do not
  count (F10).

Its lines:
- `finding: delivery: no full sweep started on main at or after the landed merge <sha12>`
- `finding: delivery: no stores sweep started on main at or after the push <sha12>`

**The check-trigger table.** `sweep_ci`'s row becomes `(ABSENCE,)`. Its hosting read happens at the home's read,
never at the merge sweep (F9). The criterion's absence term gains "a sweep not delivered".
`dyad/tests/test_check_trigger.py` gains a behavioural test:
- it runs `sweep`, `sweep --stores` and `stall_lines` with every part stubbed;
- it fails on a part classed with an input whose trigger never calls it.

That catches the `sweep_ci` kind of mismatch for good.

**The run-book health** (`workstation-corpus/runbooks/automaton.md`) replaces the 13-hour clock. It passes when
`dyad board resume`'s stall block holds no `finding: delivery` line and the hosting was read. An unread hosting is
not a pass (F18). The stores sweep leaves no event (#617), so the event store alone cannot show it.
