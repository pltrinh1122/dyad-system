**Counter.** The audit is the system's independent view (two-models). If it only reads what the automaton computes,
nothing checks the automaton.
**Reconciliation.**
- The audit executes the sweep itself (A1), so the result is observed, not taken from the automaton's notice.
- Whether the automaton delivered becomes a coded finding in the report, which the audit judges (item 4).
- What is given up is a second implementation of the coded checks. Today that exists for four checks, and those run the
  same code anyway.

## Definition of done (proposed, for the intent-Y to accept)
1. The audit play-book's first act is `dyad automaton sweep` on `main`, run by the auditing unit with no `--row`. The
   record's mechanical section is that report: its summary line, every finding grouped as standing or new, `main`'s
   head, and the stall lines. No audit or self-diagnostic step re-runs a check the report carries.
2. Every coded check now only in the audit or hardening play-books runs in the automaton instead, each classed in the
   check-trigger table so #618's test covers it, its findings arriving in item 1's report:
   - the survey watermark (tree, interpreter, git) and the guard list, against the last audit;
   - executable bits on hooks and the entrypoint;
   - Rules edited since the last coherence review;
   - incident sizing and the hardening watermark;
   - a backlog row for each fence still to build, and each closed mode's fence still registered;
   - the newest record's two watermark lines;
   - the levels file.

   The one exception is the auditor's own `core.hooksPath` (A4).
3. The audit play-books keep only inference, each kept step marked so:
   - judging each finding (Rule-9);
   - host documents against the kernel;
   - a delta proposed as a row;
   - grouping incidents into failure modes, and the inventory of what guards each mode;
   - whether a mode is addressed and its fences still meet their incidents;
   - the L3 and L4 readings;
   - the coherence judgement.
4. The report says whether the automaton delivered: a full sweep after each landed merge, and a stores sweep after each
   ledger or events push. The automaton run-book's health checks that in place of its 13-hour clock. The check-trigger
   table's `sweep_ci` row says where it runs.
5. Rule text follows wherever a Rule names who runs a check: Rule-12 Boundaries (the audit play-book), Rule-14 property 3
   (what the sweep runs).
   - One zone per PR: the agent zone, plus the workstation zone for the run-book. `dyad check --pr` clean, evidence
     fail 0.
   - The completion evidence shows the new report once, on `main`, beside the phases it replaces.

Intent-Y: accepts this reading and the definition of done. The plan (mutation, falsification, files) follows it.
