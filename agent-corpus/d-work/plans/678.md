**Ambiguous, with the reading taken:**
- **A1. Which dmc.** "Playbook" here is §6 of `collateral.md`, the method this desk follows. It is not a core
  play-book in `dyad/playbooks/`, since the method stays in the chronicle craft (#674's reconciliation). A record
  answers one question. A node's depth and a tree's completeness are two questions, so read: **revise
  `collateral-problem-depth`** (one node) and **add `collateral-why-tree`** (the whole tree). Say "one record" and the
  tree tests fold into the depth record instead.
- **A2. "Five".** Read: five is the **ceiling** of a branch's depth, never a quota. A branch stops at a root cause, at
  the anchor, at a join, or at five whys. A sixth why is a sign the branch has left the segment.

**The tree's form (§6, revised):**
- The root node is the stated symptom. Each node is one statement, with an id (`N0`, `N1`, `N1.1` …) and an outcome.
- Each node is asked why. It may have **several** answers, each a child (a branch). A child may be an existing node
  elsewhere (a **join**), recorded by its id, never copied.
- One branch always asks the reverse question: "why do I feel I must do this at all?" That branch is meant to reach
  the anchor and show what the symptom protects.
- Every leaf is a root cause, the anchor, or a join. Any other leaf is an **open branch**.

**`collateral-problem-depth`, revised (one node):** `symptom` · `cause` · `root-cause` · `anchor` (new: the answer is
the root anchor itself) · `solution-shaped`. A `root-cause` must not reword an ancestor in its own branch.

**`collateral-why-tree`, new (the whole tree)**, "Is this tree ready to select root causes from?", in precedence:
1. `open-branch`: a leaf that is neither a root cause, the anchor nor a join;
2. `circular`: a root cause rewords an ancestor in its branch (C2's fault);
3. `too-deep`: a branch passes five whys without stopping;
4. `no-anchor-branch`: no branch reaches the anchor, so nothing shows why the symptom matters;
5. `untested`: a root cause has not passed the removal test (removing it removes most of the symptoms whose branches
   reach it);
6. `ready`: select root causes, ranked first by whether the anchor branch exits through them, then by how many branches
   join them.

**What changes.** Revision 1 treated the tree as a step of the method, done and then left behind. Read now: **the tree
is a maintained record**, one per segment, kept beside the canvas. A claim that a problem is a symptom or a root cause
is validated by **looking it up**, never by deriving the tree again.

### The claim, falsified (Rule-9): "a maintained full tree lets a claim be validated without re-deriving it"
| id | attack | result | survivor |
|---|---|---|---|
| T1 | **Staleness.** A tree built once goes stale: new evidence, a reader's interview or a changed product changes a why. | survives, scoped | the tree is append-only. A node is never edited or deleted: it is **superseded** by a new node naming the one it replaces, and its id is never reused, so a citation of a node stays true of what it said. git holds the history |
| T2 | **Lookup by wording fails.** A claim reworded matches no node. | survives, scoped | lookup is by meaning (inference). It maps the claim to a node id and states the id. A claim that maps to no node is **placed** in the tree first (diverge from its parent), never judged off the tree |
| T3 | **Lookup launders a hypothesis.** A claim checked against the tree reads as "validated", while every node is my guess. | **confirmed** | a lookup returns the node's outcome **and its label**. A claim validated against an H node is validated as H, never as fact. The answer reads "a root cause, as recorded (H)". Only a reader's confirmation turns a node into E |
| T4 | **An incomplete tree answers wrongly.** A node whose branches are open looks like a leaf, so a cause reads as a root cause. | survives, scoped | the tree is a reference only while `collateral-why-tree` finds it `ready`. A lookup in a tree that is not ready says so and returns no outcome |
| T5 | **The canvas drifts from the tree.** `problem.md` says one thing and the tree another. | **confirmed** | the fit record gains **`off-tree`**: a problem entry or a symptom that is not a node of the segment's tree, or whose node's outcome differs (a problem entry must be a `root-cause` node, a symptom a `symptom` node). Each entry cites its node id |
| T6 | **The tree grows without bound.** | survives, scoped | depth stops at five whys; joins point to existing nodes instead of copying them; superseded nodes stay but are skipped by lookup |
| T7 | **Segments share symptoms.** One tree per segment duplicates them. | survives, scoped | one tree per segment, because the whys differ by segment, while the anchor is shared. A cross-segment join is not modelled, and that is named as a gap |
| T8 | **The lookup is no quicker than re-deriving.** | survives, scoped | a lookup reads one node and its branch, citing the node by id; a derivation re-asks every why. The saving holds only while T4 holds |

## Plan revision 2: T8 attacked (provenance #678, entry 4)
The operator's words: "perform an adversarial attack on whether it's more efficient querying compare to rebuilding:
T8". T8's claim: a lookup reads one node and its branch, while a derivation re-asks every why, so a lookup is quicker.

| id | attack | result | survivor |
|---|---|---|---|
| Q1 | **Upkeep is a cost too.** Every new piece of evidence means appending, superseding and re-judging the tree. If the tree changes more often than it is queried, rebuilding is cheaper. | survives, scoped | the gain holds only while lookups outnumber revisions. Both are countable from git (commits to `why-tree.md` against lookups cited by node id), so the claim can be measured rather than assumed |
| Q2 | **Matching is itself inference.** Mapping a claim to a node means reading the tree, and a wrong match costs more than a correct rebuild. | survives, scoped | a lookup cites the node's id **and its path to the root symptom**, so a wrong match shows at a glance. A claim with no clear match is placed in the tree, never forced onto a node |
| Q3 | **Checking readiness re-evaluates the whole tree.** T4 requires a ready tree, and judging readiness on every lookup reads every node. | **confirmed** | readiness is judged once and recorded in the tree file's header, `judged: <outcome> at <commit>`. A lookup checks only that the file is unchanged since that commit (git answers that mechanically) and re-judges only when it has changed |
| Q4 | **A quick answer can be a stale one.** A rebuild takes in new evidence; a lookup returns what was true when the node was written. | **confirmed** | a lookup states the node's label and the tree's judged commit. Evidence that arrived after that commit (a reader's words, a changed product) must be placed before the lookup counts |
| Q5 | **Lookup forecloses discovery.** A maintained tree anchors the next look at the problem. This session shows the cost: a lookup against the chain record would have answered "root-cause" for C2's circular step, and re-deriving as a tree found RC, a root the chains never reached. | **confirmed** | the tree is **re-derived**, not merely looked up, at two moments: when evidence from a real reader of the segment arrives, and before any pitch grounded in it goes to publication. Between those moments a lookup answers |
| Q6 | **For the agent, reading a large tree costs about as much as rebuilding one.** | survives, scoped | a tree is bounded (five whys, joins never copied), and a derivation costs inference plus its checks, while reading costs only reading. For the agent the gain is modest |
| Q7 | **Whose efficiency?** | survives | for the operator, the system's scarce budget (`dyad:problem`), a lookup is a cited node and its path, read in seconds, while a rebuild is a new tree to review. Most of the gain is the operator's |

**Verdict:** T8 **survives, scoped**. A lookup is more efficient than rebuilding while four things hold: the tree's
judged commit is current (Q3); no evidence has arrived since it (Q4); the answer cites its node and path (Q2); and the
tree is re-derived at the two moments of Q5. Q1's ratio can be measured from git. The saving is mostly the operator's
attention (Q7), little of the agent's (Q6).

**What this adds to the mutation (§6 and the records):**
- the tree file's header line `judged: <collateral-why-tree outcome> at <commit>`;
- the lookup cites node id and path, and reads only a tree whose judged commit is unchanged;
- the refresh rule: re-derive on new reader evidence and before publication;
- `collateral-why-tree` gains **`stale`**, after `untested`: the file has changed since its judged commit, or evidence
  arrived after it;
- falsification rows for Q1–Q7.
