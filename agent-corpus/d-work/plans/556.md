## Intent as read
The Operator: "`d-work` practice is fully contained in definition and structure - its processes (playbook/run-book)
and store can be encapsulated as an `automaton`. being an `automaton`, our dyadic interaction can reduce in token
especially unnecessary orchestration of the playbook/run-book via agent inferencing. falsify."

## The claim, split
- **C1:** the d-work practice is fully contained in definition and structure.
- **C2:** its processes and store can be encapsulated as an automaton (#553's word: a non-inferring party running a
  released definition).
- **C3:** that reduces tokens, by removing orchestration the agent now does by inference.

## Survivor
The d-work's **clerical edges** become an automaton; its **inferred inputs** stay with the dyad. The automaton is a
server-side workflow running on pushes to `main` (the `released` pattern), reading the ledger and doing (a), (b) and
(c). The agent's turn after a Done-`Y` reduces to one command: record the entry, with its trace.

### Note to revision 2 (2026-11-02, on the Operator's prompt: "auto and not library/cli because it's stateful. falsify.")
| # | attack | result |
|---|---|---|
| S1 | The automaton is stateful | **refuted**: by design it holds no state of its own. Every run re-reads `main` (the rows, the board, the inbox) and each step is idempotent: a merged PR is skipped, a closed row is skipped. All the state is the ledger's. That is what lets any run be retried, and lets the automaton die mid-run without loss: the property #535 bought for the home with write-ahead, here for free |
| S2 | Then a library or CLI would do | **refuted as a choice between them**: the automaton *is* a CLI (`dyad automaton scan|run`). auto versus CLI is not form versus form. The CLI is **what** runs; auto is **who** runs it and **when** |
| S3 | What actually separates auto from "the agent calls the CLI"? | **three properties, none of them state.** (1) **Trigger:** it runs on an event (a push to `main` carrying a ledger line), with no inferring turn in between, which is where the tokens are saved. A CLI waits for someone to invoke it, and today that someone is an agent turn. (2) **Place and code:** it runs server-side, at `main`'s reviewed code, never a seat's working tree (A2). (3) **Party:** it decides nothing. It runs a released definition from a recorded `Y`, so it is the countersign model's executor, and its commits carry its own identity |
| S4 | Some run-book steps need memory across runs (a retry count, a backoff) | **survives, with the same rule**: any such memory goes to the store (an events line, or a board key), never into the automaton. The automaton stays stateless and restartable |

**Survivor:** auto, *because it is triggered without inference and runs `main`'s code as a non-deciding party*, not
because it is stateful. It is deliberately stateless; the state is the ledger's. The CLI is its implementation, and
remains callable by hand by any unit for recovery. The mutation is unchanged.

## Revision 3 (2026-11-02, on the Operator's prompt: "many agent work has been authoring the identical set of scripts/code to carry out instructions with different parameters. paramterized `automaton` is an existing capability. falsify.")

| # | attack | result |

| P1 | Parameterized definitions exist | **confirmed**: run-books are parameterized through the environment. The d-work run-book takes `DWORK`, `SAID`, `PROMPT`, `TITLE` and `REFS`; the release play-book takes `CRAFT` and `CLASS`; incident-hardening takes `LEDGER`; the trace takes its id. | P2 | …so a parameterized *automaton* exists | **refuted as stated, survives in part**: the runner is a CLI a unit invokes.
