# Plan #556 — the d-work automaton: the clerical edges of the lifecycle run by a non-inferring automaton (falsified)

Base commit of main: (main at opening)

## Intent as read
The Operator: "`d-work` practice is fully contained in definition and structure - its processes (playbook/run-book)
and store can be encapsulated as an `automaton`. being an `automaton`, our dyadic interaction can reduce in token
especially unnecessary orchestration of the playbook/run-book via agent inferencing. falsify."

## The claim, split
- **C1:** the d-work practice is fully contained in definition and structure.
- **C2:** its processes and store can be encapsulated as an automaton (#553's word: a non-inferring party running a
  released definition).
- **C3:** that reduces tokens, by removing orchestration the agent now does by inference.

## Falsification
| # | attack | result |
|---|---|---|
| C1-a | The lifecycle is fully defined | **survives for the machine**: states, transitions and their inputs are data (`dyadlib.TRANSITIONS`, `dyadlib.INPUTS`, the d-work play-book), and every record a d-work is made of is a store with a guard |
| C1-b | …so every step is mechanical | **refuted**: six inputs are *inferred*, not defined. (1) Reading the operator's intent from a misspelled, quoted prompt (#553 rev 2). (2) Falsifying and writing the plan. (3) Judging evidence: is a warning standing or new, is a departure execution-detail (#555)? (4) Classifying an incident's failure mode. (5) Presenting a question at the operator's altitude (`relay-form: brief`). (6) Deciding the next best action. None has a definition an automaton could run. They are the dyad's actual work |
| C2-a | An automaton can run the d-work | **refuted as stated, survives scoped**: an automaton cannot read the operator's chat, so it cannot receive a prompt or a disposition. The words must be transcribed into the ledger by the session that holds them (Rule-7). The automaton can therefore start only *from a ledger line*, as `released` already does, never from a conversation |
| C2-b | From a ledger line, the rest is mechanical | **survives**: everything between a recorded disposition and the next inferred act is defined. (a) A `Y done (merges PR #a at <head>, …)` entry → merge each named PR, pinned, in order; refuse on a moved head or a conflict. (b) Every named head on `main` → write the dispositionless `state done`, drop the board entry, close mandate rows the entry names. (c) A `Y plan` entry → post an inbox `notice` to each owner on the row's board entry: "row #N planned; read plans/N.md". (d) A landed report → nothing to do; the cos reads its inbox |
| C3-a | Tokens drop | **survives, the largest share is (a)–(b)**. Observed today, from #535 to #552: each Done cost the cos about 6–10 turns between the operator's `Y` and the close, plus a turn per merging seat. The turns were: record, dispatch merges, read the seats' reports, verify ancestry, close, board, and mirror push. Every turn re-reads the whole session context, so the cost is per turn, not per computation. (a)–(b) remove all of them but the first, and every seat's merge turn. A count, not a measured token figure: the trace (#213) measures seconds, not tokens, and is stated as such |
| C3-b | Operator-facing interaction shrinks | **refuted**: the operator's questions stay the same (plan-`Y`, Done-`Y`), because they are the countersignatures. What shrinks is agent-side orchestration, and the operator's wait between a `Y` and its effect |
| C3-c | Plan dispatch (c) saves inference | **survives, small**: the seat still infers from the plan file. The automaton only replaces the cos's message saying "go" |
| R1 | An automaton that merges reopens A2 (code acting on authority) | **survives, better than today**: it runs `main`'s own reviewed code server-side, so the seat's working tree is out of the path entirely (A2's prevention, backlog #542). The authority is still the operator's recorded Done-`Y`. A forged entry stays detection, as today (merges are reversible). Releases keep the gate |
| R2 | The automaton writes ledger commits to `main` | **survives**: they are clerical (Rule-2 Not ratification) and fenced like any other. Its commits carry the workflow's identity, so they are distinguishable from agent commits, which is a gain for audit |
| R3 | Merge conflicts or moved heads | **survives**: the automaton refuses and posts a `notice` to the home's inbox, an escalation that decides nothing. The cos takes it from there by inference |
| R4 | Counting it as a party | **survives**: it is the countersign model's executor, #553's `automaton`. The `released` workflow is the first one, and this is the second. Neither is autonomous: each runs a released definition from a recorded `Y` |

## Survivor
The d-work's **clerical edges** become an automaton; its **inferred inputs** stay with the dyad. The automaton is a
server-side workflow running on pushes to `main` (the `released` pattern), reading the ledger and doing (a), (b) and
(c). The agent's turn after a Done-`Y` reduces to one command: record the entry, with its trace.
